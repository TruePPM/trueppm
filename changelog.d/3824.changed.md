- **Monte Carlo uses far less memory on large projects (scheduler)**: the simulation's forward pass now runs over chunks of runs and keeps only each run's finish, instead of holding five runs × tasks matrices for every run at once, and above 32M cells (runs × tasks) the sampled-duration matrix is no longer held either: each task's column is redrawn a row block at a time from the generator position its draws started at. Peak memory for 50,000 tasks × 1,000 runs drops from ~2.1 GB to ~590 MB RSS (4,000 tasks × 2,000 runs: ~302 MB → ~186 MB traced), and benchmarks assert the peak. Results are unchanged: seeded P50/P80/P95, the distribution and the sensitivity tornado are byte-identical for any chunk size and whether the matrix is held or replayed. The durations stay float64, because three-point draws are continuous and float32 would move seeded percentiles. Above the replay threshold this is a trade of time for memory, not a free win: at 50,000 tasks × 1,000 runs the replayed matrix takes ~9.3 s at ~590 MB peak RSS, against ~5.7–6.2 s at ~890–920 MB with the matrix held (the faster figure is the one the 8M-cell chunk budget entry, #4955, reports), because replaying draws each sampled column three times. Every project within the API's default caps (5,000 tasks × 1,000 runs) is below the replay threshold, holds the matrix, and pays nothing. `MC_TASK_CAP` (5,000) is deliberately left unchanged; re-evaluating it, and the floor still above the 250 MB target, is tracked in #4953. The `MAX_LAG_DELTA_CELLS` table is unaffected: it is keyed on distinct (dependency type, lag, predecessor calendar, successor calendar) and is independent of the run count.
