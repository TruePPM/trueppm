**Scheduler: a signed-off milestone's edge is now its pin, so a predecessor's recorded finish no longer moves its successors earlier.** A milestone closed with recorded actuals now sits at the end of its recorded day only when the previous run's hand-back (`Task.live_day_end_on`) names that day, and at the start of it otherwise. Its predecessors are no longer read for the edge: not their actual finishes, links or lags, and not whether they are still open. A calendar-day lag out of a milestone closed at the start of its day can still count from an earlier equivalent midnight read from completed predecessors (#4690), so a completed predecessor's change can move lagged successors later, never earlier; a pin-only link instant is tracked in [#5089](https://gitlab.com/trueppm/trueppm/-/issues/5089). Before, a closed predecessor whose `actual_finish` fell on the sign-off day pushed the milestone's successors a working day later than any other finish date did, so recording a *later* finish pulled them earlier, and raising a lag on an unrelated completed link could flip `milestone_at_day_end` with no date change. Both the Python and Rust engines apply the rule (ADR-0136, amended). Library callers that do not pass `live_day_end_on` back now get the start of the recorded day for every closed milestone. The TruePPM API already passes it back, so closing a milestone on its forecast day still moves nothing. A correction to completed work no longer releases a handed-back end-of-day edge ([#5017](https://gitlab.com/trueppm/trueppm/-/issues/5017)).
The result-stability stamp `0.5.0-dev` is re-stamped for the closed-milestone conformance fixtures whose dates moved; their task names describe the superseded rule and are kept verbatim because the `0.4.0` stamp shares those inputs, so the expected snapshots are authoritative.
