Org-level authority is no longer derived from a self-grantable project role on the resource catalog's destructive and disclosing surfaces. Any account could reach `IsOrgAdmin`/`IsOrgScheduler` in two requests — project creation is ungated and makes the creator Owner — which admitted everyone to catalog email and email search (the org-wide address-harvest control), the deactivated-resource pool (`?include_deleted=true`), resource deactivation and restore, and the cross-project `GET /api/v1/resources/{id}/assignments/` view. Those four surfaces — six endpoints, counting `restore` alongside `DELETE` and email search alongside email exposure — now require a workspace operator (the installation superuser). This does **not** yet close every path to a catalog address: the project and program `resource-allocation` endpoints build their payload by hand and still return `email` to a project-scoped caller, so the address-harvest control is narrowed here rather than completed (#3599). Separately, both derivations stopped counting memberships on archived and soft-deleted projects, and `/api/v1/task-skill-requirements/` dropped a redundant org gate in favor of the per-target project check it already ran. Ordinary catalog and skill-catalog editing is unchanged.
