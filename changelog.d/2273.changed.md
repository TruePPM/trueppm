**Monte Carlo runs on a Celery worker instead of the request thread (#2273).** `POST /api/v1/projects/{id}/monte-carlo/` now answers `202 Accepted` with `{task_run_id, status, n_simulations}` instead of a `200` carrying the forecast. Poll `GET /api/v1/projects/{id}/task-runs/{task_run_id}/` until `status` is `success`, then read the forecast from `GET /api/v1/projects/{id}/monte-carlo/latest/`; a `failed` run carries the refusal (cycle, simulation caps, busy worker, wall-clock budget) on `result_summary` with its HTTP `status_code`. Invalid `n_simulations`, too many committed tasks (402) and too many dependencies (400) are still refused synchronously, and the `monte_carlo` throttle still applies to the `POST`. The web app polls for you. **Breaking for API clients that read the forecast from the `POST` response** (the MCP server only reads `latest/` and is unaffected). See ADR-1430.
