**Monte Carlo runs on a Celery worker instead of the request thread (#2273).** `POST /api/v1/projects/{id}/monte-carlo/` now answers `202 Accepted` with `{queued, task_run_id, status, n_simulations}` instead of a `200` carrying the forecast. Poll `GET /api/v1/projects/{id}/task-runs/{task_run_id}/` until `status` is `success`, then read the forecast from `GET /api/v1/projects/{id}/monte-carlo/latest/`; a `failed` run carries the refusal (cycle, cell cap, wall-clock budget, or a 403 when the project was archived or your membership removed while the run waited) on `result_summary` with its HTTP `status_code`. Invalid `n_simulations`, an explicit `n_simulations` above `MC_SIMULATION_CAP` (402), too many committed tasks (402) and too many dependencies (400) are still refused synchronously, and the `monte_carlo` throttle still applies to the `POST`. The web app polls for you. **Breaking for API clients that read the forecast from the `POST` response** (the MCP server only reads `latest/` and is unaffected); recorded as a pre-1.0 policy exception in the API stability page. `task_run_completed`, `task_run_failed` and `task_run_cancelled` WebSocket events now also carry `task_name`. See ADR-1430.
