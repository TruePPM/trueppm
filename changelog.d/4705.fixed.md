- **Scheduler: a link between a summary task and its own descendants is now refused,
  not silently rewritten** (#4705, #4538): `expand_summary_dependencies` used to treat
  a link whose endpoints share a leaf (a summary linked to one of its own children, a
  child linked to its own parent, a summary linked to itself, or a nested summary
  linked to its ancestor) as a harmless self-reference. Depending on the shape it
  dropped the link, turned it into an invented order between sibling tasks
  (`S{a, b} → a` scheduled as `b → a`), or raised a cycle through two leaves nobody had
  linked. `find_cycle` reports every one of these inputs as a cycle, and the expansion
  now agrees with it: it raises `CyclicDependencyError` with `.cycle` naming the source
  link (`[summary, child, summary]`, or `[S, S]` for a link to itself).
  **Library callers who passed such links straight to `expand_summary_dependencies`,
  without running `find_cycle` first, used to get a silently reordered or unconstrained
  schedule. They now get `CyclicDependencyError`.** The web app already refused these
  links when they were saved, so interactive use is unchanged. A project whose stored
  data already holds one (an import can bring one in) now fails its recalculation
  with the cycle error instead of producing a schedule that ignores the link.
