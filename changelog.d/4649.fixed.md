The offline sync upload (`POST /api/v1/projects/{id}/sync/`) now returns `400` with the same structured body as `PATCH /api/v1/tasks/{id}/` when a row is refused by the progress-anchor gate, the milestone rollup lock, the zero-duration-is-a-milestone rule, or a guardrail set to block. These refusals used to surface as an HTTP `500`, which a sync client treats as retryable. The same fix turns two other `500`s into structured refusals: creating a task with progress but no planned start or sprint through `POST /api/v1/tasks/` now returns `400 progress_requires_anchor`, and a bulk task write that trips a blocking guardrail now rejects only that row instead of failing the whole batch with a `500`.
