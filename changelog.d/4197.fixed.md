- **A milestone whose shown date hops a weekend no longer reads as baseline drift or rollup variance (#4197).** Follow-up to #4178. A milestone shown at the start of a Monday is at the same point in working time as one shown at the end of the Friday before it. Several baseline and rollup numbers still subtracted the two shown dates, so a milestone baselined at the end of a Friday and now shown at the start of the next Monday could log a `baseline_drift_detected` activity entry, appear on the project overview as "Slipped +3d vs baseline", show a +3-day finish delta on the task's Baseline tab, or show a three-day `slip_days` on a closed sprint's milestone line. It could also add three days to the program rollup's baseline variance, or skew its schedule variance by three days. A sprint ending on the Friday also showed a milestone rollup `variance_days` of -3. All of these now compare in working time and still report a real slip in calendar days. Baselines now record which edge of the day each finish sits on, and a baseline's task snapshot (`GET /api/v1/projects/{id}/baselines/{baseline_id}/`, `tasks[]`) carries it as `finish_at_day_start`. A baseline captured before this release has no such record, and its finishes are read as the end of their day. The MCP server's forecast and what-if explanations now say "calendar day(s)", the unit the API returns, instead of "working day(s)". Monte Carlo run-to-run and risk-premium deltas, a task's own `schedule_variance_days`, and the baseline variance chips on the board card and schedule summary strip still subtract shown days; that is tracked in #4203.
