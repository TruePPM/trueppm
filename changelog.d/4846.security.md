A token refresh or password sign-in that was already running when a password reset committed could still hand back a fresh access and refresh token, because those two paths read the account's credential cutoff without the profile row lock that #4839 added for durable-grant creation. Both now take the same lock and re-check the cutoff against the locked row: a refresh whose token predates the reset is refused with a `401`, and a password sign-in that verified the old password before the reset committed is refused with the same `401` as a wrong password.
