Scheduler: closing work recorded after an already-closed milestone's sign-off day no longer moves that milestone's successors. The engine used to read completed work whose link placed the milestone on a later day as placing it at the end of its recorded day, so closing out-of-sequence work slipped the gate's successors, and possibly the project finish, by a working day. Now only a link from completed work that places the milestone on its recorded day gives it the end of that day, and while a link places it later, the end-of-day edge the previous schedule recorded (which the API hands back) still stands, so the result is the same as while that work was open. The link decides, not the finish date: an FS-1d link from work finishing the day after the sign-off places the milestone at the end of the sign-off day, and closing that work with no previous edge handed back still moves its successors a working day later. Both the Python and the Rust/WASM engines apply the rule (#4703).
