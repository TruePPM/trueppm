# ADR-1463: Web Push through the notification matrix's MOBILE_PUSH channel

## Status

Proposed (2026-11-22)

> **Implementation status (2026-11-22):** design only. Verified on `main`:
> `PROJECT_NOTIFICATION_DEFAULT_MATRIX` (`notifications/models.py`) has a `MOBILE_PUSH`
> column. That column sits in `PROJECT_NOTIFICATION_UNDELIVERABLE_CHANNELS` and defaults off
> (TODO #3252). There is no service worker, PWA tooling, VAPID or web-push code in
> `packages/web` or the API.

## Context

Layer: **Operations** (personal delivery). #2132 is the push foundation for the installable PWA, which **ADR-0026** names the mobile story through 1.0. The first payload is the agent-refusal alert.

Constraints:
- **ADR-0075** says push is opt-in only.
- **ADR-0075** and **ADR-0085** say channels plug into the `NOTIFICATION_CHANNELS` registry, with open channel strings.
- #2132 says there is no new per-event matrix: push rides the existing preferences.

`threat-model` (Pass 4) found three risks: the subscription endpoint is an SSRF surface, the VAPID key needs a lifecycle, and lock-screen text can disclose project data.

## Decision

1. **Channel.**
   - A `WebPushChannel` is registered in `NOTIFICATION_CHANNELS` under the existing `MOBILE_PUSH` key.
   - Delivery removes `MOBILE_PUSH` from `PROJECT_NOTIFICATION_UNDELIVERABLE_CHANNELS` **in the same change** that wires the dispatcher, following the matrix's own comment rule.
   - The column's default stays **off** for every row, so contributors start quiet.
   - Only rows with a dispatcher can deliver. Rows without one (#3016) stay labeled as undelivered.
2. **New matrix rows**, each off by default on every channel except in-app until its dispatcher ships:
   - `agent_refused`, sent only to the token's owner or principal. Repeats are **coalesced**: the first refusal per token in a 15-minute window pushes, and later ones update the same notification (same tag) with a count. The Inbox lists every refusal.
   - `resource_ask_received` and `resource_ask_decided` (ADR-1461);
   - `sprint_changed_externally`.
3. **Subscription.**
   - **`PushSubscription`** (`notifications`, core layer) holds `user`, `endpoint`, `p256dh`, `auth`, `label`, `created_at`, `last_delivered_at` and `failed_count`, with at most 10 rows per user.
   - It is managed through `/me/push-subscriptions/`. The `user` is always `request.user`.
   - A subscription is deleted on logout, on a 404 or 410 from the relay, and after repeated failures.
4. **D4, resolved: an SSRF guard.**
   - The `endpoint` host must match an allowlist. The default list is the major browser push services: FCM, Mozilla autopush, Apple and Windows.
   - Operators can **extend** the list in Helm (`push.allowedEndpointHosts`) for corporate push gateways.
   - The endpoint must use `https`, with no redirects and a short timeout. The resolved IP must not be private, loopback or link-local.
   - Dispatch runs on a worker, never on the request path.
5. **D3, resolved: lock-screen detail.**
   - Payloads are minimal: a title, a body of at most 178 characters, and an item ID.
   - They never carry amounts, rates or note text, and they are encrypted per RFC 8291.
   - A **per-user** setting, “Show details on lock screen”, defaults on, because a person opts their own device in.
   - An **operator** Helm value, `push.lockScreenDetails: allow|minimal`, can force minimal (“TruePPM · 1 agent alert”) for regulated installs, and the user can't override it.
6. **Operations.**
   - `push.enabled: false` by default in `values.yaml`, so a default install makes **zero** outbound push calls.
   - VAPID keys come from `push.vapid.existingSecret`, or are generated by the chart with `lookup` so `helm upgrade` never rotates them. Rotation is a documented, deliberate operation that invalidates subscriptions.
   - The secret is listed in the backup runbook. Egress hostnames and a NetworkPolicy example are documented in `administration/`.
   - Quiet hours, do-not-disturb and pause (existing settings) apply to push.
   - **Observability** (VoC round 3, following the ADR-0084 dead-letter alerting pattern):
     - metrics: `trueppm_push_deliveries_recent{outcome}`, `trueppm_push_dead_letter_parked`, `trueppm_push_subscriptions_disabled` and `trueppm_push_relay_responses_recent{status_class}`;
     - a `PushDeadLetterGrowing` rule in `prometheusrule.yaml`;
     - a VAPID-rotation note that names the expected spike in disabled subscriptions;
     - all of it documented in `administration/` next to the egress hostnames.
7. **Service worker.**
   - It is introduced here, and it is shared with the PWA install and the offline outbox (ADR-1465).
   - It is versioned with the web image, respects the ADR-1249 previous-asset window, and can be unregistered by a server kill-switch header.
   - On iOS, push requires the installed Home Screen app, and the UI explains this (canvas 4B).

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| A separate push preference matrix | Fine control | #2132 says don't. It would be a second preference surface that drifts. |
| Push mirrors “anything that notifies you” (an earlier Pass 4 draft) | Simple | Ignores the existing per-event `MOBILE_PUSH` column, and is noisy for contributors (VoC round 2, Priya) |
| A vendor relay (Firebase Admin and similar) | Easier delivery | A hosted dependency and account. Standard Web Push needs none. |
| Accept any endpoint URL | Fewer support tickets | SSRF from inside the cluster network |

## Consequences

- Easier: one preferences surface, and the 0.7 approval remote (#1312) reuses this plumbing.
- Harder: a service worker is a new version-skew surface, and egress has to be documented for compliance reviews.
- Risks:
  - Relay outages delay notices. The Inbox stays authoritative.
  - iOS users who don't install the PWA get nothing. The UI explains why.

## Implementation Notes

- P3M layer: Operations.
- Affected packages: api, web (service worker, permission UX), helm, docs.
- Migration: yes. `CreateModel(PushSubscription)` and new matrix rows. Matrix `schema_version` handling is in `notifications/schema_migrations.py`.
- API changes: yes. `/me/push-subscriptions/`, the new matrix rows, and the per-user lock-screen setting.
- New dependency: a Web Push library (pywebpush or equivalent). Run the `dependency` gate.
- OSS.

### Durable Execution
1. Broker-down behavior: push dispatch rides the existing notification outbox. A delivery row is written with the notification and drained.
2. Drain task: extends the notification delivery drain with the `MOBILE_PUSH` channel, which shares its semantics (per-channel delivery attempt).
3. Orphan window: 5 minutes, as for email delivery.
4. Service layer: `notifications/services.py` dispatch, plus the new `WebPushChannel.send()`.
5. API response: N/A, because push is a side effect of an event. Subscription endpoints are synchronous.
6. Outbox cleanup: the existing notification delivery purge.
7. Idempotency: keyed per delivery row. A relay 201 marks it done, and a retry after a lost acknowledgement may duplicate a notification, which is accepted (the OS collapses by tag).
8. Dead-letter: 3 retries with backoff. On 404 or 410 the subscription is deleted. After N consecutive failures it is disabled and shown as failing in the device list.

### AI-review amendments (2026-11-22)
- **Write safety:** `/me/push-subscriptions/` requires a human session (`IsNotTokenAuthenticated`). An agent can't register a device.
- **Provenance:** the `agent_refused` push body is generated from the same `AgentAction` refusal record (constraint name and value) that the Inbox and API show, never separate prose. The item ID links back to that record.
- **MCP:** N/A, because delivery is a side effect. The refusal record is already MCP-readable through the agent-oversight read (ADR-0677).

### VoC round 3 amendments (2026-11-22)
Surfaced by a simulated persona panel (VoC round 3, evidence tier E0). It is not user research. Each change is adopted on its merits.
- **Operator metrics and alert rule** (Decision 6). This closes the "dead letters visible only to the user" gap.
- **Coalescing `agent_refused`** (Decision 2), so a looping agent can't produce a stream of pushes.
- **Recipients are unchanged.** Each new row is its own matrix row, off by default and targeted: `resource_ask_received` goes to pool managers, `resource_ask_decided` to the requester, and `sprint_changed_externally` to the sprint's PO and SM. So someone who opted into blocker pushes doesn't receive these.
