# `transaction.on_commit` Durability Audit

**Issue:** #659 · **Date:** 2026-05-23 · **Trigger:** durability gap analysis after ADR-0080

## Why this audit exists

TruePPM defers async side effects to after the DB commit with
`transaction.on_commit(...)` so that a rolled-back request never fires a worker
or a broadcast. The risk that motivated this audit: any `on_commit` callback
that dispatches durable work (`.delay()`, `.apply_async()`, an external write)
**without first writing a durable row in the same transaction** silently loses
that work if the broker or channel layer is unavailable in the window between
commit and dispatch — with no PENDING row for a drain task to replay.

This document classifies every `transaction.on_commit` callsite in
`packages/api` so the durability surface is explicit rather than assumed.

## Classification rubric

| Bucket | Definition | Verdict |
|---|---|---|
| **outbox-protected** | Callback dispatches Celery work, but a durable outbox row was committed earlier in the same transaction. A Beat drain replays the row if dispatch fails. | Safe |
| **best-effort by design** | Callback only pushes a WebSocket event (`broadcast_board_event`). Loss is recoverable because clients re-fetch via the sync delta protocol on reconnect. | Safe (acceptable loss) |
| **durability-hole** | Callback dispatches Celery work or performs an external write with **no** preceding outbox row and **no** client-pull recovery path. | Must fix |

### The outbox machinery (what "protected" means)

Every Celery-dispatching callback must sit behind a durable outbox row with a Beat drain
task that re-dispatches stranded PENDING rows. The registered helpers and best-effort
primitives are **data**, kept in `packages/api/on-commit-registry.txt`; the table below is
generated from it (`python3 scripts/check-on-commit-durability.py --write-docs`) and the
gate fails when it drifts.

Any callback that calls a registered outbox helper is outbox-protected *by definition*
— the helper writes the durable row before (or instead of) dispatching.

### The best-effort contract (why broadcasts are safe to lose)

`broadcast_board_event` (`apps/sync/broadcast.py`) is **best-effort by design**.
A broadcast is a
push optimization, not the source of truth: every event it carries is also
durably persisted in the DB before the broadcast is scheduled, and clients
reconcile their state by pulling the sync delta on (re)connect. If the channel
layer is down at commit time, the event is dropped and the connected client
recovers it on its next delta fetch. Losing a broadcast therefore loses nothing
durable. This contract is documented on the two primitives' docstrings; it is
**not** repeated as an inline comment on each best-effort callsite (the gate classifies them; run `python3 scripts/check-on-commit-durability.py --report`) —
that would duplicate one rationale at every callsite and violate the repo's
comment-discipline rule (comments explain non-obvious *why*; the why here is a
property of the broadcast mechanism, stated once at its definition).

## Result

The 2026-05-23 snapshot (91 callsites, 0 holes) was a hand-written table and drifted to
~290 callsites with nothing enforcing the rule (#2473). The per-callsite tables were
removed; `scripts/check-on-commit-durability.py` now classifies every callsite on each
push and CI run. Current totals are the gate's own output
(`python3 scripts/check-on-commit-durability.py`), not prose.

Callsites the gate cannot classify mechanically (`hole`, `unclassified`) are listed with
a reason in `packages/api/on-commit-baseline.txt`, a ceiling that can only shrink.
**A baselined entry is not an audited-safe entry**: several entries are read and
row-backed, the rest are simply not yet audited into the registry. Read each entry's
reason before citing the gate as proof of durability.

### Note on #658 (`close_sprint` durability)

#658's reported hole does not exist: `enqueue_sprint_close()` writes a `SprintCloseRequest`
PENDING row before the deferred dispatch, and `drain_sprint_close_requests` reclaims
orphaned rows. `enqueue_sprint_close` is a registered outbox helper.

## How to keep this audit true

The gate is `scripts/check-on-commit-durability.py` (`make on-commit-durability-check`,
CI job `lint:on-commit-durability`, part of `make pre-push`). Details, the ratchet and its
blind spots are in `docs/harness/on-commit-durability.md`.

When you add a `transaction.on_commit` callback:

- **Broadcast only** (a registered best-effort primitive) -> nothing to do.
- **Dispatch Celery work** (`.delay()` / `.apply_async()`) -> commit an outbox row first via a
  registered helper, or register a new helper (model + drain) in
  `packages/api/on-commit-registry.txt`. Never `.delay()` from `on_commit` without a durable row.
- **External write** (HTTP, email) -> route through an outbox + drain; never fire directly.
- **Genuinely safe but unrecognized** -> `# on-commit-ok: <reason>` on the line or the line above.

`broadcast-check` (pre-MR gate) verifies new mutations defer their broadcast via
`on_commit`; this gate is the durability complement.
