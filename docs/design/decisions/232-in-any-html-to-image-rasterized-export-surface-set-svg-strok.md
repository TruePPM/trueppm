# Rule 232 — In any html-to-image-rasterized export surface, set SVG stroke/fill via inline style (a rgb(var(--token)) CSS var), NEVER a Tailwind stroke-/fill- class — html-to-image silently drops CSS-class stroke on <path> (it keeps class fill on <polygon>), so a class-based connector rasterizes as 0 ink while its arrowhead survives

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Client-rasterized export surfaces — SVG stroke + row-aware pagination (Issue #1694, ADR-0276)*

**In any `html-to-image`-rasterized export surface, set SVG `stroke`/`fill` via inline `style` (a `rgb(var(--token))` CSS var), NEVER a Tailwind `stroke-`/`fill-` class — html-to-image silently drops CSS-class `stroke` on `<path>` (it keeps class `fill` on `<polygon>`), so a class-based connector rasterizes as 0 ink while its arrowhead survives.** This was the schedule PDF's "arrowheads but no dependency lines" bug (#1694): confirmed empirically — a class-stroke path rasterizes to 0 ink, an inline-style stroke path rasterizes fully. The inline-`style` CSS-var form (`style={{ stroke: 'rgb(var(--neutral-text-secondary))' }}`) is the reliable path AND stays gate-safe (no hex literal; single-sourced through the DS custom property, so the `design-system-v2` hex gate passes) — do not "fix" it back to a `stroke-*`/`fill-*` utility class. This is `style`-for-a-reason (rule 10 carve-out: a rasterizer-compatibility requirement, not styling convenience); comment the why at the call site. Print-surface FS dependency arrows are **charcoal always** (`--neutral-text-secondary`), hard vs soft = **solid vs dashed** (never color — ADR-0063 rule 75: critical is the red bar; a red arrow over a red bar merges). Reference: `schedulePrintTheme.ts::arrowColorVar`, the `<path>`/`<polygon>` `style` in `SchedulePrintLayout.tsx`.
