# Rule 268 — The ⌘K recent group renders in the empty-query (cold) state only, and cold-state duplication with jump is intentional (Spotlight pattern) — do not try to de-dupe cold

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *⌘K `recent` group is cold-only; scope-aware task cap splits sprint vs. project tasks (Issue #1557, ADR-0508)*

**The ⌘K `recent` group renders in the empty-query (cold) state only, and cold-state duplication with `jump` is intentional (Spotlight pattern) — do not try to de-dupe cold.** `recent` (from `GET /me/recent-projects/` via `useRecentProjects`) sits directly above `jump` in `GROUP_ORDER` because it is a *pre-filtered slice of jump*; it is dropped in `applyResultCaps` when `hasQuery` (the inverse of the `task` gate) AND the hook itself only builds items when the trimmed query is empty, so typed search is owned solely by the existing `jump` fuzzy filter and a project is never listed twice *once the user types*. Cold, a recently-visited project appears in **both** Recent and the full Jump list — this is the macOS-Spotlight/Raycast shortcut-strip pattern, not a bug; the `RECENT` header and the `· 2h ago` recency hint differentiate the two appearances. Recent rows use the **bare project name** as `label` (identical to their Jump twin — same `Project` object, same neutral `Project` chip), **never** an `Open:` prefix (that prefix is reserved for `task`/`sprintTask` rows, which open a drawer rather than navigate). Program breadcrumb + recency go in the single muted-mono `detail` span as `{program_name} · {formatRelative(new Date(visited_at))}`, program dropped via `.filter(Boolean)` when the project has none. Zero recent projects → the group self-hides (`length === 0 → null`); no skeleton, no empty row. `useRecentProjects` guards `Array.isArray(res.data)` because the endpoint returns a **plain array** (not a paginated envelope) and an e2e catch-all `{count,results}` reaching `.map` would tear down the app via the error boundary. **Scope-aware task cap:** a **separate** `sprintTask` group ("Current sprint tasks", cap `SPRINT_TASK_RESULT_CAP = 25`) renders **above** a disjoint `task` group ("Tasks", cap `TASK_RESULT_CAP = 8`) — a task in the active sprint (`task.sprintId === activeSprint.id`) appears in `sprintTask` only, never both, so keyboard nav stays single-listed and each cap applies to its own set; with no active sprint every task falls to `task` (unchanged Waterfall/no-sprint behavior). Only the live "Sprint" *board* action is chip-tinted; sprint-scoped **tasks** keep the neutral `Task` chip. Overflow-cue asymmetry is deliberate: the bounded sprint uses `Showing 25 of {M} — …` (countable working set), the unbounded project-wide set keeps `Showing first 8 — …` (no alarming total). Reference: `features/shell/commandPalette/` (`CommandPalette.tsx`, `useCommandItems.ts`, `commandItems.ts`), `hooks/useRecentProjects.ts`.
