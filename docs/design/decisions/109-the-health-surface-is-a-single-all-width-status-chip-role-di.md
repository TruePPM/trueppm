# Rule 109 — The health surface is a single all-width status chip + role="dialog" popover — NOT a responsive md:flex / md:hidden split

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Shell Navigation Rules (Issues #204–#205)*

**The health surface is a single all-width status chip + `role="dialog"` popover — NOT a responsive `md:flex` / `md:hidden` split** (issue #205; tablet breakpoint #1562; reshaped to the chip in #1644, ADR-0128 §B progressive disclosure). `HealthCluster.tsx` renders one `data-testid="health-cluster"` chip `<button>` at **every** width (no breakpoint-gated dual render): a health **dot** (`aria-hidden`, rule 6), the worst-state **band word** (`On track` / `At risk` / `Critical` — the non-color signal, rule 6; the one health vocabulary of rule 7 / ADR-0126, read from `HEALTH_BAND_LABEL` in `lib/healthBand.ts` and never a chip-private synonym; the band itself is the **server's** `health_band`, read off `useShellStats` and never computed here — see the #3501 amendment below — independent of the methodology segment set), an optional **neutral** P80 forecast fragment (`hidden sm:inline-flex`; neutral even inside a red/amber chip, rule 172), and a caret. Clicking it toggles a popover (`role="dialog"` `aria-label="Project health"`, `shadow-pop` pop-surface exception to rule 1) whose rows are exactly the methodology's `healthClusterModel` segments — forecast band (P50 + P80 rows, neutral, `Details ›` opens the MC panel, issue #196), at-risk/critical drill groups, sprint/points/velocity — with the ADR-0104 velocity privacy wall honored (rule 168, no number when suppressed). The popover **must** trap focus with `useFocusTrap` (rule 206): focus in on open, Esc closes + restores focus to the chip, outside pointer-down closes. **Do NOT reintroduce the pre-#1644 `hidden md:flex` expanded cluster or the `md:hidden` "Health ▾" phone dropdown** — the all-width single control is deliberate (both to reduce the surface and to avoid the rule-211 `hidden`-toggle double-render, where the same `getByRole` control resolves to two DOM nodes). The chip word colors clear WCAG 1.4.3 in both modes (at-risk `#92400E` / critical `#B91C1C` light, `#FB923C` / `#F87171` dark; on-track word is neutral `text-neutral-text-secondary` with the green carried by the dot).

**Amendment (#3470).** The chip originally mapped the three bands onto its own words — `At risk` for the *critical* band and `On watch` for the *at-risk* band — so the top bar and the page beneath it printed different words for the same project, and `On watch` was a word no ADR or design document defined and no other surface rendered. The chip now prints the band word itself. A task-count nuance belongs in the popover rows, **not** in the word: the chip is a single worst-state read, and inventing a fourth word for a three-value vocabulary is what rule 7 / ADR-0126's "one status vocabulary" forbids. Do not reintroduce `On watch`.

**Amendment (#3501), superseding this record's original derivation claim.** This record used to say the band "is derived from the project-wide `at_risk_count` / `critical_count` on `useShellStats` by `deriveHealthBand`, which mirrors the server's `compute_band`". All three halves of that are now false, and the middle one was the bug. `views.py::compute_health_band` (renamed from `compute_band`) checks the manual `Project.health` report **before** the counts, and the counts cannot see that report — so the chip printed "On track" over a project its own PM had reported Critical, and "Critical" over one reported On track, on Schedule / Board / Table where the top bar is the only health reading. `GET /projects/{id}/status-summary/` now returns `health_band` from that same callable, the chip prints it, and `deriveHealthBand` is **deleted** — `lib/healthBand.ts` deliberately exports no way to compute a band at all. Do not reintroduce one; if a new payload cannot carry a band, add the field to that payload (`packages/web/CLAUDE.md` rules 396(b) and 301(a), ADR-0599).

One consequence this record's "single worst-state read" language no longer covers: the chip word can now be **better** than the worst signal in the popover rows beneath it, so a `Critical` header can sit over `At risk — 0 tasks`. The popover does not yet say which of the two it is showing — #3525 owns that, and `packages/web/CLAUDE.md` rule 397 records the obligation as knowingly unsatisfied.
