# Rule 266 — Native window.confirm / alert / prompt are banned for in-app decisions — especially mid-gesture board interactions

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *A field's contextual-help affordance is the shared `FieldHelp` component, not a hand-rolled tooltip (Issue #1975)*

**Native `window.confirm` / `alert` / `prompt` are banned for in-app decisions — especially mid-gesture board interactions.** They are unstylable, ignore the design system, name no entity (which task? which column?), sit outside the focus trap and screen-reader flow, and return focus unpredictably after a pointer gesture (on some platforms a `confirm()` during a pointer sequence renders oddly). Use a `role="alertdialog"` + `aria-modal="true"` panel driven by `useFocusTrap` (Escape → cancel, focus restore) with Cancel-first ordering (rule 245): the safe action is first-focused and emphasized, the risky action de-emphasized. For a drop/move that must be gated, **defer** the action behind the dialog — stash the full completion closure (`perform`) plus the context the copy needs, show the dialog, and run `perform()` on confirm — rather than blocking the gesture with a synchronous prompt; wire both the drag-end and the keyboard "Move to…" paths through the same deferred candidate so neither write path falls back to a native prompt. One inherent limitation: after a *pointer* drop `document.activeElement` may be `<body>`, so the trap's restore-to-trigger is best-effort on the drag path (the keyboard path restores cleanly) — an accepted trade-off, not a defect. Reference: `features/board/WipLimitConfirmDialog.tsx` + the `wipMoveCandidate` deferral in `features/board/BoardView.tsx` (#2050); canonical dialog shape is `features/settings/components/ConfirmDiscardDialog.tsx`.
