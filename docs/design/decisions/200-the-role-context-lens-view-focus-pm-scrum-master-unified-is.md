# Rule 200 — The role_context lens ("View focus": PM / Scrum Master / Unified) is PRESENTATION-ONLY — it re-orders and re-points already-permitted surfaces for the active user and MUST NEVER gate a write, a permission, a data fetch, or what anyone else sees

> Original section: *Role-context lens — "View focus" (ADR-0162, issue 1263 / issue 412)*

**The `role_context` lens ("View focus": PM / Scrum Master / Unified) is PRESENTATION-ONLY — it re-orders and re-points already-permitted surfaces for the active user and MUST NEVER gate a write, a permission, a data fetch, or what anyone else sees.** A user in "PM mode" has exactly the same RBAC authority as in "Scrum Master" or "Unified" mode; the lens is never read in a permission class, a `canEdit`/`canManage` predicate, a mutation guard, or a query-enable condition — only in presentation code that arranges surfaces the user is *already* allowed to see. `unified` is the genuine neutral default (the value while `user` is still loading), so an unconfigured or loading user gets exactly today's behavior — **no flash of the wrong lens**. The lens does two things, both additive: (a) **default project view** — `ProjectIndexRedirect` (`router.tsx`) lands `/projects/:id` on `lensDefaultView(role_context)` (PM→`schedule`, Scrum Master→`board`, Unified→`overview`), holding (renders nothing; the `ProjectShell` chrome stays painted) until `['current-user']` resolves so it redirects once; (b) **view-bar emphasis** — `applyRoleContextLensOrder(groups, lens)` (`features/shell/lensOrder.ts`, pure) promotes the lens's priority views to the front of their *own group*, composed in `ViewTabs.tsx` **after** `groupedVisibleViewsForUser` + the role gate (it only re-orders already-permitted, already-visible views — never reveals or hides one) and **never edits the canonical view registry** (`viewMeta.ts`/`methodologyTabs.ts`). It is orthogonal to `default_landing` (rule 182 / ADR-0129): `default_landing` owns the surface at `/`; the lens owns emphasis *inside* a project. The switcher lives in two places mirroring existing patterns: an inline segmented control in `UserMenu` (`RoleContextMenuRow`, the `ThemeToggle`-style `role="group"` + `aria-pressed` toggle group with a **rule-179** `bg-brand-primary text-neutral-text-inverse` active fill — never a same-surface shade) and a radio-card group on `MyGeneralPreferencesPage` (`RoleContextRadioGroup`, the rule-167 roving-tabindex radiogroup). Both write `role_context` via `useUpdateRoleContext` → `PATCH /auth/me/profile/` with optimistic state reverted on error (the reverted selection + an `aria-live` line are the error feedback). Read it via `useCurrentUser().role_context` (server fact on `/auth/me/`, default `'unified'`). **Deferred, do not assume they exist:** bespoke PM/SM dashboards + per-lens alert widgets, a Sprint-Goal-health callout, velocity-forecast surfacing, per-team lens context, and mobile (`BottomNav`/React Native) lens parity.
