> Original section: *Touch targets and calendar day-type encoding (Issue #906)*

**A calendar day cell never encodes its day-type by color alone (WCAG 1.4.1): each non-working type carries a pattern fill + a legible glyph/label + an `aria-label` naming the blocking calendar(s), and a multi-source day adds a split-corner mark.** The four-part encoding is mandatory on any `--cal-*` day-cell grid: (a) a **pattern fill** — weekend diagonal hatch, holiday dots, shutdown cross-hatch — built as inline `background-image` gradients over the translucent `--cal-*-bg`; (b) a **≥12px-legible glyph** (rule 50 floor) — holiday `H` / shutdown `S` — placed as the cell's own content (in a ~18px dense month grid, swap the day number for the glyph rather than shipping a sub-12px corner tag; the exact date stays in the `title`/`aria-label`); (c) an **`aria-label`** giving the full date plus the names of the calendar(s) that blocked the day, so the "why is this day off?" answer is never mouse-`title`-only; (d) a **split-corner** triangle (`aria-hidden`) when more than one calendar overlaps the day. The `--cal-*-fg` ink for the glyph/label is contrast-checked against the **composited** fill (the translucent `-bg` over the white card, e.g. holiday ≈ `#FBF0DB`), not the raw rgba — the composite reads lighter, so a token that clears 4.5:1 on paper can fail on the cell. Reference: `features/settings/project/ProjectCalendarsPage.tsx` (`DayCell`) + the `--cal-*` tokens in `styles/globals.css` (ADR-0251).
