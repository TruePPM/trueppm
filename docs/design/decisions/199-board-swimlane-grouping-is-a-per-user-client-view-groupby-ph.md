# Rule 199 — Board swimlane grouping is a per-user *client view* (groupBy: 'phase' | 'assignee' in useBoardToolbarPrefs), never saved-view/server state — and the two modes emit the same lane shape so everything downstream stays mode-agnostic

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Board swimlane grouping (Issue #324)*

**Board swimlane grouping is a per-user *client view* (`groupBy: 'phase' | 'assignee'` in `useBoardToolbarPrefs`), never saved-view/server state — and the two modes emit the same lane shape so everything downstream stays mode-agnostic.** The board's "Group" toolbar chip is a real `role="radiogroup"` (Phase / By assignee), mirroring the Sort/Density chips. `groupBy` is an additive, backwards-compatible field on the same `trueppm.board.toolbarPrefs.v1` localStorage blob as `zoom`/`density` (a stored blob without the key defaults to `'phase'`; an unknown value coerces to `'phase'`) — it is a personal lens, not shared board config, so it does **not** live in `BoardSavedView`. Phase grouping (`buildPhases`, by WBS summary parent) is unchanged; assignee grouping (`features/board/grouping.ts::buildAssigneeLanes`) groups leaf cards by **primary assignee = the first of `assignees[]`** (matching the card chip's lead) into one `BoardLane` each, sorts lanes alphabetically by name with the **"Unassigned" lane pinned last**, **excludes summary tasks** (WBS structure, not assignable work), and returns only lanes that hold cards (no empty-assignee noise). Both modes feed the same `phaseTaskMap` (which buckets each lane's `phase.tasks` by status) and `mobileTasksByStatus` (which flattens across lanes) — so the mobile reflow (rule 193) and the drag handler need no per-mode branch. **Workshop mode always forces phase grouping** (`groupMode = workshopMode ? 'phase' : prefs.groupBy`) because workshop authors WBS phase structure. Two consequences for assignee lanes: (a) the per-lane "+ add task" affordance is **suppressed** — a lane id there is a *resource*, not a parent, so `LaneMeta` renders the add button only when `onAddTask` is provided (it is optional; `BoardView` passes none in assignee mode), never a dead button (rule 122); (b) **drag-to-reassign is deferred** — a cross-assignee-lane drop never changes the assignee, but a same-drop status (column) change still applies and the `aria-live` region announces "reassign from the card". **Deferred follow-ups, do not assume they exist:** team grouping (needs a server-side `task.team` field — team is derived via `TeamMembership` today) and cross-lane drag-to-reassign (a separate `TaskResource` multi-assignee write-path design pass; note the legacy `assignee` User FK vs `assignees[]` mismatch). Reference: `features/board/grouping.ts`, `useBoardToolbarPrefs.ts`, the Group chip in `CalmToolbar.tsx`, and the `groupMode` branch + reassign hint in `BoardView.tsx`.
