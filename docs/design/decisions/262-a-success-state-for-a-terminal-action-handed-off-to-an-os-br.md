# Rule 262 — A success state for a terminal action handed off to an OS/browser-owned dialog (print, native file-save, share sheet) must announce that the dialog *opened / was dispatched* — never that the action *completed*

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *A terminal action handed to an OS/browser-owned dialog announces the dialog *opened*, never that it *completed* (Issue #1970)*

**A success state for a terminal action handed off to an OS/browser-owned dialog (print, native file-save, share sheet) must announce that the dialog *opened / was dispatched* — never that the action *completed*.** The app cannot observe whether the user confirmed or canceled an OS-owned dialog, so the heading and the `role="status"` live-region copy say **"Print dialog opened"**, never "Printed"/"Saved"/"Shared", and the state transitions to success once the dispatch call returns without throwing — it is **not** gated on `afterprint`/`oncancel` (which are unreliable cross-browser and never report the outcome). Three invariants: (a) **derive the success copy from the *result* payload** (which action actually ran — e.g. `result.destination`), not from the requested option, so a stale option can never mislabel the confirmation; (b) **pair it with a manual fallback affordance** ("Open printable PDF") for browsers that ignore the auto-dispatch (Firefox pdf.js / some Safari builds skip the embedded auto-print `OpenAction`), and **gate the fallback prose and its button on the same condition** (`result.blobUrl`) so the "open it yourself" sentence never points at an absent control; (c) **keep the dispatch client-local** — a print/share that must honor "nothing leaves the project" uses a hidden same-origin iframe (`features/export/printPdf.ts` `dispatchPrintViaIframe`), never a popup (`window.open` is blocked because generation is async and the click gesture has expired) and never `window.print()` on the live DOM (it prints the app chrome/theme, not the rendered artifact). The iframe + its object URL MUST outlive the open dialog — revoking early cancels the print — so cleanup waits for `afterprint` with an unconditional long-timeout fallback armed at mount (not inside `onload`, or a frame that never loads leaks forever). Reference: `features/schedule/export/ScheduleExportDialog.tsx` (print-success branch), `features/schedule/export/exportSchedulePdf.ts` (`finalizePdf`), `features/export/printPdf.ts`.
