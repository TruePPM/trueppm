# Rule 170 — A board-scoped ephemeral drop notice is bottom-center, role="status" + aria-live="polite", neutral-toned, and carries the SAME hollow ○ as the pending chip — never success-green

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Board-scoped ephemeral drop notice (Issue #1140)*

**A board-scoped ephemeral drop notice is bottom-center, `role="status"` + `aria-live="polite"`, neutral-toned, and carries the SAME hollow ○ as the pending chip — never success-green.** `BoardDropNotice` in `features/board/` is the reference: it fires when a card is dragged into an ACTIVE sprint and creates a *pending* scope-change (ADR-0102 post-activation injection) — a read-state, not a celebration — so it MUST NOT use success-green chrome (rule 149). Surface is `bg-neutral-surface-raised border border-neutral-border text-neutral-text-primary shadow-lg`, positioned `absolute bottom-4 left-1/2 -translate-x-1/2 z-40` inside the `relative` board container, auto-dismissing after 4s and fading via `transition-opacity`. The leading glyph is the SAME hollow `○` (`text-neutral-text-secondary`, `aria-hidden`) used by `PendingAcceptanceChip` so the toast and the card chip can never drift in tone. It is a single instance: a new message replaces the prior one and resets the timer (key the notice with a changing value so two identical drops still re-trigger it). Only an ACTIVE-sprint drop that creates a pending injection toasts — a PLANNED-sprint link (commitment baseline, no pending gate) and a plain status move do not. Reuse this anatomy for any future board-local transient confirmation; do NOT reach for a global toast library.
