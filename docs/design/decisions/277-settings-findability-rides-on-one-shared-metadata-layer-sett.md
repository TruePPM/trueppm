# Rule 277 — Settings findability rides on one shared metadata layer: SettingsNavItem.keywords (ADR-0606). Author keywords on every new settings section, and index workspace palette entries from buildWorkspaceNavGroups, never a hand-copied list

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *AppShell owns the only `<main>`; the 404 keeps the shell (Issue #2184)*

**Settings findability rides on one shared metadata layer: `SettingsNavItem.keywords` (ADR-0606). Author `keywords` on every new settings section, and index workspace palette entries from `buildWorkspaceNavGroups`, never a hand-copied list.** Two surfaces consume the same source so they can't drift: (a) the desktop rail filter (`SettingsShell`, #2320) narrows sections by `label + keywords` (case-insensitive substring), hides now-empty groups, jumps to the first match on Enter, and is **desktop-only** — mobile keeps its native `<select>` jump-to-section; the filter `<input>` is a form field so it uses `focus-visible:` (rule 214 carves out shell-chrome *buttons*, not inputs), while its clear `✕` is chrome (`focus:`). (b) the ⌘K **`settings`** command group (#2319) is **query-only** (in `QUERY_ONLY_GROUPS` — a cold palette shows only the three top-level `jump` settings targets, not ~20 section rows); its workspace entries derive from `buildWorkspaceNavGroups({ linked: true })` (so `keywords` authored once serve both surfaces and every item carries a `/settings#<id>` anchor) and personal entries from the exported `ME_SETTINGS_LINKS`. Workspace-section entries are **admin-gated and hidden** (the whole `/settings` tree is `RequireWorkspaceAdmin`) via the same `workspace_role >= WORKSPACE_ADMIN_ROLE` check the cold `jump:workspace-settings` uses; personal entries are ungated; the `detail` line (`Workspace` / `Personal`) disambiguates same-named sections. The cold `jump:trash` is admin-gated too (it lives under the admin tree) and the section group **omits `trash`** so it isn't duplicated. When you add a settings section, add its `keywords` and — if it's a new nav *source* — make sure the palette reads from that source. Reference: `features/settings/SettingsShell.tsx`, `features/settings/workspace/workspaceNav.tsx`, `features/me/MeSettingsSubNav.tsx`, `features/shell/commandPalette/{useCommandItems.ts,CommandPalette.tsx,commandItems.ts}`.
