# Rule 198 — A multi-<fieldset> checklist and its permanently-disabled (server-denylist) rows must be programmatically named and explained, not left to per-group legends alone

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Inheritable set (allow-list) field (ADR-0153, issue 976)*

**A multi-`<fieldset>` checklist and its permanently-disabled (server-denylist) rows must be programmatically named and explained, not left to per-group legends alone.** Two a11y requirements for the rule-197 checklist family (and any future grouped-checklist control): (a) the checklist container that holds several `<fieldset>`s carries a single `role="group"` + `aria-label` (threaded from the field's `ariaLabel`) so screen-reader users hear one accessible name for the whole region — the per-group `<legend>`s name the *groups*, not the collection; (b) a row rendered DISABLED to mirror a server-enforced denylist (`aria-disabled="true"`, not a real input) must point at its reason via `aria-describedby` (e.g. a shared "Blocked for security and can't be enabled." note with an `id`) — `aria-disabled` alone leaves SR users with an unexplained dead control. Also name each `<fieldset>` via `aria-labelledby={legendId}` (the group name), not `aria-describedby` (a description). The informational delta line that changes as the user edits gets `role="status" aria-live="polite"` so the narrower/wider feedback is announced. Reference: `AttachmentTypesChecklist` (`ariaLabel`, `deniedReasonId`), `InheritableMultiSelectField`.
