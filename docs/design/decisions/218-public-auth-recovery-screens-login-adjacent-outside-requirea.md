# Rule 218 — Public auth/recovery screens (login-adjacent, outside RequireAuth) share the AuthShell centered-card primitive and treat any client-side password meter as advisory-only

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Mobile bottom rail caps at 5 slots; overflow goes to a BottomSheet, never a scroller (Issue #1464)*

**Public auth/recovery screens (login-adjacent, outside `RequireAuth`) share the `AuthShell` centered-card primitive and treat any client-side password meter as advisory-only.** The password-reset flow (issue 765, ADR-0209) added `features/auth/passwordReset/AuthShell.tsx` — a mobile-first centered card with the brand lockup, an optional 3-step progress-dots indicator (`role="img" aria-label="Step N of 3"`), title/subtitle, body slot, and an optional "Back to sign in" footer link, all on theme-aware neutral/brand tokens (light+dark). New public auth surfaces (email verification, SSO-error, future recovery steps) render inside `AuthShell` rather than re-rolling a centered card, so the whole unauthenticated set stays visually one product. Two conventions travel with it: (a) an inline **requirements checklist** built from icon + color must also carry the state in text for AT (rule 6) — client-verifiable items toggle a check/dot with an `sr-only` "Met:"/"Not yet met:" prefix, and a server-only item (e.g. "not a previously used password") stays neutral `text-neutral-text-secondary` (never `text-disabled`, which fails 1.4.3) with no met/unmet prefix since it is unknown until submit; (b) the **strength meter is advisory** — the score/label and the two live checks gate the submit button, but the server's `AUTH_PASSWORD_VALIDATORS` + reset-confirm policy are the authority, so never present the client meter as the enforcement. Reference: `AuthShell.tsx`, `ResetPasswordConfirmPage.tsx` (`RequirementItem`, `StrengthBar`).
