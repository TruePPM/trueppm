# Rule 48 — Export / print surfaces force the light theme island — never assume the app is in light mode (issue #1683, corrects the pre-dark-mode assumption)

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *UI Harmonization Rules (Issue #44)*

**Export / print surfaces force the light theme island — never assume the app is in light mode (issue #1683, corrects the pre-dark-mode assumption).** A PDF/PNG export surface (`SchedulePrintLayout`, `BoardPrintLayout`) is a deliberately LIGHT document (white sheet, navy ink) but is mounted in the live app DOM and rasterized with `html-to-image`, so it inherits `html.dark` when the exporter is in dark mode: the sheet stays a fixed `bg-white` while every CSS-variable token (`text-neutral-text-primary`, `bg-neutral-surface`, `border-neutral-border`, `semantic-*` fills) resolves to its **dark** value, and the rasterizer captures near-white ink on a white page (WCAG 1.4.3 fail — the original bug). The root of any export/print surface MUST carry the **`.theme-light`** class (the token island in `globals.css` — the mode-paired `:root` token blocks extend to `:root, .theme-light`, so the light values are single-sourced and re-asserted on the subtree regardless of the ancestor `.dark`). This supersedes the earlier "the Schedule view already uses a light surface; no override needed" note, which predated the Schedule view adopting real dark theming (rule 40 / ADR-0103). Still ensure `@media print` does not reintroduce dark browser-default backgrounds. When adding a new client-rasterized export surface, apply `theme-light` to its root and assert it in the layout's unit test.
