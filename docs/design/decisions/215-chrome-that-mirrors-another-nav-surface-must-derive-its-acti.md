# Rule 215 — Chrome that mirrors another nav surface must derive its active-view state and its labels from the SAME shared source as the surface it mirrors — never reimplement either

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Mobile bottom rail caps at 5 slots; overflow goes to a BottomSheet, never a scroller (Issue #1464)*

**Chrome that mirrors another nav surface must derive its active-view state and its labels from the SAME shared source as the surface it mirrors — never reimplement either.** When a second navigation surface (the mobile `BottomNav`) reflects the same view set as a primary one (the desktop `ViewTabs`), three things silently diverge if reimplemented locally, and each is a ux-review finding: (a) **active view** — derive it from the path segment *after the projectId* (`pathSegments[indexOf(projectId) + 1]`), exactly as `ViewTabs` does, NOT from the last path segment; the last segment misfires on nested detail routes (`/board/<cardId>`) and leaves no tab marked current. (b) **iteration label** — resolve the Sprints/Cycles label through the shared `useIterationLabel(projectId)` chokepoint (ADR-0116 workspace→program→project inheritance), NOT off the raw `iteration_label` field; the raw field is null when the label is inherited, so a local read shows "Sprints" while the desktop bar shows the inherited "Cycles". (c) **overflow-active label** — when an overflow-parked surface is active, resolve its accessible name off the *view key* (`activeOverflowView`), NOT off `currentView`; on a sub-route like `/settings/notifications` the trailing segment is `notifications`, so a `currentView`-based label degrades the More button to "More, view selected" instead of "More, Settings selected". Reference: `BottomNav.tsx` (mirror) against `ViewTabs.tsx` (source).
