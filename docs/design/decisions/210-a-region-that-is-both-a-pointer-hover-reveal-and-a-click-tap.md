# Rule 210 — A region that is *both* a pointer hover-reveal and a click/tap disclosure MUST source aria-expanded and its collapse behavior from the explicit toggle state only — never add group-focus-within:block alongside the toggle

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Hover-reveal + click disclosure must source aria-expanded from the toggle state only (Issue #1305)*

**A region that is *both* a pointer hover-reveal and a click/tap disclosure MUST source `aria-expanded` and its collapse behavior from the explicit toggle state only — never add `group-focus-within:block` alongside the toggle.** Mixing the two desyncs the announced state from what is visible: tabbing into the card fires `group-focus-within` and renders the region `display:block` while `aria-expanded` is still `false` (WCAG 4.1.2 state mismatch), and the collapse toggle is *inert* for a keyboard user because focus inside the card keeps `group-focus-within` true regardless of the toggle. The correct split: `group-hover:block` is the **pointer-only** convenience (mouse users don't consume `aria-expanded`); keyboard and touch reveal flow through the toggle state (`peekOpen`) which also drives `aria-expanded`, so the announced state always matches what is visible and the collapse is never inert. Everything the toggle reveals must live inside the single `aria-controls` target — fold sibling panels (e.g. a baseline-variance sub-panel) into the controlled region rather than gating them on the same state from outside it. Reference: the worst-offender badge peek in `features/board/BoardCard.tsx` (#1305).
