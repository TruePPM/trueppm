# Rule 209 — An async action wired into a ToolbarOverflowMenu (or any menu that closes on select) MUST surface its in-flight/disabled state in a *persistent* region — a role="status" toast/bar or an always-visible control — NOT on the menu item itself

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Async action launched from an overflow menu needs a persistent status region (Issue #1437)*

**An async action wired into a `ToolbarOverflowMenu` (or any menu that closes on select) MUST surface its in-flight/disabled state in a *persistent* region — a `role="status"` toast/bar or an always-visible control — NOT on the menu item itself.** Action items call `activate()` → `setOpen(false)`, so the menu (and the item) unmount the instant the user clicks; a busy label (`'Generating…'`) or `disabled` set on the item is rendered into a closed popover the user never sees, leaving a slow operation (a 1–2s client-side rasterize, a network export) with *zero* feedback until it errors. This surfaced on the Schedule's **Export schedule as PDF** item (#1437): the `exportingPdf ? 'Generating PDF…'` label on the overflow item was invisible because the ⋯ menu closes on select. The fix is the same docked-bottom `role="status"` region the **MS Project export** uses (`ScheduleView.tsx` — "Preparing your export…" / "Generating your PDF…"), or the **board export**'s always-on toolbar button that shows "⏳ Generating PDF…" inline (`CalmToolbar.tsx`, never in a menu). The `role="status"` form is preferred for menu-launched actions — it also gives screen-reader users the busy announcement the transient menu item cannot. General principle: feedback for an action must outlive the surface that launched it. Reference: the `exportingPdf` status region in `ScheduleView.tsx`, the MS Project export status region beside it, `ToolbarOverflowMenu.activate()`.
