# Rule 278 — A story-point estimate chip is scale-aware and its "Unestimated" prompt is methodology-gated — a Waterfall (duration-estimated) task is NEVER scolded for a missing point value, and neither is a summary/milestone (#2315 slice 3)

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *AppShell owns the only `<main>`; the 404 keeps the shell (Issue #2184)*

**A story-point estimate chip is scale-aware and its "Unestimated" prompt is methodology-gated — a Waterfall (duration-estimated) task is NEVER scolded for a missing point value, and neither is a summary/milestone (#2315 slice 3).** The task-drawer header `HeaderEstimateChip` is the reference (it replaced the cryptic unlabeled "· estimated" badge): a concrete estimate renders `{formatStoryPoints(pts, scale)}{storyPointsUnit(pts, scale)} · {Readiness}` (so a T-shirt "M" drops the " pts" unit and an off-scale integer still shows its number — the `lib/storyPoints` single source, ADR-0510), readiness **sentence-cased**. The amber **"Unestimated"** state renders ONLY when `effective_methodology ∈ {AGILE, HYBRID}` AND the task is a non-summary, non-milestone leaf with `storyPoints == null` — a points-based team that hasn't estimated yet. A Waterfall task (or any rollup/marker) falls back to the plain `ReadinessChip`, never "Unestimated", because it estimates by duration/CPM, not points; showing "Unestimated" there is a false scold. Read `effective_methodology`/`effective_estimation_scale` off `useProject(projectId)` (never the raw `methodology` field). Any surface that surfaces a story-point estimate (board card, backlog row, drawer) uses the `lib/storyPoints` helpers for the value + unit and gates a "needs an estimate" affordance on methodology the same way. Reference: `features/schedule/HeaderEstimateChip.tsx`, `lib/storyPoints.ts`.
