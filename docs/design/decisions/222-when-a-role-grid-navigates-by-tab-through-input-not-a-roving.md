# Rule 222 — When a role="grid" navigates by Tab-through-<input> (not a roving-tabindex arrow-key model), every *non-input* cell that carries user-relevant state must be tabIndex={0} so its aria-label is reachable in a screen reader's focus mode — a title tooltip must never be the sole channel for "why is this cell different?"

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Mobile bottom rail caps at 5 slots; overflow goes to a BottomSheet, never a scroller (Issue #1464)*

**When a `role="grid"` navigates by Tab-through-`<input>` (not a roving-tabindex arrow-key model), every *non-input* cell that carries user-relevant state must be `tabIndex={0}` so its `aria-label` is reachable in a screen reader's focus mode — a `title` tooltip must never be the sole channel for "why is this cell different?".** A grid that announces `role="grid"` primes AT users for arrow-key cell traversal; if the real model is tabbing between editable inputs, the read-only / summed / over-limit cells fall out of the focus order and their explanatory `aria-label` (and any mouse-only `title`) becomes unreachable in the focus mode the grid role advertises. Make those cells focusable (`tabIndex={0}` + the standard `focus:ring` per rule 4) and keep the explanation in the `aria-label`, with `title` only as a redundant mouse affordance. Reference: the read-only multi-entry summed cell in `features/timesheet/TimesheetCell.tsx` (#1435, ADR-0224) — a `(task, date)` cell with ≥2 entries is a non-editable sum, made `tabIndex={0}` so its "N entries — edit on My Work" name is announced.
