# Rule 269 — SSO is multi-provider off a fixed FE/BE-shared registry keyed by slug; the login screen renders one button per *enabled* provider, and settings field hints must be programmatically associated

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Multi-provider SSO registry + settings-hint association (Issue #2108, ADR-0517)*

**SSO is multi-provider off a fixed FE/BE-shared registry keyed by `slug`; the login screen renders one button per *enabled* provider, and settings field hints must be programmatically associated.** The provider registry lives in `features/settings/workspace/ssoProviders.ts` — the `slug` (`generic`/`google`/`entra`/`keycloak`/… /`github`) is the value sent to the API and the `SocialAccount.provider` key, **not** allauth's internal provider name (every OIDC IdP maps to `openid_connect`, GitHub to `github` server-side). Each entry's `kind` (`free`/`fixed`/`derived`/`oauth`) drives the add/edit panel's issuer section, and `resolve(fields)→issuer` / `decompose(issuer)→fields` are inverses so the Edit panel pre-fills from the stored `server_url` (server persists only the composed issuer, not its parts); on a decompose miss the panel falls back to a raw editable issuer input. The composed issuer is re-validated server-side as an absolute https URL, so the FE derives nothing the server couldn't — the table is convenience, not a trust boundary. Two deliberate departures from the design handoff, both correct against the backend model: **(a)** the provider-type picker is a native `<select>` (fully keyboard/SR-operable for free) rather than a custom `role="listbox"`; **(b)** there is **no workspace-global master toggle** — the data model is per-provider (`SsoProviderPolicy.enabled`) and login discovery keys off enabled providers, so the Status card is a *derived* `role="status"` summary ("N providers enabled" / "not enabled yet") and each provider is enabled inside its panel. `LoginPage` discovers enabled providers on mount via bare `axios` (never `apiClient` — the login leaf must not pull the 401→refresh interceptor) and renders a "Continue with {display_name}" button per provider, hiding the whole SSO block (including the OR divider) when none are configured so a password-only install shows no dangling chrome. Provider tiles use intentional per-provider `color-mix()` brand hues with the glyph `aria-hidden` and the accessible name from adjacent text; all inline status glyphs (`🔒`, `✓`/`✗`, `Copied ✓`) are `aria-hidden` (rule 6) since a real `aria-live` text node carries the meaning. **New a11y rule surfaced by ux-review:** a `FieldRow` hint that is only a visible `<div>` is invisible to screen-reader users of the associated control — settings forms should wire hints to their input via `aria-describedby`. The shared `FieldRow` in `SettingsShell.tsx` does not yet expose a hint id (a systemic, pre-existing gap across every settings page), so the full fix is tracked as a follow-up FieldRow enhancement rather than a per-form patch; new settings forms should adopt it once `FieldRow` forwards the id. Reference: `features/settings/workspace/{ssoProviders.ts,WorkspaceSsoPage.tsx,SsoProviderPanel.tsx}`, `features/auth/LoginPage.tsx`, `hooks/{useSso.ts,ssoLogin.ts}`.
