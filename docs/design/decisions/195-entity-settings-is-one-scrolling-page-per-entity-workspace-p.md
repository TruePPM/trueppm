# Rule 195 — Entity Settings is ONE scrolling page per entity (workspace/program/project): every section is an anchored <section data-settings-section="<id>"> region mounted together, the left rail is a scroll-spy (buttons, not links), and the dirty/discard save bar is a single surface keyed across all sections

> **Decision record.** Moved out of `packages/web/CLAUDE.md` by #2433 (ADR-0653): precedent bound to one surface, not a general invariant. It is still binding for the surface it governs.
>
> Original section: *Mobile board reflow (Issue #853, v3 case 8)*

**Entity Settings is ONE scrolling page per entity (workspace/program/project): every section is an anchored `<section data-settings-section="<id>">` region mounted together, the left rail is a scroll-spy (buttons, not links), and the dirty/discard save bar is a single surface keyed across all sections.** (ADR-0146, supersedes ADR-0061.) Do **not** add a new settings section as its own route + `lazy()` chunk under an `<Outlet/>` — that was the per-section architecture that flashed/refetched on every nav. Instead mount the section's existing form inside a `<SettingsSection id="<slug>">` on the entity's consolidated page (`ProjectSettingsPage`/`ProgramSettingsPage`/`WorkspaceSettingsPage`) and add a rail entry (no `to` → scroll-spy button; a `to` makes it a real route departure for tool areas like System Health). `SettingsSection` wraps children in a `SettingsSectionContext.Provider` (section identity) and a `SettingsSectionErrorBoundary` (blast-radius containment — because all sections mount at once, an unguarded render throw would hit the **root** boundary and replace the whole app; the boundary degrades the one section to a contained "unavailable" message, mirroring ADR-0050 §Error containment). The save store (`useSettingsSaveStore`) is a **keyed** multi-section registry: each section registers under its id via `useDirtyForm`, the bar aggregates dirtiness across sections, **Save** commits every dirty section sequentially (short-circuiting on the first rejection with that section's message), **Discard** reverts them all. A rail **section** click scroll-spies in place — it must NOT trip the dirty guard and must NOT change the route; the guard fires only on a real departure (scope switcher, or a `to`-routed rail item). Deep links (`…/settings#<slug>`) scroll to the section on load (instant under `prefers-reduced-motion`, else smooth, focusing `[data-settings-section-heading]`); legacy `…/settings/<slug>` paths are sibling redirect routes (`SectionRedirect` → `…/settings#<slug>`) — they must be siblings of the consolidated route, never nested children, because the consolidated page renders **no `<Outlet/>`**. **E2E consequence:** all sections render at once, so a label/heading/button that appears in multiple sections is a strict-mode collision — scope locators to `page.locator('[data-settings-section="<id>"]')`; rail section nav is a `button` (`exact: true`), not a `link`; test the dirty guard via the scope switcher, not a section click; and a data-driven section needs its object endpoint mocked with its real shape or it renders the contained error fallback. Reference: `features/settings/SettingsShell.tsx`, `SettingsSection`, `SettingsSectionErrorBoundary.tsx`, `hooks/useScrollSpy.ts`, `hooks/useSettingsSaveStore.ts`.
