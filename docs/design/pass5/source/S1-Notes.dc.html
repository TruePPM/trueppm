Section 1 · Role-seeded view composition · #3715, designed with #3713 (methodology seeding)

Notes

Ground truth

Today the role lens reorders the project rail and never changes which views are in it, so a Scrum Master carries the full waterfall rail. This section adds a suggest layer. On a user's first open of a project it seeds their hidden views as a default they can override. It never enforces anything: permissions, workspace capabilities (Pass 4 · §1, #4888) and methodology still own what is allowed. The prototype states the same principle, “the preset communicates; it never enforces”, and “hidden views stay reachable by URL” (proto-designer.js).

Precedence · one line

permissions ∩ capability ∩ methodology → the allowed set. The lens seed then suggests hiding some of it, and the user's own choices override the seed. A seed can only narrow the allowed set. It can't show something the allowed set excludes, and it can't hide an always-on view.

Pins · 1A first open

1The tab row is seeded. People is gone and Deliver comes first. The lens control sits in the context header, as it does today, so this adds no new chrome. Tab order still comes from the lens, which is today's behavior.
2The explanation, “◌ Shown for Scrum Masters · 3 views hidden · Show all ✕”, is a toolbar item in row 3, not a banner. The layout toggle keeps its place and the 3-row limit holds. It shows once per project. Dismissing it is stored server-side per user. “Show all” clears the seed's hides for this project only and leaves the user's own hides alone.
3The same Hybrid project for three lenses. The seed acts on tabs and on layouts inside Plan and Deliver, which is why it still matters after consolidation (see Q8.2 below). Outlined tabs are always on.

Pins · 1B More and settings

1A seeded-hidden view sits in More under “Hidden from your tabs” and opens from there. Opening it doesn't un-hide it: the view opens with a one-line “Keep Gantt in your tabs” offer in row 3.
2A view that is off for the workspace (#4888) is listed but can't be opened, and it says why (“⊘ Time & cost is off · Why”), using the Pass 4 · 1B AreaOff copy. It never appears as merely hidden, because the user can't turn it back on.
3View visibility settings: one list with one switch per view, and a source label on each: ■ Always on · Shown · ◌ Suggested hidden · {lens} · ⊖ Hidden by you · {date} · ⊘ Off in {workspace}. “Reset to {lens} suggestions” rewrites only the seed entries.

Decision · seeded vs user-hidden

✓Decided Nov 24 A distinct state. It uses the same control and position, a different label, and a distinct glyph (◌ vs ⊖). The source is stored per entry: {view, hidden, source: seed|user, lens, at}. Without the stored source, a re-seed can't tell the user's curation from the seed's, and a user can't tell why Gantt is missing. No new color is used. The difference is words and a glyph.

Pins · 1C lens change

1Changing the lens reorders the tabs immediately and changes no visibility. Row 3 then carries the offer “Apply Product Owner suggestions…” in place of the toolbar until it is dismissed. This is the one Pass 5 case where a banner replaces row 3, and the layout toggle returns once it is dismissed.
2The confirm is a diff: Will hide, Will open on, and Kept, which names the user's own choices so it's visible that they survive. The action is “Apply 2 changes”, a count, never “OK”.
3Methodology × lens decides where the project opens. ◑ marks a cell where the lens asked for a view the methodology doesn't include.
4When they disagree, the note names the methodology (“This project is Waterfall, so it has no sprints”), so nobody hunts for a missing view. The methodology wins, because it governs the allowed set.
5Never empty: Overview, one Plan layout and More are always on. The last Plan layout's switch is disabled and says why. The server rejects a seed that would hide an always-on view, so a bad seed can't empty the rail.

Decision · re-seed on lens change

✓Decided Nov 24 Never re-seed automatically. Offer it once per lens change, with the 1C diff confirm, and touch only seed-sourced entries. Lens switches are often a quick look, and an automatic re-seed would destroy weeks of curation on a look.

Seed keyed to a role context, not a list

lensA key in a server registry (project_manager, scrum_master, product_owner, …). Adding a lens means adding an entry, with no redesign.
seed.hide[]View ids from the shared view registry (the same ids #3887's inventory produces).
seed.landing{method}The landing view per methodology, which is the 1C matrix.
seed.order[]Tab order, which exists today.
GET …/views/Returns the resolved view set for this user and project, with each entry's source. The UI renders it and never resolves precedence itself.
entry.bindingadvisory (seed or user hide: opens from More and by URL) vs enforced (off in workspace, or not in the methodology: refused). A client must never read “hidden” as “forbidden”.

Migrating from what shipped in #3713 ✓Decided Nov 24 · surfaced by a simulated panel

Today UserProfile.hidden_views is one flat per-user list, seeded once on a user's first project from methodology, with no source per entry. This design replaces it with per-user-per-project entries {view, hidden, source, lens, at}. The migration:

aEach existing entry becomes source: user for every project the user already belongs to. Nobody's curation is re-seeded or lost, and nothing they hid reappears.
bA new project the user opens for the first time gets the lens seed, so the flat list no longer drives new projects.
cThe profile field stays readable for one minor release. It returns the user's user-sourced hides across all projects, de-duplicated, and never the seeded ones. Responses carry Deprecation and Sunset headers, and the schema and changelog both say so. Writes to it return a pointer to …/views/. source and binding are enums in the OpenAPI schema.
dThe 1A toolbar line is the hint #5088 asks for. #5088 was closed against this section on Nov 24, so no separate rail hint ships.

People for resource owners ✓Decided Nov 24 · surfaced by a simulated panel

No lens seed may hide People from a capacity-pool manager (ADR-1461), because they are often the one who reads the grid (Q1.7). The rule is applied server-side, so the 1A Scrum Master example still holds for everyone else.

Pass 4 Q8.2 · does this need its own pass, or is it moot after consolidation?

It isn't moot, and this section is its pass. Consolidation reduces the tabs to six, but about seven layouts still live inside Plan and Deliver, and More carries the rest. The seed still decides which layouts a lens sees and where the project opens. It no longer needs to hide whole tabs often, so it gets smaller. Because the seed is keyed to view ids, #3887's inventory can drop or merge views without a redesign here. A seed entry naming a retired view id is ignored and logged.

Open questions

Q1.1Does methodology own the allowed set, or only suggest? The brief says methodology owns what is allowed. The prototype says the methodology preset “never enforces” and hidden views stay reachable by URL. I followed the brief: a Waterfall project has no Sprints view. Confirm this, or demote methodology to a second suggest input beside the lens.
Q1.2Is the seed per project or per user? I seeded per user per project, at first open. The alternative is one per-user default that every project inherits. Per project is noisier, but it is the only option that respects methodology differences.
Q1.3Who maintains the seed registry? Are seeds shipped defaults only, or can a workspace admin edit them? Editable seeds would edge toward org governance, which may need an enterprise-check.
Q1.4What happens when a project's methodology changes (Waterfall to Hybrid)? I propose the same opt-in offer as a lens change, never an automatic re-seed. Not drawn.
Q1.5✓Decided Nov 24 · surfaced by a simulated panel Yes, as an MCP read tool. …/views/ holds no domain data, but an agent explaining “why can't I see Sprints?” needs source and binding.
Q1.6Which seeds are right? The PM, Scrum Master and Product Owner seeds in 1A are my proposal. They have not been checked against #3713's methodology defaults or real users.
Q1.7✓Decided Nov 24 · surfaced by a simulated panel Someone who manages a capacity pool (ADR-1461) never has People seed-hidden, in any project. Their own hide still works, and the seed never overrides it. Scheduler rights alone don't count, so a Scrum Master who isn't a pool manager still gets the 1A seed.
