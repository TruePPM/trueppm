# Rule 167 — A roving-`tabindex` group (`role="radiogroup"`/`"tablist"`) MUST move DOM focus on arrow keys, and arrow …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A roving-`tabindex` group (`role="radiogroup"`/`"tablist"`) MUST move DOM focus on arrow keys, and arrow navigation MUST NOT commit a side-effect — only activation (click / Enter / Space) commits.** `PulseRadioGroup` in `TeamHealthPulse.tsx` is the reference: it holds a `focusIdx` + a `btnRefs` array; arrow keys advance `focusIdx` and call `btnRefs.current[next]?.focus()` (real focus movement — setting `aria-checked`/`tabIndex` alone strands the user on a now-untabbable element, WCAG 2.1.1), and they do **not** call the commit handler. The native `<button role="radio">` commits via `onClick` (which fires on Enter/Space too). The bug this prevents: routing arrow keys through the same `onPick`→mutate path as click, so a keyboard user scanning 1→5 silently records four throwaway answers — and for the pulse, those pollute the privacy-sensitive team aggregate (the #923 ux-review 🔴). Only the focused option is tabbable (`tabIndex={i === focusIdx ? 0 : -1}`); the group is reached by Tab, navigated by arrows, committed by activation. This applies to **every** `role="radiogroup"`/`"tablist"` built from native buttons — including single-select **filter-segment** controls (e.g. the Risk register's All/High/Unmitigated/Mine segment, `RiskSegmentedFilter.tsx`). A facet filter is a radiogroup and MUST use the roving-tabindex + arrow-focus pattern, not N independent tab stops — even when the committed action is non-destructive (a filter), arrow keys move focus only and activation applies it.
