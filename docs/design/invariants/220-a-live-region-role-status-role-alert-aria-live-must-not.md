# Rule 220 — A live region (`role="status"` / `role="alert"` / `aria-live`) must not carry a per-tick-updating accessible …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Signal encoding*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A live region (`role="status"` / `role="alert"` / `aria-live`) must not carry a per-tick-updating accessible name — announce discrete state transitions (start / stop / appear), never a running clock or counter; put the ticking value in an `aria-hidden` element and keep the region's name stable.** A live region whose accessible name embeds a value that changes every second (a running timer, an elapsed counter, a live countdown) fails two ways depending on the AT: screen readers that recompute the name re-announce roughly once per second (an announcement flood), and those that key off subtree text announce nothing on the state change that actually matters (start/stop). The region's name must reflect *what changed* (the timer started on task X; it went stale), not *the current value*. Keep the digits in a sibling `aria-hidden` span. Reference: the running-timer chip `TimerChip.tsx` (#1415, ADR-0185 §C) — `role="status"` named `Timer running on {task}` (plus the discrete `— running a long time` stale suffix), with the `formatElapsed` clock rendered in an adjacent `aria-hidden` span; contrast the safe `TaskRunIndicator` whose name changes only on discrete count changes. A non-live control (a plain `<button>`) may hold a ticking label — this rule is specifically about live regions.
