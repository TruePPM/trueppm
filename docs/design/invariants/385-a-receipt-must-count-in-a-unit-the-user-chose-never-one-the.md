# Rule 385 — A receipt must count in a unit the user chose — never one the server's tally loop happens to hold, and never …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Surface states*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A receipt must count in a unit the user chose — never one the server's tally loop happens to hold, and never a write the receipt is structurally unable to show.** Two failures with one cause: the surface reports what was convenient to compute rather than what the user can check. **(a) The unit.** The classification cascade's toast read `${governance.applied + delivery_mode.applied} fields written across ${matched} rows`. That first number is neither rows nor fields nor columns — `_AxisTally.applied` increments once per row PER AXIS, and the governance branch writes two model columns per increment, so a 10-row both-axes cascade announced "20 fields written" having written 30 columns (#3306). Nobody notices, because the number is plausible and there is nothing on screen to check it against — which is precisely the property that makes it useless. The test is not "is it accurate" but **"can the user falsify it?"**: rows are countable on the grid, axes are what the popover's own controls name, and columns are an implementation detail with no on-screen referent. Prefer the count the user's own selection produced; when the client cannot derive it — and here it genuinely cannot, since a row written on one axis and withheld on the other appears in exactly one per-axis total — **add the count to the response** (`rows_written`) rather than summing what is already there. Say both numbers when they disagree ("9 of 10 rows reclassified") and collapse to one when they agree, because "10 of 10" reads as a caveat where there is none; a no-op still speaks ("0 of 10"), since going quiet is how a user concludes the click was lost. **(b) The invisible write.** The same cascade's *other* receipt — the task's Activity tab — showed nothing at all for the one case where the only column that moved was `parent_governance_inherited`: the field sat in `_HISTORY_DIFF_DISPLAY_EXCLUDED` as bookkeeping, and the renderer drops any `~` record whose visible diff is empty. A real write (version bumped, undo ledger row created, `tasks_bulk_mutated` broadcast) with no record on any surface. **The repair is to PROMOTE the excluded field when it is a record's only change, not to widen the drop rule** — rendering every empty-diff update resurrects the bare "Updated" pill issue 874 removed, for every `sprint_rank` reorder in the tree. Promotion keeps the exclusion's intent (no noise beside a change the reader can already see) while making "a write with no record" structurally impossible. Three obligations on any field promoted this way: give it a **`FIELD_LABEL`** that names the change and not the column (`Governance source`, not `parent_governance_inherited`), a **`fmtValue`** mapping for its values (the diff pipeline is `str(value)`, so a boolean arrives as Django's `"True"`/`"False"` and renders as a receipt nobody can read), and a **`FIELD_TO_GROUP`** entry — without one the rescued record appears only under "All" and vanishes again the moment anyone touches a filter chip, which is half a fix. **State the denominator — there is more than one diff pipeline, and they now share one policy.** Task field changes reach users through three renderers: the task drawer's Activity tab (`apps/projects/views.py`), the project **Changes** tab (`apps/history/views.py::_compute_diffs` → `ProjectActivityPage`), and the board activity feed (`apps/projects/board_activity.py`, a curated allow-list). Until #3435 the first two carried disagreeing exclusion sets and only the drawer had a label map, so `ProjectActivityPage` rendered `c.field` raw — `governance_class`, `wbs_path`, `assignee_id` — for every change the drawer rendered as prose, and #3306's promotion fixed the drawer alone. **Superseded 2026-09-05 (#3435):** which fields are compared, hidden, and promoted is now decided once in `apps/history/diff_policy.py` (`HISTORY_DIFF_NOISE` / `HISTORY_DIFF_PRIVACY_GATED` / `HISTORY_DIFF_PROMOTED_WHEN_ALONE`, `visible_changes()`), both pipelines key rows by model **field name** (`assignee`, never `assignee_id`), and `activityFormat.ts::fieldLabel` is the ONE label map — with a humanized fallback, so an uncurated field renders as prose, never as an identifier. The remaining differences are deliberate and named in the policy: the drawer resolves FK ids to names and hides `is_deleted` (object-scoped); the project page carries ids and keeps `is_deleted` (the only record a soft delete leaves). The board feed shares no code and is pinned against the privacy set by `test_diff_policy.py`. When you add a diff field, add it to the **policy** and to `FIELD_LABEL` — never to one renderer — and still name which surfaces you verified. Note the mechanism honestly (rule 300): no check reads a count's unit and no check asks whether a written field can reach a surface, so the sweep is manual, and the standing question for any batch write is **"name the receipts and say what each one counts."** Reference: `features/schedule/classification/useClassificationPopover.ts` (`describeRowsWritten`), `features/schedule/activityFormat.ts`, `features/schedule/ActivityTimeline.tsx` (`GOVERNANCE_SOURCE_LABELS`), `apps/projects/views.py` (`_HISTORY_DIFF_PROMOTED_WHEN_ALONE`) — #3306.
