# Rule 280 — A roving-tabindex list must move DOM focus only when a *keyboard path* asked for it — never as a side effect …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A roving-tabindex list must move DOM focus only when a *keyboard path* asked for it — never as a side effect of the list changing.** The natural shape, `useEffect(() => optionRefs.current[activeIndex]?.focus(), [activeIndex, items.length])`, is a focus thief: any re-render that changes the list length also re-runs it, so a search field *above* the list loses focus after the first keystroke and every subsequent character is swallowed by the list's own type-ahead. The symptom is a search box that only ever holds one letter while the list narrows to the wrong thing — and it passes a naive unit test that types a single character. Gate the effect on an intent ref set by the keyboard handlers (`moveActive()` and the "open with ↓" path) and cleared when consumed, and drop `items.length` from the deps: `if (!open || !focusActiveRef.current) return; focusActiveRef.current = false; refs.current[activeIndex]?.focus()`. Test it by typing a **multi-character** query and asserting both the input's value and that the input still `toHaveFocus()` — a single-character test cannot see this bug. Reference: `components/filters/LabelFacet.tsx` (#2383).
