# Rule 420 — A container that holds real controls may not take a widget role; demoting it means …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Accessibility floors*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A container that holds real controls may not take a widget role (`role="button"`, `link`, `option`, `tab`, …) — put the accessible name and the tab stop on a real `<button>` INSIDE it, and when you demote the container, strip `aria-label` and `aria-roledescription` with the role, including the ones a library spreads on.** ARIA gives a widget role *presentational children*, so a `role="button"` wrapped around a card, row or cell that carries its own controls is axe `nested-interactive` — serious, WCAG 2.1 A 4.1.2 — and the controls inside it are not reliably reachable. This is the most common shape on this codebase: the board card was `role="button"` + `tabIndex={0}` around its health badge, dependency and risk chips, accept ✓ and ··· overflow trigger (#2618), and the same sweep found it on risk rows, program-backlog rows and My Work (#3482, 14 nodes). **Four obligations.** **(a) The name and the tab stop go on an inner `<button>` that contains nothing focusable** — keep the name string byte-identical when you move it, and every `getByRole('button', { name: … })` locator in `e2e/` and `src/**/*.test.tsx` keeps resolving, to the inner button instead of the container; that is what turns a role change from a hundred-locator rewrite into a handful. **(b) Whole-container click stays, and needs no role** — a click handler on the container is a *pointer enlargement* of an action that already has a real control, not the only route to it, so it is correct to keep `onClick` there; eslint's `jsx-a11y/click-events-have-key-events` and `no-static-element-interactions` will both fire, and the right response is a disable comment naming the inner control, never a role and `tabIndex` that recreate the violation. **(c) A roleless element is `generic`, which permits NEITHER `aria-label` NOR `aria-roledescription`** — leaving either behind trades `nested-interactive` for `aria-prohibited-attr` and the scan stays red, which is the trap, because the attribute that bites is usually not one you wrote: `useDraggable` spreads `role`, `tabIndex`, `aria-disabled`, `aria-roledescription` and `aria-describedby` onto its node, and they must be explicitly overridden to `undefined` after the spread. Move `aria-roledescription` onto the inner button with the name. **(d) The focus ring moves with the tab stop** — `focus:ring-*` on the container is dead once the container cannot hold focus, so switch it to `focus-within:ring-*` (never `focus-visible:`, rule 214) and the container still outlines when the user is anywhere inside it; any code that called `container.focus()` for roving/keyboard navigation is now a silent no-op and must target the inner control, which needs a stable `data-` handle to find. Reference: `features/board/card/CardShell.tsx`, `features/board/card/CardTitleButton.tsx`, `features/board/BoardCard.tsx` and the `project Board` scan in `e2e/a11y.spec.ts` — #2618, class tracked by #3482, surfaced by `ux-review`.
