# Rule 316 — A control that STATES where its effect will land must derive the sentence and the mutation from one function …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A control that STATES where its effect will land must derive the sentence and the mutation from one function — and the sentence must describe what the mutation actually composes, not what the design sketch promised.** The Schedule had three ways to add a row and all three fired a create, which is why the defect survived: the bug was never a missing call, it was that a button at the foot of the plan silently inserted after whatever row happened to be selected, and no test asserting "a POST fired" could tell the difference (#2957, part of #2946). Once an affordance narrates itself — *"⏎ adds a row after 2.4 · same level"* — the narration becomes a second implementation of the placement rule, and a hand-maintained mirror of a mutation drifts in the worst direction, because a confident wrong sentence gets acted on. Three obligations. **(a) One derivation.** A single pure function resolves the focus/selection state into a *target* (`buildMode/insertTarget.ts`'s `deriveInsertTarget` → `InsertTarget`); the component renders `describeInsertTarget(target)` and activates that same `target`. There is no second place to keep in step, and the sentence is unit-testable without mounting the surface. **(b) Check what the mutation composes, not what the design wrote.** The handoff sentence names the focused row; `insertBelow` creates a sibling and the create endpoint **appends at the end of the parent's children** (no `after_id` positioning in v1), so with the cursor mid-list the row lands after the *last* sibling and naming the focused one is a false claim of the rule-308 class. `InsertTarget` therefore carries `landsAfterWbs` — the last sibling — which collapses to the focused row on the common path (typing down a list) and stays honest off it. Where a truthful sentence is genuinely unavailable, render **nothing**: with no selection there is no row to land after, and borrowing a *different* affordance's behavior for the empty state re-collapses exactly what the split was for. **(c) A stated outcome must be asserted VISIBLE, not merely present — and never made conditional on the viewport.** Two failure modes, and the obvious fix for the first causes the second. `min-w-0` + `truncate` inside a `flex-nowrap` bar lets the span shrink to **zero width** while keeping its full text in the DOM: `toHaveText` passes, `toBeVisible` fails, and the sentence ships unreadable on exactly the crowded viewport it was written for — so pair a `min-w-` floor with the `max-w-` cap and assert `toBeVisible`. Reaching instead for `hidden lg:…` is worse, because the control keeps branching on state at the widths where the explanation was dropped, and `display:none` takes it out of the **accessibility tree** too, so a screen-reader user loses it at every width. Use `sr-only lg:not-sr-only` — readable to AT always, drawn where it fits — and point the control's **`aria-describedby`** at it. Corollaries: the sentence names its **keyboard twin** rather than the button (`⏎ …`), because that is what makes the toolbar a place someone learns the outline instead of a second way to click; it carries **no `aria-live`** (it changes on every arrow-key row move and would speak over the row announcement the planner is navigating by — same reasoning as web rule 194's contextual hint strip), which is precisely why `aria-describedby` is the right seam: it is announced on focus, when someone is about to act; and the control's accessible **name stays stable** across branches — a button that renames itself as the cursor moves is disorienting, so the qualification belongs in the description, not the label. Where a branch's precondition means the control would do nothing, make it **inert and say why** rather than firing a handler with no observable outcome: the toolbar's `+ Task` is `disabled` while the focused row is unnamed, because a click there would blur the cell, commit nothing, and leave the user unable to tell whether it worked. Reference: `features/schedule/buildMode/insertTarget.ts`, `features/schedule/ScheduleInsertTargetStatement.tsx`, `features/schedule/ScheduleAppendTaskFooter.tsx`, `e2e/schedule-insert-affordances.spec.ts` (which asserts *where the row ends up*, never that a request fired).
