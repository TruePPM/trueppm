# Rule 171 — `aria-label` on a non-widget element (`<p>`/`<div>`/`<span>`) does NOT suppress its descendant text in …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Signal encoding*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**`aria-label` on a non-widget element (`<p>`/`<div>`/`<span>`) does NOT suppress its descendant text in NVDA/JAWS — to expose a multi-span line as ONE accessible string, mark every visible child `aria-hidden`.** The `BoardSprintHeader` meta line ("{name} · {range} · Day N of M") is the reference: the `<p>` carries the composite `aria-label`, and **all** visible children — the name/range/counter spans AND the `·` separators — are `aria-hidden="true"`, so the screen reader reads only the label, never the label *then* the spans again (the double-read bug the #1138 ux-review caught, WCAG 1.3.1). This applies only to non-widget containers: on a real widget (`button`/`role="radio"`/etc.) `aria-label` does override the accessible name, so this extra step is unneeded there. The alternative pattern — `role="presentation"` on the container + a single `sr-only` span for the composite string — is equivalent; pick one, never leave readable child spans exposed alongside a container `aria-label`.

**See rule 421**: hiding every visible child stops the double-read but does not, on its own, make `aria-label` legal on a roleless container — axe `aria-prohibited-attr` fails it regardless (#3482). The `sr-only`-span alternative above is the one that also passes that check; prefer it over the `aria-hidden`-children-plus-`aria-label` shape for new code.
