# Rule 362 — A focus trap assumes its focusable set and its restore target are both stable — a one-way action invalidates …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A focus trap assumes its focusable set and its restore target are both stable — a one-way action invalidates both, and neither rule 206 nor rule 245 catches it as written.** Two failures on one confirm sheet (#3129), each a shape an existing rule describes with the wrong trigger, and both invisible to the unit tests that shipped with them. **(a) `disabled` empties a trap without unmounting anything.** Rule 245(a)'s `focusKey` requirement is written around *phase* dialogs where the focused control unmounts, so a sheet that merely disables its own buttons for the duration of a write does not read as covered — but `FOCUSABLE_SELECTOR` is `button:not([disabled])`, so the set goes **empty**, the browser drops focus to `<body>`, and nothing re-seats it. On any error path that leaves the sheet **open**, `document.activeElement` is then neither the first nor the last focusable, the Tab handler stops intercepting, and Tab walks into the page behind the scrim — an `aria-modal="true"` surface the keyboard can leave (WCAG 2.4.3 / 2.1.2). **Any dialog that disables its own controls while a request is in flight passes that pending flag as `focusKey`**, and gives the container `tabIndex={-1}` so the empty phase has a seat. **(b) A one-way action's trigger is gone before focus comes back, and open/close is the wrong key.** Rule 206 prescribes restoring an unmounting trigger "via an effect keyed on the open/close state" — insufficient here, because the trigger is still mounted when the sheet closes and disappears one refetch later when the lifecycle flips. The trap's cleanup then calls `.focus()` on a detached node, which is a **silent no-op**, so focus lands at the top of the document immediately after the single most consequential action on the page. **Key the restore on the trigger being *gone*, not on the dialog closing, and seat focus on a neighbour that survives the state change** — and do not fire it on Cancel/Escape, where the trap's own restore is already correct. Corollary for the guard, and the reason this class keeps shipping: **jsdom does not blur a focused element when it is disabled**, so a vitest assertion that focus stayed inside the trap passes with the fix reverted. It is vacuous by construction and must not be written; this class can only be pinned in a real browser. Reference: `features/project/CommitPlanConfirmDialog.tsx`, `features/project/ProjectOverviewPage.tsx` (`restoreFocusAfterCommit`), `e2e/commit-plan.spec.ts` — #3129.

**Enforced, as of #3352 — `scripts/check-focus-trap-focuskey.sh` (CI job `lint:focus-trap-focuskey`, `make pre-push`).** (a) was stated here and enforced by nothing: #3298 reintroduced it seventeen issues after #3129, caught only because a `ux-review` happened to look. The #3352 sweep re-read all 72 `useFocusTrap<` call sites against the tree and fixed **25 traps in 24 files**. The gate flags a `useFocusTrap` call with no third argument in a file that also renders a `disabled={<expr>}` naming an in-flight flag; the false positives it cannot resolve statically — is the disabled control *inside* this trap? — are paid for by `scripts/focus-trap-focuskey-waivers.txt`, a ratcheted list (a waived trap that stops tripping the detector fails as **stale**, so a fix forces its own waiver out) that seeds at **2**. Two shapes are deliberately invisible to it and must still be caught by reading: an in-flight flag reached through a derived boolean (`disabled={!canLog}`), and two traps in one file sharing a ref name.

**Corollary (c), #3352: a `focusKey` re-seat must stand down for a modal stacked above it, and the activation seat must not.** Giving 25 dialogs a `focusKey` created a second-order leak the single #3129 fix could not show: the global session-expired gate opens *on top of* an open write dialog, seats focus on **Sign in**, and then the dialog underneath settles its own pending flag one commit later and drags focus back out of the topmost modal — WCAG 2.4.3 in reverse, and reproduced by `e2e/session-expired.spec.ts`. `useFocusTrap`'s seat effect therefore returns early when `document.activeElement` sits inside a *different* `[aria-modal="true"]` element — **but only on a `focusKey` re-seat**. Guarding the activation seat as well is not a smaller version of the same rule, it is the opposite bug: the gate saw the dialog below holding focus, stood down, and never seated itself at all. The newly-opened surface always wins; the surface underneath waits.

Reference for the gate and corollary: `scripts/check-focus-trap-focuskey.sh`, `hooks/useFocusTrap.ts` (`seatedOnce`), `hooks/useFocusTrap.test.tsx`, `e2e/baseline-manage.spec.ts` ("a failed delete leaves the confirm open WITH focus still trapped inside it") — #3352.
