# Rule 324 — A gesture that acts on a SELECTION cannot be reached if a child of the row swallows the click — and the …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A gesture that acts on a SELECTION cannot be reached if a child of the row swallows the click — and the swallow is invisible to every test that drives the keyboard.** The Schedule outline had `⇧↑`/`⇧↓` and `⌘A` multi-select since #2727 and no pointer way to build a range, because `TaskListRow`'s `onClick` took no event at all (`onClick={() => handleRowClick(surface)}`); giving it one was not enough. A row's Name cell occupies most of its width, and `EditableCell`'s click handler `stopPropagation()`s so the row's own handler cannot re-set `RowFocused` after the cell has entered `CellEdit` — correct for a plain click, and it meant a **shift**-click landed on the cell, opened an inline edit, and never reached the range logic. The tell is specific and worth memorizing: the row *did* end up focused, the act *did* fire, and only the range was missing, so it reads as "extendSelection is broken" rather than "the event never arrived". Four obligations. **(a) A modifier that means SELECTION must bypass an edit affordance, not compete with it** — `if (e.shiftKey) return;` before the `stopPropagation()`, so the event bubbles; shift-click is never an edit gesture on any surface, and a cell that starts one on it is wrong independently of ranges. **(b) Route the pointer gesture through the SAME reducer action as the keyboard one.** `extendSelection(toRowId, visibleOrder)` owns the anchor semantics — the anchor is fixed for the life of the selection while `rowId` tracks the moving edge — and the case that separates a correct implementation from a plausible one is shift-clicking *back inside* an existing range, which must shrink it rather than restart it. Computing a range at the call site gets that wrong and nothing else notices. **(c) An E2E spec must leave cell-edit before it uses the keyboard, and must not use Escape to do it.** A plain row click opens the Name cell, so the next `press()` types into an `<input>` and every window-level chord is swallowed by `isTypingInInput` — a binding that works by hand fails in Playwright with **no error anywhere**, because `useScheduleKeyboard`'s guard returns before the handler runs. Escape is not the way out either: the row's own Esc handler is `focus.clear()`, which discards the very selection the next act reads. Gate on the state you need (`aria-selected="true"`, or the rename `textbox` being visible) and dismiss the editor through it. **(d) Assert the selection, not the control's enabled state** — a Group button is legitimately enabled for a single focused row, so `toBeEnabled()` passes on the exact failure the spec exists to catch. Reference: `features/schedule/TaskListRow.tsx` (`handleRowClick`), `features/schedule/buildMode/EditableCell.tsx`, `features/schedule/buildMode/useScheduleFocus.ts` (`EXTEND_SELECTION`), `TaskListRow.multiSelect.test.tsx`, `e2e/schedule-group-ungroup.spec.ts` — #2955.
