# Rule 314 — A settings section is five coupled edits across four files and two packages — and four of them fail somewhere …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Controls and composition*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A settings section is five coupled edits across four files and two packages — and four of them fail somewhere other than the file you are writing.** Adding a row to a settings rail feels like one change (`buildProjectSettingsNav` gets an entry, the page gets a `<SettingsSection>`), and the other three only announce themselves as red in test files you had no reason to open. The full set: **(a)** the nav entry, whose icon must be unique *within its group* — a repeat fails `settingsNavIcons.test.tsx`, not the page's own spec, because a column where most glyphs are identical trains the eye to skip it; **(b)** the `<SettingsSection id="…">` mount in `ProjectSettingsPage.tsx` / `ProgramSettingsPage.tsx` / `workspaceNav.ts`, keyed to the same id the rail scroll-spies on — the shell is ONE scrolling page (ADR-0146), so the address is `/projects/:id/settings#<id>` and there is no route to add; **(c)** an entry in `SETTINGS_DOCS` (`settingsDocs.ts`), enforced by a coverage suite that fails on *any* nav id with no help mapping — the regression #2487 was filed for was 38 of 44 sections having none; **(d)** the hard-coded section total in `settingsDocs.test.ts` (`covers all N sections`), which is a bare number and gives no hint what it counts when it fails; **(e)** a real `##`/`###` heading in the mapped page under `packages/website/src/content/docs/`, because the resolution suite reads the docs tree **off disk** and slugifies headings the way github-slugger does (lowercase, drop everything outside `[a-z0-9 -]`, spaces to hyphens, runs of hyphens **not** collapsed — so an em-dash in a heading yields a double hyphen in the anchor). That last coupling is the one that surprises: a frontend-only branch cannot ship a settings section without touching `packages/website`, and that is deliberate — it is the mechanism that keeps in-product help links from rotting into 404s. Point at the parent page with no fragment rather than inventing an anchor if the section has no docs of its own yet. Reference: `features/settings/ProjectSettingsPage.tsx`, `features/settings/settingsDocs.ts`, `features/settings/settingsDocs.test.ts`, `features/settings/settingsNavIcons.test.tsx` — #2971.
