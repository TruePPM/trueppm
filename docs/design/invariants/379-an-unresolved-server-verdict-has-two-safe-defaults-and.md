# Rule 379 — An unresolved server verdict has TWO safe defaults, and which one is safe depends on whether the output is an …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Surface states*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**An unresolved server verdict has TWO safe defaults, and which one is safe depends on whether the output is an AFFORDANCE or a WITHDRAWAL — never carry a `can_*` field's polarity across the two.** `canAuthorPlan(undefined) === false` is right because a `can_author` still in flight must not raise a control the server will refuse: absence beats a false affordance (#2949, rule 302). Applying the same `!flag` shape to a *disclosure* inverts the harm. `shouldDiscloseUndoFloor` renders a standing sentence telling the reader what they cannot do, so defaulting `undefined` to "disclose" states something **false** to the one reader who holds the right — on every render before the project query lands, and only to the privileged reader, which is why nobody reports it. Assuming rights on an unknown costs a note that arrives a beat late; assuming denial libels the Project Manager. So: **a capability field read to RAISE something defaults to withheld (`=== true`); a capability field read to WITHDRAW, WARN, or DISCLOSE defaults to silent (`=== false`).** Four obligations. **(a) Write the helper as an explicit three-way test against the value you mean** — `flag === false`, never `!flag` and never `flag !== true`. Both negations read as "no" and neither records which default was chosen, so a reviewer cannot see the decision and a later refactor flattens it. **(b) Name the helper for the OUTPUT, not the capability.** `shouldDiscloseUndoFloor`, not `canUndo`: a `can*` name reads as a capability check, and every call site then has to remember to negate it *and* re-handle `undefined` — which is the shape that produces the wrong default in the first place. **(c) Pin the two polarities against each other in ONE test**, including the input where they diverge, so a future "make these consistent" refactor has to confront the asymmetry rather than erase it: `canAuthorPlan(undefined) === false` beside `shouldDiscloseUndoFloor(undefined) === false`, then `canAuthorPlan(false) === false` beside `shouldDiscloseUndoFloor(false) === true`. **(d) The silence this buys is also what hides a broken prop chain, so a silent-defaulting disclosure MUST be proven to RENDER, per route the prop travels.** `undefined` renders nothing, a dropped link in the chain is `tsc`-clean, and every absence assertion then passes vacuously — the failure has no symptom anywhere. Assert the note's presence on each surface separately (the Schedule threads it through `ScheduleOverlayLayer`, which does not hold `projectDetail`; the backlog reads it directly), and **default the field explicitly in the shared E2E fixture** rather than omitting it (`setupApiMocks` sets `can_undo_batch_operations: true`) so a spec that wants the refusal has to ask for it. **Do NOT read this as a licence to name the floor in the copy either** — the field flips with the server predicate, so a sentence naming *what happens to this caller* stops rendering when the rule changes, while a sentence naming the ROLE becomes wrong copy for everyone still seeing it; keep the role in the recovery clause and phrase it as rights ("someone with Project Manager rights"), because a threshold admits Owner under a different label and an Enterprise band role under an arbitrary one. Reference: `lib/roles.ts` (`shouldDiscloseUndoFloor` beside `canAuthorPlan`), `features/schedule/classification/ClassificationPopover.tsx`, `e2e/fixtures/api-mocks.ts` — #3357, surfaced by `ux-review`, extending #2949/rule 302 and rule 373(d).
- **(e) Both safe defaults assume the branch you did NOT pick is SILENCE — where it is a positive CLAIM, neither is safe, so establish which case you are in rather than picking a polarity.** `shouldDiscloseUndoFloor(undefined) === false` is safe because the alternative to disclosing is saying nothing. When the other branch instead asserts a *fact about the data* — "No closed sprints yet" beside a series the server may have withheld (#3472) — an unresolved verdict picks a falsehood whichever way it resolves, and the spec written to cover it (`'still says X when the verdict is absent'`) pins that falsehood. So before choosing a default, **trace the server**: if the field is always emitted, type it required and delete the `undefined` case rather than defaulting it; if absence is reachable, the fallback must be non-committal ("Velocity unavailable"), never a claim. **Trace it in the endpoint that actually serves the surface, not a same-named field elsewhere** — #3472's `velocity_suppressed` is a required `BooleanField` on the *sprint-forecast* serializer and is set unconditionally on the *webhook* payload, while `GET /projects/<id>/velocity/` returns `velocity_summary()`'s raw dict through no serializer at all and adds the key **only** in `suppress_velocity_summary`. Absence there is therefore not "unknown": it is a fourth state, *"the server had no reason to say"*, which is unambiguous and makes the neutral branch TRUE. That is a good outcome and it is only knowable by reading the view — a review that reasons from the field's name across three payloads gets it backwards, and the fix it prescribes (typing the field required) would have asserted a key the endpoint does not send.
