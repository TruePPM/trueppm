# Rule 329 — A key that is BOTH text and a command needs a state that says which — and the state must be set by an …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A key that is BOTH text and a command needs a state that says which — and the state must be set by an explicit gesture, never inferred from the pointer.** The Schedule dependency picker taught `Space` as its multi-add commit and bound only Arrows and Enter, so `Space` typed into the search field and `Enter` — which closes on success — was the only commit. That made the picker one-link-per-open *by construction*, from the keyboard as well as the pointer, and the whole reason linking three predecessors cost three round trips (#3024). Four obligations. **(a) Disambiguate with a mode the user entered on purpose.** `Space` commits only once `↓` has walked the caret into the listbox (`inList`), and it goes back to typing on any keystroke into the field or a scope switch. Crucially, **hover must not set that flag**: reusing the visual `activeIdx` as the arming signal means a pointer user who brushes the list on the way back to the field creates a dependency the next time they type a two-word query. Two states that *look* the same on screen — "row 0 is highlighted" and "the keyboard is on row 0" — are different states, and collapsing them is how a command lands inside a word. Give the mode a reversible exit (`↑` off the first row steps back out), or the disambiguation is a trap rather than a rule. **(b) A roving VISUAL highlight is not a listbox.** Focus that stays in the input is the right pattern for a combobox, but only with `role="combobox"` + `aria-controls` + `aria-activedescendant` resolving to a rendered option `id` — without it a screen-reader user is never told the list exists. Assert it by **looking the id up in the DOM**, not by string-comparing it: a dangling `aria-activedescendant` is exactly as broken as a missing one and only a lookup separates them. Enter the list on the row already highlighted rather than advancing — an unconditional `i + 1` on the first press skips row one, which reads as the list starting at the second item. **(c) A row you can highlight is a row you can commit twice.** When a commit keeps the surface open, the committed row must leave the list on the surface's own state — the `excludedIds` prop cannot refresh until the parent's query refetches, and the second `Space` lands inside that window. And because the surface stays open, the add produces no other feedback: state it in a `role="status"` line, which is simultaneously the sighted confirmation and the announcement. **(d) Highlighting a name changes its accessible name.** Accessible-name computation **trims each text node before joining**, so wrapping the matched substring in a `<mark>` makes `Design review` announce as `Designreview` — and on this surface that string is what `aria-activedescendant` reads out on *every* arrow press. Any row that marks a match states its name with an explicit `aria-label` built from the same parts (including whatever a status chip contributes, or the chip silently drops out of the announcement).
