# Rule 326 — A persisted preference and a taught keystroke are both CLAIMS — each must resolve against the thing that …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A persisted preference and a taught keystroke are both CLAIMS — each must resolve against the thing that implements it, and the gate that proves it must DERIVE the resolution rather than restate it.** Two controls on one Schedule surface shipped claiming something nothing implemented, and neither was catchable by any test of the control itself. `Comfortable rows` toggled, persisted to `localStorage`, echoed back into the menu's `checked` — and was read by nobody, because row height came from the pointer class alone (#3019). The coach bar's first chip taught `⇥` for indent, and Tab is bound to nothing on purpose: binding it reproduces the WCAG 2.1.2 keyboard trap fixed in #2192/#2727 (#3020). Four obligations. **(a) Grep for a CONSUMER, not for the field.** A preference that persists is not wired; the question is which code *reads* it. A control's absence of effect is invisible to every test of the control itself, and the menu row had no test of its own either — so nothing anywhere went red for the whole life of the defect. Cover the entry point *and* assert a downstream effect; the first without the second is what lets a control be renamed or unwired in silence. **(b) A preference that modifies a runtime-resolved value is a second INPUT to that value's single owner (rule 315), never a second resolution.** Latch it in the owner beside the existing input and recompute from all of them — do **not** widen the existing setter to take both, because the writers know different halves: eight components call `syncRowMetrics(coarse)` on every render and none of them knows the preference, so a combined setter clobbers it back to `false` on the next paint. Unlike a media query the preference has no ambient event to listen to, so the owner must publish its own subscription (`subscribeComfortableRows` + `useSyncExternalStore`) or a memoized consumer keeps drawing 28px boxes around 44px canvas bands. Express the widening as `Math.max` over the named heights rather than `a || b`: an option that *raises a floor* must be written so it cannot lower one, and WCAG 2.5.5 is not a preference. **(c) Test the branch the heuristic cannot reach.** Comfortable rows exists precisely for the user a coarse-pointer rule misses — a desktop planner who wants bigger targets — and the pre-existing suite exercised only the coarse path, which is *why* a dead control shipped. The new-input test belongs on the **fine** pointer. **(d) A gate over teaching strings must derive the live set from the BINDINGS.** A test listing expected chords rots exactly as the string did — which is how both `⌥⌘G` and `⇥` got there. Derive it: read `ScheduleView`'s `out['token'] =` registrations straight off the source (they are already in `formatKey`'s grammar), and derive the row layer from `TaskListRow`'s guard expressions, so a statement testing `e.key` against a literal registers that key qualified by the modifiers the same statement tests. Err **wide**: a false negative ships another dead chip, while the worst false positive admits a chord nothing names. And distinguish a keystroke claim from a glyph that names a **button** — a `<kbd>` chip is a claim, prose is one only when it carries a modifier glyph. That line is load-bearing rather than tidy: the coach bar's third line reads `+ ⇤ ⇥ ◆`, which is the row's own button glyphs and is correct where it stands, so a guard matching glyphs anywhere would demand a wrong "fix" to a right string. Corollary — **fix the claim wherever it is made**: the same dead `Tab` was being taught by `features/summary-tasks.md` and `features/subtasks.md` while `features/schedule-build-mode.md` three pages away documented `Alt + →` correctly, so grep the docs tree for a keystroke you are correcting in the UI. Reference: `features/schedule/scheduleConstants.ts` (the owner and both inputs), `hooks/useRowHeight.ts` (`useComfortableRows`), `features/schedule/scheduleTeachingChords.test.tsx` (the derivation), `e2e/schedule-coarse-row-height.spec.ts` — #3019, #3020.
