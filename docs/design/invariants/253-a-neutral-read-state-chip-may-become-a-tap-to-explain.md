# Rule 253 — A neutral read-state chip may become a tap-to-explain disclosure, but the disclosure must stay neutral, grant …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Controls and composition*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A neutral read-state chip may become a tap-to-explain disclosure, but the disclosure must stay neutral, grant no capability, and portal out of any clipping scroll container.** `PendingAcceptanceChip` (`features/board/PendingAcceptanceChip.tsx`) is the reference: pass an optional `explainer` string and the chip renders a real `<button aria-expanded aria-controls>` toggling a `role="note"` popover with one plain-language sentence + a **neutral** "Got it" close button; omit `explainer` and it stays the passive read-state `<span>` (rule 149) with no disclosure state mounted (a hook-free early return, so read-only surfaces keep the passivity contract — no `button` in the tree). Five invariants: (a) **tone** — trigger, popover, and close button use neutral tokens only (`bg-neutral-surface-sunken`/`surface-raised`, `text-neutral-*`, `border-neutral-border`, `shadow-pop`); do **not** reach for the shared `Button` `ghost` variant, which is sage-brand-toned (`text-brand-primary`) and violates rule 149 — hand-roll a neutral ghost. (b) **No capability** — the popover explains only; it never gains accept/reject/any-mutation control (the decision stays team-owned on role-gated planning surfaces, rule 144), and the close button uses dismissal copy ("Got it"), never an action verb; the acknowledge is ephemeral (close-only, no persistence, no API) because the read-state is server-owned and clears on accept/reject (ADR-0102). (c) **Disclosure a11y** — Escape and "Got it" both close **and** return focus to the trigger; click-outside closes without stealing focus (check the trigger **and** the portaled popover, which is no longer a DOM descendant of the wrapper); `stopPropagation` on pointerdown+click so opening never drags/selects/opens the host card; `before:inset-[-12px]` for a ≥44px hit target; rule-4 `focus-visible` ring. **The inset numbers are stated in PADDING-box terms and every chip here has a `border`, so a pad written as `-N` on a bordered control buys `N-1` on each side and the target is 2px short of the arithmetic** — an absolutely-positioned child resolves its offsets against the padding box, which the border is outside of. `ConfirmDeleteStrip` reads -5/-13 rather than -4/-12 for exactly this (#3446), and it was found by a browser hit-test reading 43, not by anyone doing the sums. So: **a hit-area claim is only worth what a `document.elementFromPoint` scan says it is.** Bisect the run of y-values that resolve to the control and assert the span; a whole-pixel scan quantizes by ±1 against a floor of 44 and is a coin flip, and a `toContain('before:inset-...')` class assertion cannot see a border, a clipping ancestor, or a later-painting sibling that takes the overhang back. This chip's own ≥44px is unverified and, by the arithmetic above, ~42 — unmeasured, not fixed. (d) **Escape the clip** — the chip lives in a board column whose card stack is `overflow-y-auto` and can be as narrow as 208px (narrower than the popover); an in-flow `absolute` popover would be clipped and `z-index` does **not** defeat an overflow-clipping ancestor, so **portal the popover to `document.body`** with `position: fixed`, position it from the trigger's `getBoundingClientRect()` (flip above when there's no room below, clamp horizontally to the viewport), and **close on scroll/resize** since a fixed popover can't track its anchor (pattern: `features/schedule/UnscheduledTaskRow.tsx`). Portaling also sidesteps the `<p>` phrasing constraint on My Work — the wrapper/trigger stay `<span>`/`<button>` (phrasing content) inside the paragraph while the popover renders out in the body. (e) **Copy** — built by `pendingAcceptanceExplainer(iterationLabelLower?)`: role-neutral ("someone on the team accepts it", never "your Scrum Master" — acceptance authority is any Admin/SM/PO holder), outcome-only (no state-machine jargon like "scope injection"), iteration-label-aware on the board (`itl.lower`) and generic on cross-project My Work. Reference: `features/board/PendingAcceptanceChip.tsx`, `features/board/BoardCard.tsx`, `features/me/MyWorkTaskRow.tsx`.
