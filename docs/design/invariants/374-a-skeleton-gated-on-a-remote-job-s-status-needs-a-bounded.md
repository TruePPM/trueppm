# Rule 374 — A skeleton gated on a remote job's STATUS needs a bounded exit — "the job never reported" and "the job is …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Surface states*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A skeleton gated on a remote job's STATUS needs a bounded exit — "the job never reported" and "the job is still running" are the same two seconds and different hours.** Rule 246 covers a query that *fails* and rule 248 covers a skeleton's *shape*; neither reaches a query that keeps **succeeding** with a non-terminal value forever. A state derived from a polled job status (`pending` / `running`) has no terminal condition when the worker dies without writing one — Celery stopped, task lost from the queue, worker OOM-killed mid-write — so nothing errors, `isError` stays false, `QueryErrorState` never renders, and the surface polls and pulses indefinitely. Three obligations. **(a) Pair every status-derived skeleton with a timeout that falls through to the surface's ORDINARY empty state**, as `ScheduleView` does for `ScheduleSeedingState` and `ProductBacklogPage` does for `BacklogSeedingState` (both 60s, both polling the application's real status, so the timer is the last resort for a worker that died without writing a terminal status — not the primary exit). The backlog's was 10s while it guessed from a `?seeding=1` URL flag; see rule 391 for why that flag could never have been made to work and was retired (#3422). Falling through is the right landing, not an error: by then the surface really is empty, and the empty state's own affordance is the best thing on offer. **(b) Where the entry token is consumed one-shot from the URL, a reload is NOT a remedy the user can find.** `?templateApplication=` is stripped on consume by both surfaces, so reloading silently drops the id and escapes the state — which means the one escape that works is invisible, and nothing on screen suggests it. That is an argument for the timeout, never a substitute for it. **(c) A terminal status the skeleton does NOT cover must be a tracked deferral, not an implied one.** `ScheduleSeedingState` deliberately excludes `failed` — the project really is empty and the ordinary empty state is correct for it — but "correct for it" is a decision, so it carried an issue (#3348) and a negative-control spec that pinned the fall-through, rather than living as an absent branch nobody could find. **That deferral has since closed, and how it closed is the lesson: `failed` still is not seeding and the fall-through still is correct — what was missing was never this predicate, but that nothing ELSE read the status.** See rule 381; the fix was a sibling banner over an untouched canvas, not a third state in `resolveScheduleSeeding`. **Corollary — a job reporting `success` does not mean its rows are ON SCREEN.** Where the writes arrive over a WebSocket and the fallback poll is slow (`useScheduleTasks` drops to 30s on a healthy socket), clearing the skeleton on the status transition alone hands the user straight back to the empty state the skeleton existed to replace. Invalidate the data query on the terminal transition and re-derive the rows, instead of waiting for an event that may not come. Reference: `features/schedule/ScheduleView.tsx` (`resolveScheduleSeeding`, `seedingTimedOut`), `features/schedule/ScheduleSeedingState.tsx`, `features/project/backlog/hooks/useBacklogSeed.ts` (`resolveBacklogSeeding`) — #3312, #3422.
