# Rule 408 — A "previous value" ref that drives an announcement, a change badge, or a diff highlight must be keyed to the …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Signal encoding*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A "previous value" ref that drives an announcement, a change badge, or a diff highlight must be keyed to the ENTITY the value describes — a component that outlives the entity turns NAVIGATION into a change event.** The pattern is a `useRef` holding last render's value, compared against this one to decide whether something *changed*. It is correct only while the ref and its subject are born and die together, and shell chrome breaks that by construction: `HealthCluster` is mounted by `TopBar`, so a project→project navigation swaps the subject underneath a ref that survives it and the effect announces "Project health changed to Critical, reported by the project manager" about a project the reader has merely arrived at — a fabricated state-change claim, falsely attributed to a named person. Nothing changed; somebody navigated. **Three things conspire to hide it.** `useProjectId()` returning null on My Work masks the common path, so the bug is reachable only by the DIRECT project→project routes — the rail switcher, ⌘K, My Work's worst-project link, and, in the case that produced this rule, the popover's own cross-team sprint jump rows — which is why it survives a manual walkthrough. A `staleTime` hit serves the second project synchronously, so there is not even a loading tick to mask the false announcement. And initialising the ref to `null` genuinely does prevent the announcement on first render, so the guard that looks like it covers this is real, correct, and about something else: it fires once per MOUNT, and the mount is exactly what outlives the project. **Two obligations. (a) Store the subject WITH the value** — `useRef<{ projectId, band } | null>` and compare both. Adding the id to the dependency array does not fix it: that re-runs the effect without telling the comparison which entity the memo belongs to. **(b) A "do not reset on absent" branch is where this hides.** A memo that deliberately survives a failed fetch — so that a value which genuinely changed *during* an outage still announces, rather than every recovery from a 5xx announcing as a change — is precisely what carries the stale value across a navigation, because a failure and a navigation are indistinguishable at that check. The subject key is the only thing that separates them; without it the two requirements are in direct conflict and the correct-looking one wins. **Note the mechanism honestly (rule 300):** "is this ref scoped to its subject?" is decidable by neither grep nor AST, so this is review-only. The proportionate mechanism is a unit case that rerenders with a DIFFERENT entity id and asserts silence, written in the same MR as the announcer — and it must be run against the unguarded code once, because a test that asserts an empty live region passes just as well when the region is empty for the wrong reason. Reference: `features/shell/HealthCluster.tsx` (`lastBand`, `BandAnnouncer`, the announce effect) — #3525, surfaced by `ux-review`.
