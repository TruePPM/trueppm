# Rule 288 — Inside a `useFocusTrap` container, a `tabIndex={-1}` programmatic focus target must never be the first or …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Accessibility floors*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**Inside a `useFocusTrap` container, a `tabIndex={-1}` programmatic focus target must never be the first or last element in the trap's *tab* order — seat focus on a real focusable, or give the trap a focusable sentinel before/after it.** `useFocusTrap`'s `FOCUSABLE_SELECTOR` ends in `[tabindex]:not([tabindex="-1"])`, so a `tabIndex={-1}` heading/paragraph/status node is **invisible to the trap**: it is not in `focusables()`, so the `activeElement === first` / `=== last` wrap branches in the Tab handler never fire and the browser's native Tab/Shift+Tab runs unguarded. When such a node is focused and nothing focusable precedes it inside the container, **Shift+Tab walks straight out of the dialog** — the #1776 escape the trap exists to prevent, reintroduced through the front door. The trap's own re-seat effect does not save you: it skips whenever focus is already inside the container, and a target focused later (on a poll reaching a terminal state, on a mutation settling) never re-runs it at all. Rule 224's "focus the heading on mount" pattern is still correct — it is safe in `RouteErrorBoundary` only because that surface's heading sits *after* focusable chrome, which is an accident of that layout, not a property of the pattern. So when copying it: (a) prefer focusing the surface's **primary action** when the outcome has one and needs no reading (this is also the better UX — one keystroke to the next step); (b) when the user must read before acting, focus the `tabIndex={-1}` outcome node **only if** the container renders a focusable ahead of it in DOM order, otherwise the trap has a hole on Shift+Tab; (c) whichever you pick, the target carries a `focus:` ring (never `focus-visible:`, which browsers may withhold on a *scripted* `.focus()` — the rule-204(b)/214 caveat) and never bare `focus:outline-none`, or the sighted keyboard user is left with focus at an invisible location. Verify by tabbing **backwards** from the auto-focused element — a forward-Tab-only check passes on a broken trap. **The exclusion is narrower than it looks, and the other half of it bites harder.** `[tabindex]:not([tabindex="-1"])` is only the *last* branch of the selector; the earlier branches — `button:not([disabled])`, `input`, `select`, `textarea`, `a[href]` — match on TAG, and none of them re-checks `tabindex`. So a **native focusable carrying `tabIndex={-1}`** is the inverse case: it is not invisible to the trap, it is wrongly VISIBLE to it. A roving-tabindex group built from `<button tabIndex={-1}>` (web rule 167's model, i.e. every segmented control in this tree) puts all of its options in `focusables()` even though only one is a real tab stop, so the trap's `first`/`last` resolve to elements the user can never Tab to — and the `activeElement === first` wrap branch then never fires from the stop they actually reach. If that group sits at either end of the container, Shift+Tab (or Tab) walks straight out of the dialog. This is latent wherever real focusables happen to bracket the group and goes live on the next reorder, which is exactly what #3130 did to `NewProjectModal`. The fix is to apply `:not([tabindex="-1"])` to **every** branch, not just the generic one. **Superseded 2026-09-17 (#3208, !MR):** this paragraph used to end "`hooks/useFocusTrap.ts` and its ~11 hand-copied siblings still carry the original selector (tracked separately); until that lands, do not assume the shared hook agrees with the corrected copy." That has landed. There were **12** implementations of the selector; all of them now resolve to one exported `FOCUSABLE_SELECTOR` in `hooks/useFocusTrap.ts`, alongside a `getFocusable(container)` helper, and the eleven copies (including `NewProjectModal`'s, which was the corrected reference form) are deleted. So: **import the selector, never re-derive it** — the copies had already drifted in two opposite directions (`MonteCarloDetailPanel` dropped `:not([disabled])`, `ScheduleExportDialog` dropped `textarea` and `select`), which is what a hand-copied selector does over time. A component that owns bespoke trap behavior the hook cannot express (`NewProjectModal`'s capture-phase Escape, its `guardOpen` yield) still imports `getFocusable` rather than writing a selector. Reference: `components/import/CsvImportWizard.tsx` (result step), `hooks/useFocusTrap.ts`, `components/RouteErrorBoundary.tsx`.
