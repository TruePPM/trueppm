# Rule 406 — A lane reserved only on some pointer classes is not a lane — and an `absolute` control shifts nothing, so no …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Signal encoding*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A lane reserved only on some pointer classes is not a lane — and an `absolute` control shifts nothing, so no width, alignment or bounding-box test can see it lying on its neighbour. Hit-test.** `resolveGripReserve` returned the ⋮⋮ grip's full width on a coarse pointer and **0** on a fine one, on the reasoning that "a 14px grip overlays the row's left edge, a mouse can aim at it, and no column loses width". That was true when written: the row's left edge was empty. #3026 then moved the ⇤/⇥/◆ nudges out of the WBS cell into a lane at that same edge — correctly, and for its own good reasons — and the two correct changes composed into a `z-10 absolute left-0` grip sitting on top of a 16px ⇤ outdent, covering all but 2px of it and **taking its clicks**, since the grip's `onPointerDown` starts a drag (#3078). **(a) The invisibility is the lesson, not the overlap.** An absolutely-positioned control contributes no width, so the header and every row went on agreeing about every column position while one control lay on another; `schedule-row-chrome.spec.ts` measured the outline's left reserve to the pixel and passed. jsdom computes no layout at all, so both elements merely "existed" in every vitest render. The assertion that sees it is `document.elementFromPoint` — the question the *user* is asking — and the repo already had that precedent one control over, where the insert `+`'s coarse tap box was verified by hit-testing rather than by arithmetic (`resolveInsertLaneGap`, #3029). Reach for it whenever a control is positioned rather than laid out. **Sample across the control's width, never at its corners**: the failure is horizontal, a lone centre probe lands in whatever seam is left (here the surviving 2px), and `rounded-control` clips hit-testing to the border radius, so a corner inset tests the radius and reds on correct code. The same trap runs the other way for the control you expect to still be there: **`toBeVisible()` ignores `opacity`**, so asserting it on a hover-revealed affordance passes whether that affordance is painted, `opacity-0`, or deliberately deleted — read the computed opacity, or hit-test its own centre. **(b) "Small enough to be harmless" is not a size, it is a bet on what the neighbours will be.** Rule 328's corollary says to *pay the honest width for a pair of 44px targets rather than letting one cover the other* — scoped, in its own words, to the coarse-pointer half. This **extends** that to every pointer class, because two controls overlap at 14px exactly as they do at 44px and nothing in the 44 was doing the work. A reserve derives from the control's own width at every class (`resolveGripReserve` ≡ `resolveGripWidth`) — pin the identity, not the literals, or a grip that grows past a lane that does not re-creates this silently. **(c) Neither commit was wrong, so review the SEAM, not the diff.** Nothing in #3026 touched the grip and nothing in the grip's own history anticipated a neighbour; the defect was authored by the *pair*, months apart, and no gate in the pipeline reads two merged branches against each other. When a change moves a control to a coordinate some other control names literally (`left-0`, `inset-y-0`, a `z-` index, a negative margin), grep that coordinate across the surface before merging — the collision is with code the diff does not contain. **The seam also runs into constants nobody in either diff had a reason to open**: `MIN_OUTLINE_WIDTH` floors the outline's *rendered box*, the lanes live inside that box, so #3026 and #3078 between them spent 27.5% of a floor whose own docstring promises "WBS + a readable name" and left 6px over `MIN_TASK_WIDTH`. A floor that can be eaten by a sibling change must **state its dependency** (`outlinePaneWidthFor`'s `leftReserve`), not wait to be noticed. **(d) Selection is the state to test in, and the reason is persistence — not visibility.** The grip is `opacity-0` until `group-hover` **or** `group-focus-within`; the nudges are never hidden at all, only dimmed (`opacity-[0.32]`, brightening on the same two). Since `opacity-0` does not disable hit-testing, the grip took the ⇤'s clicks **at rest as well** — the user saw a 32% ⇤, clicked it, got a drag, and had nothing on screen to explain why. So hover is a real repro state; selection is the better one because clicking a row to work on it **pins** the collision for as long as that row stays selected, which is what turns a blemish into a control that cannot be used. Reference: `features/schedule/scheduleConstants.ts` (`resolveGripReserve`, `resolveGripWidth`), `features/schedule/paneFloors.ts` (`outlinePaneWidthFor`), `features/schedule/TaskListRow.tsx` (`RowReorderHandle`, `RowStructureNudges`), `e2e/schedule-row-chrome.spec.ts` — #3078, extending rule 328 and the left-edge stacking contract of rule 309, from `design_handoff_trueppm_v4/README.md` "Reading structure".
