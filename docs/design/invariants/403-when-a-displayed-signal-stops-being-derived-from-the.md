# Rule 403 — When a displayed signal stops being derived from the evidence its own drill-through lists, the drill-through …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Signal encoding*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**When a displayed signal stops being derived from the evidence its own drill-through lists, the drill-through must say where the value now comes from — a header that disagrees with every row beneath it is worse than the derivation it replaced.** A badge, chip or pill whose word was computed from the rows it expands into carries a guarantee nobody writes down: opening it always explains it. The moment the word moves to a server verdict that folds in something those rows cannot show — a manual report, an override, a policy decision, an SLA class — the guarantee is gone and nothing in the markup announces that it went. The shipped shape of the failure is a red **Critical** popover header sitting above `At risk — 0 tasks` and `Critical path — 0 tasks`, which reads to a team member as a broken tool rather than as "your PM reported this" (#3501). Three obligations. **(a) Detect the divergence, never re-derive the value** — branch the *disclosure* on where the value came from; the printed value stays the server's, always. This clause used to say to *compare* the server verdict against what the listed evidence alone would produce. **Superseded 2026-09-07 (#3525): the comparison is not a weaker form of (c), it is wrong, and (c) is now mandatory rather than preferred.** A comparison answers "does the verdict differ from the evidence?", which is not the question — the question is "did the evidence produce it?", and the two come apart in both directions. A PM reporting At risk on a plan whose counts also say at-risk produces exactly the band the counts would, so the comparison concludes "derived" and never names the report, silently, on precisely the projects where nothing looks wrong. And a reported `on_track` over a critical plan is a disagreement the comparison attributes to stale counts rather than to the person who created it. There is no client-side comparison that gets this right, because provenance is not a function of the outputs. **(b) Name the source and route to it** — a signal is visible on routes where the surface owning the override is not (the shell chip is on Schedule and Board; the report lives on Overview), so a status a reader cannot resolve from where it is shown is a dead-end indicator. **(c) Take a server-declared source; there is no supported inferred one** — a `*_source: 'reported' | 'derived'` field beside the verdict removes the client's need to shadow the server's rule at all (API-first, ADR-0599; the argument rule 301(a) already makes for severity). Return it from the **same call** that decides the verdict, never from a helper beside it: a second function re-taking the same branch is the drift ADR-0133 exists to make structurally impossible. Publish it on **every** endpoint that publishes the verdict — `status-summary` and `health-summary` both carry `health_band` from one `compute_health_band`, and shipping provenance on one alone would reintroduce one level up exactly the disagreement #3501 fixed. Corollary: audit the surface's **other** methodologies before calling it done — `healthClusterModel`'s segment set is methodology-adaptive, so an AGILE cluster renders no at-risk/critical rows at all and a Critical chip there has no drill-through of any kind. **That corollary also dictates where the row goes, and getting it wrong fails silently:** render the provenance row in the popover's own header region, above the segment map and unconditional on methodology — a new `HealthSegment` kind would have to be opted into by each methodology's array, so it would be absent on exactly the methodology that has no other drill-through, and every test written on the default methodology would pass. **And audit the other SURFACES that print the same verdict, not only the other methodologies.** Publishing the source field on the endpoints is the server half; a field with no reader closes nothing. `MyProjectsHealthSummary`'s `worstReason()` built its drill-through line from the counts alone and so rendered "0 critical tasks" under a red dot for a PM-reported Critical — this rule's exact shipped shape, on the second of the two surfaces that print a band beside its own counts, found by `ux-review` and `regression-check` independently. Both were fixed in #3525; the denominator is the thing to state, because "the chip is fixed" reads as "the class is closed". **`HealthCluster` now satisfies (a), (b) and (c)** (closed by #3525): it reads `health_band_source` off `status-summary`, renders a provenance row naming the report and routing to Overview, and compares nothing. The route is a plain navigation, not the report's editor — mounting `UpdateStatusDialog` from the shell would drag a role-ordinal edit gate into the TopBar. **Two copy traps came out of that, and both are the kind a reviewer catches only by opening the destination.** The verb is "View", not "Update": editing the report is Admin+, so a Member offered "Update" follows it to a dialog reading "View only" — and the `aria-label` said "see or change" while the visible line said "Update", which inverts rule 287's usual failure by giving the *sighted* reader the less honest copy. And the destination is named **"Dashboard"**, not "Overview": the route segment is `/overview` (rule 108) but the project rail labels that view Dashboard (ADR-0942 §7), and "Overview" is the **program** rail's first view — so a row saying "Overview" sends the reader hunting for a nav item that does not exist, which is the dead end (b) exists to close. **A destination's route segment is not its name; read the rail, not the URL.** Reference: `features/shell/HealthCluster.tsx` (`ProvenanceRow`, the popover header block), `features/shell/healthClusterModel.ts`, `hooks/useShellStats.ts`, `features/me/MyProjectsHealthSummary.tsx` (`worstReason`), `hooks/useProjectsHealthSummary.ts`, `e2e/shell-health-band.spec.ts` — #3501 and #3525, both surfaced by `ux-review`.
