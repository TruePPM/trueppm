# Rule 364 — `?? []` says "the query has not answered" and "the answer is empty" with the same word — so nothing that …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Surface states*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**`?? []` says "the query has not answered" and "the answer is empty" with the same word — so nothing that REMOVES may read it.** A `X ?? []` / `?? {}` / `?? new Set()` fallback is correct and near-universal for *rendering*: an empty list draws as an empty list either way, and rule 248's skeleton is what carries the difference visually. It becomes a defect the moment a **destructive** consumer reads it — a cleanup effect that prunes ids, a reconcile that drops rows, a cache eviction, a snapshot that overwrites — because effects run on the **first commit**, before the query settles and before any `isLoading` early-return further down the component body can stop them. The empty value is then acted on as though it were an answer. **The guard is one line and it goes on the RAW handle**, never the coalesced one: `if (!rawTasks) return;` before the effect acts, so an empty array is trusted only when it is genuinely an answer. Three things this rule turns on, each learned from a real instance:
- **Permanence is what makes it expensive, and it comes from the write-back.** In #3213 the phase-in-waiting cleanup pruned every remembered id on a cold load and the persist effect immediately above it saved the emptied set to `sessionStorage`, so the re-run once tasks arrived found `size === 0`, returned early, and nothing restored it — session memory that exists precisely to survive a reload did not survive one. The sweep (#3214) found the same shape with two louder backing stores: `useBoardOffline`'s snapshot is a whole-record `db.put`, so an unanswered `['dependencies']` query overwrote the last good **IndexedDB** snapshot with `[]` and the next offline board opened with every dependency edge silently gone; and `hidden_views` is PATCHed as a **full replacement set**, so a toggle clicked before `/auth/me/` answered un-hid every other view the user had hidden — server-side, on every device, confirmed rather than repaired by the invalidation that followed.
- **Guard the *delay*, not the behavior — and pin both halves.** An empty array from a query that HAS answered is a real answer and must still prune, still persist, still commit. A test that only asserts "nothing was deleted" passes with the feature deleted outright, and a guard keyed on `.length` instead of on `undefined` silently stops handling genuinely-empty projects. Where a write is fed by several independent queries, the guard also has to be paired with a **wider trigger**: `useBoardOffline` was subscribed to the tasks key alone, so guarding without also subscribing to `['dependencies']` and `['boardConfig']` would have converted the race into "no snapshot is ever written" — a delay that never ends is a disable.
- **When the guard blocks a control, disable the control — this is the one case where `disabled` is right.** A switch that paints "on" from an unanswered query and silently swallows the click is a worse affordance than one that is visibly not ready (rule 359's honesty requirement, applied to load state). **Do not read this as license to disable a *permission*-gated control**: those are hidden from the DOM entirely, because a permanently dead focusable button that announces "[label], dimmed" is a lie about what the user can do. The distinction is duration and cause — a load-state block is transient, self-clearing, and identical for every user, so `disabled` states a temporary fact; a permission block is permanent for that user, so hiding states the real one. A full skeleton (rule 248) is the alternative and is correct when the whole surface is unreadable; prefer `disabled` when the surface is legible and only its *writes* must wait. Note the consequence for tests: `disabled` shadows the handler guard in jsdom, so a click assertion goes red only when both are removed — say so in the test rather than letting it read as evidence about the guard alone.

**This is deliberately not a lint rule, and the audit method is the reusable part.** `?? []` is right almost everywhere — 383 instances in `packages/web/src` at the time of writing — and what makes one dangerous is a property of the *consumer*, not of the expression, which no syntactic rule can see. So enumerate **destructive consumers**, not fallbacks: effects, store actions and cache updaters that delete, prune, evict, or overwrite a persisted record. There were 13 tree-wide against those 383, which is a denominator you can actually read, and the check is then blind to spelling — `?? []`, `|| []`, `?? new Map()`, `?? null` and `const { data: x = [] }` all collapse to the same question. Two traps in the method itself: scan for the *storage* verb as well as the collection verb (`db.put` overwriting a whole record is destructive and matches no `delete`/`filter` grep — that is how the IndexedDB instance survived the first pass), and remember that the cache layer is already solved — `lib/optimisticCache.ts` uses `(current) => (current ? updater(current) : current)`, which is the correct form and needs no per-hook reasoning. The reason this is written down rather than left to be rediscovered: the correct guard already existed *forty lines above* the effect that lacked it (`pendingTaskIds`, `if (!rawTasks || …) return;`), and it still took a load-dependent CI failure to find the sibling.
