# Rule 289 — A server-derived advisory signal may be cleared by client state only for the specific item the user acted on …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Accessibility floors*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A server-derived advisory signal may be cleared by client state only for the specific item the user acted on — never re-derived, and never allowed to drain a count the server owns.** An "N items need your attention" banner computed from a server field (import mapping confidence, validation severity, sync conflict class) drains as the user works only if each clear is a *fact about that item* the client can know. Two failure modes, both of which ship looking correct: (a) **cross-item staleness** — resolving item A changes the server's verdict on item B (a duplicate claim released, a constraint satisfied), but the client only rewrote A, so B keeps a now-false advisory until the next round-trip; (b) **round-trip laundering** — the client echoes its *whole* current state back as an override on re-validate, so the server marks every item "user-chosen" and returns zero flags, silently converting items the user never reviewed into items they appear to have approved. Send only the fields the user actually changed, keep the server's original verdict alongside any local override so an untouched guess still reads as a guess, and treat a count the server computed as stale-until-refetched rather than recomputing it locally. The tell: an advisory whose whole purpose is "look at these two of eleven" that reports zero after the one action the UI invites. Reference: `components/import/CsvImportWizard.tsx` (`handleFieldChange` / "Re-check mapping"), `hooks/useCsvImport.ts` (`toColumnMap`, `flaggedColumns`).
