# Rule 341 — Whether a value is COMPUTED or COMMITTED is a property of the value, not of the record's workflow state — …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Signal encoding*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**Whether a value is COMPUTED or COMMITTED is a property of the value, not of the record's workflow state — gate the cue on the value alone, and derive it from the same predicate the surfaces that act on it use.** A CPM `early_start` shown where a committed `planned_start` would go is unattributed regardless of whether the task is NOT_STARTED, IN_PROGRESS or COMPLETE: it came from the scheduler and it will move when a predecessor does. #3063 hung the drawer's computed cue off `isMissingCommittedStart()`, a *defect* predicate that additionally requires IN_PROGRESS/REVIEW/COMPLETE — so the one status that reliably has no bar on the timeline (NOT_STARTED, the state that fills the Unscheduled gutter) was the one status that rendered its scheduler date as a plain, committed-looking value with nothing anywhere explaining the blank row. Three obligations. **(a) Split the provenance predicate from the defect predicate and name both.** `isStartComputed()` answers "did a human commit this?" and drives the cue; `isMissingCommittedStart()` answers "is this task in a state it should not be in?" and drives the amber flag and its demotion. Fusing them makes the narrower one silently govern the wider one's surface, and the direction of that error is always the same — the cue goes missing exactly where the value is least trustworthy. Assert the containment (`flagged ⇒ computed`) in a test, because the reverse is what regressed. **(b) A renderer that DROPS a row and a cue that EXPLAINS the drop must read one predicate.** `GanttRenderer.drawTaskBar` and `useUnscheduledTasks` both gate on bare `!plannedStart`; the drawer did not, and a user looking at Start, Finish, Duration and a red critical-path banner had no way to learn why the row was empty. When one surface hides something, the surface a user opens next is where the reason has to be, and shared code is the only thing that keeps the two from drifting apart again. **(c) An ordinary state must not borrow the defect state's treatment.** Uncommitted-and-not-started is normal unplanned work; uncommitted-and-underway is a data-integrity problem. The second earns amber, a warning icon, and a "Move to To Do" demotion — giving the first the same treatment scolds the user for the default and teaches them to discount the color that means something on the other branch (rules 8b/12). Same fact, same explanation, calmer surface, and only the action that is not a no-op. Reference: `features/schedule/missingCommittedStart.ts` (`isStartComputed` vs `isMissingCommittedStart`), `features/schedule/TaskScheduleStrip.tsx` (`UncommittedStartNote` vs `NoCommittedStartAdvisory`) — #3063.
