# Rule 351 — A floating `role="menu"` / `role="listbox"` panel must carry BOTH a height guard and `overflow-y-auto` — a …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Controls and composition*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A floating `role="menu"` / `role="listbox"` panel must carry BOTH a height guard and `overflow-y-auto` — a panel that can grow taller than the viewport and has neither spills off the bottom of the screen with nothing to bring the rest into view.** The Schedule "Display" dropdown (`ScheduleDisplayMenu.tsx`) was a plain `absolute` `<div>` with no `max-height` and no `overflow-y-auto`; with its Outline + View filters + Render filters + optional Columns + optional Chart sections, content routinely reached 600–700px, taller than a laptop viewport at 100% zoom — and the audit that followed found the identical gap in roughly a dozen more panels, because no shared primitive owned vertical viewport-collision handling: `useAnchoredPopover` (rule 260) computed horizontal clamp and flip-above but never exposed a height (#3109). Two obligations, matched to how the panel is built: **(a) hook consumers** (rule 260) get it for free — `useAnchoredPopover` now derives `maxHeight` into `popoverStyle` (the real gap to whichever viewport edge the panel opened toward, not a guessed pixel value), so the call site only has to add its own `overflow-y-auto` on the actual scrolling element (which may be a descendant of the element carrying `style={popoverStyle}`, not that element itself — a search box or a keyboard handler routinely sits between them). **(b) bespoke panels** (a hand-rolled `absolute`/`position:fixed` implementation, not yet on the hook) add an explicit viewport-relative guard directly — `max-h-[min(70vh,<cap>)] overflow-y-auto` is the tree's standard spelling (`ScheduleDisplayMenu.tsx`, `ToolbarOverflowMenu.tsx`, `BoardViewDropdown.tsx`, `UserMenu.tsx`, `CardOverflowMenu.tsx`); `components/FieldHelp.tsx`'s `max-h-[min(60vh,320px)]` is the original reference for the pattern. **Never `overflow-hidden`** on a panel with unbounded content — it clips silently instead of scrolling, which is worse than doing nothing (`LoadSampleButton.tsx` was fixed for exactly this). A panel is exempt only when it is provably safe by construction — content is small and fixed (2–3 static items), hard-capped (`slice(0, MAX)`), or in-flow inside an ancestor that already scrolls (rule 260's clipping-ancestor case run in reverse, e.g. `ViewsMenu.tsx` inside the nav rail) — and that judgement is not mechanizable, so it is recorded as a reviewed, commented exclusion, never inferred per-component at review time. **That exclusion is a comment on the offending line itself** — `role="menu" // dropdown-scroll-ok: <reason>`, or `/* dropdown-scroll-ok: <reason> */` inline; both forms are legal in JSX attribute position, and the reason may not be empty. It has to be same-line, and that is the entire mechanism: the exemptions used to be `path:LINE` pairs inside the gate script, which any insert above the line invalidated — so the gate reddened against code the author had not touched, named a line they had not written, and prescribed a fix that would have been wrong to apply. It fired three times in nine days on `ScheduleView.tsx` alone, twice also producing a merge conflict where *neither* branch's renumbered value was correct on the merged tree (#3114, #3113, #3117). A same-line marker moves with the line, and — the property a coordinate could never have — the line cannot be edited without the reason landing in the same diff hunk as the edit. **A content hash was rejected on the tree's own data**: 15 of the 21 reviewed sites are the byte-identical text `role="menu"` or `role="listbox"` and two files hold identical pairs, so one hash entry would have covered both members of a pair and silently covered a third, unreviewed panel added later. A marker whose line no longer declares a role is itself an error — the panel was refactored away and the exemption outlived it. Enforced by `scripts/check-dropdown-scroll.sh` (`make dropdown-scroll-check`, CI `lint:dropdown-scroll`): every `role="menu"`/`role="listbox"` in `packages/web/src` must show both markers within a window of its declaration, OR (for a hook consumer) `overflow-y-auto` locally plus `useAnchoredPopover` + `style={popoverStyle}` anywhere in the file, OR carry a same-line `dropdown-scroll-ok:` marker — a ratchet, not zero-tolerance, per rule 300(c): the exception list is separated from the violation mechanically so it cannot become the hole. A `[role="menu"]` written as a CSS attribute selector inside a `document.querySelector` string is skipped structurally — it is not a rendered panel and there is nothing there to scroll. Reference: `hooks/useAnchoredPopover.ts`, `hooks/useAnchoredPopover.test.tsx` (`maxHeight` cases), `e2e/schedule-display-menu.spec.ts` ("short viewport scroll").
