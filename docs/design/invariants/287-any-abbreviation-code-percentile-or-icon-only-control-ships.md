# Rule 287 — Any abbreviation, code, percentile, or icon-only control ships with a plain-English explanation reachable by …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Controls and composition*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**Any abbreviation, code, percentile, or icon-only control ships with a plain-English explanation reachable by hover AND keyboard focus AND touch — via the shared `Tooltip` (`components/Tooltip.tsx`), never a bare `title` and never a `group-hover` class (#2389).** The bug class this closes is an *inversion*, not an omission: the codebase repeatedly added an `aria-label` to satisfy WCAG 1.4.1 and stopped, so a screen-reader user heard "Waterfall workspace" and a sighted mouse user got two undecodable letters (`MethodologyIndicator`'s `WF` chip was the trigger case; `SyncStatusBadge`, the `CP` float suffix, and the Monte Carlo row were the same shape). Whenever you write an `aria-label` for a token whose visible form is shorthand, ask what the *sighted* user sees — if the answer is "the shorthand", the job is half done. Seven invariants: (a) **three input paths** — `mouseenter`, focus, and tap; `group-hover` never fires on a touch device and `title` is invisible to keyboard focus, unreachable on touch, ~1s delayed, and unstyleable (rules 22a/121/166/222), so neither satisfies this rule alone. (b) **text only** — `content` is typed `string`; the moment it needs a link or a control it is a `FieldHelp`-style non-modal `role="dialog"` instead (rule 263), because an `aria-describedby` target's link is unreachable (rule 121). (c) **`describe={false}` when the content restates the trigger's own `aria-label`** — the panel then renders `aria-hidden` so AT hears the sentence once; wiring `aria-describedby` to a duplicate of the accessible name is a double announcement, not extra help. Corollary for tests: an `aria-hidden` panel is out of the accessibility tree, so assert it with `page.locator('[role="tooltip"]')`, not `getByRole('tooltip')`. (d) **never the sole carrier of meaning** — it supplements the accessible name, it does not replace it. (e) **positioning is delegated to `useAnchoredPopover`** (rule 260) and the panel is portaled (rule 253) — no hand-rolled flip/clamp math. (f) **Escape peels one layer** — capture-phase `document` listener + `stopPropagation()`, so a tooltip open inside a modal dismisses without closing the modal (the rule-263f pattern). (g) **keyboard-vs-pointer focus is decided by pointer recency, NOT `:focus-visible`** — jsdom answers `false` to `element.matches(':focus-visible')` under every condition, so a `:focus-visible` guard silently kills the keyboard path while the unit suite stays green; `Tooltip` records the last `pointerdown` and treats a focus within 300ms of one as pointer-driven. Do not "simplify" it back to the pseudo-class. Shared strings live in `lib/abbreviations.ts` and `lib/percentileExplanation.ts` so the same token never acquires two different definitions on two surfaces. Exemption worth knowing: a decorative `aria-hidden` header row (`OutlineMode`'s column strip) must NOT get a tooltip — the trigger is a tab stop, and a tab stop inside an `aria-hidden` subtree is its own violation. Reference: `components/Tooltip.tsx`, `features/shell/MethodologyIndicator.tsx`, `features/schedule/MonteCarloTimeline.tsx`.
- **(d, sharpened) A `Tooltip` child that is not natively focusable must carry its OWN `aria-label` — an `sr-only` sibling is not an accessible name.** `Tooltip` gives any non-native child a tab stop (`needsTabStop`), and a bare `<span tabIndex={0}>` computes to role `generic`, which **does not support name-from-content**. So descendant text — including a visually-hidden line that reads perfectly in browse mode — leaves that tab stop announcing as **blank** when a screen-reader user Tabs onto it. The fix is `role="img"` + `aria-label` on the trigger (which also makes the glyph presentational, so drop the `sr-only` node rather than keeping both and double-reading it per rule 171). The house pattern was already right everywhere else — `MethodologyIndicator.tsx:68`, `CardHealthPeek.tsx:100,121`, `ScheduleSummaryChip.tsx:129` all name the span explicitly; #3148's lane-header em-dash was the one that did not. **Do not read a green `a11y.spec.ts` as coverage here:** the only axe rule that fires on an unnamed focusable is `focus-order-semantics`, which is tagged `best-practice`, and `e2e/fixtures/a11y.ts` runs `wcag2a/2aa/21a/21aa` only — so the gate is *structurally* incapable of reporting this, in any file, in any tree (rule 300(a)). **No mechanism exists yet.** The proportionate one is an AST selector over every `JSXElement[name='Tooltip']` whose single child is outside `NATIVELY_FOCUSABLE` and declares neither `aria-label` nor `aria-labelledby`; it is *not* built, and until it is this clause is a convention, not a gate — tracked as follow-up, and per rule 300(a) whoever builds it must run it against `origin/main` and watch it report before trusting a zero. Reference: `features/board/LaneMeta.tsx` (the uncommitted progress slot) — #3148.
