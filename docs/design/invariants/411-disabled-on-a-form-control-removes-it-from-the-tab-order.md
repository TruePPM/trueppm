# Rule 411 — `disabled` on a form control removes it from the tab order and takes its `aria-describedby` explanation with …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**`disabled` on a form control removes it from the tab order and takes its `aria-describedby` explanation with it — so the state that most needs explaining becomes the one a keyboard or screen-reader user cannot reach. Use `readOnly` + an `onChange` guard for "inert right now", and reserve `disabled` for controls with no explanation to offer.** This is the input-shaped twin of rule 302, and it bites in the opposite direction. Rule 302 settles *presence*: no rights ⇒ the apparatus is **absent**, a rights-holder in the wrong state ⇒ **present and inert, with refusals that explain themselves**. But "present and inert" is where the trap is, because the obvious spelling of inert is `disabled`, and a disabled input is not focusable — so the very `aria-describedby` you attached to explain the refusal is unreachable, and the control announces "[label], dimmed" with no reason. `ActualDatesSection`'s finish field is the case: off a sign-off status it is inert, and the whole point is the sentence *"Set when the task moves to In review or Complete."* — which a `disabled` input would have hidden from exactly the users who cannot see the dimming. Four obligations. **(a)** When the inert state carries an explanation, spell it `readOnly` and style it with `read-only:opacity-50 read-only:cursor-not-allowed`, not `disabled:*`. **(b)** `readOnly` is an affordance, not enforcement — a `readOnly` `<input type="date">` still opens its picker in some browsers, and `readOnly` does nothing at all on a checkbox, radio or `<select>`. Guard the handler (`if (!allowed) return;`) and keep the server as the thing that actually refuses; never treat the attribute as the gate. **(c)** The read-only *rendering* under rule 302 (no rights) is not an input at all — render the value as text (`<dl>`/`<dt>`/`<dd>`), because a Viewer still needs to **read** the value and a disabled input withholds it from the tab order. An em-dash for an unrecorded value, never a blank. **(d)** Assert the attribute and the wiring, not the appearance: `expect(input).toHaveAttribute('readonly')`, `expect(input).not.toBeDisabled()`, and `expect(input.getAttribute('aria-describedby')).toBe(help.id)` — a spec that only checks the dimming passes on the broken build. In Playwright the attribute assertion is `toHaveAttribute('readonly', '')`.
