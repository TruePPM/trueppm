# Rule 312 — When a new dimension subdivides an existing key, the derived key must be BYTE-IDENTICAL to the old one …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Foundations*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**When a new dimension subdivides an existing key, the derived key must be BYTE-IDENTICAL to the old one wherever the dimension is unused — and a test must pin that identity.** A surface eventually grows a second axis over something it already keys on: a board status column splits into named lanes, a resource row splits by allocation, a timeline band splits by scenario. The tempting shape is a new composite key everywhere (`${status}#${lane}`), and it is silently destructive, because the *old* key is load-bearing in places that carry no types and produce no error when it changes: `localStorage` (persisted column widths, collapsed sets), `dnd-kit` droppable ids, `data-testid` and every E2E selector built on it, keyboard-traversal state, saved-view payloads. Every one of those degrades to "the user's saved state is gone" rather than to a failure anyone sees. So make the composite key **collapse to the original** when the subdivision is empty — ``key = laneKey ? `${status}#${laneKey}` : status`` — and give the expansion function a unit test asserting `tracks.map(t => t.key)` equals the original key list on an unsubdivided input. That one assertion is the whole safety property: with it, a feature nobody has turned on is provably a no-op end to end, and the migration for existing data is *nothing*. Corollaries: (a) **subdivide the render, not the semantics** — the axis being split (`Task.status`) must keep its original values so every downstream reader is untouched; the new dimension rides alongside it; (b) **status-level controls stay status-level** — collapse, the card's "Move to…" menu, the mobile status board and any milestone rail must reduce the track list back to one entry per original key, or one milestone renders N times and a menu offers the same destination three times; (c) **resolve a dangling sub-key on read, in exactly one place, and make the server resolve it the same way** — deleting a lane must not require rewriting rows (a bulk `UPDATE` skips the `server_version` bump every synced write depends on), so both sides fall back to the first sub-key and the header count can never disagree with the cards beneath it. Reference: `features/board/statusLanes.ts` + `statusLanes.test.ts` ("leaves an unladen board byte-identical to its column list"), `apps/projects/services.py::_annotate_lane_breach` — #2967.
