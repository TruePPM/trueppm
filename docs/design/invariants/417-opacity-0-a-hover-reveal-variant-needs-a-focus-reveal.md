# Rule 417 — `opacity-0` + a hover-reveal variant needs a focus-reveal counterpart

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Accessibility floors*. The index carries the rule's headline; this file carries its full text (#3619). Binding everywhere, not only on the surface that produced it.

**`opacity-0` + a hover-reveal variant (`hover:opacity-100`, `group-hover:opacity-100`, or a named-group form like `group-hover/row:opacity-100`) needs a focus-reveal counterpart in the same class string** — `focus:opacity-100`, `focus-within:opacity-100`, `focus-visible:opacity-100`, or the matching `group-focus-within:`/`group-focus-visible:` (and named-group) form. Without one, a control that only appears while the pointer is over its row or card — a delete icon, a "···" overflow trigger, a drag handle — is fully reachable by Tab (it is not `disabled`, not `aria-hidden`, `tabIndex` untouched) and never becomes visible while focused, because nothing outside `:hover` ever raises its opacity above 0. That is a WCAG 2.1.1 (Keyboard) / 2.4.7 (Focus Visible) failure hiding behind a class string that reads correctly at a glance — `opacity-0 group-hover:opacity-100` looks identical whether or not a focus variant sits a few tokens away, and in the two components that motivated this rule the focus variant was two lines below in a wrapped `className` string, easy to miss reading top-to-bottom.

**This is not a new pattern to learn — it is the established one.** Every other hover-reveal control in this tree already pairs the two (`TaskListRow.tsx`, `PinToggle.tsx`, `OutlineRow.tsx`, `BacklogListRow.tsx`, `RiskRegisterView.tsx`, `SprintBacklogTable.tsx`, `BoardViewDropdown.tsx`, `CardOverflowMenu.tsx`). The rule exists because the pairing has been dropped three times on three different components (#1029 in 0.3, #1802 in 0.4, #3619) — each incident fixed by a hand sweep of the component it was filed against, with nothing sweeping the *pattern* itself, so the next hover-reveal control written from a stale copy-paste template reintroduced the gap. `scripts/check-hover-reveal-focus.sh` (wired into `make pre-push` and CI job `lint:hover-reveal-focus`) is the sweep that does not need to be re-run by hand: it scans every `.tsx` file under `packages/web/src` for `opacity-0` paired with a hover-reveal variant on the same line, and requires a focus-reveal variant within the following ~20 lines (Tailwind class strings on this codebase routinely wrap across several JSX lines).

**Scope note: `opacity-0` only, not `opacity-40`/`opacity-50`/etc.** A partially-dimmed-at-rest control (e.g. `opacity-40 group-hover:opacity-100`) is already visible to a keyboard user — dimmer, not gone — so it is not the keyboard-reachability failure this rule targets, and the gate does not flag it. It also does not match `opacity-0.NN` (an arbitrary-value decimal opacity, a different Tailwind token entirely — see the `opacity-0.22` comment in `ScheduleView.tsx`).

**Escape hatch, same shape as rule 351's `dropdown-scroll-ok:`.** A hover-reveal control with genuinely no focusable content inside it (pure decorative chrome — nothing to Tab onto, so nothing is ever unreachable) carries a same-line marker instead of an unreachable focus style:

    className="opacity-0 group-hover:opacity-100 ..." // hover-reveal-ok: decorative gradient, nothing focusable inside

The marker must sit on the same line as the `opacity-0`/hover-reveal pair and state a non-empty reason — colocated so no unrelated edit can invalidate it, and so the reason appears in the same diff hunk as any future edit to the line. A marker whose line no longer declares an `opacity-0`/hover-reveal pair is stale and is itself a gate failure.

Reference: `features/board/BoardViewDropdown.tsx`, `features/board/card/CardOverflowMenu.tsx`, `scripts/check-hover-reveal-focus.sh` — #3619.
