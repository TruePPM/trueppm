# Rule 301 — A client-side severity map over a server-owned token vocabulary must fail LOUD, and its unknown branch must …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Foundations*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A client-side severity map over a server-owned token vocabulary must fail LOUD, and its unknown branch must never be the neutral one.** When the server owns a vocabulary that grows with a feature's taxonomy (a delivery outcome, a job reason code, a sync verdict) and the client maps each token to a *tone* — good / bad / neutral — that map is a hand-maintained mirror of a list which changes without it. The drift is inevitable and acceptable; failing in the *reassuring* direction is not. A `tone = KNOWN[token]?.tone ?? 'idle'` fallback renders the next server-side **failure** token in the same grey as "nothing to report", with no remediation hint, on the surface whose entire purpose is telling an operator something is wrong — and a unit test asserting "an unknown token still renders" makes the gap look covered while locking it in. Three obligations. **(a)** Prefer making severity a **server fact** — return `ok: boolean` or a severity enum beside the token so tone is rendered from the API rather than from a copy of it (API-first, ADR-0599: the authoritative classification of a server-computed outcome is itself server-computed). **(b)** Where the map must stay client-side, the unknown branch takes the **cautious** tone, never the neutral one: an unrecognized outcome on a diagnostic surface is a problem until proven otherwise. **(c)** Never render a raw snake_case token as user-facing copy — humanize it (`replace(/_/g, ' ')`) so the fallback degrades rather than leaking an identifier. Corollary for the server side of the same feature: publish the vocabulary as an OpenAPI `enum` (a `ChoiceField`, not a bare `CharField`) so the mirror can at least be checked against something. **(d) The same applies when the value is ABSENT rather than unrecognized.** A query still in flight, a failed fetch, and a field an older server does not send all arrive as `undefined`, and `?? <best value>` renders all three as good news. Read the hook's `isLoading` / `error` and render *no* value rather than the reassuring one — `useShellStats` returned both and `HealthCluster` read neither, so a 5xx on `status-summary` showed a calm "On track" over a project whose PM reported it Critical. **Closed 2026-09-07 (#3525), and the shape of the fix is the reusable part.** Three states, not two: *in flight* takes a skeleton, *failed* takes a muted no-value read that is still a trigger, and they are separate because a `staleTime` with no retry override lets the failure persist while a skeleton that never resolves is rule 246's perpetual-pulse defect. Two traps found closing it, neither obvious from this clause alone. **The absent case is not only the failed fetch** — a 200 whose body did not carry the field (an older server, a proxy, a test mock serving the wrong shape) reaches the same `undefined` by another door and must take the same branch, or the guard covers the loud failure and misses the quiet one. **And the cautious fallback of (b) does not apply here**: (b) governs an *unrecognized* value, where a cautious tone is a defensible reading of something real; an *absent* value has nothing to be cautious about, so `at_risk` would be as invented as `on_track` and, for a band, is the client-side derivation rule 397(b) deleted, wearing a new name. Render no value.
