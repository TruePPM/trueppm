# Rule 337 — Every rung of one ordered notice ladder shares one live-region contract — decide it at the ladder, from the …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Surface states*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**Every rung of one ordered notice ladder shares one live-region contract — decide it at the ladder, from the most announcement-worthy branch, never per rung.** When a component returns one of N notices from a single ordered `if` chain and the rungs look the same to a sighted user, they must all be live regions or none of them may be. A rung that quietly drops `role="status"`/`aria-live` hands the AT user a different product depending on which branch the server happened to hit, and nothing surfaces it: the markup is valid, `role="note"` is a real role, and an axe scan sees a well-formed note. The same reasoning covers the *action*: if one rung names a remedy, every rung must either offer that remedy or name a different one honestly — a notice that says "reconnect to replace it" on a card whose only controls are Sync now and Disconnect is worse than a notice that says nothing, because the user goes looking for a button that is not there. A notice that is genuinely a different *kind* of thing belongs outside the ladder, not inside it as an odd rung: `ConnectedAccountsPage`'s truncation note is neutral-toned and non-live because a truncated pull **succeeded**, so it renders as its own sibling rather than as a fourth branch of the health ladder. Reference: `features/me/ConnectedAccountsPage.tsx` (`ConnectionHealthNotice` — three rungs, all `ReconnectBanner`, `actionLabel={null}` on the rung whose remedy is not the wizard; `TruncationNotice` deliberately outside it), `features/integrations/syncOutcome.ts` (`syncFailureNeedsReconnect`) — #2925.
