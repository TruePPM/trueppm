# Rule 431 — A stored preference is only a preference when the login is one person's; on a shared credential it is the last visitor's choice applied to a stranger

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Surface states*. The index carries the rule's headline; this file carries its full text. Binding everywhere, not only on the surface that produced it.

**Every `localStorage` preference keyed `…<userId>.<projectId>` carries an unstated premise: that the user id identifies a person.** On a deployment that publishes one shared credential — ADR-1197's interactive demo, a kiosk, a conference laptop, a shared support account — it does not. The key resolves, the read succeeds, and the value that comes back belongs to somebody else. Nothing errors. The surface simply opens in a state this visitor never chose, and the more considerate the preference system is, the more confidently it gets it wrong.

**So: on a shared-credential deployment, do not read the stored preference and do not write it.** Initialize to the value that is right for a first-time arrival, let the visitor change it for the page session, and let that choice die with the page. This is not "disable the feature" — the control still works, ⌥A still toggles, the tray still expands. It is that the *persistence* is switched off, because persistence across visitors is not memory, it is contamination.

Three preferences hit this on the Schedule alone (#4050): `trueppm.schedule.authorMode.<user>.<project>` opened the demo in Author because a previous visitor had authored; `trueppm.gantt.unscheduledGutter.collapsed` re-opened a tray nobody had asked for; and the legend's collapse state did the same. Each is correct on a normal install and each is a first-impression defect on a shared one.

**The fact to branch on is the deployment, not the user.** `useDemoMode().isDemoReadOnly` (rule 427's `['edition']` read) is a property of the server, so one predicate covers every preference and a normal install is untouched by construction. Do not try to detect a shared account from the user payload: "is this login shared" is not something `/auth/me` knows, and a heuristic on the username is a guess that will eventually be wrong in the direction that loses a real person's settings.

**A preference that is genuinely per-browser rather than per-user keeps its scope and loses the user id.** The demo's landing-hint dismissal (`tppm.demo.tips`) is the case: it is right that a visitor who closed the tips does not meet them again on the next page, and there is no honest user to key it to. Writing it as `tppm.demo.tips.<userId>` would be a single global key wearing a disguise, and would then read in code as "this person dismissed it" when what happened is that somebody else did. Name the scope you actually have.

**How this differs from rule 430.** 430 governs *controls* on a gated surface — every mutating affordance deriving from one predicate. This one governs *state that was restored before the visitor arrived*. A surface can pass 430 completely, refusing every write with a clear explanation, and still open in a mode, a zoom, a collapse state and a panel arrangement that the previous stranger left behind.
