# Rule 331 — A server-computed rollup is not maintained by any optimistic update, so it must be invalidated on the …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A server-computed rollup is not maintained by any optimistic update, so it must be invalidated on the ORIGINATING client too — and it must be added to an EXISTING `useProjectWebSocket` handler, never a new `on()` registration.** Two independent traps meet on the same line. **(a) Self-echo suppression is about the optimistic cache, not about freshness.** ADR-0152 skips the `tasks` refetch when `actor_id === currentUserId` because that client already applied its own edit locally — correct for rows the client wrote, and exactly wrong for `/overview/`, `/attention/`, `/my-tasks/` or a critical-path query, because nobody optimistically recomputes a server-side aggregate. Suppressing those leaves the *editor's own* health chip and critical path stale, so the defect survives the fix and moves one user over. Decide the self-echo branch per key: skip it for what the client wrote, never for what the server computed. **(b) `on()` is last-write-wins** (`eventHandlers[t] = handler`) — a second registration for an event type silently REPLACES the first, and the symptom is the *old* invalidation disappearing, not the new one failing. Extend the existing handler; `scheduleInvalidate` does accumulate, so several calls in one handler are fine and are also what keeps a paste-many or CPM cascade to one refetch per key instead of one per event. **(c) The hook is where this is testable.** Spy on `invalidateQueries`, dispatch the event, advance past the ~300ms debounce; a spec that only checks a collaborator event passes while the self-echo branch is wrong, so assert both. **(d) Do not invalidate a key no event reports — but ask what the RESPONSE is a function of, not what the endpoint is named.** *Superseded in part by #3140 (2026-08-30).* This clause originally cited `monte-carlo-latest` as the worked example: it serves the cached result of the last simulation, no broadcast announces a simulation, so wiring it to task events re-fetched an identical row. **That stopped being true when the payload gained a per-response staleness discriminant** derived from the project's live sync version and last recalc — every task event moves that input, so the row genuinely differs, and the forecast bar gates its Rerun *action* on it. The key is in `OVERVIEW_KEYS` now and the pin test asserts the inverse. The general rule survives and is sharper for it: a key is "reported" by any event that moves an input of its response, which includes inputs the server derives at read time and the endpoint's name never mentions. What has NOT changed is the other half of the original note — propagating a *collaborator's completed simulation* still needs a server-side event that does not exist; #3140 refreshed the verdict, not the forecast. This page's five rollups were invalidated by zero events and sat stale behind a 60s `staleTime` with `refetchOnWindowFocus: false` until the route remounted, which is indistinguishable from being current. Reference: `hooks/useProjectWebSocket.ts` (`OVERVIEW_KEYS`), `features/project/ProjectOverviewPage.tsx`, `lib/queryClient.ts` — #2912, sibling of #1867.
