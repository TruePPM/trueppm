# Rule 206 — A dialog that declares `role="dialog"`/`role="alertdialog"` + `aria-modal="true"` MUST trap focus itself …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A dialog that declares `role="dialog"`/`role="alertdialog"` + `aria-modal="true"` MUST trap focus itself (`useFocusTrap`) — you cannot clone a confirm dialog that relied on a parent modal for focus containment into a standalone/bare mount and keep `aria-modal` honest.** The board's `DeleteConfirmDialog` has no internal trap because it is always nested inside `TaskFormModal`, which contains focus. `EpicDeleteConfirmDialog` (#1339) was cloned from it but is mounted **bare** on the Product Backlog page (rendered by `EpicHeader`, no outer modal), so without a trap Tab/Shift-Tab walks straight out behind the scrim — violating the `aria-modal` contract (WCAG 2.4.3 / 2.1.2). The fix is the house hook: `const ref = useFocusTrap<HTMLDivElement>(true, onCancel)` on the **panel** (not the scrim) — it autofocuses the first focusable (which, for a destructive dialog, must be **Cancel**, never the destructive button — so order Cancel before Delete in the DOM), wraps Tab, and routes Escape to the close handler (do NOT also add a separate `document` Escape listener — it double-fires, the rule-204 lesson). Pair this with **focus restoration**: the surface that opened the dialog (e.g. the epic kebab) must return focus to its trigger on close — for a trigger that unmounts while the action is open (the kebab is hidden during rename), restore via an effect keyed on the open/close state, not a direct `.focus()` in the close handler. Reference: `EpicDeleteConfirmDialog.tsx`, the `restoreFocusRef` effect in `EpicHeader.tsx`, `useFocusTrap`.
