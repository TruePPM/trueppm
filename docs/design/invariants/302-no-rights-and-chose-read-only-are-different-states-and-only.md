# Rule 302 — "No rights" and "chose read-only" are different states, and only one of them gets a disabled control

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Foundations*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**"No rights" and "chose read-only" are different states, and only one of them gets a disabled control.** A surface that computes one `readOnly` flag by OR-ing an entitlement check with a user's own mode toggle (`!canEditTask(role) || mode === 'read'`) will render the same dimmed apparatus to both, and that is wrong for one of them. A user with **no edit rights** must find the authoring apparatus **absent, not disabled** — no create buttons, no Read/Author toggle, no grips, no insert points, no delete — and its mutation guards stay **silent**, because with nothing offering the action there is no gesture left to explain. A user **with** rights who pressed the toggle must find it **present and inert**, with refusals that explain themselves, because one key gets them back. Offering a control and then refusing it teaches a viewer the product is broken; explaining a refusal to someone who should never have seen the button is noise. Derive the two separately (`hasEditRights` for presence, `readOnly` for behavior) and put one static badge where the apparatus was, naming what to do instead — a badge, not a button, since an action would put an affordance back on a surface whose whole point is that it offers none. This is presentation only: the server stays the thing that actually refuses. Note it also satisfies rule 6.1's "conditional permission-gated affordances" check, which a `disabled` control fails by announcing "[label], dimmed" to a screen reader. **A TEACHING surface is covered by this rule too, and it is the instance that gets missed — because nothing on it looks like a control.** The apparatus can be correctly absent and the surface that *narrates* the apparatus still name it. `BuildModeHintStrip` took no rights term at all until #3231: `buildModeActive = !isMobile` and `tryBuildModeFocusMove` gates on `buildMode` alone, so a Viewer arrows into `RowFocused` and was taught `⏎ New row below` / `⌥→ Indent` / `F2 Edit` — three mutations with no control anywhere to look dimmed. This is worse than a disabled button, not better: #3020's argument is that a user who tries the thing the bar teaches and gets nothing concludes the **feature** is broken rather than the hint. Three obligations. **(a)** Every glyph, chord and label on a teaching surface must resolve to an act **this** reader can perform; scope the *content* by rights, and take the content from the handler's own reader branch rather than choosing it for tone — `BuildModeHintStrip`'s `READER_HINTS` are read off `TaskListRow`'s `if (!canEdit)` arm, which is why `⏎` reads `Open details` (it sets `selectedTaskId`) and not `Select row`. **(b)** Withholding the surface is usually the wrong fix — it takes the reader-safe parts with it (here the `? All shortcuts` route, the strip's only job that survives without rights) and strands a reader who navigates with no hints at all. So the rights term belongs in what the surface **says**, not in whether it renders; keep the render predicate a statement about which surface owns the space. **(c)** A hint set is not verified by rendering it — assert the mutation labels are **absent** across every focus state and selection size, not just the one that was reported, and pin which set is up (`data-hints`) so an E2E can see the leak. Reference: `features/schedule/ScheduleView.tsx` (`hasEditRights` vs `readOnly`), `features/schedule/ScheduleViewOnlyBadge.tsx` — #2949, from `design_handoff_trueppm_v4/` "No edit rights"; `features/schedule/buildMode/BuildModeHintStrip.tsx` (`READER_HINTS`), `e2e/schedule-hint-strip-viewer.spec.ts` — #3231.
- **At the row (#2961), the rule needs three flags, not two — and the third is the one that gets missed.** `TaskListRow`'s `buildMode` object is two things wearing one name: the outline's *navigation* model (row focus, arrow traversal, ⌘A, Shift+↑/↓, the roving tab stop) and its *authoring* API (insert, indent, reorder, delete, cell edit). The one-line fix — null `buildMode` for a viewer — takes the navigation with it and leaves a grid nobody can move around in. Absence must remove what **authors** the plan, never what **reads** it. So: `buildMode` for navigation sites, `authoring = canEdit ? buildMode : null` for mutation sites, and a separate **`canEdit` boolean** for the "may this reader mutate at all" question — because `authoring` is *also* null for an editor who simply is not in build mode, and gating the flag-off keyboard reducer on it silently deletes that editor's Space / ⌘D / F2 / double-click-rename. Cells take `authoring`: every cell primitive already branches `buildMode ? <EditableCell> : <text>`, so passing it is what makes a viewer read a plan instead of a form someone locked.
- **Presence follows the *settled* entitlement — an unresolved role is not "no rights".** `useCurrentUserRole` returns `isLoading: true` before the membership query lands, so `canEditTask(role)` is false on first paint for everyone. Gating presence on that directly makes every row grow its controls a beat after it appeared — a layout shift on every schedule load. Assume rights while loading and let the settled value decide: the server is the enforcement point, so a control briefly offered to a viewer costs at worst one silent refusal, while a control briefly withheld from an editor is visible on every load. A server-sent per-task capability (`task.canEdit`) is already settled and wins outright. Write it as `task.canEdit ?? (roleUnsettled ? true : canEditTask(role))`, where `roleUnsettled = isLoading || isError`. **A failed lookup is unresolved too, and that is the case that gets missed**: the hook sets `retry: false`, so before #2961 an error was indistinguishable from "settled: not a member" and one dropped request would have stripped an editor's whole apparatus with no error state anywhere to explain it. `useCurrentUserRole` exposes `isError` for exactly this; the `lint:design-system-v2` rule-246 ratchet is what surfaced it, by counting a destructure that takes `isLoading` and never `error` — treat that gate as a finding about the code, not a number to get back under.
- **A test that renders one of these surfaces must declare a role, and the failure mode if it does not is disguised.** Without a `useCurrentUserRole` mock the real hook resolves to "no role" *asynchronously*, so a synchronous `fireEvent` case passes while its `await user.click` twin fails — which reads as a flake rather than as a missing fixture. Mock it (`{ role: 100, roleLabel: null, isLoading: false }`) in any spec that exercises authoring. The e2e default is already an editing role (`api-mocks.ts` serves `role: 300` for `?self=true`), so only specs that pass an explicit lower-role `members` need attention. Reference: `features/schedule/TaskListRow.noEditRights.test.tsx`.
