# Rule 413 — A chart label that collides with its neighbor moves to a new ROW — the marker it names never moves, and the p…

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Signal encoding*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A chart label that collides with its neighbor moves to a new ROW — the marker it names never moves, and the packing is a generic N-label layout problem, not a special case for one named pair.** `MonteCarloHistogram`'s P50/P80/P95 percentile labels were each drawn with `textAnchor="middle"` at a fixed y, directly below their rule line's x-coordinate, with no collision check. On any project where two percentiles land on adjacent (or the same) week bucket — the bar pitch is 10px, a three-character label is roughly 25px wide — the labels render on top of each other and read as one illegible run, e.g. "P80P95" (#3736). Two things make the fix durable rather than a patch for the one pair that got reported: **(a) the rule line and the label are two different things, and only one of them is allowed to move.** The dashed/dotted/solid marker is a fact about the data — the P80 date really is at that x — and moving it to avoid a layout collision would be a lie about the distribution. Only the text, which exists to *name* the marker, is free to reposition; keep it anchored at the marker's true x (so the color-coded label still sits directly under its own line) and give it a second row of vertical space instead. **(b) treat the labels as a set to be packed, not as a fixed handful of special cases.** A hand-written `if (p80 and p95 are close) nudge one down` breaks the moment a project's P50 and P80 collapse onto the same bucket instead, or a future chart adds a P20/P95 pair. `assignLabelRows` sorts every label by its x-coordinate and walks left to right doing greedy interval packing — the same shape as a calendar's event-layout algorithm — placing each label in the first row whose last-placed occupant doesn't overlap it, opening a new row only when every existing row is still occupied at that x. This scales to any label count without new branches, and it degrades correctly: percentiles spaced far enough apart never leave row 0 and the chart's height is unchanged from before the fix. Label width for the packing decision is estimated from character count (`text.length * 7 + 4` for 12px medium-weight sans-serif) rather than measured via a DOM layout pass — SVG `<text>` has no cheap synchronous measurement hook, and a slightly generous estimate that opens one more row than strictly necessary is the safe failure direction; an estimate that runs narrow is the one that lets a real collision back through. Reference: `features/schedule/MonteCarloHistogram.tsx` (`assignLabelRows`, `estimateLabelWidth`, `LABEL_BASE_Y`/`LABEL_ROW_H`/`LABEL_ROW_GAP`) — #3736.
