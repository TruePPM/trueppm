# Rule 322 — When two controls write ONE persisted layout value, they share one clamp and one announced range — and a …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**When two controls write ONE persisted layout value, they share one clamp and one announced range — and a bound must never reach backwards past the value the user already holds.** The Schedule stores `widths.task` once and offers it two `role="separator"` handles: `TaskListHeader`'s per-column `ResizeHandle` and `ScheduleView`'s `PanelSplitter`. #2960 gave the splitter a container-aware clamp so a drag could not push the bar track off the viewport — and left the header handle's pointer path **entirely unbounded** and its keyboard path on a local `MAX_COL_WIDTH` of its own. So the invariant the change existed to establish was defeated by the *other* control on the same value, and on the Timeline (where Task is the last column) the two hit zones ended up adjacent with the unclamped one three times wider: aim at the divider in the header row and you get the unbounded control, aim one row lower and you get the clamped one. Three obligations. **(a) One clamp function, taking the measurement, called by every writer.** A second writer is not a duplicate — it is the escape hatch, and it is invisible to any test that drives only the control the change touched, so the first thing to grep when adding a bound is who *else* writes the value. **(b) `aria-valuemin ≤ aria-valuenow ≤ aria-valuemax` is an invariant, not a rendering detail, and two separators over one quantity must announce the same range.** A range computed from available room goes inverted the moment the sibling columns eat the room — a 600px outline in a ~780px pane yields a max of 120 against a current of 220 — and an inverted range is a WCAG 4.1.2 failure that no visual check sees; assert `valuenow` inside `[valuemin, valuemax]` in the spec that adds the bound. **(c) An upper bound is permission to grow, never an instruction to shrink.** Clamp to `Math.max(bound, current)`: a user who has held 220px for a year did not ask for 120px by pressing ArrowLeft once, and a clamp that snaps on first contact reads as the control being broken rather than as a limit being enforced. Corollary, and it costs a debugging round: **a bound resolved from a DOM measurement must not be read during render or inside a pointer handler.** During render a null ref on first paint silently yields the fallback constant, which is then announced to assistive tech as fact; inside `onPointerMove` it is a write-then-read cycle at pointer rate, flushing layout for the whole pane 60–120 times a second on the one gesture whose job is to feel direct. Measure into state with a `ResizeObserver` (`useObservedWidth`) so the announcement and the enforcement come from the same number at the same time. Reference: `features/schedule/ScheduleView.tsx` (`PanelSplitter`, `clampTaskWidth`, `maxTaskWidthFor`, `useObservedWidth`), `features/schedule/TaskListHeader.tsx` (`ResizeHandle`), `hooks/useBoardResize.ts` (the same class, 2026-06) — #2960.
