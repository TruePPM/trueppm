# Rule 231 — The OSS UI shows what one team can do; an Enterprise affordance appears ONLY at a surface where the user …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Product boundary*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**The OSS UI shows what one team can do; an Enterprise affordance appears ONLY at a surface where the user reaches for something inherently cross-program or org-governing — never as an ambient padlock, disabled control, or upsell teaser in the OSS daily path.** TruePPM is adoption-first (the GitLab model): the free tier must be *completely sufficient for one PM/team/program*, and the Enterprise need is discovered **structurally** — when a second program, a portfolio roll-up, org-wide SSO enforcement, or a directory sync becomes the actual task — not through locked doors sprinkled across the shell. Three constraints for any **new** shell/navigation or extension-point-slot surface:
- **(a) No render absent the edition.** Enterprise features register into stable OSS extension points (slot registration ADR-0029; edition-based routing ADR-0030). When the enterprise package is not installed, `registry.get(<slot>)` returns `[]` and the OSS UI renders **nothing** in that slot — no grayed-out or padlocked placeholder. A disabled control the OSS user can never enable is a wall, and walls in the daily path are the "you must upgrade to work" signal adoption-first exists to avoid.
- **(b) Discovery at the seam, not on the surface.** The upgrade signal is allowed only where the *shape of the work* crosses the boundary — the moment a user tries to compare two programs, open a portfolio roll-up, enforce org-wide SSO, or sync a directory. That is contextual and honest (it coincides with a need the user just expressed) and is the ONLY sanctioned place a "this is an Enterprise capability" affordance may appear. It is never ambient chrome.
- **(c) An Enterprise affordance is a distinct opt-in surface, not a disabled OSS control.** Where an enterprise slot *is* registered, present it as its own surface with its own label — never as `disabled aria-disabled="true"` OSS UI. (Contrast rule 42's WBS/Table `disabled` state, which gates an *OSS* feature coming to *this* edition — a legitimate "not built yet" disable; an Enterprise capability is "not in this edition," a different meaning that must not read as "temporarily off.")

Load-bearing at the shell seams: the 3-tier rail (You / This project / **Jump**, #1642) and the location switcher (#1643) are exactly where cross-program/portfolio scope becomes visible. In OSS, `Program` is a first-class entity, so *within-program* navigation is fully OSS; only **cross-program** and **portfolio** destinations are the Enterprise seam. The classification test is the CLAUDE.md two-repo test verbatim: "Would a PM/program manager need this to run their program?" → OSS, render it; "Is this cross-program coordination, org policy, or compliance evidence?" → Enterprise, surface it only at the seam per (b). Basic OIDC/OAuth login is OSS (auth carve-out) — never gate it. If a practitioner hits a locked door doing single-program work, the boundary is drawn wrong and no visual treatment can rescue it — fix the boundary, not the padlock.

**Surface classifier — daily path vs seam.** Rules 231 and 121 are the *same* principle applied to two surface types, not competing rules. **Daily-path surfaces** (the shell, rail, nav, project workspace, My Work) get 231: empty slots, zero ambient upsell. **Seam surfaces** — where a user's own action crosses into governance (Settings → Roles & permissions, org-identity/governance settings, the `/programs`→portfolio boundary) — may carry a single contextual affordance, because that *is* discovery at the seam (constraint (b) above), not ambient chrome. This maps onto the project's own adoption-vs-governance boundary: the daily path is where a team gets work done, the governance/settings seam is the natural home for an upgrade signal. Consequences:
- **Rule 121's `EnterpriseBadge` on the Settings→Roles capability matrix stays** — the matrix's job is to show the *full* capability space, so hiding Enterprise rows would misrepresent it. The badge is constrained to **seam surfaces only**, never the daily-path shell/nav.
- **Rule 178 was corrected by this rule and the correction has SHIPPED (#1677, closed):** the disabled "Portfolio rollup" row in the rail was a slot on the *daily path* wearing a padlock. `Sidebar.tsx` now renders the empty `nav.portfolio_section` slot instead, with discovery moved to the `/programs` seam. **Do not re-add a padlocked or disabled Portfolio row.** This bullet previously ended "until it lands, leave the shipped `Sidebar.tsx` row in place" — a now-inverted instruction sitting inside the load-bearing anti-upsell rule for the whole shell (#2859).
