# Rule 421 — `aria-label` on a roleless element is prohibited outright, not just double-read-prone

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Signal encoding*. The index carries the rule's headline; this file carries its full text (#3482). Binding everywhere, not only on the surface that produced it.

**`aria-label` on an element with no ARIA role (a bare `<span>`/`<div>`/`<section>`/`<p>`) is axe `aria-prohibited-attr` — serious, WCAG 2.1 A 4.1.2 — even when every visible descendant is already `aria-hidden`.** Rule 171 documents the NVDA/JAWS double-read symptom and its fix (hide the visible children); it does not say that hiding the children does not, by itself, make the attribute legal. The implicit role of a plain container is `generic`, and `generic` is one of the roles the ARIA spec marks `aria-label` **Prohibited** on — the browser drops the label from the accessibility tree regardless of what else is on the element, so a scan that only checks "is the string somewhere" (a screen-reader smoke test) can miss this while axe still fails the build. `BulkFieldsMatrix.tsx`'s `ValueCell` was the reference instance (#3482): every branch already wrapped its visible text in an `aria-hidden` sibling per rule 171, and every branch still failed `aria-prohibited-attr`, because the outer `<span>` still carried the attribute.

**The fix is to delete the attribute, not just hide more children.** Replace it with a **second real DOM child** — `<span className="sr-only">{fullString}</span>` — as a sibling of the `aria-hidden` visible span, inside the same roleless container. This is the same shape rule 171's "alternative pattern" already describes (`role="presentation"` + one `sr-only` span), generalized to the common case where the container keeps its default (no) role: the container needs no `role="presentation"` addition — plain elements already carry no accessible-name-bearing role — it just needs the `aria-label` **attribute** gone. Two elements this landed on in the same sweep: the Risk register's "Unassigned" owner cell (`RiskRegisterView.tsx`) and the sprint goal card's points-committed chip (`SprintGoalCard.tsx`), both `<span aria-label="…">` with no role.

**Do not confuse this with a real widget.** On an element that already carries an ARIA role that permits naming (`button`, `role="img"`, `role="status"`, `role="group"`, `role="radiogroup"`, …), `aria-label` is legal and is the right tool — do not go hunting for roleless spans to "fix" among the many `role="group"`/`role="img"`/`role="status"` + `aria-label` combinations already in this codebase; they are correct as written. The trap is specifically the container that has **no** role at all.
