# Rule 367 — A sized glyph that is a DIRECT FLEX CHILD needs `shrink-0`, and `inline-block` / `align-[…]` on one are inert …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Accessibility floors*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A sized glyph that is a DIRECT FLEX CHILD needs `shrink-0`, and `inline-block` / `align-[…]` on one are inert — they do not merely fail to help, they misdirect the next reader into a cascade hunt.** The Schedule's milestone diamond rendered `h-3 w-3 inline-block align-[-0.125em]` in a `flex items-center` gridcell whose content overflows its fixed `widths.task` (measured: 224px in a 219px box). With the default `flex-shrink: 1` the glyph absorbed the entire overflow and resolved to **`width: 0px` while `height` stayed `12px`** — the asymmetry that makes this look impossible, and which is simply that shrinking is main-axis only (#3273). Three things follow. **(a) Read `display: block` on a flex child as blockification, not as a losing utility.** CSS Display §2.7 blockifies every flex item, so `inline-block` computes to `block` and `vertical-align` never applies. #3273 was filed against Tailwind preflight's `svg { display: block }` "being ordered ahead of the utilities" and feared a blast radius of *every inline SVG in the app*; that was wrong on both counts — an element selector cannot outrank a class, `.w-3` and `.inline-block` both matched and applied exactly as authored, and the true radius was **one element**. When two utilities on the same element appear to lose at once, ask what recomputed them, not what overrode them. **(b) The name truncates; the glyph does not.** A glyph is usually the only channel asserting a row's *type* — the rest of the row states consequences — and it is typically `aria-hidden`, so at 0px neither a sighted nor a screen-reader user has the type at all. The sibling `seeded-untouched-glyph` in the same cell already carried `shrink-0`, which is why only one of the two was ever broken. **(c) `toHaveCount()` passes throughout this defect; only `toBeVisible()` catches it.** Playwright treats a zero-area element as hidden, which is the single assertion that separates "rendered" from "rendered at 0px" — so a presence-only guard on any glyph is not a guard. Before reaching for `inline-block` on an icon, check the parent's `display`: in genuine inline flow (`<p>`, `<span>` — `ScheduleLegend`, `ScheduleSummaryChip`, `SensitivityList`) the idiom is correct and must stay. Reference: `features/schedule/TaskListRow.tsx`, `e2e/schedule-milestone-conversion.spec.ts`, `e2e/seeded-landing.spec.ts` — #3273.
