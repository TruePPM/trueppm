# Rule 415 — A capability claim that decays with TIME must be REPLACED when it stops being true …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Surface states*. The index carries the rule's headline; this file carries its full text. Binding everywhere, not only on the surface that produced it.

**A capability claim that decays with TIME must be REPLACED when it stops being true — not left standing beside a warning that contradicts it.** ux-review §6.3 catches copy that asserts a capability the product never had; this is its harder sibling, because the sentence was *true when it was written* and nothing re-evaluates it. The sample-data banner promised "It includes 60 days of history — forecast trend, sprint velocity, and baseline variance render out of the box," which was exactly true on the day the demo loaded and false seven weeks later, when the same screen showed an "Active" sprint that had completed six weeks earlier and nine overdue tasks per project (#3481, the 2026-09-06 UX audit H10). No gate can see this: there is no version string for `docs:version-accuracy` to read, the control below the sentence works perfectly, and every test renders the component at t=0 where the claim holds. **Three obligations.** **(a) Find the decaying claim by asking "when does this sentence expire?" of every present-tense assertion about rendered data** — anything of the form "includes N days of", "shows your current", "is up to date", "reflects your latest" carries an implicit *as of now* that the component cannot verify. **(b) Swap the sentence, do not append to it.** The instinct is to keep the promise and add "(this demo is 47 days old)" next to it; that leaves a false claim on screen and makes the reader reconcile two statements, one of which the product knows to be wrong. Branch the copy on the freshness fact and render exactly one. **(c) The freshness fact must be a SERVER field, never a client subtraction** — `sample_days_stale` is computed on `Program` and read by both the banner and the per-project indicator, because two components deriving "how stale" from a raw timestamp is how they end up disagreeing on the same screen, and neither is authoritative. Pair the replacement with the remedy where one exists: the stale copy names the action ("Shift them forward…") and the control appears at primary weight in the same band, so the screen that admits the problem is the screen that fixes it. Reference: `features/programs/SampleDataBanner.tsx` (bands on `sampleDaysStale`) and `features/project/ProjectSampleIndicator.tsx` — #3481, ADR-1175, surfaced by `ux-review`.
