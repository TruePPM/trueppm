# Rule 339 — A control that performs two acts must SAY which one the next press does — and the label and the accessible …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Surface states*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A control that performs two acts must SAY which one the next press does — and the label and the accessible name must be one derived string, spelled for the platform reading it.** `⌘⌥P` / `+ Phase` gained a subject in #2951: with a leaf row focused it adopts **that** row as the container; with nothing focused it still mints a fresh phase at the insertion point. The control's tooltip said "Add new phase, with its first task" for both, which is a claim about a write the user is about to make **to a row it never mentions** — rule 326's failure with a subject rather than a keystroke. Four obligations. **(a) Derive the sentence once and use it for both surfaces.** The `title` and the `aria-label` were separate literals here, and they had already drifted: the tooltip said "with its first task" and the accessible name did not, so a screen-reader user was told strictly less about what the press would do than a sighted one — rule 328's "a fact with three phrasings has no owner", reached by two. **(b) Never hardcode a chord in an accessible name.** The same `aria-label` spelled `Option+Cmd+P` as a literal while the tooltip beside it resolved `formatChord('mod+alt+p')`, so every Windows and Linux user was told the Mac chord by the one surface they could not visually correct against — and three e2e specs asserted the wrong string, passing only because the literal matched itself. Derive it, and derive it in the **test** too: a spec that restates the chord rots exactly as the label did and will pass on whichever OS CI happens to run (#3028, rule 326(d)). **(c) The stated act is the observable proof the mode is armed.** A gesture whose arming lives only in a component's state cannot be asserted except through the write it eventually makes; a control that names its subject gives the test something to gate on *before* the click, which is what separates "the gesture is armed" from "the mutation happened to fire". **(d) Prefer a second act on an EXISTING control over overloading a directional key.** The design wrote this gesture as `⇥`, and the tree binds indent to `⌥→` — but indent means "move this row under the row above", which makes the row ABOVE the container, not the row you just named. They are different acts, and giving one key both, distinguished only by which row is focused, is rule 329's trap (a key that is both text and a command needs a state that says which). Hanging the second act on the control that already produces the outcome costs one label and no ambiguity. Reference: `features/schedule/ScheduleAddPhaseButton.tsx` (`action`, `adoptsRowName`), `features/schedule/ScheduleView.tsx` (`phaseAdoptionTarget`, `handleAddPhase`), `e2e/schedule-add-phase.spec.ts` — #2951.
