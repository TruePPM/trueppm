# Rule 356 — A capped set of transient surfaces must NOT evict by age when dwell is set by importance — give each class …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Controls and composition*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A capped set of transient surfaces must NOT evict by age when dwell is set by importance — give each class its own slot instead.** Age is a proxy for disposability, and the moment dwell length encodes importance the proxy inverts: the item that deserves to live longest becomes the oldest soonest, so drop-oldest kills exactly what the long dwell was bought for. The global toast host had an unbounded stack (three at once covered a third of the plan) and the obvious fix — cap at two, evict oldest — would have been worse than the bug it replaced: with a 2.6s passive dwell and an 8s actionable one, two routine confirmations evicted a "Deleted — Undo" before the user's hand arrived, and the failure is invisible in review because each toast is individually correct and the collision needs three (#3149). Five obligations. **(a) Slot by role, not by arrival — and the role axis is *every* field that already encodes importance, not the first one that suggests itself.** `toastStore` holds `{ transient, action }`, each a single item — a passive replaces the passive, an actionable replaces the actionable, and neither can touch the other. The cap is then *structural*: there is nowhere for a third to go, so no `while`, no `slice`, and no test that can pass while the bound leaks. But actionability is not the only importance signal in the tree: `variant` is one too, and a split that reads only `action ? … : …` drops a failure notice and a routine confirmation into the same slot, where the confirmation wins purely by being newer — which is drop-oldest walking back in through a second door. Before shipping a slot split, enumerate every dimension the surface already varies by importance (dwell, variant, severity, whether the user asked for it) and either read all of them or say why one is excluded. Concretely here: a passive `error` holds its slot against a `success`/`info` until its own dwell is up, and only another `error` replaces it early. **(b) The cap lives in the store, not the renderer.** A host that renders `items.slice(0, 2)` still holds the other items, still runs their timers, and still announces them — the bound has to be enforced where the state is or it is cosmetic. **(c) Order the slots by reachability, not recency.** The slot that can hold a control renders lowest (nearest the thumb); "newest on top" is a queue's habit and a queue is what was removed. **(d) An element with focus inside it is never auto-removed and never displaced** — the only way a keyboard user loses a control is by leaving it. An incoming item waits at **depth one** (newest wins, the loser is not silently dropped); an unbounded wait-queue is the same unbounded stack, only invisible. **(e) Eviction may cost convenience, never capability — so gate the eviction on the durable home, do not merely assert one exists.** Anything evicted must leave its action reachable somewhere durable *before* the eviction path ships, and *no copy explains the demotion in the moment*, because a notice about where the previous notice went is a notice about notices. The trap is that "it demotes to the session trail" is easy to write in a design and easy to implement as a field nothing reads: a store slot that collects evicted items is not a durable home, it is a leak with a name. Make the durability a **property of the item** (`ToastItem.trailBacked`) that the eviction branch actually reads, defaulting to *not* durable, so a surface with no trail queues at depth one instead of evicting. Then the invariant is true by construction on every surface rather than true on the one surface the designer had in mind — and the asymmetry is a contract a reader can see, not an inconsistency. Expect the honest answer to be that **no** caller qualifies yet: at 0.4 every global action toast is un-backed, because the one surface with a session trail (the Schedule) renders its own toast and does not use the global host. An eviction branch that is unreachable in production and correct is better than one that is reachable and destroys undos. Live-region corollary: the region **contains** the rendered items and nothing is written to it out of band, which makes "announced but never shown" impossible by construction rather than by discipline; it needs an explicit **`aria-atomic="false"`** or a re-render of one slot re-reads the other. Note the mechanism honestly (rule 300): jsdom has no layout and no `:focus-visible`, so slot *order* and real focus retention are `e2e/toast-host.spec.ts`, and the slot algebra — every eviction-table row, the coalescing window, the depth-one queue — is `toastStore.test.ts`. Generalizes past toasts to any bounded transient stack: snackbars, inline banners, presence chips, undo receipts. Reference: `components/Toast/toastStore.ts`, `components/Toast/ToastHost.tsx` — #3149.
