# Rule 434 — Every `aria-modal="true"` dialog must pair with a real focus trap, and a gate proves it, not prose

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#4085, #4125). Binding everywhere, not only on the surface that produced it.

**Every file that renders a literal `aria-modal="true"` or `aria-modal={true}` JSX attribute must pair it with one of: a `useFocusTrap` import, an inline `// focus-trap: <reason>` waiver, or a `<BottomSheet>` shell — and `scripts/check-aria-modal-focus-trap.sh` (`make aria-modal-focus-trap-check`, CI job `lint:aria-modal-focus-trap`) is what checks this, not rule 206's prose alone.** Rule 206 already said a dialog declaring `aria-modal="true"` must trap focus itself; #2193 found ~17 dialogs violating it anyway, fixed them by hand, and added no gate. #4085 found 14 fresh instances recurring with the exact same shape eighteen issues later — a rule stated once and enforced by nothing is a rule that gets re-broken on a schedule, and `/pre-release full` finding the same class twice (#2977-style) is the tell that a prose rule needs a script, not a third sweep.

The gate's three recognized pairings, in the order it checks them:

1. **`useFocusTrap` import** — the normal case. Attach the hook's returned ref to the dialog's own container (the panel, not necessarily the full-viewport scrim — see rule 419 for when that distinction is load-bearing), give the container `tabIndex={-1}`, and pass the close handler as `onEscape`. Remove any hand-rolled Escape/Tab keydown listener the migration replaces.
2. **An inline `// focus-trap: <reason>` waiver** — for a component that hand-rolls a *verified-correct* Tab trap instead of importing the hook (`ScheduleTaskDialog.tsx` is the one on this tree: it predates `useFocusTrap`, its Tab/Shift+Tab containment matches the hook's own wrap behavior exactly, and migrating it would be pure churn). The waiver is a code comment, not a separate waiver-list file — reviewable in the diff that adds it, unlike `scripts/focus-trap-focuskey-waivers.txt`'s external ledger for rule 362.
3. **A `<BottomSheet>` shell** — a component whose only modal surface is a `<BottomSheet>` (which owns its own trap/scrim/Escape) has nothing further to pair. `CardPopoverShell.tsx` is the reference: its desktop branch is `aria-modal="false"` (board stays keyboard-navigable), and its mobile branch renders through `<BottomSheet>`, which carries the real `aria-modal="true"`.

What the gate does **not** try to resolve, and why that is deliberate rather than a gap: a docstring or `//` comment that quotes `aria-modal="true"` in prose is skipped (not a rendered attribute), and a `document.querySelector('[role="dialog"][aria-modal="true"]')` CSS-selector string is skipped too (`SprintsView.tsx` — a runtime lookup over *other* dialogs' DOM, not a declaration of this component's own modal). Both are read by checking the line itself, not by understanding JSX — a grep-shaped gate, same family as rule 362's `check-focus-trap-focuskey.sh`, and it inherits that script's convention of a `--self-test` that plants an offender and asserts every non-offending shape is *not* flagged, run first in CI so a green scan is never unfalsifiable.

A migrated dialog very often also needs rule 362's `focusKey`: if ANY control the dialog renders carries a `disabled={…}` bound to an in-flight flag (`isPending`, `confirmPending`, …), pass that flag as `useFocusTrap`'s third argument — not only when it disables *every* control (rule 419's narrower trigger), but whenever the specific control the user just focused (typically the button they clicked) is the one that goes disabled. `check-focus-trap-focuskey.sh`'s cheap text match does not distinguish the two cases, and neither does the actual browser: focusing a control and then disabling it blurs to `<body>` regardless of what else in the dialog stays enabled.

Reference: `scripts/check-aria-modal-focus-trap.sh`, rule 206, rule 362, rule 419, `hooks/useFocusTrap.ts`, `ScheduleTaskDialog.tsx` (the one standing waiver), `CardPopoverShell.tsx` (the `<BottomSheet>` shape).
