# Rule 401 — A role-tier name and a display-only FK must never share a phrase, and UI copy names a tier with the SCOPE's …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Signal encoding*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A role-tier name and a display-only FK must never share a phrase, and UI copy names a tier with the SCOPE's role label — never the raw `Role` enum key.** `Role`'s own labels are project-scoped ("Project Manager" at ordinal 300, "Project Admin" at 400); `_PROGRAM_ROLE_LABELS` remaps the same ordinals to "Program Manager" and "Program Admin" for program surfaces, and that is what the server emits and what the user reads on a role badge. So copy saying "Owner", "Admin", or "Scheduler" is printing an internal key the product never shows — and "Admin" is the worse case, because it is not shorthand for ordinal 300 at all, it is the first word of ordinal **400**'s label, so "you are demoted to Admin" names the tier being given away. Three obligations. **(a) Name the tier in the scope's vocabulary, and sweep the scope, not the screen.** The phrase recurs in provenance strings (`ReadOnlyIndicator`), disabled-control `title`s, lifecycle card notes, and docs — and in each it must name the tier the *gate actually checks*, precisely: a threshold gate (`role >= ROLE_ADMIN`) admits Program Manager **and** Program Admin, so copy must say "program manager or above" — not bare "program manager", which a Program Admin reading it has no reason to parse as including themselves (#3524, surfaced by `ux-review`: the codebase's own docs already establish this exact phrasing — `features/settings/program-rollup.md`, `program-risk-policy.md` — "Only a Program Manager or above can…"). Reserve the bare tier name for an equality gate (`role === ROLE_OWNER`) or a project ceiling action, where there is no higher tier to fold in — e.g. Project Admin transferring ownership, which is `IsProjectOwner`-gated with no "or above" to name. **(b) A display FK takes a distinct noun** — `lead` → "Program lead" / "Project lead" — and its copy states that it grants nothing; a `lead` labeled with a role's words collides with that role the moment both render on one screen, which is how the two ended up side by side in the Transfer sponsorship dialog. **(c) A scope rename is mirrored, so sweep the mirror before merging and either fix it in the same MR or file it and name the issue in the MR** — the project and program lifecycle dialogs are one component rendered twice, and fixing one alone leaves the product with two registers for one action. Note the mechanism honestly (rule 300): nothing checks UI copy against `_PROGRAM_ROLE_LABELS`, so this is a convention, not a gate, and a green pipeline is not coverage of it. Reference: `apps/projects/serializers.py` (`_PROGRAM_ROLE_LABELS`), `apps/access/models.py` (`Role`), `features/settings/components/TransferOwnershipDialog.tsx`, `features/settings/{program,project}/*ArchivePage.tsx`, `features/settings/program/{ProgramCadence,ProgramRollup,ProgramRiskPolicy,ProgramCalendar}Page.tsx`, `StakeholderReachSummary.tsx` — #3476, #3513, #3524 (which also swept the project/workspace transfer copy and the program-provenance sites, and fixed this rule's own (a) to say "or above").
