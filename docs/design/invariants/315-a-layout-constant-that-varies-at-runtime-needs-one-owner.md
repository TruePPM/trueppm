# Rule 315 — A layout constant that varies at runtime needs ONE owner and a read path that does not require React — a …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Dialogs, focus and keyboard*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**A layout constant that varies at runtime needs ONE owner and a read path that does not require React — a second declaration is not a duplicate, it is a silent mis-hit.** Schedule rows are 28px on a mouse and 44px on a coarse pointer (web rule 5, WCAG 2.5.5), and `ROW_HEIGHT` was read by five subsystems, three of which are not React and cannot take a hook: the canvas renderer, the pointer hit index, and the engine's virtualization. Before #2997 the same `= 28` was declared **three** times (`scheduleConstants.ts`, `engine/GanttHitIndex.ts`, `engine/GanttRenderer.ts`) and nothing noticed, because while the value is a literal the copies agree by luck. The moment it varies they can disagree, and **the disagreement has no visible symptom**: the hit index lays out rows at one pitch, the canvas paints them at another, taps open the task above or below the one under the finger, and every screenshot looks correct. That is why this is a rule about *ownership* rather than about touch targets. Four obligations. **(a) One module owns it; everyone else re-exports.** `export let X` plus a setter in the owning module is an ES **live binding** — importers read through to the variable, so ~70 existing `rowIndex * ROW_HEIGHT` call sites keep working unchanged and no signature grows a parameter. `export { X }` after `import { X }` preserves liveness, so a module that used to declare its own can re-export instead and its importers never notice. **(b) Never capture a live binding at module scope** (`const TWO_ROWS = ROW_HEIGHT * 2` at the top of a file freezes the first value forever) — read it inside the function, and hoist into a local only *within* a hot loop, where it is also the right thing for the 60fps paint path. **(c) A React consumer must SUBSCRIBE, not merely read.** Reading the binding during render yields the right number and will not re-render when the pointer class flips (a tablet gaining a keyboard, a hybrid laptop folding shut); the hook that subscribes must also be the thing that *writes* the binding and must return what it wrote (`useRowHeight`/`useRowMetrics` → `syncRowMetrics(coarse)`), so a hook computing `coarse ? 44 : 28` itself is exactly the second definition the rule forbids. Caching consumers need an explicit invalidation: TanStack Virtual keeps its measured sizes, so changing `estimateSize` alone leaves rows at the old pitch inside taller boxes — `virtualizer.measure()` on the height is what actually moves them. **(d) Gate the population, not the instance** (rule 300): a source scan asserting the declaration appears exactly once is the only thing that can see somebody *adding* a fourth copy, since no behavioral test on the existing consumers can. Two corollaries that cost a debugging round each: a derived inset must be *derived* (`BAR_TOP_OFFSET = (ROW_HEIGHT - BAR_HEIGHT) / 2`, which is 5 at 28 and 13 at 44 — a retained literal 5 pins bars to the top of a 44px row with 21px of dead space under them); and **size a target from `top-0` + an explicit height, not `inset-y-0`**, because the row's own `border-b` is inside its border box, so a stretched child is `rowHeight - 1` — 43px, which has not met a 44px floor however close it looks. **The breakpoint-keyed half of this is a population, not an instance:** `packages/web/src` carries **162 occurrences across 62 files** of `md:h-` / `md:w-` / `md:min-h-` / `md:min-w-` control sizing, six of them inside `features/schedule/` itself (`ScheduleDependencyPicker`, `EstimatesTab`, `sections/RelatedLinkPicker`, `sections/GuardrailNotice` ×2, `sections/GuardrailBlock`) and one structurally identical to the grip (`features/grid/VirtualRows.tsx` — a virtualized row height keyed on `useBreakpoint()`). #2997 converted one of them; the rest are tracked, not fixed, and quoting this rule at a new `md:`-sized control is fair while quoting it as "the tree is clean" is not. Reference: `features/schedule/scheduleConstants.ts` (the owner), `hooks/useRowHeight.ts`, `features/schedule/engine/{GanttHitIndex,GanttRenderer}.ts` (the re-exports), `features/schedule/scheduleConstants.test.ts` (the population gate), `e2e/schedule-coarse-row-height.spec.ts` — #2997, from `TruePPM - Designer Prototype.html` "Coarse pointers". **A second instance, and the sharper one: #3012 split `HEADER_HEIGHT`.** The same literal `28` meant *two different things* at 19+ sites — "the date ruler band" and "the y where row 0 starts" — and nothing could tell them apart because they were the same number. Inserting the 16px sprint cadence rail between them required half those sites to move and half to stay, and the failure mode of getting the split wrong is invisible: the outline's rows sit a rail-height above the canvas's, every screenshot looks right, and taps open the neighbouring task. So the general form is **one constant, one meaning** — a constant serving two meanings is a latent bug even while the meanings coincide, and the moment they diverge is the moment you find out which sites were which. `CHART_HEADER_HEIGHT` is the live binding (`export let` + `syncCadenceRail`, subscribed by `hooks/useChartHeaderHeight.ts`); `HEADER_HEIGHT` stays a plain const for the ruler's own ink. Three DOM readers had to follow it — `TaskListHeader`'s height, `ScheduleMainArea`'s scroll spacer, and `PreviewOverlay`/`MonteCarloGanttMarkers`' `top` — and a test that pins only ONE height proves nothing here, because rail height 0 is exactly the state where both meanings coincide again: `features/schedule/cadenceRailGeometry.test.tsx` asserts the DOM header, the hit test and the renderer agree **at 0 and at 16**.
