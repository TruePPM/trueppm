# Rule 402 — On the consolidated `#hash`-anchored settings page (ADR-0146), an in-page deep link whose hash equals the …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Signal encoding*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**On the consolidated `#hash`-anchored settings page (ADR-0146), an in-page deep link whose hash equals the current hash WILL NOT SCROLL — the destination section must scroll itself.** `SettingsShell`'s hash effect is guarded once-per-hash-*value* (`lastHandledHashRef`), and nothing rewrites the hash when the user scrolls — only `handleSectionNav` does. So a link from one section to another on the same page works exactly once per page session: the first click lands on a fresh hash and scrolls, and every click after it changes only the search string, early-returns out of the shell's effect, and leaves the viewport where it was **while the destination arms itself off-screen**. That is worse than a dead link — the primary CTA reads as broken while it mutates state the user cannot see. Three obligations. **(a) The section that consumes the deep link calls `scrollIntoView` (or seats focus) from its own arming effect**, deferred a frame so the narrowed rows are laid out first, and targets the `[data-settings-section]` element rather than the widget — `SettingsSection`'s `scroll-mt-6` is what clears the sticky header, and it is on the section. Keep carrying the hash on any param-strip navigate anyway: the shell is still the thing that scrolls on a **cold** load. **(b) A spec that asserts arrival STATE cannot see this.** Filter applied, rows checked, field chosen and params stripped are all true in the broken case; only position is false. The regression test has to (i) use the link, (ii) scroll back to the origin section and assert the destination is `not.toBeInViewport()`, (iii) use the link again, and (iv) assert `toBeInViewport()` — and entering the page via `/settings/<section>` gives a fresh hash, so a spec that only ever clicks once is structurally blind no matter how much state it checks. **(c) The same guard makes the reverse bug possible**: because the effect keys on the hash *value*, a link that varies only its query string can never re-announce or re-scroll, so any per-arrival side effect (a live-region line, a selection seed) belongs on the params, not on the hash. Reference: `features/settings/SettingsShell.tsx` (the `lastHandledHashRef` guard), `features/settings/program/ProgramProjectsPage.tsx` (the arming effect and its scroll), `e2e/program-methodology-align.spec.ts` (the repeat-use case) — #3293, surfaced by `ux-review`. Not covered by rule 317(b), which is about landing on the wrong *block* within a section rather than failing to move at all.
