# Rule 381 — When a terminal status has no surface, widening the PREDICATE is usually the wrong repair — ask which …

> **Invariant.** Indexed from [`packages/web/CLAUDE.md`](../../../packages/web/CLAUDE.md), section *Surface states*. The index carries the rule's headline; this file carries its full text (#3744, ADR-0653 amendment). Binding everywhere, not only on the surface that produced it.

**When a terminal status has no surface, widening the PREDICATE is usually the wrong repair — ask which component should have been READING the status, and check the failure state does not evict the recovery path that is already on screen.** `resolveScheduleSeeding` folded `failed` into `false` alongside `success`, and the obvious fix was a three-state union. It would have been wrong twice over. **(a) The predicate was already right.** A failed apply is a *total rollback* — `apply_template` runs the claim and `materialize_structure` inside one `transaction.atomic()`, every nested write is a savepoint, nothing defers to `on_commit` — so the project really is empty and the live draft row really is the correct affordance. `failed` is genuinely "not seeding". The defect was that `SeedBanner` gated on `status === 'success'`, `ScheduleSeedingState` on the predicate, and **nothing at all** on `failed`; `error_detail` had shipped on the serializer with zero readers in `packages/web`. Widening the union would have grown a new arm on each of its four consumers (`ScheduleMainArea`, `MobileSchedule`, `TaskListPanel`, the ladder ternary) to encode a distinction none of them acts on. **(b) Do not replace a surface that already IS a recovery path.** Of the three routes out of a failed apply — retry, pick another, continue empty — "continue with an empty project" is not an affordance to build: it is the blank canvas underneath, already correct because nothing was written. A full-surface failure state would have *evicted* it and forced a dismiss to reach the thing the user was going to do anyway. So the failure is stated in a banner ABOVE an untouched ladder. A corollary worth taking: mounting it beside `SeedBanner` — above `ScheduleMainArea`'s `isMobile` early return — annotated `MobileSchedule`'s "No items yet" for free, the card whose own comment says it *reads as* "the apply failed" and which until then could not confirm it. **(c) State what did NOT happen; it is usually the most valuable sentence available and the one nobody writes.** "Nothing was written. This project is exactly as empty as it was before" is the fact that turns an alarming blank screen into an ordinary one, and no amount of accurate error reporting substitutes for it. Conversely, offer no undo when the rollback was total — `created_task_ids` is never populated on the failure path, so there is nothing to reverse. **(d) A retry that mints a NEW job id must release every one-shot latch the first one tripped.** `seedTerminalHandledRef` is a ref already fired, and `seedingTimedOut` is sticky state whose effect only restarts a *timer*; swapping the id without resetting both yields a retry that never invalidates on success and, past 60s, never shows the skeleton at all — invisible when wrong, because it looks like it worked and then quietly lands on an empty canvas. **(e) Surface the server's reason VERBATIM, unclamped, with a generic fallback for the empty string** — matching `ImportProgramButton`, `CsvImportWizard`, `ScheduleReconcileStrip` and `exportJobDisplay`. A `line-clamp` on a diagnostic makes it undiagnosable, and redacting to guard against an arbitrary `str(exc)` would suppress the two curated messages that are the actual answer ("Template no longer exists."). Render a dangling `Reason:` prefix never — when the detail is empty the whole line changes, because a prefix with nothing after it reads as a rendering bug. **(f) A control cloned from a sibling surface inherits its LOOK, not its COST — re-derive what dismissing throws away before you copy the `onDismiss`.** This banner's × was `SeedBanner`'s ×, verbatim down to the `onDismiss={() => setSeedApplicationId(null)}` the parent handed both. On the success banner that handler is free: it discards a *summary* of rows still on screen, and disposability is that banner's whole stated design. On the failure banner the identical handler was destructive and unrecoverable — this is the only reader of `error_detail` in the entire web, and the id it needs was stripped one-shot on consume (rule 374(b)), so a reload could not bring it back and nothing on screen said the × was permanent. When two surfaces share a dismiss handler, ask what each one is the *sole copy of*; give the destructive one its own `…Dismissed` flag rather than nulling the shared handle. And put the recovery control BEFORE the dismiss in the DOM: a first tab stop that destroys the surface's payload is the wrong first tab stop. **(g) The retry's own refusal is a DIFFERENT error from the one on screen.** The role can be lost since load, the template deleted between render and click, the project archived meanwhile — none of which the displayed `error_detail` explains, and "Try again" on a 403 or 404 names the one act guaranteed not to help. Route it through `describeWriteRefusal` (rule 372) rather than assuming the standing explanation covers it; "the banner is still mounted" justifies a *generic* toast only for the error it actually describes. Reference: `features/schedule/SeedFailureBanner.tsx`, `features/schedule/ScheduleView.tsx` (`handleSeedRetried`, `seedFailureDismissed`, `resolveScheduleSeeding`), `features/sprints/SprintCloseFailedBanner.tsx` (the shape this copied), `e2e/seeded-landing.spec.ts` — #3348, amending rule 374(c).
