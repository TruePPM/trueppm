# TruePPM Web Frontend — Design Rules

These rules are enforced at review time. Violations block merge.

> ## ⭐ Design System v2 — the golden standard (ADR-0126)
>
> The canonical UI is the **v2 redesign** (`docs/design/v2-golden-standard.md`,
> upstream `design_handoff_trueppm_v2/`). Every new screen, component, fix, and
> feature must conform. Foundation tokens are in `globals.css` + `tailwind.config.ts`;
> conformance is machine-checked by `scripts/check-design-system-v2.sh` (in `make lint`
> / CI). Key invariants beyond the numbered rules below:
> - **Warm-paper canvas:** page backgrounds use `bg-app-canvas` (warm `#F2EEE5`),
>   cards use `bg-neutral-surface` (white) and pop against it. Never a cool-grey or
>   pure-white app canvas.
> - **Sage has two roles (ADR-0126 §3):** `--sage` `#3E8C6D` is the **fill/accent**
>   (with navy or white text); normal-weight **text/border/ring** use
>   `brand-primary` (sage-700, AA). sage-600 is 4.06:1 on white — never body text.
> - **One status vocabulary:** a **dot** = health, a **pill/chip** = state; color is
>   signal only, calm-neutral by default.
> - **Borders over shadows:** `shadow-card`/`shadow-pop` are reserved for
>   popover/drawer/modal/command-palette/toast (see rule 1).
> - **Full Light/Dark/Auto** via the `.dark` token swap on `<html>` — never a dark
>   sidebar on a light app.
> Staged adoption of the remaining surfaces is tracked in epic #1163.

## Foundations

*What every file in `packages/web` obeys.*

9. **No default exports** — all components use named exports

10. **No CSS-in-JS** — Tailwind utility classes only; use `style` prop only for dynamic values (e.g., CSS custom properties, inline widths derived from state)

11. **Stub hooks over mock network** — while real API hooks don't exist, return fixture data from the hook (`src/hooks/`). Components never import from `src/fixtures/` directly.

12. **Responsive breakpoints** (from `tailwind.config.ts`): `xs`=320px, `sm`=375px, `md`=768px, `lg`=1024px, `xl`=1280px, `2xl`=1440px

1. **No drop shadows anywhere** — use `border border-neutral-border` for separation instead of `shadow-*`

299. **Every optimistic edit to a cached *list* goes through `optimisticListUpdate` / `optimisticListAppend` (`src/lib/optimisticCache.ts`) — never `setQueryData(key, [...(previous ?? []), row])` or `(prev ?? []).map/filter` by hand.** A cache entry that is momentarily absent means "not loaded right now", never "this collection is empty". Defaulting it to `[]` and writing the result back replaces a populated list with the single row the user just added — a real race, not a theoretical one: `cancelQueries` is awaited, and a `useProjectWebSocket` collaboration invalidate, an offline reconnect flush, or the mutation's own `onSuccess` can clear the entry inside that window. The helpers skip the updater entirely on a nullish entry *and* read the cache functionally at write time (so an invalidation landing between the snapshot and the write is observed, not overwritten); they still return the snapshot for `onError` rollback. Defaulting a row's own nested field (`t.labels ?? []`) is unrelated and fine. This class was fixed instance-by-instance on the board (#2717) and then found again on six sibling sites (#2862), so it is now machine-checked: the conformance block in `src/lib/optimisticCache.test.ts` source-scans every `setQueryData` call in the tree and fails on a bare identifier defaulted to `[]`/`{}`. Do not hand-enumerate the hooks — hand-enumeration is what let the class survive.

## Accessibility floors

*Non-negotiable minimums. A surface that misses one is not shippable.*

4. **Focus rings on all interactive elements**: `focus-visible:ring-2 focus-visible:ring-brand-primary focus-visible:ring-offset-1`
   - **Standalone-control carve-out (rules 214/261(e)): standalone triggers, menu items/rows, tabs, chips-as-buttons, and dropdown/popover triggers use `focus:` — never `focus-visible:`.** Firefox and desktop Safari do not match `:focus-visible` on pointer-initiated focus of a button, so `focus-visible:` leaves these controls with no visible focus after a click. Write `focus:outline-none focus:ring-2 focus:ring-brand-primary` plus `focus:ring-offset-1` (freestanding) or `focus:ring-inset` (menu rows, tight popover items). Form fields (`input`, `select`, `textarea`, checkboxes whose wrapping label carries a `focus-within:` ring) keep `focus-visible:` — browsers always match `:focus-visible` on editable fields, and a persistent `focus:` ring on a field the user is typing in is noise. The Schedule tree (`features/schedule/`) stays `focus-visible:` deliberately per rule 137. Reference: `features/shell/UserMenu.tsx`, `CreateMenu.tsx`, `NotificationBell.tsx`, `HealthCluster.tsx`, `BottomNav.tsx`; board/sprints/backlog converted in #2042.
   - On a **sage fill** (primary button, `bg-sage-500`): use `focus-visible:ring-navy-700 focus-visible:ring-offset-sage-500` (navy-on-sage 6.8:1) — with `focus:` variants instead when the control falls under the standalone carve-out above.
   - **No dark-mode override needed for `brand-primary` (ADR-0103/0125).** `brand-primary` is mode-aware sage — sage-**700** #316F57 (light, 5.93:1) / sage-400 #66B998 (dark, ≥3:1) — so `ring-brand-primary` passes WCAG 1.4.11 in both modes. (sage-600 #3E8C6D is only 4.06:1 on white — a fill/dot shade, never the foreground/ring token; see rule 143 and ADR-0126 §3.) The old `dark:focus-visible:ring-semantic-on-track` escape hatch (for green #1C6B3A's 2.81:1 dark failure) is **retired** — do not reintroduce it.
   - Never use `outline-none` without a visible replacement

214. **Rail tabs, the "More" trigger, and `MoreSheet` nav rows use `focus:ring-*`, not `focus-visible:ring-*`.** They are standalone tab/menu controls — `focus-visible:` withholds the ring on pointer-driven focus in Firefox/desktop Safari (the ux-review HIGH gate). This is the rule-4/ux-review focus rule applied to the mobile rail; when rebuilding a rail file, convert any pre-existing `focus-visible:` on its controls to `focus:` in the same change rather than carrying it forward. Do NOT reuse the backlog `FOCUS_RING` constant (`features/programs/backlog/styles.ts`) in rail/sheet nav rows — it is `focus-visible:`-based; write `focus:outline-none focus:ring-2 focus:ring-brand-primary focus:ring-inset` inline. Reference: `BottomNav.tsx`, `MoreSheet.tsx`, `bottomNavItems.ts`.

5. **Touch targets** — minimum 44×44px at all breakpoints

6. **Color dots** (8px project color indicators) are always `aria-hidden="true"` — health state must also be conveyed via text or `aria-label`

50. **`text-[10px]` is prohibited** — the design system floor is `text-xs` (12px). Arbitrary size values below 12px bypass the token ladder and introduce WCAG 1.4.3 failures on any surface. Exception: `text-[11px]` is permitted in the global StatusBar only (rule 45 documents the rationale).

87. **`text-neutral-text-disabled` on `bg-neutral-surface-sunken` is prohibited** — this
    combination yields 1.97:1 contrast, failing WCAG 1.4.3 on all text sizes. MINIMAL severity
    labels must use `text-neutral-text-secondary` (#6B6965, 3.12:1 on #EBEBEB) at minimum.
    This prohibition applies everywhere in the app, not only to risk register.
    The disabled token has almost no contrast headroom, so the prohibition extends to **any
    surface darker than `bg-neutral-surface` (#FFFFFF)** — including `-raised`, `-sunken`, and
    any `hover:bg-*` state on a row that contains disabled-token text (the hover state is the
    worst case and the one that must pass AA). Informational text that must stay legible uses
    `text-neutral-text-secondary` as the floor. (Surfaced by ux-review on #590.)

169. **`neutral-text-disabled` is for inert/disabled affordances ONLY — never for readable content.** The token resolves to `#A09D99` (~2.66:1 on white) light / `#64748B` (~3.7:1 on navy) dark — both below the WCAG 1.4.3 AA 4.5:1 floor for normal text. De-emphasized but *readable* content — timestamps, "by {user}" attributions, parenthetical context (the `SprintDailyDeltaPanel` since-hint and burndown `prior → current` context were the #925 ux-review 🔴) — must use `neutral-text-secondary` (4.63:1 light / 7.45:1 dark, passes), and lean on **size/weight** for the quieter visual hierarchy, not a sub-AA color. Reserve `neutral-text-disabled` for genuinely non-interactive/disabled controls where the low contrast *is* the "you can't use this" signal. Corollary (the #925 burndown 🔴): when meaning is carried by an `aria-hidden` glyph + semantic color (an ▲/▼ arrow + green/amber), the accessible name must restate that meaning in words (`aria-label="Remaining work down 8 points — on track"`), not just the raw number — the SR user otherwise loses the polarity a sighted user reads from the arrow/color (1.4.1).

118. **Settings-surface density exception (rules 5, 45, 50).** Pages and components under `features/settings/` use a compact admin density: `text-[11px]` / `text-[10px]` for secondary and label text, and `h-6` / `h-7` controls, are permitted — an explicit override of rules 5, 45, and 50. Rationale: settings is a desktop-admin-first surface, and matching the established Workspace/Project/Program settings density (e.g. `WorkspaceMembersPage`, `ProjectWorkflowPage`) is better UX than per-component rule conformance that would make one page visually inconsistent with its siblings. This exception is **scoped to `features/settings/` only** — it does not apply elsewhere. Two clauses remain non-negotiable inside settings: (a) every interactive control still requires the full rule-4 ring, **in the form rule 4 prescribes for its control type** — `focus:` for standalone triggers, menu rows, tabs, and chips-as-buttons per the rule-214 carve-out (Firefox/desktop Safari withhold `:focus-visible` on pointer-initiated focus regardless of surface, so the density exception covers sizes and text, never ring form), `focus-visible:` for form fields; navigating anchors (`EnterpriseBadge`, doc links) keep `focus-visible:` since a clicked link does not retain focus; (b) a third-party-fidelity preview (e.g. a Slack-message mock) may use the third party's literal palette as product content, exempt from rule 8, but must carry a code comment stating the intent. Modal focus-trap/restore and sub-44px touch targets remain a known codebase-wide a11y gap tracked separately — not introduced by, nor required to be fixed in, settings MRs. The settings density exception floor is `text-[10px]`; `text-[9px]` and below are prohibited everywhere, including settings.

288. **Inside a `useFocusTrap` container, a `tabIndex={-1}` programmatic focus target must never be the first or last element in the trap's *tab* order — seat focus on a real focusable, or give the trap a focusable sentinel before/after it.** `useFocusTrap`'s `FOCUSABLE_SELECTOR` ends in `[tabindex]:not([tabindex="-1"])`, so a `tabIndex={-1}` heading/paragraph/status node is **invisible to the trap**: it is not in `focusables()`, so the `activeElement === first` / `=== last` wrap branches in the Tab handler never fire and the browser's native Tab/Shift+Tab runs unguarded. When such a node is focused and nothing focusable precedes it inside the container, **Shift+Tab walks straight out of the dialog** — the #1776 escape the trap exists to prevent, reintroduced through the front door. The trap's own re-seat effect does not save you: it skips whenever focus is already inside the container, and a target focused later (on a poll reaching a terminal state, on a mutation settling) never re-runs it at all. Rule 224's "focus the heading on mount" pattern is still correct — it is safe in `RouteErrorBoundary` only because that surface's heading sits *after* focusable chrome, which is an accident of that layout, not a property of the pattern. So when copying it: (a) prefer focusing the surface's **primary action** when the outcome has one and needs no reading (this is also the better UX — one keystroke to the next step); (b) when the user must read before acting, focus the `tabIndex={-1}` outcome node **only if** the container renders a focusable ahead of it in DOM order, otherwise the trap has a hole on Shift+Tab; (c) whichever you pick, the target carries a `focus:` ring (never `focus-visible:`, which browsers may withhold on a *scripted* `.focus()` — the rule-204(b)/214 caveat) and never bare `focus:outline-none`, or the sighted keyboard user is left with focus at an invisible location. Verify by tabbing **backwards** from the auto-focused element — a forward-Tab-only check passes on a broken trap. Reference: `components/import/CsvImportWizard.tsx` (result step), `hooks/useFocusTrap.ts`, `components/RouteErrorBoundary.tsx`.

289. **A server-derived advisory signal may be cleared by client state only for the specific item the user acted on — never re-derived, and never allowed to drain a count the server owns.** An "N items need your attention" banner computed from a server field (import mapping confidence, validation severity, sync conflict class) drains as the user works only if each clear is a *fact about that item* the client can know. Two failure modes, both of which ship looking correct: (a) **cross-item staleness** — resolving item A changes the server's verdict on item B (a duplicate claim released, a constraint satisfied), but the client only rewrote A, so B keeps a now-false advisory until the next round-trip; (b) **round-trip laundering** — the client echoes its *whole* current state back as an override on re-validate, so the server marks every item "user-chosen" and returns zero flags, silently converting items the user never reviewed into items they appear to have approved. Send only the fields the user actually changed, keep the server's original verdict alongside any local override so an untouched guess still reads as a guess, and treat a count the server computed as stale-until-refetched rather than recomputing it locally. The tell: an advisory whose whole purpose is "look at these two of eleven" that reports zero after the one action the UI invites. Reference: `components/import/CsvImportWizard.tsx` (`handleFieldChange` / "Re-check mapping"), `hooks/useCsvImport.ts` (`toColumnMap`, `flaggedColumns`).

290. **A fixed-height chrome strip that can grow (a status cluster, a tab rail, a filter row) gets an explicit overflow rule — it scrolls; it never pushes its neighbours — and the rule is the whole contract below, not just `overflow-x: auto`.** A row of `shrink-0` segments with `white-space: nowrap` and no overflow rule does not wrap and does not scroll: it *pushes*, silently, at whatever viewport the user happens to be on, and the thing it pushes is whatever sits next to it (in the shell bar, the breadcrumb, and then the account chip straight off the screen). "It fits today" is not a rule — the first surface to add a segment breaks it, and nobody measures. Seven parts, all load-bearing: (a) **`min-w-0` + `overflow-x-auto`** on the strip, with **`[&>*]:shrink-0`** on its children — without the child rule the flex items compress instead and the overflow never happens, so the strip silently degrades to unreadable segments (the #2208 trap read from the other side); (b) a **`min-w-*` floor** on the strip, because a `min-w-0` box under shrink pressure is driven to *zero* before a rigid neighbour yields a pixel — with no floor the strip vanishes, taking with it the scroll affordance that was supposed to save it; past the floor the neighbour truncates, which is the correct order of sacrifice; (c) **hidden scrollbar** (`[scrollbar-width:none] [&::-webkit-scrollbar]:hidden`) so overflow appearing reserves no gutter and shifts nothing; (d) **both edge fades**, `aria-hidden` + `pointer-events-none`, each rendered only while that side actually overflows — a right-only fade is only correct for a strip that always scrolls from a fixed left origin (the board), and a strip whose offset moves when Tab focuses a segment is not that; (e) **`tabIndex={-1}` chevron nudges as the pointer-only path** — with the scrollbar hidden, a vertical-wheel mouse has *no* way to scroll the strip, so without chevrons a scrolled-out control is unreachable for a large share of desktop users; they are never the keyboard path, which is Tab; (f) **no `tabindex` on the region itself** — axe's `scrollable-region-focusable` is satisfied by focusable children, and a `tabindex` there mints a redundant tab stop; the corollary is that **every child must be focusable**, or the region becomes both unreachable and an axe failure; (g) **motion gated** — `scroll-smooth motion-reduce:scroll-auto` plus `behavior: reducedMotion ? 'auto' : 'smooth'` on the nudge (rule 70: motion only, never function). **Overlay corollary (the rule that bites):** `overflow-x: auto` establishes a clipping context on *both* axes and `z-index` does not defeat it, so **only children whose popovers portal to `document.body` or are `position: fixed` may live inside such a strip** — an in-flow `absolute` panel (the pre-rule-253/260 shape, e.g. `QuickLogTime`, `CreateMenu`) is clipped the moment it opens and must stay outside the scroller. Reference: `features/shell/StatusClusterScroller.tsx` (the implementation), `features/shell/TopBar.tsx` (the scroll/pinned split and the `shrink-[9999]` weight that makes the strip, not the breadcrumb, absorb the squeeze), `features/shell/ShellNavScroller.tsx`, `hooks/useHasScrollRight.ts`.
291. **A "the baseline is already on screen" predicate must also be checked against whether the *derived value* is already on screen — the component that supplies the baseline is usually printing the delta too (#2531).** Rule 284 says a value renders once per surface; this is its inverse, and it is the harder one to see. When a chip or strip decides it may print a bare signed delta *because* some other component supplies the reference point, that reference-supplying component is almost always the same one that already computed and printed the delta — so the predicate that unlocks the terse form is the same fact that makes the whole fragment redundant. The reference failure: added time's `BASELINE_ON_SCREEN_VIEWS = {'schedule'}` qualified Schedule because `ScheduleForecastBar` renders a dashed `CPM: Oct 24` chip, but the chip *beside* it already reads `P80: Nov 4 (+11d)` — from the same `delta_vs_cpm` the premium is derived from — so the one place a bare number was legible was the one place it was already printed, twice on screen at once with nothing marking either as authoritative. Three obligations: (a) **grep the baseline-supplying component for the derived value, not just for the baseline date**, before adding a route to a baseline-on-screen set; (b) when the grep finds it, the correct outcome is to **suppress the new fragment on that route** — not to add a qualifier, and not to suppress the older, page-level rendering, which is the one the user came to that page for; (c) a *popover or drawer* row is not a second render in this sense and may stay, because it is behind a deliberate click and is usually the only carrier of the operational states (`needs estimates`, a stamped stale read) that the page-level rendering structurally cannot express. Corollary: when two surfaces print one server field they must also share **one formatter** — `useForecastPresentation.deltaLabel` emits ASCII `-4d` while `addedTime.deltaLabel` emits U+2212 `−4d`, which is invisible until something puts them in the same row. Reference: `features/shell/addedTimeChip.ts`, `features/schedule/{useForecastPresentation,MobileMonteCarloCard}.tsx`.

## Color and tokens

*Color is a token, never a literal, and a shade carries a role.*

8. **No custom hex colors in components** — always use Design System tokens from `tailwind.config.ts`. The `design-system-v2` gate (`scripts/check-design-system-v2.sh`) ratchets hex **color literals** — a `#hex` that is quoted (`'#f59e0b'`), in a Tailwind arbitrary value (`bg-[#…]`), or a CSS value (`stroke: #fff`). It does **not** count a bare `#1236`-style issue reference in a comment, so cite issue numbers freely — do **not** rewrite them to "issue N" to appease the gate (that was a workaround for an old false positive, now fixed). If the gate fails, you added a real hardcoded color: tokenize it, don't launder the number.

8a. **`--chrome-*` tokens are for fixed UI furniture** (sidebar, Schedule task-list panel, TopBar) that follows the active theme. `--neutral-*` tokens are for page content surfaces. Use `bg-chrome-surface` on shell chrome, `bg-neutral-surface` on content areas. Both adapt with the `.dark` class on `<html>`. In dark mode `--chrome-surface` equals the legacy `gantt-surface` deep navy (#0F1117). Chrome tokens: `surface`, `surface-raised`, `border`, `text-primary`, `text-secondary`, `row-hover`, `row-active`, `grid`.

8b. **`--sem-*-bg` tokens are for badge pill fills and status cards** — `bg-semantic-critical-bg`, `bg-semantic-at-risk-bg`, `bg-semantic-on-track-bg`, `bg-semantic-warning-bg`. These are pre-computed RGBA values so they cannot be combined with Tailwind's opacity modifier. Always pair with the matching full semantic token for text/border (e.g. `border-semantic-at-risk/80 bg-semantic-at-risk-bg text-semantic-at-risk`). **Never substitute `bg-semantic-{state}/N` (the opacity modifier) for `bg-semantic-{state}-bg`** — `/N` applies Tailwind's alpha to the token's RGB channels and will NOT match the pre-computed dark-mode RGBA in `globals.css`, so a `/10` badge fill silently diverges from the design system in dark mode. The `-bg` tokens are the only correct form for semantic badge/pill fills. (Surfaced by ux-review on #691.)

8c. **`.tppm-mono` applies JetBrains Mono with tabular numerals** — use it on every numeric value: KPIs, percentages, dates, durations, counts, build hashes. It is defined as a Tailwind utility in `globals.css` and maps to `font-family: 'JetBrains Mono'; font-feature-settings: "tnum"`.

8d. **`bg-neutral-overlay` is the scrim token for a modal/slide-out's full-screen backdrop** — never a raw `bg-black/N` literal. Like the `--sem-*-bg` family (rule 8b), it is a pre-computed RGBA custom property (`rgba(0, 0, 0, 0.4)` in both light and dark — the scrim doesn't get a dark-mode-specific treatment) and therefore **cannot be combined with Tailwind's `/N` opacity modifier**; write `bg-neutral-overlay` alone, not `bg-neutral-overlay/40`. Popover/edge scrims that intentionally use a different opacity for a lighter touch (e.g. a mobile drawer's `/30` edge, a cheatsheet's `/20`) are a distinct visual role, not this token — `bg-neutral-overlay` is specifically for the `role="dialog" aria-modal="true"` full backdrop. (Surfaced by ux-review follow-up, issue 575.)

286. **A `--sem-*-bg` token may never be the sole background of a floating surface — a portaled, `position:fixed` or `absolute` panel needs an opaque base (`bg-neutral-surface`), with its warning/error tone carried by the border, icon and text (#2447).** The `-bg` family is 8–15% alpha (`--sem-at-risk-bg: rgba(146,64,14,0.10)` light / `rgba(251,146,60,0.15)` dark), which rule 8b already scopes to **badge pill fills and status cards** — surfaces that sit on an opaque parent, where the alpha composites over a known background. A floating surface has no such parent: it composites over whatever page content it happens to overhang, so the rows, digits and chips behind it read straight through the copy. This is not a dark-mode bug — light mode is *worse*, because its alpha is lower (10% vs 15%), so the popover body ends up ~90% transparent over the task list. Two invariants: (a) **the opaque base is `bg-neutral-surface`, not a hand-composited hex** — a pre-multiplied "amber over white" token would bake in an assumption about which surface the panel floats over, and a portaled panel does not know; (b) **the semantic tone survives the swap** because it was never carried by the fill alone — the border (`border-semantic-at-risk`), the `WarningIcon` and the heading/body colour all remain, which is also what keeps colour off the sole-signal path (rule 6). `ScheduleCommitPopover` (`bg-neutral-surface border border-neutral-border`) is the reference every pop surface should already have matched. The trigger *chip* keeps `bg-semantic-at-risk-bg` — an in-flow element on an opaque row is exactly rule 8b's sanctioned use, and only the floating panel changes. Reference: `features/schedule/MissingCommittedStartChip.tsx`, `features/timesheet/TimesheetCell.tsx`.

7. **Health state color encoding**:
   - On-track → `text-semantic-on-track` / `bg-semantic-on-track`
   - At-risk → `text-semantic-at-risk` / `bg-semantic-at-risk`
   - Critical → `text-semantic-critical` / `bg-semantic-critical`
   - Unknown → `text-neutral-text-disabled`

143. **Sage shade discipline (WCAG).** sage-500 `#4FA884` = **fills only**, always with navy text (navy-on-sage 6.8:1); it is ~2.9:1 on white so it is **never** body text, a foreground icon, or a thin border on a light surface. **sage-700 `#316F57` = foreground text / link / ring / border on light (5.93:1)** — this is what `brand-primary` resolves to in light mode. (sage-600 `#3E8C6D` is only **4.06:1** on white — it fails AA for normal text; it is a *fill/dot* weight, e.g. the on-track `-bg` tint, never foreground text.) sage-400 `#66B998` = text/affordance on **dark**. Putting sage-500 or sage-600 on white as foreground text is a 1.4.3 failure — use sage-700. This includes the **wordmark "PPM"**: it is foreground text, so it uses `text-brand-primary` (sage-700), not sage-500 (rule 142; #1689). The **only** sage-500-on-light usages that are legitimate are *fills* (bar/dot/tint fills with navy text, and the `LogoMark` arrowhead).

145. **Semantic amber/red: brand hue is a FILL, on-light text keeps the AA-dark variant.** at-risk fill/dot `#DE9326` but text/border `#92400E`; warning fill/dot `#D97706` (it lives only in `--sem-warning-bg`) but text/border `#854D0E` — yellow-800, ≥5.4:1 on the warning-bg tint; critical fill/dot `#CF4438` but text/border `#B91C1C`. Never set `text-semantic-at-risk`/`text-semantic-warning`/`text-semantic-critical` to the brand hue — those brand values fail AA as text on white (2.4:1 / 2.9:1 / 4.0:1; warning brand `#D97706` as text was only ~2.74:1, the 1.4.3 fail in issue 1377). `#854D0E` is kept deliberately distinct from at-risk's `#92400E` so the two amber states stay separable. on-track `#3E8C6D` and info `#2F6FD1` are AA as text and used directly.

147. **Body ink and dark surfaces are navy.** `--neutral-text-primary` = navy `#1B2A4A` (light) / reversed `#E9EDF3` (dark). Dark surfaces are navy: `--neutral-surface` #15223C, `--chrome-surface` #0E1626. (Canvas bar-label `COLOR.text` stays `#1A1917` — legibility-tuned for bar fills, rule 72; the divergence is intentional.)

144. **Primary actions use the shared `Button` component** (`src/components/Button.tsx`), not ad-hoc `bg-brand-primary` fills. `variant="primary"` is the brand recipe `bg-sage-500 text-navy-900 border-sage-600` (+ sage-400 fill on dark). New primary/secondary/ghost/danger buttons import `Button`; do not hand-roll the fill recipe.

148. **Three type families (brand §06):** `font-display` (Space Grotesk) for display/wordmark/big numbers; `font-sans` (Inter) for UI/body; `.tppm-mono` (JetBrains Mono, rule 8c) for data. Load via the `index.html` Google-Fonts link.

## Signal encoding

*How a value tells the truth about itself — including to someone who cannot see it.*

120. **Health/variance values pair color with a non-color signal (rule-12 reinforcement for rollups).** A health band card shows the band *text* ("At risk") alongside the semantic color and an `aria-label` on any pill; a day-variance shows a signed `+9d` / `-3d` so the sign — not only the color — conveys late-vs-early. Counts and scores are plain numerals. This keeps KPI cards WCAG 1.4.1-compliant without a legend.

119. **A configured-but-not-computable metric renders as a muted card with a reason, never hidden.** When a dashboard or overview is driven by a user-selected metric set (e.g. the program rollup KPIs), a metric the user enabled but for which no value can be computed yet MUST render as a muted card (`border-dashed border-neutral-border`, value `—` in `text-neutral-text-disabled`) with a short plain-language reason in the `sub` slot (e.g. "Needs cost data"). Do not silently drop it from the grid — the user enabled it and must see *why* it is blank. The machine-readable `reason` from the API drives the human label via a lookup map; never render the raw reason code. See `ProgramOverviewPage.tsx`.

161. **A responsive abbreviation must always carry its full accessible name.** When a control shows a short label at narrow widths and the spelled-out term at `md:`+ — the `<span className="hidden md:inline">{full}</span><span className="md:hidden">{abbrev}</span>` pattern established by the Signal-privacy ladder rungs (`SignalLadder.tsx`), the matrix-lens column headers (`SignalMatrixLens.tsx` `<th>`), and any future status/role chip — the **full** term must be the element's `aria-label` (and `title` for hover) so a screen reader or pointer never gets the ambiguous abbreviation regardless of which span is visible. The decorative abbrev/full spans carry no `aria-*`. Where horizontal space always allows (a roomy vertical list, e.g. the raise-ceiling radio options), skip the responsive split and render the full term directly. A single source-of-truth label map pairs the abbreviated and full forms (`AUDIENCE_RUNG_LABEL` / `AUDIENCE_RUNG_LABEL_FULL`); never inline either string.

171. **`aria-label` on a non-widget element (`<p>`/`<div>`/`<span>`) does NOT suppress its descendant text in NVDA/JAWS — to expose a multi-span line as ONE accessible string, mark every visible child `aria-hidden`.** The `BoardSprintHeader` meta line ("{name} · {range} · Day N of M") is the reference: the `<p>` carries the composite `aria-label`, and **all** visible children — the name/range/counter spans AND the `·` separators — are `aria-hidden="true"`, so the screen reader reads only the label, never the label *then* the spans again (the double-read bug the #1138 ux-review caught, WCAG 1.3.1). This applies only to non-widget containers: on a real widget (`button`/`role="radio"`/etc.) `aria-label` does override the accessible name, so this extra step is unneeded there. The alternative pattern — `role="presentation"` on the container + a single `sr-only` span for the composite string — is equivalent; pick one, never leave readable child spans exposed alongside a container `aria-label`.

216. **A status adornment inside a header decides `aria-hidden` vs `role="img"`+`aria-label` by whether its meaning is ALREADY in the header's accessible name — never by "it's a small glyph, hide it".** A header (a board column `<h2>`, a card title, a lane label) that already folds a state into its own `aria-label` — e.g. the column name computed as `` `${label}, ${count} tasks, over limit` `` — must render the *visual* chip for that same state as `aria-hidden` so a screen reader hears it once, not twice (the `WipBreachChip` case, ADR-0130 D2). But an adornment that carries **net-new information not present in the accessible name** must be an announced element (`role="img"` with an `aria-label`, plus a `title` mirroring it), or it silently vanishes for AT users. The `WipTrendArrow` (#1213) is the second case: the recent-trend direction is nowhere in the column's `<h2>` name, so it is `role="img" aria-label="trending up toward WIP limit"` with the visible ▲/▼ glyph `aria-hidden` inside it. Before adding a header glyph, check the header's computed `aria-label`: if the state is in there, `aria-hidden` the glyph; if not, label the glyph. Do NOT make a net-new-info glyph `aria-hidden` (drops it for AT) and do NOT label a redundant glyph (double announce). Direction/trend meaning must also survive color loss (rule: color-not-alone) — the glyph orientation carries it, amber (`text-semantic-at-risk`, AA-as-foreground per the token) marks only the actionable "about to breach" case, everything else is `text-neutral-text-secondary`. Reference: `WipTrendArrow` (labeled, net-new) vs `WipBreachChip` (aria-hidden, redundant) in `features/board/BoardView.tsx`.

220. **A live region (`role="status"` / `role="alert"` / `aria-live`) must not carry a per-tick-updating accessible name — announce discrete state transitions (start / stop / appear), never a running clock or counter; put the ticking value in an `aria-hidden` element and keep the region's name stable.** A live region whose accessible name embeds a value that changes every second (a running timer, an elapsed counter, a live countdown) fails two ways depending on the AT: screen readers that recompute the name re-announce roughly once per second (an announcement flood), and those that key off subtree text announce nothing on the state change that actually matters (start/stop). The region's name must reflect *what changed* (the timer started on task X; it went stale), not *the current value*. Keep the digits in a sibling `aria-hidden` span. Reference: the running-timer chip `TimerChip.tsx` (#1415, ADR-0185 §C) — `role="status"` named `Timer running on {task}` (plus the discrete `— running a long time` stale suffix), with the `formatElapsed` clock rendered in an adjacent `aria-hidden` span; contrast the safe `TaskRunIndicator` whose name changes only on discrete count changes. A non-live control (a plain `<button>`) may hold a ticking label — this rule is specifically about live regions.

255. **Any `line-clamp-*` or `truncate` element that renders user-authored or variable-length data (titles, filenames, comment previews, risk names) must expose the full value via `title` — and via `aria-label` where the clamped line is the sole channel for that value.** Rule 161 already covers truncated *abbreviations*; this extends the same guard to *user data*. A clamped line silently drops text with no hover or assistive-tech recovery, so the full string must live somewhere reachable. The task-drawer Activity timeline's secondary detail line (`features/schedule/ActivityTimeline.tsx`) is the reference: its `line-clamp-1` `<p>` carries `title={secondary}` so a long risk title or filename is recoverable on hover. Do not clamp a value whose full form appears nowhere else in the view without adding `title`.

## Redundancy

*The class whose absence produced #2424, #2425 and #2426.*

284. **A value renders once per surface: the task drawer's summary strip is the READ surface, the sections below it are the EDIT surface, and a value belongs to exactly one of them (#2424).** The #2315 at-a-glance strip landed *on top of* the existing sections rather than replacing their content, so Status, Finish and Float each rendered **twice inside one 270px band** — the strip, then again as a control roughly 150px below. Nothing in the layout said which copy was authoritative, so both read as inputs and whichever one the user did not touch looked stale for a frame; the redesign meant to reduce density doubled it. Four invariants: (a) **anything editable is not in the strip, anything in the strip is not editable there** — Status is a `<select>` below, Finish and Float are in the Schedule grid, so all three left; the strip header carries a `read only` pill so the contract is visible, not just documented. (b) **A read-only value still does not belong in the strip if another surface already carries it** — the drawer header renders the WBS code and `DrawerRecentActivity` sits directly above the strip, so re-rendering either there would trade one duplicate for another; the strip keeps only the owner and the baseline comparison, which are carried nowhere else. This is the rule the design handoff's cell list did not know about, and the general form is worth stating: *before adding a cell to a summary surface, grep the surface for the value.* (c) **`FLAGS` renders only non-empty flag content and returns `null` otherwise** — no header, no "No flags" placeholder, no reserved height. A flag is a condition that is **false for a healthy task** *and* **actionable** (blocked, negative float); float, baseline variance, % complete and SPI are metrics every task has, and a band headed FLAGS that delivers a routine number teaches the reader to skip it, so a genuine exception later will not read as one. Critical-path membership and a missing committed start are deliberately **not** flags here — the Schedule strip carries its own critical banner and the row chip is the primary point-of-fix for an uncommitted start (rule 276), so either would be a third copy. (d) **Float keeps the `computed` qualifier treatment** (rule 276) in the Schedule grid so it never reads as editable, and **negative float turns the cell critical** as well as raising the flag. Reference: `features/schedule/{TaskSummaryStrip,TaskFlagsSection,TaskScheduleStrip}.tsx`.

## Surface states

*Loading, empty, and failed are three different things and must look like it.*

248. **A data surface's loading state is a skeleton ghost that mirrors the shape of the real content, never a bare `Loading…` text line.** Every primary surface (Schedule, Grid, My Work, Overview, Reports, Today, and — since #1774 — Board, Sprints, and the project Backlog) renders pulsing placeholder blocks while its query is in flight, so the layout doesn't jump when data lands. The idiom: one `role="status"` wrapper with an `aria-label="Loading X…"` accessible name (the E2E wait-for-paint gate resolves on this node detaching — gate specs on `getByRole('status', { name: /Loading X/i })`, not on a visible text string), and every ghost child is a `motion-safe:animate-pulse rounded-* bg-neutral-surface-sunken` block marked `aria-hidden="true"`. Mirror the surface's real shape — column ghosts for the Board (a row of lane placeholders), row ghosts for list/table surfaces (Backlog, Grid), card ghosts for card lists (Sprints). `motion-safe:` is mandatory so the pulse honors `prefers-reduced-motion`. Never gate an E2E on the *absence* of a visible "Loading…" string (it reads count-0 before the surface even mounts, racing the assertion); gate on the skeleton's `role="status"` node detaching, which is the true "loading finished" signal. **The rule covers chunk-loading as well as query-loading (#2431).** The route-level `Suspense` fallback is the *first frame of every navigation* — the single most-seen loading state in the app — and it used to be the one place that rendered the bare centred `Loading…` this rule forbids, so a Board navigation opened on ~3s of unstyled text before the (compliant) board skeleton appeared. Both loading states that have no surface shape of their own take the shared `components/LoadingSkeleton.tsx` instead of hand-rolling one: the Suspense fallback and the `/` root-redirect hold use `variant="shell"` (toolbar band + content rows — deliberately generic, because which surface is arriving is exactly what an unresolved chunk does not know), and in-page settings sections use the default `variant="rows"`. **The settings density exception covers ghost *size*, not the skeleton contract** — a settings section still ghosts, just more compactly. Reach for a surface-specific skeleton only when the real content has a distinctive shape worth mirroring. Reference: `components/LoadingSkeleton.tsx`, `router.tsx`, `features/board/BoardView.tsx`, `features/sprints/SprintsView.tsx`, `features/project/backlog/ProductBacklogPage.tsx`, `features/grid/GridView.tsx`.

177. **A primary surface's zero-data state is a warm `EmptyState`, not a bare "No data" line; its single entrance animation is `motion-safe:` only.** The shared `EmptyState` (`components/EmptyState.tsx`) is the v2 anatomy — a `role="status"` block with a decorative (`aria-hidden`) icon in a `72px` `rounded-full border bg-neutral-surface-raised` circle, a `text-[17px] font-semibold` `<h2>` title, optional `max-w-[380px] text-[13px]` orientation copy, and an optional CTA (the shared `<Button>`). Use it for the genuinely cold cases (Schedule read-mode `ScheduleEmptyState`, Risk register, Grid); surfaces with bespoke needs — role-flavored copy or multiple CTAs (`MyWorkEmptyState`, `BuildModeEmptyState`, `EmptyBacklog`) — keep their own component but follow the same anatomy. Pass `className="h-full …"` when the host must fill its area; the icon is always decorative (the `role="status"` + title carry the announcement). **Motion:** the block fades+lifts once via `motion-safe:animate-empty-state-in` (160ms brand ease; keyframe in `globals.css` beside `cmdk-in`) — gated at the class layer so `prefers-reduced-motion` users get the content with no animation (the v2 motion contract: motion only, never content — rule 70). Do not add a second always-on empty-state animation, and never animate content in/out without the `motion-safe:` gate.

246. **A TanStack Query fetch failure on a primary surface renders the shared `QueryErrorState` (`components/QueryErrorState.tsx`), never an empty or perpetual-skeleton state — a dead request must be visually distinct from "nothing here yet".** A page that destructures only `data`/`isLoading` and ignores `error` renders a failed fetch as empty (Board) or a skeleton that never resolves (Overview) — indistinguishable from a genuinely empty or slow surface, which corrupts beta feedback and support triage (#1764). Wire `error`/`isError` into the query hooks and render `QueryErrorState` in place of the empty/skeleton branch. Two variants: **`fill`** (`role="alert"`, `bg-neutral-surface`, `h-full`, centered) for a whole-page/pane failure the user navigated to (Board, Grid, Schedule) — assertive because the surface is dead; **`inline`** (`role="status"`, `rounded-card border-neutral-border bg-neutral-surface-raised`, `min-h-24` to match the skeleton footprint it replaces) for a single widget on a still-working page (each Overview widget) — polite, so a total outage does not fire N assertive announcements that interrupt each other. Retry defaults to `window.location.reload()`; pass a query `refetch` (`onRetry={() => void refetch()}`) when the hook exposes one so retry re-runs just the failed request. Copy is one terse `Couldn't load <X>.` per surface. This completes the surface-state trio with `EmptyState` (rule 177, `role="status"`, calm zero-data) and the route `errorElement` (rule 224, `role="alert"`, self-focuses on a render-throw): widget fetch error → polite in-place; empty data → calm; route throw → assertive-and-self-focusing. Reference: `components/QueryErrorState.tsx`, `features/board/BoardView.tsx`, `features/project/ProjectOverviewPage.tsx`.

224. **A route-level error surface (`errorElement`) that offers recovery actions must move focus to its heading on mount — the erroring subtree unmounted, dropping focus to `document.body`, so keyboard/AT users otherwise cannot reach the recovery CTAs.** When a route subtree throws (or a lazy chunk fails to load) React Router swaps it for the route's `errorElement`; the element that had focus (the `NavLink` the user just clicked, a button) unmounts, so focus falls back to `<body>`. An error surface whose whole point is recovery (Reload / Go to home) must pull focus to itself in a mount `useEffect` — a `tabIndex={-1}` `<h2>` with a `focus:` ring (**not** `focus-visible:`, which a browser may withhold on a *scripted* `.focus()` — the rule-204(b) / rule-214 caveat) — or the keyboard/screen-reader user has to blind-Tab from `body` to reach the only actions on the page. This is the inverse of the calm `EmptyState` (rule 177), which is a zero-data view with no required action and therefore does **not** grab focus; an `errorElement` is `role="alert"` (assertive, an error the user landed in) and self-focuses, whereas `EmptyState` is `role="status"` (polite) and does not. Reference: `components/RouteErrorBoundary.tsx` (the `headingRef` mount-focus + `isChunkLoadError` chunk-vs-generic copy split), wired as `errorElement` at the route-tree root, on `ProjectShell`/`ProgramShell`, and — since #2834 — on every shell child via `shellRoutes()` (rule 298).

298. **A route boundary is inherited, never opted into: every child of the `AppShell` route gets its `errorElement` from `shellRoutes()` in `router.tsx`, and a recovery action that leaves the document asks the write queue itself before discarding it.** Issue 1654 added the shell-preserving `errorElement` by hand to `projects/:projectId` and `programs/:programId`; every route added afterwards (My Work, My Assets, Timesheet, the notification inbox, `me/settings/*`, the org resource catalog, the programs list) silently missed it, because omission was the default and protection the exception (#2834). Without a boundary *below* the shell, a render throw or a failed lazy chunk bubbles to the `RequireAuth` net and unmounts `AppShell` — which takes `PendingWritesGuard` with it, so the `beforeunload` warning that is the only thing protecting TanStack Query's **in-memory** write queue is gone on the very screen whose job is to offer a reload. Two consequences, both load-bearing: **(a)** add new shell routes *inside* the `shellRoutes([...])` call and do not paste an `errorElement` of your own unless you genuinely want a closer boundary (a nested shell like `ProjectShell` is a legitimate one — the helper keeps any `errorElement` a route already declares); **(b)** any recovery affordance that reloads or hard-navigates reads `getPendingWriteCount()` at click time and interrupts with a focus-trapped `role="alertdialog"` naming the count, because the guard it would otherwise rely on may already have been unmounted by the same crash. Read the count imperatively, not with a hook — the boundary can render *outside* the `QueryClientProvider`, which `AppShell` owns. The enumeration test in `src/router.test.tsx` is the regression guard: it fails if any shell child lacks a boundary, which is the only thing that stops this from recurring. Reference: `router.tsx` (`shellRoutes`), `components/RouteErrorBoundary.tsx` (`DiscardPendingWritesDialog`), `hooks/useSyncStatus.ts` (`getPendingWriteCount`), `src/router.test.tsx`.

## Motion

*Motion is never content.*

70. **`prefers-reduced-motion` is evaluated at engine init and on media query change.**
    When true: disable the today-line pulse, CP-flip animation, preview-bar fade,
    scroll-to-date smooth behavior. Functionality is never disabled — only motion.

181. **All transform/overlay motion uses the shared `ease-brand` + a named `duration-*` token, and the four entrance keyframes live in `globals.css` and are applied under `motion-safe:` — never hand-rolled per call site, never ungated.** The v2 motion layer is centralized so it stays consistent and honors the motion contract (rule 70: motion only, never content).
    - **Tokens (`tailwind.config.ts`):** `ease-brand` = `cubic-bezier(.2,.7,.2,1)` is the standard easing for every transform/overlay transition; durations are the named `duration-fast` / `duration-base` / `duration-slow` (120 / 200 / 320ms, aliasing `--dur-1/2/3`). Do not hard-code `duration-150`/`duration-200` or rely on Tailwind's default ease for v2 surfaces. The `checkpop` spring is the one exception — it uses the overshoot ease `cubic-bezier(.34,1.56,.64,1)` for its 1.22 bounce, baked into the keyframe.
    - **Keyframes (`globals.css` `@layer utilities`, beside `cmdk-in`/`empty-state-in`):** `checkpop` (220ms, task-complete spring), `toast-rise` (240ms, global toast entrance), `modal-scale-in` (180ms, dialog/modal panel), `save-bar-slide` (220ms, docked save bar). Each has a paired `.animate-*` class applied at the call site under `motion-safe:` — the keyframe itself carries no `@media` guard (the gate is at the class layer, matching the established pattern). Do not add the dead `tailwindcss-animate` utilities (`animate-in`/`fade-in`); they emit no CSS.
    - **Micro-interactions:** the shared `<Button>` presses via `motion-safe:active:translate-y-px`; interactive cards (`ProgramCard`, `BoardCard`) lift via `motion-safe:hover:-translate-y-px`. **No shadow on the lift** (rule 1) — the card's own border (or a `hover:border-*` emphasis on a single-state border) supplies the depth cue the prototype's hover shadow would have; on a card whose border is state-driven (e.g. `BoardCard`'s critical/dashed border) use translate-only so the lift never overrides the state border. `shadow-pop` remains allowed only on true pop surfaces (toast/popover/drawer/modal/command palette — rule 1's standing exception).
    - **Coexisting transitions:** when a transform animation must share an element with an existing color/opacity transition, use ONE multi-property declaration (`transition`, or `transition-[opacity,transform]`) — never stack `transition-transform` on top of `transition-colors`/`transition-opacity`, which collide on `transition-property` (the later one in the cascade silently wins and drops the other).

## Controls and composition

*Reach for the shared primitive before writing a new one.*

179. **A segmented control (`role="radiogroup"` of `role="radio"` buttons) must fill the active segment with a token that contrasts against its container surface — never the same surface token the control sits on — and selection is conveyed by fill, not text color alone.** Active = `bg-brand-primary text-neutral-text-inverse`; inactive = `bg-neutral-surface text-neutral-text-secondary hover:bg-neutral-surface-raised` (visually distinct from the active fill). The failure this prevents: a toolbar segmented control filling the active segment with `bg-neutral-surface-raised` while sitting *on* a `surface-raised` toolbar renders zero fill contrast, leaving text shade as the only selection signal (WCAG 1.4.1). Roving tabindex (`tabIndex={selected ? 0 : -1}`), Arrow (wrapping) + Home/End key handling **bound to the focusable radios** (not the non-focusable group, per `jsx-a11y/interactive-supports-focus`), and the rule-4 focus ring (no dark-mode override — `brand-primary` is mode-aware sage, rules 4/137; the old `dark:focus-visible:ring-semantic-on-track` override is **retired**, do not reintroduce it) are mandatory; the selection commits immediately on move. Reference implementations: `features/schedule/ScheduleToolbarToggle.tsx` (single pressed/unpressed) and `features/schedule/ScheduleViewModeToggle.tsx` (multi-option Grid↔Timeline). Pattern also in use: `RetentionPurgePage`, `CalmToolbar`.

183. **App-wide confirmations use the global `toast()` API + the single `ToastHost`; board-local transient notices stay in `BoardDropNotice` (rule 170).** The toast system (`components/Toast/`) is a Zustand store (`toastStore`, pure — auto-dismiss timing lives in the host) + an imperative `toast.success/info/error/warm(message, durationMs?)` API callable from anywhere (mutation `onSuccess`, event handlers, plain modules — it reads the store via `getState()`, no hook) + ONE `ToastHost` mounted once in `AppShell`. The host is a bottom-center stack of inverse **ink pills** (`bg-neutral-text-primary text-neutral-text-inverse`, always high-contrast against the canvas in both themes), each rising in via `motion-safe:animate-toast-rise` (rule 181) with a decorative sage `✓` on success/info (`aria-hidden` — the message text carries the announcement), auto-dismissing after `durationMs` (default ~2.6s). The wrap is `role="status" aria-live="polite" pointer-events-none` so toasts are announced without stealing focus and never block the UI beneath; individual pills re-enable pointer events. `shadow-pop` is allowed (a toast is a pop surface — rule 1's standing exception). **Fire it only for genuinely app-wide events** (task created/completed/saved, pin/unpin, theme); do NOT route board-local pending-state notices here — rule 170 keeps `BoardDropNotice` board-scoped, neutral-toned, and off the global toast library.

250. **Menu/panel group headers (eyebrows) use one canonical recipe: `text-xs font-semibold uppercase tracking-[.06em] text-neutral-text-secondary`; inside a `role="menu"` or dialog, wrap the grouped rows in a `role="group"` labeled "like the header" (`aria-label` or `aria-labelledby`), with the visible header div `aria-hidden`.** The tree had grown ≥4 competing eyebrow treatments (`text-[11px] tracking-[.08em]`, `text-[11px] tracking-wide`, `tracking-widest`, …); `text-xs` is the rule-50 floor, so it is the canonical size — do not mint new size/tracking combos. `role="group"` is a permitted owned element of `role="menu"` and is transparent to `useFocusTrap` (descendant selector) and to Escape/outside-click handling. Reference: `features/shell/UserMenu.tsx` ("Personal" group).

253. **A neutral read-state chip may become a tap-to-explain disclosure, but the disclosure must stay neutral, grant no capability, and portal out of any clipping scroll container.** `PendingAcceptanceChip` (`features/board/PendingAcceptanceChip.tsx`) is the reference: pass an optional `explainer` string and the chip renders a real `<button aria-expanded aria-controls>` toggling a `role="note"` popover with one plain-language sentence + a **neutral** "Got it" close button; omit `explainer` and it stays the passive read-state `<span>` (rule 149) with no disclosure state mounted (a hook-free early return, so read-only surfaces keep the passivity contract — no `button` in the tree). Five invariants: (a) **tone** — trigger, popover, and close button use neutral tokens only (`bg-neutral-surface-sunken`/`surface-raised`, `text-neutral-*`, `border-neutral-border`, `shadow-pop`); do **not** reach for the shared `Button` `ghost` variant, which is sage-brand-toned (`text-brand-primary`) and violates rule 149 — hand-roll a neutral ghost. (b) **No capability** — the popover explains only; it never gains accept/reject/any-mutation control (the decision stays team-owned on role-gated planning surfaces, rule 144), and the close button uses dismissal copy ("Got it"), never an action verb; the acknowledge is ephemeral (close-only, no persistence, no API) because the read-state is server-owned and clears on accept/reject (ADR-0102). (c) **Disclosure a11y** — Escape and "Got it" both close **and** return focus to the trigger; click-outside closes without stealing focus (check the trigger **and** the portaled popover, which is no longer a DOM descendant of the wrapper); `stopPropagation` on pointerdown+click so opening never drags/selects/opens the host card; `before:inset-[-12px]` for a ≥44px hit target; rule-4 `focus-visible` ring. (d) **Escape the clip** — the chip lives in a board column whose card stack is `overflow-y-auto` and can be as narrow as 208px (narrower than the popover); an in-flow `absolute` popover would be clipped and `z-index` does **not** defeat an overflow-clipping ancestor, so **portal the popover to `document.body`** with `position: fixed`, position it from the trigger's `getBoundingClientRect()` (flip above when there's no room below, clamp horizontally to the viewport), and **close on scroll/resize** since a fixed popover can't track its anchor (pattern: `features/schedule/UnscheduledTaskRow.tsx`). Portaling also sidesteps the `<p>` phrasing constraint on My Work — the wrapper/trigger stay `<span>`/`<button>` (phrasing content) inside the paragraph while the popover renders out in the body. (e) **Copy** — built by `pendingAcceptanceExplainer(iterationLabelLower?)`: role-neutral ("someone on the team accepts it", never "your Scrum Master" — acceptance authority is any Admin/SM/PO holder), outcome-only (no state-machine jargon like "scope injection"), iteration-label-aware on the board (`itl.lower`) and generic on cross-project My Work. Reference: `features/board/PendingAcceptanceChip.tsx`, `features/board/BoardCard.tsx`, `features/me/MyWorkTaskRow.tsx`.

260. **A floating popover / menu / listbox that must escape a clipping ancestor (an `overflow-hidden` card, an `overflow-y-auto` scroll panel) or stay on a narrow viewport uses the shared `useAnchoredPopover` hook (`hooks/useAnchoredPopover.ts`) as its positioning + dismissal engine — do not hand-roll the `getBoundingClientRect` → `position:fixed` → flip-above → clamp → scroll(capture)/resize → outside-`pointerdown` math inline.** This names the *implementation* of web-rule 253, which remains the *specification* of those mechanics; the two are complementary (a new site could "follow 253" and still re-introduce a clip/flip bug by hand-rolling the math). The hook owns exactly four concerns: portal-`fixed` positioning, flip-above, horizontal/width clamp (to the viewport, replacing any `max-w-[calc(100vw-…)]`), and outside-`pointerdown` dismiss spanning the trigger + the portaled panel (once portaled they are no longer DOM-nested, so a single `containerRef.contains` check treats panel clicks as "outside"). The **call site keeps** its own contents, keyboard model (`aria-activedescendant` roving, two-stage Escape), open-state ownership, and focus-return — the hook deliberately does NOT handle Escape (a duplicate document listener double-fires — the rule-204 lesson). Usage: pass `open`, `width` (`number` | `'trigger'` to match the anchor), `estimatedHeight` (flip heuristic only), and optional `align` / `gap` / `margin` / `onDismiss` (omit `onDismiss` to keep a site's own `onBlur` dismissal); attach `triggerRef` to the anchor and `popoverRef` to the panel; render `open && popoverStyle && createPortal(<panel ref={popoverRef} style={popoverStyle} className="z-50 …" />, document.body)`. The hook returns a non-null off-screen `popoverStyle` immediately when `open` (real coords are measured in `useLayoutEffect` before paint), so the portal mounts in the **same** commit — required for a panel that focuses its own input on open (comboboxes). **A `role="menu"` with focusable items MUST move focus into the menu on open** (`popoverRef.current?.querySelector('[role="menuitem"]')?.focus()` in a `[open]` effect) and rove with Arrow/Home/End + close on Tab/Escape returning focus to the trigger — portaling removes the items from natural tab order, so without this a keyboard user cannot reach them. The two original inline implementations — `features/board/PendingAcceptanceChip.tsx` and `features/schedule/UnscheduledTaskRow.tsx` — are **grandfathered reference specs** (do not rewrite them onto the hook); every new call site uses the hook. Reference: `hooks/useAnchoredPopover.ts`, `components/EntitySelectCombobox.tsx`, `features/settings/SettingsContextSwitcher.tsx`, `features/settings/members/InviteForm.tsx`, `features/settings/program/ProgramCadencePage.tsx`.

287. **Any abbreviation, code, percentile, or icon-only control ships with a plain-English explanation reachable by hover AND keyboard focus AND touch — via the shared `Tooltip` (`components/Tooltip.tsx`), never a bare `title` and never a `group-hover` class (#2389).** The bug class this closes is an *inversion*, not an omission: the codebase repeatedly added an `aria-label` to satisfy WCAG 1.4.1 and stopped, so a screen-reader user heard "Waterfall workspace" and a sighted mouse user got two undecodable letters (`MethodologyIndicator`'s `WF` chip was the trigger case; `SyncStatusBadge`, the `CP` float suffix, and the Monte Carlo row were the same shape). Whenever you write an `aria-label` for a token whose visible form is shorthand, ask what the *sighted* user sees — if the answer is "the shorthand", the job is half done. Seven invariants: (a) **three input paths** — `mouseenter`, focus, and tap; `group-hover` never fires on a touch device and `title` is invisible to keyboard focus, unreachable on touch, ~1s delayed, and unstyleable (rules 22a/121/166/222), so neither satisfies this rule alone. (b) **text only** — `content` is typed `string`; the moment it needs a link or a control it is a `FieldHelp`-style non-modal `role="dialog"` instead (rule 263), because an `aria-describedby` target's link is unreachable (rule 121). (c) **`describe={false}` when the content restates the trigger's own `aria-label`** — the panel then renders `aria-hidden` so AT hears the sentence once; wiring `aria-describedby` to a duplicate of the accessible name is a double announcement, not extra help. Corollary for tests: an `aria-hidden` panel is out of the accessibility tree, so assert it with `page.locator('[role="tooltip"]')`, not `getByRole('tooltip')`. (d) **never the sole carrier of meaning** — it supplements the accessible name, it does not replace it. (e) **positioning is delegated to `useAnchoredPopover`** (rule 260) and the panel is portaled (rule 253) — no hand-rolled flip/clamp math. (f) **Escape peels one layer** — capture-phase `document` listener + `stopPropagation()`, so a tooltip open inside a modal dismisses without closing the modal (the rule-263f pattern). (g) **keyboard-vs-pointer focus is decided by pointer recency, NOT `:focus-visible`** — jsdom answers `false` to `element.matches(':focus-visible')` under every condition, so a `:focus-visible` guard silently kills the keyboard path while the unit suite stays green; `Tooltip` records the last `pointerdown` and treats a focus within 300ms of one as pointer-driven. Do not "simplify" it back to the pseudo-class. Shared strings live in `lib/abbreviations.ts` and `lib/percentileExplanation.ts` so the same token never acquires two different definitions on two surfaces. Exemption worth knowing: a decorative `aria-hidden` header row (`OutlineMode`'s column strip) must NOT get a tooltip — the trigger is a tab stop, and a tab stop inside an `aria-hidden` subtree is its own violation. Reference: `components/Tooltip.tsx`, `features/shell/MethodologyIndicator.tsx`, `features/schedule/MonteCarloTimeline.tsx`.

273. **`AppShell` renders the single `<main id="main-content">` landmark — a feature page, panel, or state-branch (loading/error/empty) rendered inside the shell must NOT emit its own `<main>`; use a labeled `<section aria-label>` (or a `<div>` when it already owns a `role`).** The skip-link (`#main-content`) and "jump to main content" both target AppShell's one main; a second `<main>` nested inside it is invalid HTML and makes the SR "jump to main" ambiguous. This recurs at the page root and, easy to miss, in early-return branches (a page with a `<main aria-busy>` loading state, a `<main role="alert">` error state, and a `<main aria-label>` success state is **three** nested mains, not one). The batch that established this rule demoted five pages / eight tags (`MyWorkPage`, `SprintsView` ×2, `PersonalAccessTokensPage`, `MyGeneralPreferencesPage`, `ConnectedAccountsPage` ×3). Grep before adding any page-level wrapper: `grep -rn "<main" packages/web/src/features/` — the only legitimate matches are `AppShell.tsx` (the shell's one main) and the standalone **public share pages** (`PublicScheduleSharePage`, `PublicBoardSharePage`), which render *outside* AppShell (no auth, no shell) and therefore own their page's sole `<main>`. Keep the element's existing `aria-label`/`aria-busy`/`role` when demoting (`<main aria-label="X">` → `<section aria-label="X">`; `<main role="alert">` → `<div role="alert">`). Corollary — the authed catch-all 404 renders **inside** AppShell (`path: '*'` as a child of the `/` AppShell route), not as a shell-less sibling, so an unknown URL keeps the sidebar, TopBar, and ⌘K palette; the `NotFoundPage` reuses the `RouteErrorBoundary` anatomy (`role="alert"`, `tabIndex={-1}` heading self-focused on mount per rule 224, `focus:` not `focus-visible:`) and offers client-side "Go to My Work" / "Go to home" recovery — never a dead-end with nothing focusable. Reference: `components/NotFoundPage.tsx`, `features/shell/AppShell.tsx`, `router.tsx` (dual `path: '*'`).

## Dialogs, focus and keyboard

*Where focus goes, and what commits.*

217. **Every dialog/drawer/modal/panel that edits existing information or collects new information presents an explicit, consistent commit/discard affordance — Save (primary) + Cancel (secondary), Save disabled until dirty, a Cancel that reverts to the original values, and an unsaved-changes guard on any dirty dismiss — composed from the shared `@/components/dialog` primitives, never re-decided per surface.** The contract (issue #1361, generalizing web-rule 164 from the backlog drawers to all editable surfaces):
    - **Save is disabled until the form is dirty** (a field actually changed vs. the last-saved snapshot) and re-disabled after a successful save. Dirty is a structural `JSON.stringify(draft) !== JSON.stringify(baseline)` compare of flat scalars.
    - **Cancel discards pending edits and restores the baseline** — it never mutates.
    - **Dismissing while dirty** (Esc, scrim/backdrop click, close ✕) opens the **unsaved-changes guard** (`role="alertdialog"`, focus-trapped, default focus on the safe "Keep editing") instead of silently committing OR silently discarding. A clean dismiss closes immediately with no prompt.
    - Compose these, do not hand-roll them: **`useDirtyDraft<T>(initial)`** owns draft/baseline/dirty + `reset()` (Cancel) + `commit()` (post-save re-snapshot); **`useUnsavedChangesGuard({ dirty, onClose })`** owns the close-vs-guard decision, the guard's open state, and the document Escape listener; **`DialogFooter`** renders the Save/Cancel bar (shared `Button` primitive, ghost Cancel + primary Save, the muted "Unsaved changes" status, an inline `role="alert"` for validation/save errors); **`UnsavedChangesDialog`** is the discard prompt. Two valid compositions: a **deferred drawer** mounts `{dirty && <DialogFooter/>}` so the bar appears only while dirty (backlog drawers, rule 164); an **always-on modal** renders the footer for its whole lifetime and passes `dirty` so Save stays inert until a change. Reference implementations: `EpicDetailDrawer.tsx`, `StoryDetailDrawer.tsx`.
    - **Instant-toggle carve-out (must be visually distinct, never batched behind a Save bar):** a single non-destructive control whose change *is* the action — a lone switch/checkbox that optimistically PATCHes on toggle, a child-collection row on its own flat endpoint (acceptance criteria), a server-gated semantic toggle the surface reflects live (Definition of Ready). These commit immediately and correctly have **no** Save/Cancel/guard, because there is nothing staged to lose. The line: *does a dismiss risk losing staged edits?* If yes → the surface needs the footer + guard; if the change already persisted on interaction → it is an instant toggle and is exempt. Never give an instant toggle a Save bar (implies a batch that isn't there), and never let a surface that stages multiple scalar edits commit-on-dismiss without a guard.
    - **Settings pages are the shell-scoped specialization:** inside `/settings` the equivalent contract is provided by `useDirtyForm` → `useSettingsSaveStore` → the `SettingsShell` save bar + its own `ConfirmDiscardDialog` (rule 115). Settings forms use *that* mechanism, not `@/components/dialog`; the two are parallel implementations of the same rule for different mount contexts.
    - **The Schedule `TaskDetailDrawer` is on this contract for its own scalar columns (#1977).** Its **name** and **description** stage in a `useDirtyDraft` and batch into one `PATCH /tasks/{id}/` behind the shared `DialogFooter`, with the `UnsavedChangesDialog` guard on Esc / close ✕ / backdrop and on Expand (Discard navigates to the full page). There is **no auto-flush** — the old #962 "B-lite" flush-on-blur/tab-switch/close was replaced; blur returns the Markdown field to read mode but never saves, and switching tabs keeps the draft intact. The name and description stage inline; the **three-point estimate** (O/M/P) also stages into the *same* draft (#1985) — but it renders through the `EstimatesSection` registry section, so it receives its draft slice via the **`TaskDraftContext`** binding (ADR-0439), NOT through `DrawerSectionProps` (which stays frozen for Enterprise). A section binds only when `binding.taskId` matches its own task; absent the binding (the full-page `TaskDetailPage`, no Save bar) it falls back to immediate blur-PATCH. Everything else stays immediate as the instant-toggle / relational carve-out above: **STATUS** (single-select whose change is the action; also commits via board drag), **PROGRESS** (direct-manipulation slider, commits on release), **ASSIGNEES** / **LABELS** (relational controls with their own mutations), sprint **Remaining (pts)** (sprint-scoped, active-gated), the **DURATION** cell in the schedule vitals strip (`TaskScheduleStrip`, #2106/ADR-0515 — a deliberate instant-commit scalar, NOT staged: it PATCHes `duration` immediately via `useUpdateTask` because Start/Finish/Float are server-computed by CPM and only meaningful *after* the recompute, so a staged duration would leave the strip's other three cells stale; it honors the ADR-0151 recalc-% policy and never joins `ScalarDraft`/`buildScalarPatch`), and every other registry section — dependencies, sprint, blocker, recurrence, comments, attachments — which self-mutate through their own endpoints. The three estimate keys diff into the one PATCH via a shared `buildScalarPatch` used by Save, the #1978 "Save & open" swap verb, AND Cmd/Ctrl+S so no path drops an estimate edit; an out-of-order complete triple (`optimistic ≤ most_likely ≤ pessimistic`, server-enforced #1982) sets `DialogFooter` `saveDisabled` + a validation message so the drawer never Saves-then-400s. The bar's `statusText` names the changed fields, collapsing O/M/P to one **"Estimates"** token ("Unsaved changes: Name, Estimates") while each changed field carries its own `aria-hidden` **`UnsavedDot`** "•" (the shared marker, `@/components/dialog`); a visually-hidden `role="status"` region announces the same for AT. PERT E/σ recomputes from the **draft** live, suppressing σ to `±—` with a non-blocking ordering hint while the triple is out of order; velocity **Accept/Dismiss** is disabled while the estimate draft is dirty (and re-baselines Most Likely via `useDirtyDraft.commitField` on a clean accept). `Cmd/Ctrl+S` saves when dirty. The desktop container is a true non-modal inspector (rule 264, ADR-0437).

206. **A dialog that declares `role="dialog"`/`role="alertdialog"` + `aria-modal="true"` MUST trap focus itself (`useFocusTrap`) — you cannot clone a confirm dialog that relied on a parent modal for focus containment into a standalone/bare mount and keep `aria-modal` honest.** The board's `DeleteConfirmDialog` has no internal trap because it is always nested inside `TaskFormModal`, which contains focus. `EpicDeleteConfirmDialog` (#1339) was cloned from it but is mounted **bare** on the Product Backlog page (rendered by `EpicHeader`, no outer modal), so without a trap Tab/Shift-Tab walks straight out behind the scrim — violating the `aria-modal` contract (WCAG 2.4.3 / 2.1.2). The fix is the house hook: `const ref = useFocusTrap<HTMLDivElement>(true, onCancel)` on the **panel** (not the scrim) — it autofocuses the first focusable (which, for a destructive dialog, must be **Cancel**, never the destructive button — so order Cancel before Delete in the DOM), wraps Tab, and routes Escape to the close handler (do NOT also add a separate `document` Escape listener — it double-fires, the rule-204 lesson). Pair this with **focus restoration**: the surface that opened the dialog (e.g. the epic kebab) must return focus to its trigger on close — for a trigger that unmounts while the action is open (the kebab is hidden during rename), restore via an effect keyed on the open/close state, not a direct `.focus()` in the close handler. Reference: `EpicDeleteConfirmDialog.tsx`, the `restoreFocusRef` effect in `EpicHeader.tsx`, `useFocusTrap`.

245. **A dialog that stays open while its content swaps state passes that state as `useFocusTrap`'s `focusKey`; a confirm dialog nested inside a modal whose parent trap yields must run its own `useFocusTrap` — never ship a modal surface where Tab can reach the background page (WCAG 2.4.3 / 2.1.2).** Two failure shapes, one hook. (a) **Multi-state dialogs**: `useFocusTrap(active, onEscape)` seats initial focus only when `active` toggles, so a wizard/phase dialog (ImportModal's picking → uploading → success/error, PromoteMilestoneDialog's conflict ↔ form) drops focus to `<body>` when the phase unmounts the focused control — and Tab then escapes the "modal." Pass the phase/mode as the third `focusKey` param; the trap re-seats on change (first focusable, else the container — give the container `tabIndex={-1}` so a control-less phase like a progress screen still has a seat), skips the re-seat when focus is still inside (so swaps that keep the focused control mounted don't yank it), re-seats off the container itself once controls reappear, and still restores the *activation-time* trigger on close. A consumer wanting a nicer target than "first focusable" keeps a small `useEffect` focusing its preferred ref *after* the hook (call order = effect order), like PromoteMilestoneDialog's first-form-field seat. Do **not** hand-roll trap/Escape/restore logic in a component — convert it to the hook. (b) **Nested confirm dialogs**: a parent modal that disables its trap while a child `alertdialog` is open (TaskFormModal's `!showDeleteConfirm && !showDiscardConfirm` gate) is only safe if **every** such child runs its own `useFocusTrap` — an untrapped child (the old DeleteConfirmDialog: autofocus + Escape only) leaves Tab free to tunnel into the background form. Order the child's buttons so the safe action is the first focusable (the trap's default seat) — destructive actions never autofocus the destructive button. Reference: `hooks/useFocusTrap.ts` (`focusKey`), `components/import/ImportModal.tsx`, `features/sprints/PromoteMilestoneDialog.tsx`, `features/board/TaskFormModal/DeleteConfirmDialog.tsx` vs `features/settings/components/ConfirmDiscardDialog.tsx`.

167. **A roving-`tabindex` group (`role="radiogroup"`/`"tablist"`) MUST move DOM focus on arrow keys, and arrow navigation MUST NOT commit a side-effect — only activation (click / Enter / Space) commits.** `PulseRadioGroup` in `TeamHealthPulse.tsx` is the reference: it holds a `focusIdx` + a `btnRefs` array; arrow keys advance `focusIdx` and call `btnRefs.current[next]?.focus()` (real focus movement — setting `aria-checked`/`tabIndex` alone strands the user on a now-untabbable element, WCAG 2.1.1), and they do **not** call the commit handler. The native `<button role="radio">` commits via `onClick` (which fires on Enter/Space too). The bug this prevents: routing arrow keys through the same `onPick`→mutate path as click, so a keyboard user scanning 1→5 silently records four throwaway answers — and for the pulse, those pollute the privacy-sensitive team aggregate (the #923 ux-review 🔴). Only the focused option is tabbable (`tabIndex={i === focusIdx ? 0 : -1}`); the group is reached by Tab, navigated by arrows, committed by activation. This applies to **every** `role="radiogroup"`/`"tablist"` built from native buttons — including single-select **filter-segment** controls (e.g. the Risk register's All/High/Unmitigated/Mine segment, `RiskSegmentedFilter.tsx`). A facet filter is a radiogroup and MUST use the roving-tabindex + arrow-focus pattern, not N independent tab stops — even when the committed action is non-destructive (a filter), arrow keys move focus only and activation applies it.

280. **A roving-tabindex list must move DOM focus only when a *keyboard path* asked for it — never as a side effect of the list changing.** The natural shape, `useEffect(() => optionRefs.current[activeIndex]?.focus(), [activeIndex, items.length])`, is a focus thief: any re-render that changes the list length also re-runs it, so a search field *above* the list loses focus after the first keystroke and every subsequent character is swallowed by the list's own type-ahead. The symptom is a search box that only ever holds one letter while the list narrows to the wrong thing — and it passes a naive unit test that types a single character. Gate the effect on an intent ref set by the keyboard handlers (`moveActive()` and the "open with ↓" path) and cleared when consumed, and drop `items.length` from the deps: `if (!open || !focusActiveRef.current) return; focusActiveRef.current = false; refs.current[activeIndex]?.focus()`. Test it by typing a **multi-character** query and asserting both the input's value and that the input still `toHaveFocus()` — a single-character test cannot see this bug. Reference: `components/filters/LabelFacet.tsx` (#2383).

211. **When a persistent left rail collapses into a mobile header that re-hosts the *same* interactive controls (scope switcher, context switcher, copy-link — anything queried by role/label), render exactly ONE copy via a `useBreakpoint()` conditional, NEVER two copies gated by `hidden md:flex` / `md:hidden`.** Tailwind's `hidden` is a CSS-only visibility toggle: both the rail and the mobile header stay mounted in the DOM, so every shared control exists twice. That is invisible in the browser but breaks every role/label query — jsdom (`window.matchMedia` absent → `useBreakpoint()` reports `lg`) and Playwright strict mode both resolve `getByRole('button', { name: 'Workspace' })` to two elements and throw. Extract the shared controls into small components (`ScopeSwitcher`, `ContextRow`) and render `{!isMobile && <aside…>}` / `{isMobile && <header…>}` off `const isMobile = useBreakpoint() === 'sm'` so only one instance is ever in the tree. The `SettingsShell` collapse is the reference: the 240px scroll-spy rail (md+) becomes a compact header below `md` whose scroll-spy nav is a native `<select>` "Jump to section" (`value={activeId}`, `optgroup` per nav group — OS-native, 44px, zero popover code), and `FieldRow` swaps its fixed inline `gridTemplateColumns: '240px 1fr'` for `grid-cols-1 md:grid-cols-[240px_1fr]` so label+control stack instead of overflowing a phone. Corollary for a `NavLink` whose active state must persist across sub-routes (a Settings gear that stays active on `…/settings/general`, `…/settings#access`, …): point `to` at the base the URL actually settles on (`…/settings`), because `NavLink` overrides an explicit `aria-current` prop with its own route match — a `to` that never equals the settled path renders `aria-current` unset even when your own `isActive` styling says active. Reference: `SettingsShell.tsx` (`isMobile` split, `ScopeSwitcher`/`ContextRow`, the jump-to-section `<select>`), `BottomNav.tsx` (the Settings entry's base `to`). **Focus-trap corollary (#2148):** the same single-shell discipline is mandatory whenever a `ref` must bind to the *visible* one of two responsive shells — a `useFocusTrap` container ref or a shared `closeButtonRef`. A `hidden md:flex` / `md:hidden` dual-render binds the ref to the DOM-first (desktop) copy while the mobile copy is `display:none`, so a hand-rolled trap covers only the desktop shell and the shared close-button ref focuses an invisible element (both were live bugs in `RiskDrawer`/`ResourceOverallocationDrawer` before #2148). Render one shell off `const isMobile = useBreakpoint() === 'sm'` and attach the trap to it. When the two shells differ in *modality* — a non-modal desktop inspector that sits beside content vs. a modal mobile sheet (rule 264) — gate the trap on the breakpoint as well (`useFocusTrap(isMobile && isOpen, …)`) so the desktop panel stays Tab-transparent and only the mobile sheet traps. Reference: `RiskDrawer.tsx`, `ResourceOverallocationDrawer.tsx`.

225. **An `aria-invalid` field must gate its form's primary action — the submit/primary button's enabled state derives from that validity AND the submit handler re-guards it; never leave the primary action live while showing an error, and never let it commit a stale/previous value the user did not type.** The trap is an input whose parse only *updates* the committed value on success (`if (parsed !== null) setValue(parsed)`): on invalid text the field shows red + `role="alert"`, but the underlying value silently keeps its last valid figure, so a primary button whose `disabled`/`canX` predicate omits the invalid flag stays enabled — and Enter or a click logs the previous value the error is actively warning against. Compute the invalid flag before the enabled predicate, fold it into both the predicate and the submit-handler early-return, so an `aria-invalid={x}` field always has its `x` term reflected in what commits. Reference: the quick-log manual-duration input in `features/timeentry/QuickLogTime.tsx` (#1416, ADR-0185 §C) — `manualInvalid` gates both `canLog` and `handleSubmit`, so a half-typed "abc" disables Log rather than logging the prior 1h.

294. **A new Alt/Option+letter keyboard shortcut matches on `e.code`, never `e.key`.** Holding Option while pressing a letter on macOS composes `KeyboardEvent.key` into an accented/special character in every browser — Option+A delivers `key: 'å'`, not `'a'` — so a binding keyed on `e.key.toLowerCase()` silently never fires there; the binding is dead on the platform most of this team develops on, with nothing in a synthetic-event unit test to catch it unless the test constructs the composed key (a test built with `key: 'a', altKey: true` and no `code` passes even though production is broken). `e.code` is the *physical* key — layout- and OS-independent — so resolve an Alt+letter combo through it instead (`e.code === 'KeyA'` → `'a'`); arrow keys, function keys, and punctuation (`?`, etc.) are unaffected by Option composition and stay on `e.key`. Reference: `features/schedule/useScheduleKeyboard.ts`'s `resolveKeyToken` (Alt+A Author/Read toggle, #2727 — found by `ux-review`, since the existing regression test synthesized the un-composed key and passed against the broken binding).

295. **When a count is narrowed to a subset, re-check every predicate that reads it.** Redefining an existing variable from a total to a subset (`tasks_created` → `plan_tasks_created`; "all rows" → "rows excluding the parked ones") silently invalidates every `count > 0` gate written against the total, and the newly-excluded case is exactly the one nobody demos. The failure is a CTA, empty-state branch, or navigation affordance that vanishes for a state that is now real and reachable — and nothing catches it: the types are unchanged, the tests still pass because none of them exercises the excluded case, and a screenshot of the happy path looks identical. This is how the CSV wizard's "View schedule" button disappeared for exactly the import that most needed it (#2732: every row unresolvable → zero plan tasks, but the operator's data IS in the outline, under the Import review branch the result step had just told them about). When you narrow a count, grep every read of the identifier — including gates in sibling components that receive it as a prop — and decide the predicate for the excluded case explicitly, rather than letting it fall out of the arithmetic. Reference: `components/import/CsvImportWizard.tsx` (`tasksCreated` / `parkedCount`, `WizardFooter`).

296. **A truncation notice ships with a way past the cap, on the same surface.** "and N more", "showing the first 12", "top 8" is an honest label and an incomplete affordance: it tells the user the thing they want may be unreachable and then does not hand them a route to it. Every surface that caps a list carries its escape hatch — expand, paginate, or export — *on that surface*, not only on a later step that happens to render the same component. The trap is a shared component whose escape hatch is an optional prop: it gets wired at the site where the reviewer noticed the cap and silently omitted everywhere else, so the cap is honest in one place and a dead end in another. Where the surface is a pre-commit confirmation, the rule is strongest — that is the screen where the decision is made. Reference: `components/import/CsvImportWizard.tsx` (`RowIssueList`'s `onDownload`, wired on both the confirm and result steps).

297. **A client-triggered file download needs a polite live-region confirmation.** A download is the one user-initiated action that produces *no* in-page change, so without an announcement it is indistinguishable from a dead button for screen-reader and low-vision users (WCAG 4.1.3). Mount the region **unconditionally** and set its text on success — a live region created in the same tick as its content does not reliably announce, which is why the reference implementation renders an empty `sr-only` span up front rather than conditionally rendering the whole node. The pattern was already in the tree when a second download button was added to the same file without it, which is the reason it is written down. Reference: `components/import/CsvImportWizard.tsx` (`UploadStep`'s "Template downloaded." span, `RowIssueList`'s "Problem rows downloaded.").
279. **An effect that needs a DOM node takes the node from `useElementRef` and lists it as a dependency — never `someRef.current` read inside an effect that cannot re-run when the node mounts (#2365).** A `RefObject`'s identity never changes and mutating `.current` does not re-render, so the ubiquitous shape `useEffect(() => { const el = ref.current; if (!el) return; el.addEventListener(…) }, [])` is **silently dead** whenever the node mounts after the first commit — which is the normal case on any surface that returns a loading skeleton or an error state before its real container (rules 246/248): the first commit renders the skeleton, the effect runs against `null`, bails, and never runs again. Use `const { el, setEl } = useElementRef<HTMLDivElement>()` (`hooks/useElementRef.ts`), attach `ref={setEl}`, and key the effect on `[el]`; a hook that owns such an effect exposes a **callback ref** (`setScrollEl`) plus the node (`scrollEl`) in its public API rather than a `RefObject`, so a consumer cannot reintroduce the bug, and any sibling hook that measures the same container takes `HTMLElement | null` rather than a ref. Three consequences: (a) `setEl` sets state, so it must only be called the way React calls a callback ref — after commit, never during render; (b) the effect's cleanup now genuinely runs when the node is swapped, so listeners/observers rebind correctly instead of leaking onto a detached node; (c) **a unit test must mount the container after the first commit** — the pre-#2365 tests passed a hand-built `{ current: el }` or assigned `ref.current` in the render body, which pre-seeds the very state the bug depends on and is why three broken hooks tested green. This bug class presents as e2e flake (it races query-cache warmth), so a spec covering such a surface should force the cold path with the `delayRoute` fixture (`e2e/fixtures/cold-load.ts`) rather than leave the ordering to chance. Reference: `hooks/{useElementRef.ts,useSpaceDragPan.ts,useHasScrollBelow.ts,useHasScrollRight.ts}`, `e2e/fixtures/cold-load.ts`, `e2e/board-space-pan.spec.ts`.

## Canvas

*The canvas is outside the DOM, so it inherits none of the guarantees above.*

235. **On the interactive canvas Gantt, the task bar FILL carries task STATE and the critical path is a red BORDER frame — never colour the fill by criticality.** Same principle as the PDF export (rule 234 / ADR-0277), applied to `GanttRenderer.ts`. `barFillColor()` resolves fill by state only (external → `textSecondary`, summary → `barSummary`, complete → `barComplete` sage-600 green, else → `barNormal` blue-500); it must **not** return `barCritical`. `drawTaskBar()` draws a **2px red critical frame** (`barCritical` = #B91C1C light / #F87171 dark) as an inset border for non-external, non-summary critical tasks. The reason: `barFillColor` checks `isComplete` *before* `isCritical`, so a red critical fill lost to a completion-wins-precedence race — a done critical bar rendered solid green and the critical path vanished on a mostly-complete schedule. A completed critical task must read as a **green bar in a red frame**; the critical signal can never be masked by state. Constraints:
     - **Draw order:** the 30% progress overlay paints BEFORE the borders so they stay crisp rather than dimmed by the tint; the selection ring paints next; the **critical frame paints LAST**.
     - **Selection nests inside the critical frame; risk outranks selection.** The navy `selectionRing` (#1B2A4A) is a 2px inset ring; when a critical frame is present and `barWidth >= MIN_NEST_WIDTH` (12px) it nests one step further in (inset 3px, 1.5px wide) so a selected critical bar reads red-frame-outside / navy-ring-inside. Below 12px the two concentric rings collide, so the ring uses the standard inset and — because the frame is drawn last — the red frame paints over it: a narrow selected critical bar keeps its criticality rather than losing it under the navy ring (the dropped-signal bug the #1699 UX review caught). **Gantt bar visual channels are orthogonal — fill = state, border = risk, ring = selection, line = time (ADR-0103/0277/0280); never encode two on the same channel** (the pre-#1699 bug was critical stealing the fill channel from complete). When channels stack on one bar, each must stay independently perceivable: draw inner channels at a smaller inset than outer ones, and below a minimum width abandon nesting in favor of a treatment that preserves the higher-priority signal (**risk > selection**). A channel another can fully occlude is a dropped signal.
     - **The `%` chip uses the surface treatment only** (`chipPillOnSurface` dark pill + `chipTextOnSurface` white). The old white-on-red chip existed for the red critical fill; with no bar red-filled, every chip pairs with the blue/green state fill via the surface treatment. Do not reintroduce a criticality branch in `drawTaskBarChip`.
     - **Border clears WCAG 1.4.11** (≥3:1 non-text) in both modes as a 2px frame (#B91C1C ≈ 7:1 on white, #F87171 ≈ 4.87:1 on navy); criticality is additionally backed non-color by the task-list red dot + the critical-path-only filter (1.4.1) — do not remove them.
     - **`ScheduleLegend.tsx::CriticalSwatch`** must mirror the canvas: a red-framed neutral bar, not a solid red fill.
     - **`barCritical` still legitimately strokes late actuals** in `drawActualDateBar` (#80) — that path is unrelated and must stay.
     - **Scope:** the canvas `Task` exposes only `isCritical` (binary), so this is a critical-only red frame; graded at-risk/on-track amber bands (present on the PDF) wait until the risk-band data is plumbed to canvas tasks. Reference: `GanttRenderer.ts::{barFillColor,drawTaskBar,drawTaskBarChip}`, `ScheduleLegend.tsx::CriticalSwatch`.

244. **A `<canvas>` is not touched by the forced-colors (Windows High Contrast) user-agent transform, so canvas-drawn UI must detect `(forced-colors: active)` and repaint with CSS *system-color* keywords — otherwise it renders its fixed colors into a high-contrast theme and becomes invisible/unreadable.** DOM chrome gets forced-colors for free (the UA remaps `color`/`background`/`border` to the theme); pixels a component draws into a canvas do not. The Gantt engine (`GanttEngineImpl`) subscribes to `window.matchMedia('(forced-colors: active)')` (mirroring the `prefers-reduced-motion` pattern — detect at init, re-detect on `change`, full-repaint on flip, unsubscribe in `destroy`) and passes the flag to `setRendererColorMode(dark, forced)`, which selects a third palette `COLOR_FORCED` built entirely from system-color keywords the 2D context resolves against the active theme: `Canvas`/`CanvasText` (surface/ink), `GrayText` (de-emphasis), `Highlight` (accent + selection), `LinkText` (links). Because the system palette is intentionally flat, **bar *kinds* must not depend on hue** in this mode — lean on shape (milestone diamond, summary endcaps) and the `Highlight` accent for critical/selection (color is never the sole differentiator, rule 6). Semi-transparent tints (row banding, weekend shading, ghost fills) collapse to the solid surface/ink so nothing relies on alpha the theme may not honor. Keep the palette-selection function (`pickPalette(dark, forced)`) pure and exported so it is unit-testable without a canvas, and assert that a draw pass in forced mode emits system-color `fillStyle`s (not brand hex). Forced-colors wins over dark/light — it is a hard accessibility preference, not a cosmetic mode. Reference: `COLOR_FORCED` / `pickPalette` / `setRendererColorMode` in `engine/GanttRenderer.ts`, the `_forcedColors` wiring in `engine/GanttEngineImpl.ts`.

295. **A forced-colors palette entry that collapses an alpha tint to a solid system colour (`Canvas`/`CanvasText`) is only safe if that fill paints BEFORE everything it would occlude — check the draw ORDER, not just the palette.** Rule 244 requires semi-transparent tints to collapse to the solid surface/ink under `(forced-colors: active)`, because the theme may not honour alpha. That collapse is a *no-op* for a fill painted first (row banding, weekend shading — both drawn before `drawGridLines`) and **destructive** for a fill painted later: at 5% alpha the grid, separators and neighbouring marks read straight through; at 100% opacity they are erased. The failure is invisible in light and dark, invisible in any unit test that asserts only "forced mode emits system-colour `fillStyle`s", and appears only to a Windows High Contrast user — who loses the row separators they need most. So for a **region** fill (as opposed to a bar or a line) the forced-colors treatment is to **skip the fill entirely** and let the mark survive as its edges, hatch and label; branch on an explicit module-level `_forcedColors` flag set alongside the palette, never on the palette value alone. Two corollaries. (a) **Shape, not just hue, must separate a new full-height rule from the today line** — under the flat system palette `Highlight` is shared, so a solid 2px band edge is pixel-identical to ADR-0103's load-bearing "now" mark; dash it (`ctx.setLineDash`), which also keeps the mark non-colour-carried at zoom levels too narrow for its text label (WCAG 1.4.1). (b) **Anything drawn on the bars layer after `drawTaskBar` must clear the bar box** (`BAR_TOP_OFFSET`…`BAR_TOP_OFFSET + BAR_HEIGHT`, i.e. y 5–23 of a 28px row) — rule 235's critical frame is the first and last 2px of that box, and a label straddling a row boundary paints over the row above *and* the row below. The free strip is the 10px inter-bar gutter (`rowTop − 5 … rowTop + 5`); a mark that will not fit there paints *before* the bars so the bar wins the collision and the risk signal survives. Reference: `COLOR_FORCED.sprintBandFill`, `drawSprintBands` / `drawSprintBandLabels` in `engine/GanttRenderer.ts`, and their call sites in `engine/GanttEngineImpl.ts` (#2738, ADR-0803 — surfaced by `ux-review`).

## Iconography

*A glyph carries information or it does not exist.*

242. **A glyph that stands in for a *UI icon* — a status/affordance mark like a warning, lock, target, chart, pin, or disabled sign — must be a house SVG from `components/Icons.tsx`, never a Unicode emoji.** Emoji render inconsistently across platforms/fonts (flat vs. glossy, differing metrics, some monochrome some multicolor), do not inherit `currentColor`, and never match the design-system stroke weight — so a functional emoji reads as a foreign, off-brand mark and can't be tinted to the surrounding text/semantic color. #1739 converted the affordance families to house icons: `⚠`→`WarningIcon`, `🔒`→`LockIcon`, `🎯`→`TargetIcon`, `📊`→`BarChartIcon`, `📌`→`PinIcon`, `🚫`→`BanIcon`, and the file-type mime map (AttachmentSection, `previewType`) to the `FileIcon`/`FileTextIcon`/`FileSpreadsheetIcon`/`FileImageIcon`/`FilePdfIcon`/`FolderIcon`/`PaperclipIcon` set. The recipe for an inline `<span aria-hidden="true">GLYPH</span>`: replace with `<Icon className="inline-block h-3 w-3 align-[-0.125em]" aria-hidden="true" />` (the `inline-block h-3 w-3 align-[-0.125em]` baseline-aligns the SVG like the emoji it replaces; a trailing space inside the old span becomes `mr-1`; preserve any existing span classes by merging them before the standard ones). Keep the glyph `aria-hidden` — the adjacent text or an `aria-label` on the wrapper carries the accessible name (rule 6). **Three carve-outs stay as emoji** (they are *content*, not icons): user-chosen **reactions** (`CommentSection` 👍), an **emoji-scale input** (`TeamHealthPulse` mood 😞😐🙂😀🤩), and third-party **brand logos** (GitHub/GitLab/Figma/Notion/Slack host marks — a separate brand-asset/licensing decision, tracked in #1748). The remaining long tail of functional glyphs is a phased follow-up (#1749) — convert **one glyph family at a time**, updating its e2e/vitest assertions in the same commit. **The sweep is complete (#1749, #2480).** Every functional-glyph family and every string-stored `icon:`/`glyph:`/`emoji:` field now holds a house SVG, including the mixed maps that stalled the earlier slices (`OBJECT_TYPE_META`, `EVENT_META`, the Gantt and Queue row menus, `CalmToolbar`/`BoardLensBanners`, `notificationFilters`). **The unblocking move on a mixed map is to type it by *meaning*, not by shape** — `OBJECT_TYPE_META`'s `□ ◇ △ ⇢ ◈ ↻` had only two same-shape house icons between them, and inventing six abstract geometric marks would have produced a column that says nothing; reusing the icon each object type already carries elsewhere (`RiskIcon`, `SprintIcon`, `RepeatIcon`, …) made it readable instead. **Convert a map whole or not at all** — a half-converted map puts an SVG next to an emoji inside one control, which is worse than either alone. Four things stay glyphs on purpose, and are *not* regressions: `forecastDelta`'s `▲ ▼ ◆` direction triple (a redundant-encoding channel, not an icon family), **keycap legends** (`⇥ ⌘D ⌫ ⇧+Tab` — those are keys), the decorative `◆` on `OSSChip`/`BuildModeEmptyState`, and `$` on the cost toggle (a currency denomination — baking USD into an SVG path is worse for i18n). Two lessons from the `✓` pass: (a) **take the inventory in a script, not `grep -P` with a multi-codepoint bracket class** — that undercounted by an order of magnitude here (it reported one glyph where 27 were live), so a phase can silently believe a family is finished; count per-codepoint and exclude comment lines. (b) **A glyph span is not always a plain wrapper** — when the span carries sizing/background/border classes (`w-4 h-4 rounded-full bg-…`, a checkbox box, a 44px badge) it is a *container*: keep it and nest the icon inside at an explicit size, rather than merging its classes onto the SVG (which yields conflicting `h-4`+`h-3` and `inline-flex`+`inline-block`). Where the "off" state hid the glyph with `text-transparent`, omit the icon instead — the box already holds the layout. When a family's mark distinguishes *kinds* of selection, give each kind its own shape (`RadioDotIcon` for a `menuitemradio` row vs `CheckIcon` for `menuitemcheckbox`; `HalfCircleIcon` for a partially-met three-state outcome) so shape carries the state, not tint alone (rule 6). When a test asserts on the old glyph text (`getByText('⚠')`), re-anchor it to the rendered SVG (`getByLabelText(/…/).querySelector('svg')` or `.closest('.inline-flex')?.querySelector('svg')`) or a `data-testid` on the container. Reference: `components/Icons.tsx`, `previewType.ts`, `features/schedule/sections/AttachmentSection.tsx`.

283. **An icon column carries information or it does not exist: no glyph repeats inside a single settings nav group, `ExternalLinkIcon` means "this leaves the app", and `WarningIcon` means "exception" (#2425).** The defect this replaced: 6 of the 9 project `Configuration` rows rendered the same glyph (`SettingsIcon` ×5, `ExternalLinkIcon` ×2), with two more collisions in Setup and Danger — a column where most entries are identical is **negative information**, because it trains the eye to stop scanning the column and that costs the rows whose icon actually distinguishes them. Four invariants: (a) **uniqueness is per nav *group*, not per rail** — the same concept deliberately keeps the same glyph across the project / program / workspace rails (General = gear, Team/Members = resources, Access/Roles = lock, Working calendar = calendar, Integrations = plug), so a cross-group repeat is intended and a within-group repeat is the bug; (b) `ExternalLinkIcon` is reserved for navigation that genuinely departs the app and therefore appears in **no** settings nav row — an arrow leaving a box is a promise about where the click goes, and Attachments/Sharing stay inside TruePPM (Sharing gets the share-*network* glyph, because it grants access *inside* the product); (c) `WarningIcon` is reserved for the **Danger** group — spending a warning triangle on routine configuration (sprint guardrails, notifications) is exactly how it stopped reading as an exception; (d) new glyphs are hand-authored into `components/Icons.tsx` on the **16-box** house grid at `strokeWidth="1.5"` (rule 242 — no emoji, no icon library). A 24-box glyph dropped in unscaled renders at ~1.0px effective stroke beside the house set's 1.5px and reads visibly thinner, so convert the geometry rather than the `viewBox`. Each rail exposes its nav as a pure builder (`buildProjectSettingsNav`, `buildProgramSettingsNav`, `buildWorkspaceNavGroups`) so the invariant is asserted on the data, not on a rendered page — `src/features/settings/settingsNavIcons.test.tsx` fails on a reintroduced duplicate. Reference: `components/Icons.tsx`, `features/settings/{ProjectSettingsPage,ProgramSettingsPage}.tsx`, `features/settings/workspace/workspaceNav.tsx`.

292. **A 2px brand-primary left rule (`border-l-2 border-brand-primary`) is this app's SELECTION/ACTIVE idiom — a static informational block uses `border-l-4`.** The 2px form means "the thing you selected / the page you are on" everywhere it appears: `Sidebar.tsx` (active nav), `SettingsShell.tsx` (the active scroll-spy rail item), `TaskListRow`, `BoardView`, `BoardColumn`, `RosterList`, `TaskRow`, `columnHeaderParts`. Reusing it for a non-interactive note inside `features/settings/` is the worst case, because the shell's active rail item renders the identical treatment **in the same viewport** — two identical marks, same screen, different meanings, and a user who has learned the idiom gets a false positive on a static paragraph. The informational form is `border-l-4 border-brand-primary pl-3` (reference: `WebhookEditorModal.tsx`, `StakeholderReachSummary.tsx`), which also happens to align the block's text edge with a sibling `px-4` table header. If the block is not brand-relevant at all, use a neutral or semantic border instead. Surfaced by the #2529 ux-review.

293. **A `text-[12px]` paragraph of running prose in `features/settings/` carries a measure cap of `max-w-[440px]`–`max-w-[480px]`.** The settings shell's content column is `max-w-[920px]`, so an uncapped 12px paragraph sets ~145 characters per line at desktop width — roughly double the 45–75 character comfortable range, at the page's *smallest* type, on the surface where an admin actually reads prose. Desktop is the primary device for these pages (rule 118's own rationale), so this is the viewport that matters. Already the de-facto convention: `WorkspaceMethodologyPage.tsx` (`max-w-[480px]`), `ProjectMethodologyPage.tsx` (`max-w-[440px]`), `ProgramCadencePage.tsx` (`max-w-[460px]`), `StakeholderReachSummary.tsx` (`max-w-[480px]`). This is about *prose* — a 12px label, chip, or table cell needs no cap. Surfaced by the #2529 ux-review.

## Placeholders and operator surfaces

*What an unavailable control is allowed to look like.*

122. **Disabled placeholder/stub controls in `features/settings/` use the `.settings-stub` recipe — never `disabled:opacity-50`.** Half-opacity body text fails WCAG 1.4.3 and diverges from the established stub treatment. Two equivalent paths: wrap a whole section in `StubFieldset` (preferred — the `.settings-stub :disabled` rule in `globals.css` recolors every descendant in one place, used by `WorkspaceDangerPage`), or for an individual button apply the recipe as `disabled:` utilities at opacity 1 — `disabled:bg-neutral-surface-sunken disabled:text-neutral-text-secondary disabled:border-neutral-border/55 disabled:cursor-not-allowed` (drop the bg/border pair for borderless text-link buttons; recolor + `disabled:cursor-not-allowed` is enough). Always keep the full rule-4 `focus-visible` ring **including `ring-offset-1`**, and add a `title` explaining why the control is unavailable: `#NNN` for an OSS gap, "Available in TruePPM Enterprise" paired with `EnterpriseBadge` (rule 121) for an Enterprise-reserved action. Dead-but-clickable buttons are worse than disabled ones (#669) — disable the placeholder, link the tracking issue, ship. The **individual-button** form of this recipe (opacity-1 `disabled:` recolor + `disabled:cursor-not-allowed` + kept focus ring + explanatory `title`) is the app-wide convention for any inert placeholder, not only `features/settings/` — e.g. the schedule-export dialog's disabled "Layout B — Report" radio (until #1439) and its Export-when-empty button (#1438) both use it. Only the whole-section `StubFieldset`/`.settings-stub` path is settings-scoped.

274. **A read-only surface for an operator / deploy-time (env or Helm) value presents an honest *status* — a state chip, the controlling env-var name, and an explicit "configured in the server environment, not editable here" — never a disabled in-app toggle or a "fix it here" link.** Such values are set outside the app (env / Helm `values.yaml`) and no authenticated user may change them through the UI — that boundary is deliberate (e.g. a platform DoS protection must not be app-toggleable). Show the live state read-only and name the lever the operator actually uses; a dead toggle, or a link that goes nowhere, is worse than plain text. This is the operator-status corollary of the rule-8 live-wiring discipline ("hide a not-yet-wired control; never present a dead control as if it works"). Reference: `RateLimitDisabledBanner.tsx` + the `RateLimitCard` in `features/settings/workspace/SystemSummaryCards.tsx` (the `TRUEPPM_RATE_LIMIT_ENABLED` kill-switch status, #2316 / ADR-0604), mirroring the read-only OTel telemetry posture card.

## Product boundary

*What OSS shows, and where Enterprise may be surfaced.*

231. **The OSS UI shows what one team can do; an Enterprise affordance appears ONLY at a surface where the user reaches for something inherently cross-program or org-governing — never as an ambient padlock, disabled control, or upsell teaser in the OSS daily path.** TruePPM is adoption-first (the GitLab model): the free tier must be *completely sufficient for one PM/team/program*, and the Enterprise need is discovered **structurally** — when a second program, a portfolio roll-up, org-wide SSO enforcement, or a directory sync becomes the actual task — not through locked doors sprinkled across the shell. Three constraints for any **new** shell/navigation or extension-point-slot surface:
     - **(a) No render absent the edition.** Enterprise features register into stable OSS extension points (slot registration ADR-0029; edition-based routing ADR-0030). When the enterprise package is not installed, `registry.get(<slot>)` returns `[]` and the OSS UI renders **nothing** in that slot — no grayed-out or padlocked placeholder. A disabled control the OSS user can never enable is a wall, and walls in the daily path are the "you must upgrade to work" signal adoption-first exists to avoid.
     - **(b) Discovery at the seam, not on the surface.** The upgrade signal is allowed only where the *shape of the work* crosses the boundary — the moment a user tries to compare two programs, open a portfolio roll-up, enforce org-wide SSO, or sync a directory. That is contextual and honest (it coincides with a need the user just expressed) and is the ONLY sanctioned place a "this is an Enterprise capability" affordance may appear. It is never ambient chrome.
     - **(c) An Enterprise affordance is a distinct opt-in surface, not a disabled OSS control.** Where an enterprise slot *is* registered, present it as its own surface with its own label — never as `disabled aria-disabled="true"` OSS UI. (Contrast rule 42's WBS/Table `disabled` state, which gates an *OSS* feature coming to *this* edition — a legitimate "not built yet" disable; an Enterprise capability is "not in this edition," a different meaning that must not read as "temporarily off.")

     Load-bearing at the shell seams: the 3-tier rail (You / This project / **Jump**, #1642) and the location switcher (#1643) are exactly where cross-program/portfolio scope becomes visible. In OSS, `Program` is a first-class entity, so *within-program* navigation is fully OSS; only **cross-program** and **portfolio** destinations are the Enterprise seam. The classification test is the CLAUDE.md two-repo test verbatim: "Would a PM/program manager need this to run their program?" → OSS, render it; "Is this cross-program coordination, org policy, or compliance evidence?" → Enterprise, surface it only at the seam per (b). Basic OIDC/OAuth login is OSS (auth carve-out) — never gate it. If a practitioner hits a locked door doing single-program work, the boundary is drawn wrong and no visual treatment can rescue it — fix the boundary, not the padlock.

     **Surface classifier — daily path vs seam.** Rules 231 and 121 are the *same* principle applied to two surface types, not competing rules. **Daily-path surfaces** (the shell, rail, nav, project workspace, My Work) get 231: empty slots, zero ambient upsell. **Seam surfaces** — where a user's own action crosses into governance (Settings → Roles & permissions, org-identity/governance settings, the `/programs`→portfolio boundary) — may carry a single contextual affordance, because that *is* discovery at the seam (constraint (b) above), not ambient chrome. This maps onto the project's own adoption-vs-governance boundary: the daily path is where a team gets work done, the governance/settings seam is the natural home for an upgrade signal. Consequences:
     - **Rule 121's `EnterpriseBadge` on the Settings→Roles capability matrix stays** — the matrix's job is to show the *full* capability space, so hiding Enterprise rows would misrepresent it. The badge is constrained to **seam surfaces only**, never the daily-path shell/nav.
     - **Rule 178 is the one correction being made:** the disabled "Portfolio rollup" row in the rail (`Sidebar.tsx`) is a slot on the *daily path* wearing a padlock, so it converts to an empty `nav.portfolio_section` slot with discovery moved to the `/programs` seam. That scoped change is tracked in **#1677**; until it lands, leave the shipped `Sidebar.tsx` row in place (do not hand-delete it outside #1677).

121. **Enterprise-only capability rows carry an inline `EE` badge that is itself the link.** On any OSS surface that advertises capabilities reserved for TruePPM Enterprise (Settings → Roles & permissions matrix today; the future `/programs` and `/portfolio` gateways), mark each Enterprise row data-driven (`ee: true` on the capability/row object — never a hardcoded list in the render, so it stays in sync as the Enterprise repo adds capabilities) and render the `EnterpriseBadge`: a focusable `<a>` to the Enterprise page (`https://trueppm.com/enterprise`), `target="_blank" rel="noopener noreferrer"`, with `title` **and** `aria-label` "Available in TruePPM Enterprise". **The badge IS the link** — a hover-tooltip that contains a link is unreachable (it dismisses as the pointer travels to the link and is invisible to keyboard users), so never wrap the link in a tooltip. Gate rendering on `useEdition() === 'community'`: under the Enterprise edition the capability is available, so the badge is suppressed (it would be noise). Badge style (settings density, rule 118): `bg-brand-primary/10 text-brand-primary text-[10px] font-semibold uppercase tracking-wide` + the standard rule-4 `focus-visible` ring. This is the concrete implementation of the ux-review §6.2 boundary-affordance requirement — it turns "dead" Enterprise cells (a check in a column that does nothing in OSS) into a purchase-decision path and stops missing Enterprise features from reading as broken OSS. The badge is the shared `features/settings/components/EnterpriseBadge.tsx` (#791) — it **self-gates** on `useEdition()` (returns null unless community), so callers render `<EnterpriseBadge />` without an edition check of their own. It applies to whole action buttons too, not just matrix cells: an Enterprise-reserved action (e.g. "Sync from directory" = LDAP, "View change history" = audit trail) renders as a disabled button with the badge alongside it as the reachable upsell link.

## The other 228 rules

Every rule this file used to carry still exists. The ones bound to a single
surface and a single issue now live as individually-linkable **decision
records** under [`docs/design/decisions/`](../../docs/design/decisions/) —
see [the index](../../docs/design/decisions/README.md).

They are still binding for the surfaces they govern. What changed is that they
are no longer mandatory reading: this file is the set you are expected to hold,
and a decision record is what you reach for when you touch the surface it
covers. Rule numbers are unchanged, so an existing `rule 176` reference in code,
an ADR, or an MR description still resolves.

**Where does a new rule go?** Ask whether it would be correct for a surface that
does not exist yet. If yes it is an invariant and belongs here. If it only makes
sense for the surface that produced it, write a decision record. See ADR-0653.
