# TruePPM Web Frontend — Design Rules

These rules are enforced at review time. Violations block merge.

> ## ⭐ Design System v2 — the golden standard (ADR-0126)
>
> The canonical UI is the **v2 redesign** (`docs/design/v2-golden-standard.md`,
> upstream `design_handoff_trueppm_v2/`). Every new screen, component, fix, and
> feature must conform. Foundation tokens are in `globals.css` + `tailwind.config.ts`;
> conformance is machine-checked by `scripts/check-design-system-v2.sh` (in `make lint`
> / CI). Key invariants beyond the numbered rules below:
> - **Warm-paper canvas:** page backgrounds use `bg-app-canvas` (warm `#F2EEE5`),
>   cards use `bg-neutral-surface` (white) and pop against it. Never a cool-grey or
>   pure-white app canvas.
> - **Sage has two roles (ADR-0126 §3):** `--sage` `#3E8C6D` is the **fill/accent**
>   (with navy or white text); normal-weight **text/border/ring** use
>   `brand-primary` (sage-700, AA). sage-600 is 4.06:1 on white — never body text.
> - **One status vocabulary:** a **dot** = health, a **pill/chip** = state; color is
>   signal only, calm-neutral by default.
> - **Borders over shadows:** `shadow-card`/`shadow-pop` are reserved for
>   popover/drawer/modal/command-palette/toast (see rule 1).
> - **Full Light/Dark/Auto** via the `.dark` token swap on `<html>` — never a dark
>   sidebar on a light app.
> Staged adoption of the remaining surfaces is tracked in epic #1163.

## Foundations

*What every file in `packages/web` obeys.*

9. **No default exports** — all components use named exports

10. **No CSS-in-JS** — Tailwind utility classes only; use `style` prop only for dynamic values (e.g., CSS custom properties, inline widths derived from state)

11. **Stub hooks over mock network** — while real API hooks don't exist, return fixture data from the hook (`src/hooks/`). Components never import from `src/fixtures/` directly.

12. **Responsive breakpoints** (from `tailwind.config.ts`): `xs`=320px, `sm`=375px, `md`=768px, `lg`=1024px, `xl`=1280px, `2xl`=1440px

1. **No drop shadows anywhere** — use `border border-neutral-border` for separation instead of `shadow-*`

299. **Every optimistic edit to a cached *list* goes through `optimisticListUpdate` / `optimisticListAppend` (`src/lib/optimisticCache.ts`) — never `setQueryData(key, [...(previous ?? []), row])` or `(prev ?? []).map/filter` by hand.** A cache entry that is momentarily absent means "not loaded right now", never "this collection is empty". Defaulting it to `[]` and writing the result back replaces a populated list with the single row the user just added — a real race, not a theoretical one: `cancelQueries` is awaited, and a `useProjectWebSocket` collaboration invalidate, an offline reconnect flush, or the mutation's own `onSuccess` can clear the entry inside that window. The helpers skip the updater entirely on a nullish entry *and* read the cache functionally at write time (so an invalidation landing between the snapshot and the write is observed, not overwritten); they still return the snapshot for `onError` rollback. Defaulting a row's own nested field (`t.labels ?? []`) is unrelated and fine. This class was fixed instance-by-instance on the board (#2717) and then found again on six sibling sites (#2862), so it is now machine-checked: the conformance block in `src/lib/optimisticCache.test.ts` source-scans every `setQueryData` call in the tree and fails on a bare identifier defaulted to `[]`/`{}`. Do not hand-enumerate the hooks — hand-enumeration is what let the class survive.

300. **A design rule that has needed a second manual sweep does not have a working mechanism — fix the mechanism in the same MR, and watch it fail before you fix the violations.** Four rules recurred here 2–6 times each and every sweep fixed only the sites (#2858). The reason each one came back was mechanical, not cultural, and none of the four was visible from the violation list: `tiny_text_offenders()`'s regex read `text-\[([0-9]|10)px\]` and **could not match `text-[11px]` in any file, in any tree** — six dedicated sweeps (#434, #650, #1023, #1229, #1332, #2043) ran against a gate that was structurally blind to the thing they were sweeping for, and reported green each time; the standalone-trigger focus guard was a Playwright spec asserting **two hardcoded controls** (#2292), which cannot sweep because a behavioral spec only reaches the routes it navigates; the `bg-semantic-{state}/N` tint had **no check at all**; and the "page swallows a fetch error as an empty state" class was fixed one page at a time across #1764/#1937/#1942 with nothing counting the population. Three consequences, all load-bearing:
     - **(a) A gate you have not seen fail is not a gate.** Run the widened/new check against `origin/main` and confirm it reports the offenders *before* you fix them, and record the before/after counts in the MR. A pattern that silently narrows reports 0 and **passes** — indistinguishable from a clean tree, which is precisely how the 11px hole survived six sweeps. Every pattern in `scripts/check-design-system-v2.sh` therefore ships with an inline both-direction self-test (`hex_pat_self_test`, `pipeline_self_test`) that runs before any count is produced and exits non-zero if a fixture stops matching; a lint-rule gate ships the equivalent as fixtures that import the real selector array, never a copy (`src/test/standaloneTriggerFocusRule.test.ts`).
     - **(b) Match the mechanism to what the rule can decide.** A textual rule (a class string) is a grep; a structural one ("this element is a disclosure trigger") is an AST selector in `eslint.config.js`, where `// eslint-disable-next-line` with a reason is the escape hatch; a rule whose predicate needs *semantic* judgement — "is this a primary data surface?" — is decidable by neither, so gate the **population size** as a ratchet instead of pretending to zero-tolerance. A zero-tolerance check that misfires gets disabled, taking the real protection with it.
     - **(c) Separate "is this the sanctioned exception?" from "is this a violation?" mechanically, or the exception list becomes the hole.** Each carve-out is a named file or tree in the filter (`features/settings/` for rule 118, `StatusBar.tsx` for rule 45, `features/schedule/` for rule 137), never a per-component judgement — and interaction-state variants (`hover:`, `focus:`) are stripped before counting resting fills, which is what separates 7 real `bg-semantic-*/N` offenders from 32 legitimate hover washes.
301. **A client-side severity map over a server-owned token vocabulary must fail LOUD, and its unknown branch must never be the neutral one.** When the server owns a vocabulary that grows with a feature's taxonomy (a delivery outcome, a job reason code, a sync verdict) and the client maps each token to a *tone* — good / bad / neutral — that map is a hand-maintained mirror of a list which changes without it. The drift is inevitable and acceptable; failing in the *reassuring* direction is not. A `tone = KNOWN[token]?.tone ?? 'idle'` fallback renders the next server-side **failure** token in the same grey as "nothing to report", with no remediation hint, on the surface whose entire purpose is telling an operator something is wrong — and a unit test asserting "an unknown token still renders" makes the gap look covered while locking it in. Three obligations. **(a)** Prefer making severity a **server fact** — return `ok: boolean` or a severity enum beside the token so tone is rendered from the API rather than from a copy of it (API-first, ADR-0599: the authoritative classification of a server-computed outcome is itself server-computed). **(b)** Where the map must stay client-side, the unknown branch takes the **cautious** tone, never the neutral one: an unrecognized outcome on a diagnostic surface is a problem until proven otherwise. **(c)** Never render a raw snake_case token as user-facing copy — humanize it (`replace(/_/g, ' ')`) so the fallback degrades rather than leaking an identifier. Corollary for the server side of the same feature: publish the vocabulary as an OpenAPI `enum` (a `ChoiceField`, not a bare `CharField`) so the mirror can at least be checked against something. Reference: `features/settings/components/integrations/GitAutomationManager.tsx` (`DELIVERY_OUTCOMES` / `TONE_CLASS` / `humanizeOutcome`), `hooks/useGitAutomation.ts` (`GitDeliveryOutcome`) — #2882, surfaced by `ux-review`.
302. **"No rights" and "chose read-only" are different states, and only one of them gets a disabled control.** A surface that computes one `readOnly` flag by OR-ing an entitlement check with a user's own mode toggle (`!canEditTask(role) || mode === 'read'`) will render the same dimmed apparatus to both, and that is wrong for one of them. A user with **no edit rights** must find the authoring apparatus **absent, not disabled** — no create buttons, no Read/Author toggle, no grips, no insert points, no delete — and its mutation guards stay **silent**, because with nothing offering the action there is no gesture left to explain. A user **with** rights who pressed the toggle must find it **present and inert**, with refusals that explain themselves, because one key gets them back. Offering a control and then refusing it teaches a viewer the product is broken; explaining a refusal to someone who should never have seen the button is noise. Derive the two separately (`hasEditRights` for presence, `readOnly` for behavior) and put one static badge where the apparatus was, naming what to do instead — a badge, not a button, since an action would put an affordance back on a surface whose whole point is that it offers none. This is presentation only: the server stays the thing that actually refuses. Note it also satisfies rule 6.1's "conditional permission-gated affordances" check, which a `disabled` control fails by announcing "[label], dimmed" to a screen reader. Reference: `features/schedule/ScheduleView.tsx` (`hasEditRights` vs `readOnly`), `features/schedule/ScheduleViewOnlyBadge.tsx` — #2949, from `design_handoff_trueppm_v4/` "No edit rights".
    - **At the row (#2961), the rule needs three flags, not two — and the third is the one that gets missed.** `TaskListRow`'s `buildMode` object is two things wearing one name: the outline's *navigation* model (row focus, arrow traversal, ⌘A, Shift+↑/↓, the roving tab stop) and its *authoring* API (insert, indent, reorder, delete, cell edit). The one-line fix — null `buildMode` for a viewer — takes the navigation with it and leaves a grid nobody can move around in. Absence must remove what **authors** the plan, never what **reads** it. So: `buildMode` for navigation sites, `authoring = canEdit ? buildMode : null` for mutation sites, and a separate **`canEdit` boolean** for the "may this reader mutate at all" question — because `authoring` is *also* null for an editor who simply is not in build mode, and gating the flag-off keyboard reducer on it silently deletes that editor's Space / ⌘D / F2 / double-click-rename. Cells take `authoring`: every cell primitive already branches `buildMode ? <EditableCell> : <text>`, so passing it is what makes a viewer read a plan instead of a form someone locked.
    - **Presence follows the *settled* entitlement — an unresolved role is not "no rights".** `useCurrentUserRole` returns `isLoading: true` before the membership query lands, so `canEditTask(role)` is false on first paint for everyone. Gating presence on that directly makes every row grow its controls a beat after it appeared — a layout shift on every schedule load. Assume rights while loading and let the settled value decide: the server is the enforcement point, so a control briefly offered to a viewer costs at worst one silent refusal, while a control briefly withheld from an editor is visible on every load. A server-sent per-task capability (`task.canEdit`) is already settled and wins outright. Write it as `task.canEdit ?? (roleUnsettled ? true : canEditTask(role))`, where `roleUnsettled = isLoading || isError`. **A failed lookup is unresolved too, and that is the case that gets missed**: the hook sets `retry: false`, so before #2961 an error was indistinguishable from "settled: not a member" and one dropped request would have stripped an editor's whole apparatus with no error state anywhere to explain it. `useCurrentUserRole` exposes `isError` for exactly this; the `lint:design-system-v2` rule-246 ratchet is what surfaced it, by counting a destructure that takes `isLoading` and never `error` — treat that gate as a finding about the code, not a number to get back under.
    - **A test that renders one of these surfaces must declare a role, and the failure mode if it does not is disguised.** Without a `useCurrentUserRole` mock the real hook resolves to "no role" *asynchronously*, so a synchronous `fireEvent` case passes while its `await user.click` twin fails — which reads as a flake rather than as a missing fixture. Mock it (`{ role: 100, roleLabel: null, isLoading: false }`) in any spec that exercises authoring. The e2e default is already an editing role (`api-mocks.ts` serves `role: 300` for `?self=true`), so only specs that pass an explicit lower-role `members` need attention. Reference: `features/schedule/TaskListRow.noEditRights.test.tsx`.

312. **When a new dimension subdivides an existing key, the derived key must be BYTE-IDENTICAL to the old one wherever the dimension is unused — and a test must pin that identity.** A surface eventually grows a second axis over something it already keys on: a board status column splits into named lanes, a resource row splits by allocation, a timeline band splits by scenario. The tempting shape is a new composite key everywhere (`${status}#${lane}`), and it is silently destructive, because the *old* key is load-bearing in places that carry no types and produce no error when it changes: `localStorage` (persisted column widths, collapsed sets), `dnd-kit` droppable ids, `data-testid` and every E2E selector built on it, keyboard-traversal state, saved-view payloads. Every one of those degrades to "the user's saved state is gone" rather than to a failure anyone sees. So make the composite key **collapse to the original** when the subdivision is empty — ``key = laneKey ? `${status}#${laneKey}` : status`` — and give the expansion function a unit test asserting `tracks.map(t => t.key)` equals the original key list on an unsubdivided input. That one assertion is the whole safety property: with it, a feature nobody has turned on is provably a no-op end to end, and the migration for existing data is *nothing*. Corollaries: (a) **subdivide the render, not the semantics** — the axis being split (`Task.status`) must keep its original values so every downstream reader is untouched; the new dimension rides alongside it; (b) **status-level controls stay status-level** — collapse, the card's "Move to…" menu, the mobile status board and any milestone rail must reduce the track list back to one entry per original key, or one milestone renders N times and a menu offers the same destination three times; (c) **resolve a dangling sub-key on read, in exactly one place, and make the server resolve it the same way** — deleting a lane must not require rewriting rows (a bulk `UPDATE` skips the `server_version` bump every synced write depends on), so both sides fall back to the first sub-key and the header count can never disagree with the cards beneath it. Reference: `features/board/statusLanes.ts` + `statusLanes.test.ts` ("leaves an unladen board byte-identical to its column list"), `apps/projects/services.py::_annotate_lane_breach` — #2967.

## Accessibility floors

*Non-negotiable minimums. A surface that misses one is not shippable.*

4. **Focus rings on all interactive elements**: `focus-visible:ring-2 focus-visible:ring-brand-primary focus-visible:ring-offset-1`
   - **Standalone-control carve-out (rules 214/261(e)): standalone triggers, menu items/rows, tabs, chips-as-buttons, and dropdown/popover triggers use `focus:` — never `focus-visible:`.** Firefox and desktop Safari do not match `:focus-visible` on pointer-initiated focus of a button, so `focus-visible:` leaves these controls with no visible focus after a click. Write `focus:outline-none focus:ring-2 focus:ring-brand-primary` plus `focus:ring-offset-1` (freestanding) or `focus:ring-inset` (menu rows, tight popover items). Form fields (`input`, `select`, `textarea`, checkboxes whose wrapping label carries a `focus-within:` ring) keep `focus-visible:` — browsers always match `:focus-visible` on editable fields, and a persistent `focus:` ring on a field the user is typing in is noise. The Schedule tree (`features/schedule/`) stays `focus-visible:` deliberately per rule 137. Enforced by `NO_FOCUS_VISIBLE_ON_TRIGGER` in `packages/web/eslint.config.js` — an AST sweep over every `<button>` carrying `aria-haspopup`/`aria-expanded`, which is what the two-control Playwright spot check (`e2e/focus-ring-pointer.spec.ts`, #2292) could never be; that spec proves the *browser behavior*, not coverage (rule 300). Reference: `features/shell/UserMenu.tsx`, `CreateMenu.tsx`, `NotificationBell.tsx`, `HealthCluster.tsx`, `BottomNav.tsx`; board/sprints/backlog converted in #2042, the tree swept in #2858.
   - On a **sage fill** (primary button, `bg-sage-500`): use `focus-visible:ring-navy-700 focus-visible:ring-offset-sage-500` (navy-on-sage 6.8:1) — with `focus:` variants instead when the control falls under the standalone carve-out above.
   - **No dark-mode override needed for `brand-primary` (ADR-0103/0125).** `brand-primary` is mode-aware sage — sage-**700** #316F57 (light, 5.93:1) / sage-400 #66B998 (dark, ≥3:1) — so `ring-brand-primary` passes WCAG 1.4.11 in both modes. (sage-600 #3E8C6D is only 4.06:1 on white — a fill/dot shade, never the foreground/ring token; see rule 143 and ADR-0126 §3.) The old `dark:focus-visible:ring-semantic-on-track` escape hatch (for green #1C6B3A's 2.81:1 dark failure) is **retired** — do not reintroduce it.
   - Never use `outline-none` without a visible replacement

214. **Rail tabs, the "More" trigger, and `MoreSheet` nav rows use `focus:ring-*`, not `focus-visible:ring-*`.** They are standalone tab/menu controls — `focus-visible:` withholds the ring on pointer-driven focus in Firefox/desktop Safari (the ux-review HIGH gate). This is the rule-4/ux-review focus rule applied to the mobile rail; when rebuilding a rail file, convert any pre-existing `focus-visible:` on its controls to `focus:` in the same change rather than carrying it forward. Do NOT reuse the backlog `FOCUS_RING` constant (`features/programs/backlog/styles.ts`) in rail/sheet nav rows — it is `focus-visible:`-based; write `focus:outline-none focus:ring-2 focus:ring-brand-primary focus:ring-inset` inline. Reference: `BottomNav.tsx`, `MoreSheet.tsx`, `bottomNavItems.ts`.

357. **Rule 4's `ring-brand-primary` is measured against an ordinary canvas — on an INVERSE surface it fails, and an alpha modifier on a ring voids the published figure entirely.** Two ways a focus ring silently stops being a focus ring, both invisible to every gate we run. **(a) Wrong ground.** The house ring is sage — `#316F57` light / `#66B998` dark. Against an *inverse* surface (an ink pill, an inverted banner, anything painted `bg-neutral-text-primary`) it measures **2.40:1 light / 2.00:1 dark**, under WCAG 1.4.11's 3:1 *at full alpha*. The fix on such a surface is that surface's own maximum-contrast ink — `ring-neutral-text-inverse`, which is 14.2:1 and 15.0:1 — not a darker sage. Rule 4 is not wrong; it is scoped to the ground it was measured on, and an inverse pop surface is a different ground. **(b) Alpha.** `ring-{token}/N` discards the token's published contrast: the toast's Undo carried `ring-brand-primary/70`, which is 1.82:1 / 1.60:1. Alpha on a *fill* is a tint and costs little; alpha on a *ring* is subtraction from the one thing whose entire job is to be seen. Use the full-alpha token or compute the composite and prove ≥3:1 in both modes **in the same diff**. **(c) Escalate when focus does more than mark position.** A ring is normally a polish finding; when the focused state changes behavior beyond its own element — pausing a timer, blocking a queue, claiming a slot (rule 356(d)) — an invisible ring is a *correctness* defect, because the user is in a mode they cannot see and did not choose. Note the mechanism honestly (rule 300): no gate reads `ring-{token}/N` and none computes a composite against the ancestor's background, so this class is review-only — when you touch a focus ring on a non-default ground, do the arithmetic and put the numbers in a comment. Reference: `components/Toast/ToastHost.tsx` — #3149.

5. **Touch targets** — minimum 44×44px at all breakpoints

6. **Color dots** (8px project color indicators) are always `aria-hidden="true"` — health state must also be conveyed via text or `aria-label`

50. **Every `text-[Npx]` below 12px is prohibited — `text-[11px]` included.** The design system floor is `text-xs` (12px); arbitrary size values below it bypass the token ladder and introduce WCAG 1.4.3 failures on any surface. Two exceptions, both named files/trees rather than judgement calls: `text-[11px]` in the global StatusBar (rule 45 documents the rationale) and `text-[11px]`/`text-[10px]` under `features/settings/` (rule 118's compact-admin density). `text-[9px]` and below are prohibited everywhere, settings included. **`aria-hidden` does not license sub-floor type on text a sighted user reads** — the two baselined survivors are glyphs inside a 16–20px shape whose meaning is carried by a sibling, not prose. Enforced by `tiny_text_offenders()` in `scripts/check-design-system-v2.sh`, whose pattern was blind to the 11px case until #2858 — see rule 300.

87. **`text-neutral-text-disabled` on `bg-neutral-surface-sunken` is prohibited** — this
    combination yields 1.97:1 contrast, failing WCAG 1.4.3 on all text sizes. MINIMAL severity
    labels must use `text-neutral-text-secondary` (#6B6965, 3.12:1 on #EBEBEB) at minimum.
    This prohibition applies everywhere in the app, not only to risk register.
    The disabled token has almost no contrast headroom, so the prohibition extends to **any
    surface darker than `bg-neutral-surface` (#FFFFFF)** — including `-raised`, `-sunken`, and
    any `hover:bg-*` state on a row that contains disabled-token text (the hover state is the
    worst case and the one that must pass AA). Informational text that must stay legible uses
    `text-neutral-text-secondary` as the floor. (Surfaced by ux-review on #590.)

169. **`neutral-text-disabled` is for inert/disabled affordances ONLY — never for readable content.** The token resolves to `#A09D99` (~2.66:1 on white) light / `#64748B` (~3.7:1 on navy) dark — both below the WCAG 1.4.3 AA 4.5:1 floor for normal text. De-emphasized but *readable* content — timestamps, "by {user}" attributions, parenthetical context (the `SprintDailyDeltaPanel` since-hint and burndown `prior → current` context were the #925 ux-review 🔴) — must use `neutral-text-secondary` (4.63:1 light / 7.45:1 dark, passes), and lean on **size/weight** for the quieter visual hierarchy, not a sub-AA color. Reserve `neutral-text-disabled` for genuinely non-interactive/disabled controls where the low contrast *is* the "you can't use this" signal. Corollary (the #925 burndown 🔴): when meaning is carried by an `aria-hidden` glyph + semantic color (an ▲/▼ arrow + green/amber), the accessible name must restate that meaning in words (`aria-label="Remaining work down 8 points — on track"`), not just the raw number — the SR user otherwise loses the polarity a sighted user reads from the arrow/color (1.4.1).

118. **Settings-surface density exception (rules 5, 45, 50).** Pages and components under `features/settings/` use a compact admin density: `text-[11px]` / `text-[10px]` for secondary and label text, and `h-6` / `h-7` controls, are permitted — an explicit override of rules 5, 45, and 50. Rationale: settings is a desktop-admin-first surface, and matching the established Workspace/Project/Program settings density (e.g. `WorkspaceMembersPage`, `ProjectWorkflowPage`) is better UX than per-component rule conformance that would make one page visually inconsistent with its siblings. This exception is **scoped to `features/settings/` only** — it does not apply elsewhere. Two clauses remain non-negotiable inside settings: (a) every interactive control still requires the full rule-4 ring, **in the form rule 4 prescribes for its control type** — `focus:` for standalone triggers, menu rows, tabs, and chips-as-buttons per the rule-214 carve-out (Firefox/desktop Safari withhold `:focus-visible` on pointer-initiated focus regardless of surface, so the density exception covers sizes and text, never ring form), `focus-visible:` for form fields; navigating anchors (`EnterpriseBadge`, doc links) keep `focus-visible:` since a clicked link does not retain focus; (b) a third-party-fidelity preview (e.g. a Slack-message mock) may use the third party's literal palette as product content, exempt from rule 8, but must carry a code comment stating the intent. Modal focus-trap/restore and sub-44px touch targets remain a known codebase-wide a11y gap tracked separately — not introduced by, nor required to be fixed in, settings MRs. The settings density exception floor is `text-[10px]`; `text-[9px]` and below are prohibited everywhere, including settings.

288. **Inside a `useFocusTrap` container, a `tabIndex={-1}` programmatic focus target must never be the first or last element in the trap's *tab* order — seat focus on a real focusable, or give the trap a focusable sentinel before/after it.** `useFocusTrap`'s `FOCUSABLE_SELECTOR` ends in `[tabindex]:not([tabindex="-1"])`, so a `tabIndex={-1}` heading/paragraph/status node is **invisible to the trap**: it is not in `focusables()`, so the `activeElement === first` / `=== last` wrap branches in the Tab handler never fire and the browser's native Tab/Shift+Tab runs unguarded. When such a node is focused and nothing focusable precedes it inside the container, **Shift+Tab walks straight out of the dialog** — the #1776 escape the trap exists to prevent, reintroduced through the front door. The trap's own re-seat effect does not save you: it skips whenever focus is already inside the container, and a target focused later (on a poll reaching a terminal state, on a mutation settling) never re-runs it at all. Rule 224's "focus the heading on mount" pattern is still correct — it is safe in `RouteErrorBoundary` only because that surface's heading sits *after* focusable chrome, which is an accident of that layout, not a property of the pattern. So when copying it: (a) prefer focusing the surface's **primary action** when the outcome has one and needs no reading (this is also the better UX — one keystroke to the next step); (b) when the user must read before acting, focus the `tabIndex={-1}` outcome node **only if** the container renders a focusable ahead of it in DOM order, otherwise the trap has a hole on Shift+Tab; (c) whichever you pick, the target carries a `focus:` ring (never `focus-visible:`, which browsers may withhold on a *scripted* `.focus()` — the rule-204(b)/214 caveat) and never bare `focus:outline-none`, or the sighted keyboard user is left with focus at an invisible location. Verify by tabbing **backwards** from the auto-focused element — a forward-Tab-only check passes on a broken trap. **The exclusion is narrower than it looks, and the other half of it bites harder.** `[tabindex]:not([tabindex="-1"])` is only the *last* branch of the selector; the earlier branches — `button:not([disabled])`, `input`, `select`, `textarea`, `a[href]` — match on TAG, and none of them re-checks `tabindex`. So a **native focusable carrying `tabIndex={-1}`** is the inverse case: it is not invisible to the trap, it is wrongly VISIBLE to it. A roving-tabindex group built from `<button tabIndex={-1}>` (web rule 167's model, i.e. every segmented control in this tree) puts all of its options in `focusables()` even though only one is a real tab stop, so the trap's `first`/`last` resolve to elements the user can never Tab to — and the `activeElement === first` wrap branch then never fires from the stop they actually reach. If that group sits at either end of the container, Shift+Tab (or Tab) walks straight out of the dialog. This is latent wherever real focusables happen to bracket the group and goes live on the next reorder, which is exactly what #3130 did to `NewProjectModal`. The fix is to apply `:not([tabindex="-1"])` to **every** branch, not just the generic one — see `features/shell/NewProjectModal.tsx`'s local `getFocusable` for the corrected form. `hooks/useFocusTrap.ts` and its ~11 hand-copied siblings still carry the original selector (tracked separately); until that lands, do not assume the shared hook agrees with the corrected copy. Reference: `components/import/CsvImportWizard.tsx` (result step), `hooks/useFocusTrap.ts`, `components/RouteErrorBoundary.tsx`.

289. **A server-derived advisory signal may be cleared by client state only for the specific item the user acted on — never re-derived, and never allowed to drain a count the server owns.** An "N items need your attention" banner computed from a server field (import mapping confidence, validation severity, sync conflict class) drains as the user works only if each clear is a *fact about that item* the client can know. Two failure modes, both of which ship looking correct: (a) **cross-item staleness** — resolving item A changes the server's verdict on item B (a duplicate claim released, a constraint satisfied), but the client only rewrote A, so B keeps a now-false advisory until the next round-trip; (b) **round-trip laundering** — the client echoes its *whole* current state back as an override on re-validate, so the server marks every item "user-chosen" and returns zero flags, silently converting items the user never reviewed into items they appear to have approved. Send only the fields the user actually changed, keep the server's original verdict alongside any local override so an untouched guess still reads as a guess, and treat a count the server computed as stale-until-refetched rather than recomputing it locally. The tell: an advisory whose whole purpose is "look at these two of eleven" that reports zero after the one action the UI invites. Reference: `components/import/CsvImportWizard.tsx` (`handleFieldChange` / "Re-check mapping"), `hooks/useCsvImport.ts` (`toColumnMap`, `flaggedColumns`).

290. **A fixed-height chrome strip that can grow (a status cluster, a tab rail, a filter row) gets an explicit overflow rule — it scrolls; it never pushes its neighbours — and the rule is the whole contract below, not just `overflow-x: auto`.** A row of `shrink-0` segments with `white-space: nowrap` and no overflow rule does not wrap and does not scroll: it *pushes*, silently, at whatever viewport the user happens to be on, and the thing it pushes is whatever sits next to it (in the shell bar, the breadcrumb, and then the account chip straight off the screen). "It fits today" is not a rule — the first surface to add a segment breaks it, and nobody measures. Seven parts, all load-bearing: (a) **`min-w-0` + `overflow-x-auto`** on the strip, with **`[&>*]:shrink-0`** on its children — without the child rule the flex items compress instead and the overflow never happens, so the strip silently degrades to unreadable segments (the #2208 trap read from the other side); (b) a **`min-w-*` floor** on the strip, because a `min-w-0` box under shrink pressure is driven to *zero* before a rigid neighbour yields a pixel — with no floor the strip vanishes, taking with it the scroll affordance that was supposed to save it; past the floor the neighbour truncates, which is the correct order of sacrifice; (c) **hidden scrollbar** (`[scrollbar-width:none] [&::-webkit-scrollbar]:hidden`) so overflow appearing reserves no gutter and shifts nothing; (d) **both edge fades**, `aria-hidden` + `pointer-events-none`, each rendered only while that side actually overflows — a right-only fade is only correct for a strip that always scrolls from a fixed left origin (the board), and a strip whose offset moves when Tab focuses a segment is not that; (e) **`tabIndex={-1}` chevron nudges as the pointer-only path** — with the scrollbar hidden, a vertical-wheel mouse has *no* way to scroll the strip, so without chevrons a scrolled-out control is unreachable for a large share of desktop users; they are never the keyboard path, which is Tab; (f) **no `tabindex` on the region itself** — axe's `scrollable-region-focusable` is satisfied by focusable children, and a `tabindex` there mints a redundant tab stop; the corollary is that **every child must be focusable**, or the region becomes both unreachable and an axe failure; (g) **motion gated** — `scroll-smooth motion-reduce:scroll-auto` plus `behavior: reducedMotion ? 'auto' : 'smooth'` on the nudge (rule 70: motion only, never function). **Overlay corollary (the rule that bites):** `overflow-x: auto` establishes a clipping context on *both* axes and `z-index` does not defeat it, so **only children whose popovers portal to `document.body` or are `position: fixed` may live inside such a strip** — an in-flow `absolute` panel (the pre-rule-253/260 shape, e.g. `QuickLogTime`, `CreateMenu`) is clipped the moment it opens and must stay outside the scroller. Reference: `features/shell/StatusClusterScroller.tsx` (the implementation), `features/shell/TopBar.tsx` (the scroll/pinned split and the `shrink-[9999]` weight that makes the strip, not the breadcrumb, absorb the squeeze), `features/shell/ShellNavScroller.tsx`, `hooks/useHasScrollRight.ts`.
291. **A "the baseline is already on screen" predicate must also be checked against whether the *derived value* is already on screen — the component that supplies the baseline is usually printing the delta too (#2531).** Rule 284 says a value renders once per surface; this is its inverse, and it is the harder one to see. When a chip or strip decides it may print a bare signed delta *because* some other component supplies the reference point, that reference-supplying component is almost always the same one that already computed and printed the delta — so the predicate that unlocks the terse form is the same fact that makes the whole fragment redundant. The reference failure: added time's `BASELINE_ON_SCREEN_VIEWS = {'schedule'}` qualified Schedule because `ScheduleForecastBar` renders a dashed `CPM: Oct 24` chip, but the chip *beside* it already reads `P80: Nov 4 (+11d)` — from the same `delta_vs_cpm` the premium is derived from — so the one place a bare number was legible was the one place it was already printed, twice on screen at once with nothing marking either as authoritative. Three obligations: (a) **grep the baseline-supplying component for the derived value, not just for the baseline date**, before adding a route to a baseline-on-screen set; (b) when the grep finds it, the correct outcome is to **suppress the new fragment on that route** — not to add a qualifier, and not to suppress the older, page-level rendering, which is the one the user came to that page for; (c) a *popover or drawer* row is not a second render in this sense and may stay, because it is behind a deliberate click and is usually the only carrier of the operational states (`needs estimates`, a stamped stale read) that the page-level rendering structurally cannot express. Corollary: when two surfaces print one server field they must also share **one formatter** — `useForecastPresentation.deltaLabel` emits ASCII `-4d` while `addedTime.deltaLabel` emits U+2212 `−4d`, which is invisible until something puts them in the same row. Reference: `features/shell/addedTimeChip.ts`, `features/schedule/{useForecastPresentation,MobileMonteCarloCard}.tsx`.

325. **A copy helper that writes a user-facing sentence is not shipped until something imports it — and on a surface where N gestures route a sentence, all N do, or the one that does not is the frequent one.** `insertSentence()` was written with its siblings, reviewed with them, tested with them, and imported by nothing for three releases (#3018): seven of the outline's eight structural gestures announced themselves through the live region and joined the session trail, and the eighth — **insert, the most frequent act on the surface** — was silent to a screen reader and left no record. That inverts the contract's own intent, since the acts performed constantly are the ones whose feedback matters most, and it is invisible to every gate we run: the helper had unit tests (they pass on a function nobody calls), the integration tests covered the four gestures that *were* wired, and a11y scans see a live region that is present and correctly formed but never written to. Four obligations: **(a)** route the sentence through **one helper**, and make its argument **required** — the recurrence guard is the type system, not a review, because an optional "and also announce it" parameter is exactly what the next insert path will omit; **(b)** record on **success**, not on the gesture — a trail entry for a row the server refused is worse than no entry, so bind it in the mutation's `onSuccess` the way delete does, and cover it with a mock that can *refuse* (a mock that only ever succeeds cannot tell a click-time record from a success-time one); **(c)** the sentence must be derived from **the same source as any statement the control already made** about where the act will land — `insertBelow` appends at the end of the parent's children, so a trail entry naming the *focused* row would contradict the toolbar sentence the user read before pressing the button; two descriptions of one mutation, disagreeing, is worse than one; **(d)** assert **each** path individually — a shared assertion over "an insert announces" lets three of four regress behind the one that still passes, which is how a suite covering indent/outdent/drag/delete stayed green through this. The general form: **when a module exports a family of related pure functions, an unimported member is a defect, not dead code** — the family exists because a contract said "every one of these", so the gap is the contract being broken, not an unused export. Reference: `features/schedule/trail/structuralActs.ts`, `ScheduleView.tsx` (`createNewTask`'s required `sentence`), `buildMode/insertTarget.ts` (`landingSiblingOf`, shared by the toolbar statement and the trail sentence).

330. **A touch target built as a `before:` pseudo-element must be SIZED, never `inset`-ed — an inset box is `size − 2×border` wide, and no vitest assertion in this repo can see the difference.** The row-edge insert `+` on the Schedule outline is a 16px disc that cannot grow (it straddles the row boundary, so a 44px circle would cover the name cell of the rows on *both* sides of it), so its target is a `before:` box drawn around the mark. It shipped as `before:-inset-3.5`, and `16 + 2 × 14 = 44` is the arithmetic that made that look correct. In a browser it measured **42**: an absolutely positioned pseudo-element resolves `inset` against its **padding** box, and Preflight's `border-box` sizing puts the control's 1px `border` *inside* its 16px border box — so the containing block is 14px, not 16, and the box came out two pixels under the floor for the control's entire life. Three obligations. **(a) Size the box, do not inset it.** `before:w-[var(--x)] before:h-[var(--x)]` with `before:left-1/2 before:top-1/2 before:-translate-x-1/2 before:-translate-y-1/2` is immune to the border, to any padding added later, and to the disc's own size; the inset form silently subtracts whichever of those changes. This is rule 315's `inset-y-0` corollary — *size a target from an explicit length, not from insets* — reaching a second geometry. **(b) The size comes from the row-height owner through a CSS custom property, not a Tailwind literal.** A Tailwind class is a static string, so writing the 44 in it is a module-scope capture of a runtime value (rule 315(b)); emit `--insert-tap-size` from `scheduleConstants` in the inline `style` and let the arbitrary-value class read it. **(c) A browser is the only instrument that can check this — jsdom renders no pseudo-element geometry at all**, so a vitest suite can pin the *mechanism* (the custom property, the class shape, the absence of any `before:*inset*`) and nothing more; the measurement belongs in Playwright via `getComputedStyle(el, '::before')`, paired with an `elementFromPoint` hit test in the overhang so a box that exists but sits behind something still fails. The general form: **when a gate is structurally blind to a property, the unit test asserts the mechanism and a browser asserts the value — do not let the mechanism assertion read as coverage of the value** (rule 300). Reference: `features/schedule/scheduleConstants.ts` (`INSERT_DISC_SIZE`, `INSERT_TAP_SIZE_COARSE`, `INSERT_TAP_INSET_COARSE`), `features/schedule/TaskListRow.tsx` (the `+`), `TaskListRow.buildMode.test.tsx`, `e2e/schedule-coarse-row-height.spec.ts` — #3029.

366. **Raising a control to the 44px touch floor is a LAYOUT change in every container that control renders in — enumerate them and measure each, because the one that overflows does it silently.** The Duration cell's `d`/`h` picker was `h-7 w-8` with no coarse branch, so it stayed 28px on a tablet (#3212). Sizing it from the row-height owner is the easy half; the half that bites is that the pair went from 66px to 90px wide, and a control's width is a claim on a box somebody else owns. The issue named one layout — the 540px drawer, where the Duration track is 126.25px and the cell's content box 97px — and there the 90px group fits with **7px** to spare. It also renders in a second layout nobody named: `TaskDetailDrawer` renders its `content` **twice**, once per shell (`hidden md:flex` 540px slide-in, `md:hidden` 85vh bottom sheet), and in the 356px sheet the strip's four tracks left an **89px cell with a 60px content box** — which the *old* 66px picker already overflowed by 6px and the new one would have overflowed by 30. A touch-target fix that lands on the tablet and regresses the phone has not met the floor; it has moved the failure to the device the floor exists for. Four obligations. **(a) Enumerate the containers before you pick the size, and count SHELLS, not components** — one component with a breakpoint-branched shell is two layouts, and grepping the component's importers finds one of them. **(b) The container yields, not the target.** 44px is not negotiable, so the fix is the strip becoming `grid-cols-2 md:grid-cols-4` below the breakpoint where four tracks stopped fitting — never a smaller control, and never a horizontal scroller for a four-value read-only strip. **(c) The overflow is invisible to every gate we run.** The grid item is `min-w-0` and the control `shrink-0`, so the box neither clips nor scrolls — it paints over its neighbour, and the picker, the Float cell and the strip all keep boxes and all pass `toBeVisible()` (rule 354(e)). Assert **non-intersection of `boundingBox()`s**, in Playwright, at each layout's own viewport; jsdom resolves no lengths, so the vitest half pins the custom property and the class shape and nothing else (rule 330(c)). **(d) A pre-existing overflow is a finding, not a baseline.** The 6px was already shipping and nobody had measured — which is the same reason #3211 exists, one release earlier, on this same cell. When a fix's arithmetic says "it still fits", that sentence is the trigger to open a browser, not a substitute for having done so. Reference: `features/schedule/scheduleConstants.ts` (`resolveUnitSegmentSize`), `features/schedule/duration/DurationUnitPicker.tsx`, `features/schedule/TaskScheduleStrip.tsx` (the two-up strip), `e2e/duration-drawer-edit.spec.ts` (540px, 390px and fine-pointer measurements) — #3212, surfaced by `ux-review`.

## Color and tokens

*Color is a token, never a literal, and a shade carries a role.*

8. **No custom hex colors in components** — always use Design System tokens from `tailwind.config.ts`. The `design-system-v2` gate (`scripts/check-design-system-v2.sh`) ratchets hex **color literals** — a `#hex` that is quoted (`'#f59e0b'`), in a Tailwind arbitrary value (`bg-[#…]`), or a CSS value (`stroke: #fff`). It does **not** count a bare `#1236`-style issue reference in a comment, so cite issue numbers freely — do **not** rewrite them to "issue N" to appease the gate (that was a workaround for an old false positive, now fixed). If the gate fails, you added a real hardcoded color: tokenize it, don't launder the number.

8a. **`--chrome-*` tokens are for fixed UI furniture** (sidebar, Schedule task-list panel, TopBar) that follows the active theme. `--neutral-*` tokens are for page content surfaces. Use `bg-chrome-surface` on shell chrome, `bg-neutral-surface` on content areas. Both adapt with the `.dark` class on `<html>`. In dark mode `--chrome-surface` equals the legacy `gantt-surface` deep navy (#0F1117). Chrome tokens: `surface`, `surface-raised`, `border`, `text-primary`, `text-secondary`, `row-hover`, `row-active`, `grid`.

8b. **`--sem-*-bg` tokens are for badge pill fills and status cards** — `bg-semantic-critical-bg`, `bg-semantic-at-risk-bg`, `bg-semantic-on-track-bg`, `bg-semantic-warning-bg`. These are pre-computed RGBA values so they cannot be combined with Tailwind's opacity modifier. Always pair with the matching full semantic token for text/border (e.g. `border-semantic-at-risk/80 bg-semantic-at-risk-bg text-semantic-at-risk`). **Never substitute `bg-semantic-{state}/N` (the opacity modifier) for `bg-semantic-{state}-bg`** — `/N` applies Tailwind's alpha to the token's RGB channels, which are **not the `-bg` token's channels**. For `warning` the base is `133 77 14` (#854D0E, the AA-safe *text* color) in light and `250 204 21` (#FACC15, yellow) in dark, while `--sem-warning-bg` is `rgba(217,119,6,…)` (#D97706 brand amber) light and `rgba(251,146,60,…)` (orange) dark: **a different hue in both modes**, not a weaker one — `globals.css` says so itself ("Brand amber #D97706 lives only in `--sem-warning-bg`"). `on-track` diverges the same way in light (`49 111 87` vs `62 140 109`); for `at-risk`/`critical` the RGB matches but the `-bg` alpha is mode-specific against a `/N`'s single fixed alpha. The `-bg` tokens are the only correct form for semantic badge/pill/card fills. A **solid** semantic indicator (a progress/countdown bar) uses the bare token at full strength, not a `/N`; an **interaction wash** (`hover:bg-semantic-critical/5`, `hover:bg-semantic-critical/90`) is legitimate opacity and out of scope. There is no `semantic-success` token — `on-track` is the green; Tailwind emits no CSS at all for an undefined token, so a typo'd semantic class renders as nothing rather than failing. Enforced by `sem_tint_offenders()` in `scripts/check-design-system-v2.sh` (zero tolerance; no check existed before #2858). (Surfaced by ux-review on #691.)

8c. **`.tppm-mono` applies JetBrains Mono with tabular numerals** — use it on every numeric value: KPIs, percentages, dates, durations, counts, build hashes. It is defined as a Tailwind utility in `globals.css` and maps to `font-family: 'JetBrains Mono'; font-feature-settings: "tnum"`.

8d. **`bg-neutral-overlay` is the scrim token for a modal/slide-out's full-screen backdrop** — never a raw `bg-black/N` literal. Like the `--sem-*-bg` family (rule 8b), it is a pre-computed RGBA custom property (`rgba(0, 0, 0, 0.4)` in both light and dark — the scrim doesn't get a dark-mode-specific treatment) and therefore **cannot be combined with Tailwind's `/N` opacity modifier**; write `bg-neutral-overlay` alone, not `bg-neutral-overlay/40`. Popover/edge scrims that intentionally use a different opacity for a lighter touch (e.g. a mobile drawer's `/30` edge, a cheatsheet's `/20`) are a distinct visual role, not this token — `bg-neutral-overlay` is specifically for the `role="dialog" aria-modal="true"` full backdrop. (Surfaced by ux-review follow-up, issue 575.)

286. **A `--sem-*-bg` token may never be the sole background of a floating surface — a portaled, `position:fixed` or `absolute` panel needs an opaque base (`bg-neutral-surface`), with its warning/error tone carried by the border, icon and text (#2447).** The `-bg` family is 8–15% alpha (`--sem-at-risk-bg: rgba(146,64,14,0.10)` light / `rgba(251,146,60,0.15)` dark), which rule 8b already scopes to **badge pill fills and status cards** — surfaces that sit on an opaque parent, where the alpha composites over a known background. A floating surface has no such parent: it composites over whatever page content it happens to overhang, so the rows, digits and chips behind it read straight through the copy. This is not a dark-mode bug — light mode is *worse*, because its alpha is lower (10% vs 15%), so the popover body ends up ~90% transparent over the task list. Two invariants: (a) **the opaque base is `bg-neutral-surface`, not a hand-composited hex** — a pre-multiplied "amber over white" token would bake in an assumption about which surface the panel floats over, and a portaled panel does not know; (b) **the semantic tone survives the swap** because it was never carried by the fill alone — the border (`border-semantic-at-risk`), the `WarningIcon` and the heading/body colour all remain, which is also what keeps colour off the sole-signal path (rule 6). `ScheduleCommitPopover` (`bg-neutral-surface border border-neutral-border`) is the reference every pop surface should already have matched. The trigger *chip* keeps `bg-semantic-at-risk-bg` — an in-flow element on an opaque row is exactly rule 8b's sanctioned use, and only the floating panel changes. Reference: `features/schedule/MissingCommittedStartChip.tsx`, `features/timesheet/TimesheetCell.tsx`.

## Signal encoding

*How a value tells the truth about itself — including to someone who cannot see it.*

120. **Health/variance values pair color with a non-color signal (rule-12 reinforcement for rollups).** A health band card shows the band *text* ("At risk") alongside the semantic color and an `aria-label` on any pill; a day-variance shows a signed `+9d` / `-3d` so the sign — not only the color — conveys late-vs-early. Counts and scores are plain numerals. This keeps KPI cards WCAG 1.4.1-compliant without a legend.

119. **A configured-but-not-computable metric renders as a muted card with a reason, never hidden.** When a dashboard or overview is driven by a user-selected metric set (e.g. the program rollup KPIs), a metric the user enabled but for which no value can be computed yet MUST render as a muted card (`border-dashed border-neutral-border`, value `—` in `text-neutral-text-disabled`) with a short plain-language reason in the `sub` slot (e.g. "Needs cost data"). Do not silently drop it from the grid — the user enabled it and must see *why* it is blank. The machine-readable `reason` from the API drives the human label via a lookup map; never render the raw reason code. See `ProgramOverviewPage.tsx`.

161. **A responsive abbreviation must always carry its full accessible name.** When a control shows a short label at narrow widths and the spelled-out term at `md:`+ — the `<span className="hidden md:inline">{full}</span><span className="md:hidden">{abbrev}</span>` pattern established by the Signal-privacy ladder rungs (`SignalLadder.tsx`), the matrix-lens column headers (`SignalMatrixLens.tsx` `<th>`), and any future status/role chip — the **full** term must be the element's `aria-label` (and `title` for hover) so a screen reader or pointer never gets the ambiguous abbreviation regardless of which span is visible. The decorative abbrev/full spans carry no `aria-*`. Where horizontal space always allows (a roomy vertical list, e.g. the raise-ceiling radio options), skip the responsive split and render the full term directly. A single source-of-truth label map pairs the abbreviated and full forms (`AUDIENCE_RUNG_LABEL` / `AUDIENCE_RUNG_LABEL_FULL`); never inline either string.

171. **`aria-label` on a non-widget element (`<p>`/`<div>`/`<span>`) does NOT suppress its descendant text in NVDA/JAWS — to expose a multi-span line as ONE accessible string, mark every visible child `aria-hidden`.** The `BoardSprintHeader` meta line ("{name} · {range} · Day N of M") is the reference: the `<p>` carries the composite `aria-label`, and **all** visible children — the name/range/counter spans AND the `·` separators — are `aria-hidden="true"`, so the screen reader reads only the label, never the label *then* the spans again (the double-read bug the #1138 ux-review caught, WCAG 1.3.1). This applies only to non-widget containers: on a real widget (`button`/`role="radio"`/etc.) `aria-label` does override the accessible name, so this extra step is unneeded there. The alternative pattern — `role="presentation"` on the container + a single `sr-only` span for the composite string — is equivalent; pick one, never leave readable child spans exposed alongside a container `aria-label`.

216. **A status adornment inside a header decides `aria-hidden` vs `role="img"`+`aria-label` by whether its meaning is ALREADY in the header's accessible name — never by "it's a small glyph, hide it".** A header (a board column `<h2>`, a card title, a lane label) that already folds a state into its own `aria-label` — e.g. the column name computed as `` `${label}, ${count} tasks, over limit` `` — must render the *visual* chip for that same state as `aria-hidden` so a screen reader hears it once, not twice (the `WipBreachChip` case, ADR-0130 D2). But an adornment that carries **net-new information not present in the accessible name** must be an announced element (`role="img"` with an `aria-label`, plus a `title` mirroring it), or it silently vanishes for AT users. The `WipTrendArrow` (#1213) is the second case: the recent-trend direction is nowhere in the column's `<h2>` name, so it is `role="img" aria-label="trending up toward WIP limit"` with the visible ▲/▼ glyph `aria-hidden` inside it. Before adding a header glyph, check the header's computed `aria-label`: if the state is in there, `aria-hidden` the glyph; if not, label the glyph. Do NOT make a net-new-info glyph `aria-hidden` (drops it for AT) and do NOT label a redundant glyph (double announce). Direction/trend meaning must also survive color loss (rule: color-not-alone) — the glyph orientation carries it, amber (`text-semantic-at-risk`, AA-as-foreground per the token) marks only the actionable "about to breach" case, everything else is `text-neutral-text-secondary`. Reference: `WipTrendArrow` (labeled, net-new) vs `WipBreachChip` (aria-hidden, redundant) in `features/board/BoardView.tsx`.

220. **A live region (`role="status"` / `role="alert"` / `aria-live`) must not carry a per-tick-updating accessible name — announce discrete state transitions (start / stop / appear), never a running clock or counter; put the ticking value in an `aria-hidden` element and keep the region's name stable.** A live region whose accessible name embeds a value that changes every second (a running timer, an elapsed counter, a live countdown) fails two ways depending on the AT: screen readers that recompute the name re-announce roughly once per second (an announcement flood), and those that key off subtree text announce nothing on the state change that actually matters (start/stop). The region's name must reflect *what changed* (the timer started on task X; it went stale), not *the current value*. Keep the digits in a sibling `aria-hidden` span. Reference: the running-timer chip `TimerChip.tsx` (#1415, ADR-0185 §C) — `role="status"` named `Timer running on {task}` (plus the discrete `— running a long time` stale suffix), with the `formatElapsed` clock rendered in an adjacent `aria-hidden` span; contrast the safe `TaskRunIndicator` whose name changes only on discrete count changes. A non-live control (a plain `<button>`) may hold a ticking label — this rule is specifically about live regions.

255. **Any `line-clamp-*` or `truncate` element that renders user-authored or variable-length data (titles, filenames, comment previews, risk names) must expose the full value via `title` — and via `aria-label` where the clamped line is the sole channel for that value.** Rule 161 already covers truncated *abbreviations*; this extends the same guard to *user data*. A clamped line silently drops text with no hover or assistive-tech recovery, so the full string must live somewhere reachable. The task-drawer Activity timeline's secondary detail line (`features/schedule/ActivityTimeline.tsx`) is the reference: its `line-clamp-1` `<p>` carries `title={secondary}` so a long risk title or filename is recoverable on hover. Do not clamp a value whose full form appears nowhere else in the view without adding `title`.

341. **Whether a value is COMPUTED or COMMITTED is a property of the value, not of the record's workflow state — gate the cue on the value alone, and derive it from the same predicate the surfaces that act on it use.** A CPM `early_start` shown where a committed `planned_start` would go is unattributed regardless of whether the task is NOT_STARTED, IN_PROGRESS or COMPLETE: it came from the scheduler and it will move when a predecessor does. #3063 hung the drawer's computed cue off `isMissingCommittedStart()`, a *defect* predicate that additionally requires IN_PROGRESS/REVIEW/COMPLETE — so the one status that reliably has no bar on the timeline (NOT_STARTED, the state that fills the Unscheduled gutter) was the one status that rendered its scheduler date as a plain, committed-looking value with nothing anywhere explaining the blank row. Three obligations. **(a) Split the provenance predicate from the defect predicate and name both.** `isStartComputed()` answers "did a human commit this?" and drives the cue; `isMissingCommittedStart()` answers "is this task in a state it should not be in?" and drives the amber flag and its demotion. Fusing them makes the narrower one silently govern the wider one's surface, and the direction of that error is always the same — the cue goes missing exactly where the value is least trustworthy. Assert the containment (`flagged ⇒ computed`) in a test, because the reverse is what regressed. **(b) A renderer that DROPS a row and a cue that EXPLAINS the drop must read one predicate.** `GanttRenderer.drawTaskBar` and `useUnscheduledTasks` both gate on bare `!plannedStart`; the drawer did not, and a user looking at Start, Finish, Duration and a red critical-path banner had no way to learn why the row was empty. When one surface hides something, the surface a user opens next is where the reason has to be, and shared code is the only thing that keeps the two from drifting apart again. **(c) An ordinary state must not borrow the defect state's treatment.** Uncommitted-and-not-started is normal unplanned work; uncommitted-and-underway is a data-integrity problem. The second earns amber, a warning icon, and a "Move to To Do" demotion — giving the first the same treatment scolds the user for the default and teaches them to discount the color that means something on the other branch (rules 8b/12). Same fact, same explanation, calmer surface, and only the action that is not a no-op. Reference: `features/schedule/missingCommittedStart.ts` (`isStartComputed` vs `isMissingCommittedStart`), `features/schedule/TaskScheduleStrip.tsx` (`UncommittedStartNote` vs `NoCommittedStartAdvisory`) — #3063.
342. **A control that asks the user to supply a value the system has already computed is friction wearing a form's clothes — seed it, and offer the computed answer as a one-click commit.** The Unscheduled tray's `···` menu opened an empty `type="date"` input with its submit `disabled={!dateInput}`, so committing a start cost four interactions and required the planner to invent a date from nothing — while CPM's `early_start` for that exact task sat one panel away, and the write that commits it (`useCommitStartOrTodo.commitStart`) had already shipped for a different surface. Three obligations. **(a) Seed the field, never open it empty.** An input born with a disabled submit reads as "the system has no opinion", which is false here and usually false generally; the seed is the computed answer, and the fallback when none exists is the most common answer (today), not blank. Then the button is live on open and the user is *adjusting* rather than *originating* — and the disabled state means what it should, that they cleared it on purpose. **(b) When two default answers can differ, offer both and put the DATE in each label.** "Earliest" and "today" are the same day only when nothing blocks the task; a predecessor makes earliest later, a slipped plan makes it earlier, and a menu that says only "Start at the earliest" hides which case the user is in until the bar lands somewhere surprising. Collapse to a single item when they resolve to the same day — two entries with identical outcomes is a choice that cannot be made wrong, which is worse than no choice. **(c) Do not suppress the option that expresses a conflict.** "Start today" stays offered when the earliest is later: that commitment is unachievable, and the gap it creates between the committed and computed start is a real scheduling conflict the planner is entitled to state. A menu that silently removes the unachievable option prevents the user from expressing the very thing the schedule exists to surface. Corollary — the quick commit must announce. Its only visible proof of success is the row *leaving* the tray, which tells a screen-reader user nothing, and the sibling path beside it (backlog promote) had announced since #318; two paths writing one field with different feedback is the drift rule 341 is about. Reference: `features/schedule/UnscheduledTaskRow.tsx` (`quickActions`), `features/schedule/UnscheduledGutter.tsx` (`handleSetDate`), `features/schedule/scheduleUtils.ts` (`todayLocalIso`) — #3064, after #3063.
343. **A fixed-height control strip that cannot wrap and must not scroll needs a MEASURED concession ladder, and the ladder's rungs are two different kinds of thing.** Rule 290 covers the strip that is allowed to scroll; this is its sibling for the strip that is not — a toolbar whose popovers are in-flow `absolute` panels, where `overflow-x: auto` would clip every one of them (rule 290's own overlay corollary) and would make a control's location depend on a scroll offset nothing announces. The Schedule toolbar's natural width is ~1,862px against 752–1,648px of room, so it was over budget at **every** supported width and the parent's `overflow-hidden` ate the difference in silence: `Export PDF`, the `···` trigger and everything inside it were painted nowhere and reachable by nothing — not a pointer, not a scroll, not a Tab (#3076). Six obligations. **(a) Measure; do not guess with a media query.** Natural width depends on the project's own strings, on the rail being collapsed, on edit rights, and on the user's pins — a `useBreakpoint()` tier can see none of that, and every width it guessed wrong clipped without a symptom. A `ResizeObserver` + a pure `nextFitStep(step, contentWidth, availableWidth, costs)` walked until it fits, with **hysteresis** (a rung is only given back once there is its own cost *plus* a margin to spare) is what stops a drag-resize oscillating. **(b) `scrollWidth` cannot measure a strip with a `flex-1` spacer** — the spacer absorbs all slack, so `scrollWidth === clientWidth` at every width and the loop can never climb back. Sum the children and charge the spacer its floor. **(c) Every child needs `shrink-0`.** One child without it absorbs the entire overflow alone and wraps its label inside the fixed height — which is both the visible bug and the thing that hides the overflow from the measurement. **(d) Rungs are collapses or demotions, and you spend every collapse first.** A **collapse** keeps the control in the bar showing its value and costs a glance; a **demotion** puts it behind a click and costs a hunt. They are not comparable by pixels saved, so ordering by cost interleaves them wrongly — and it is what made the design's own ladder demote a control that a prior issue (#2703) had deliberately promoted *out* of the overflow. **(e) Four behaviours, not two: a command may hide, a readout may only shorten, a mode may only collapse into something that still shows its value, and tier-A demotes last or never.** Treating a Read/Author indicator as an overflowable command is how someone types into a plan they believe is read-only, so give it no `overflow` state to reach. **(f) A demoted control keeps its name and `aria-keyshortcuts`, appears in exactly one place, and its menu heading states WHY it moved** — "no room at this width" is a false sentence about a control the user unpinned, and a heading that lies about the reason sends them resizing the window for something only a settings menu can return. Two corollaries. The user-facing half belongs in the surface's own Display popover, where each row states *where the control is right now* and the footer counts pins honestly ("2 of 4 fit at this width"), because that is the only place in the product that can answer "where did my button go" — and a pin is a request, never a guarantee: nothing may clip to honour one. And **an unmeasurable strip is not a cramped strip** — jsdom, a detached node and `display:none` all report 0, so a pessimistic first-paint seed held against a zero measurement parks the toolbar at its narrowest composition forever in every environment that never lays out. Testing follows rule 300's split exactly: jsdom can assert the ordering and the anti-oscillation property and nothing else, so the *measurement* is Playwright's — and `toBeVisible()` is not the assertion, because a clipped child of an `overflow-hidden` parent still has a box and still passes it (the #2974 lesson); assert each child's right edge against the bar's. Reference: `features/schedule/toolbar/toolbarLadder.ts` (the rungs, `nextFitStep`, `measureToolbarContent`), `toolbar/useToolbarFit.ts` (the loop and its `inventorySignature` — a pin toggle changes natural width without changing the box, which a `ResizeObserver` cannot see), `toolbar/useDemotionAnnounce.ts` (focus + a polite announcement when the focused control is the one demoted), `components/toolbar/ToolbarOverflowMenu.tsx` (sections), `e2e/schedule-toolbar-fit.spec.ts` — #3076.

## Redundancy

*The class whose absence produced #2424, #2425 and #2426.*

284. **A value renders once per surface: the task drawer's summary strip is the READ surface, the sections below it are the EDIT surface, and a value belongs to exactly one of them (#2424).** The #2315 at-a-glance strip landed *on top of* the existing sections rather than replacing their content, so Status, Finish and Float each rendered **twice inside one 270px band** — the strip, then again as a control roughly 150px below. Nothing in the layout said which copy was authoritative, so both read as inputs and whichever one the user did not touch looked stale for a frame; the redesign meant to reduce density doubled it. Four invariants: (a) **anything editable is not in the strip, anything in the strip is not editable there** — Status is a `<select>` below, Finish and Float are in the Schedule grid, so all three left; the strip header carries a `read only` pill so the contract is visible, not just documented. (b) **A read-only value still does not belong in the strip if another surface already carries it** — the drawer header renders the WBS code and `DrawerRecentActivity` sits directly above the strip, so re-rendering either there would trade one duplicate for another; the strip keeps only the owner and the baseline comparison, which are carried nowhere else. This is the rule the design handoff's cell list did not know about, and the general form is worth stating: *before adding a cell to a summary surface, grep the surface for the value.* (c) **`FLAGS` renders only non-empty flag content and returns `null` otherwise** — no header, no "No flags" placeholder, no reserved height. A flag is a condition that is **false for a healthy task** *and* **actionable** (blocked, negative float); float, baseline variance, % complete and SPI are metrics every task has, and a band headed FLAGS that delivers a routine number teaches the reader to skip it, so a genuine exception later will not read as one. Critical-path membership and a missing committed start are deliberately **not** flags here — the Schedule strip carries its own critical banner and the row chip is the primary point-of-fix for an uncommitted start (rule 276), so either would be a third copy. (d) **Float keeps the `computed` qualifier treatment** (rule 276) in the Schedule grid so it never reads as editable, and **negative float turns the cell critical** as well as raising the flag. Reference: `features/schedule/{TaskSummaryStrip,TaskFlagsSection,TaskScheduleStrip}.tsx`.

## Surface states

*Loading, empty, and failed are three different things and must look like it.*

248. **A data surface's loading state is a skeleton ghost that mirrors the shape of the real content, never a bare `Loading…` text line.** Every primary surface (Schedule, Grid, My Work, Overview, Reports, Today, and — since #1774 — Board, Sprints, and the project Backlog) renders pulsing placeholder blocks while its query is in flight, so the layout doesn't jump when data lands. The idiom: one `role="status"` wrapper with an `aria-label="Loading X…"` accessible name (the E2E wait-for-paint gate resolves on this node detaching — gate specs on `getByRole('status', { name: /Loading X/i })`, not on a visible text string), and every ghost child is a `motion-safe:animate-pulse rounded-* bg-neutral-surface-sunken` block marked `aria-hidden="true"`. Mirror the surface's real shape — column ghosts for the Board (a row of lane placeholders), row ghosts for list/table surfaces (Backlog, Grid), card ghosts for card lists (Sprints). `motion-safe:` is mandatory so the pulse honors `prefers-reduced-motion`. Never gate an E2E on the *absence* of a visible "Loading…" string (it reads count-0 before the surface even mounts, racing the assertion); gate on the skeleton's `role="status"` node detaching, which is the true "loading finished" signal. **The rule covers chunk-loading as well as query-loading (#2431).** The route-level `Suspense` fallback is the *first frame of every navigation* — the single most-seen loading state in the app — and it used to be the one place that rendered the bare centred `Loading…` this rule forbids, so a Board navigation opened on ~3s of unstyled text before the (compliant) board skeleton appeared. Both loading states that have no surface shape of their own take the shared `components/LoadingSkeleton.tsx` instead of hand-rolling one: the Suspense fallback and the `/` root-redirect hold use `variant="shell"` (toolbar band + content rows — deliberately generic, because which surface is arriving is exactly what an unresolved chunk does not know), and in-page settings sections use the default `variant="rows"`. **The settings density exception covers ghost *size*, not the skeleton contract** — a settings section still ghosts, just more compactly. Reach for a surface-specific skeleton only when the real content has a distinctive shape worth mirroring. Reference: `components/LoadingSkeleton.tsx`, `router.tsx`, `features/board/BoardView.tsx`, `features/sprints/SprintsView.tsx`, `features/project/backlog/ProductBacklogPage.tsx`, `features/grid/GridView.tsx`.

177. **A primary surface's zero-data state is a warm `EmptyState`, not a bare "No data" line; its single entrance animation is `motion-safe:` only.** The shared `EmptyState` (`components/EmptyState.tsx`) is the v2 anatomy — a `role="status"` block with a decorative (`aria-hidden`) icon in a `72px` `rounded-full border bg-neutral-surface-raised` circle, a `text-[17px] font-semibold` `<h2>` title, optional `max-w-[380px] text-[13px]` orientation copy, and an optional CTA (the shared `<Button>`). Use it for the genuinely cold cases (Schedule read-mode `ScheduleEmptyState`, Risk register, Grid); surfaces with bespoke needs — role-flavored copy or multiple CTAs (`MyWorkEmptyState`, `BuildModeEmptyState`, `EmptyBacklog`) — keep their own component but follow the same anatomy. Pass `className="h-full …"` when the host must fill its area; the icon is always decorative (the `role="status"` + title carry the announcement). **Motion:** the block fades+lifts once via `motion-safe:animate-empty-state-in` (160ms brand ease; keyframe in `globals.css` beside `cmdk-in`) — gated at the class layer so `prefers-reduced-motion` users get the content with no animation (the v2 motion contract: motion only, never content — rule 70). Do not add a second always-on empty-state animation, and never animate content in/out without the `motion-safe:` gate.

246. **A TanStack Query fetch failure on a primary surface renders the shared `QueryErrorState` (`components/QueryErrorState.tsx`), never an empty or perpetual-skeleton state — a dead request must be visually distinct from "nothing here yet".** A page that destructures only `data`/`isLoading` and ignores `error` renders a failed fetch as empty (Board) or a skeleton that never resolves (Overview) — indistinguishable from a genuinely empty or slow surface, which corrupts beta feedback and support triage (#1764). Wire `error`/`isError` into the query hooks and render `QueryErrorState` in place of the empty/skeleton branch. Two variants: **`fill`** (`role="alert"`, `bg-neutral-surface`, `h-full`, centered) for a whole-page/pane failure the user navigated to (Board, Grid, Schedule) — assertive because the surface is dead; **`inline`** (`role="status"`, `rounded-card border-neutral-border bg-neutral-surface-raised`, `min-h-24` to match the skeleton footprint it replaces) for a single widget on a still-working page (each Overview widget) — polite, so a total outage does not fire N assertive announcements that interrupt each other. Retry defaults to `window.location.reload()`; pass a query `refetch` (`onRetry={() => void refetch()}`) when the hook exposes one so retry re-runs just the failed request. Copy is one terse `Couldn't load <X>.` per surface. This completes the surface-state trio with `EmptyState` (rule 177, `role="status"`, calm zero-data) and the route `errorElement` (rule 224, `role="alert"`, self-focuses on a render-throw): widget fetch error → polite in-place; empty data → calm; route throw → assertive-and-self-focusing. Reference: `components/QueryErrorState.tsx`, `features/board/BoardView.tsx`, `features/project/ProjectOverviewPage.tsx`.

224. **A route-level error surface (`errorElement`) that offers recovery actions must move focus to its heading on mount — the erroring subtree unmounted, dropping focus to `document.body`, so keyboard/AT users otherwise cannot reach the recovery CTAs.** When a route subtree throws (or a lazy chunk fails to load) React Router swaps it for the route's `errorElement`; the element that had focus (the `NavLink` the user just clicked, a button) unmounts, so focus falls back to `<body>`. An error surface whose whole point is recovery (Reload / Go to home) must pull focus to itself in a mount `useEffect` — a `tabIndex={-1}` `<h2>` with a `focus:` ring (**not** `focus-visible:`, which a browser may withhold on a *scripted* `.focus()` — the rule-204(b) / rule-214 caveat) — or the keyboard/screen-reader user has to blind-Tab from `body` to reach the only actions on the page. This is the inverse of the calm `EmptyState` (rule 177), which is a zero-data view with no required action and therefore does **not** grab focus; an `errorElement` is `role="alert"` (assertive, an error the user landed in) and self-focuses, whereas `EmptyState` is `role="status"` (polite) and does not. Reference: `components/RouteErrorBoundary.tsx` (the `headingRef` mount-focus + `isChunkLoadError` chunk-vs-generic copy split), wired as `errorElement` at the route-tree root, on `ProjectShell`/`ProgramShell`, and — since #2834 — on every shell child via `shellRoutes()` (rule 298).

298. **A route boundary is inherited, never opted into: every child of the `AppShell` route gets its `errorElement` from `shellRoutes()` in `router.tsx`, and a recovery action that leaves the document asks the write queue itself before discarding it.** Issue 1654 added the shell-preserving `errorElement` by hand to `projects/:projectId` and `programs/:programId`; every route added afterwards (My Work, My Assets, Timesheet, the notification inbox, `me/settings/*`, the org resource catalog, the programs list) silently missed it, because omission was the default and protection the exception (#2834). Without a boundary *below* the shell, a render throw or a failed lazy chunk bubbles to the `RequireAuth` net and unmounts `AppShell` — which takes `PendingWritesGuard` with it, so the `beforeunload` warning that is the only thing protecting TanStack Query's **in-memory** write queue is gone on the very screen whose job is to offer a reload. Two consequences, both load-bearing: **(a)** add new shell routes *inside* the `shellRoutes([...])` call and do not paste an `errorElement` of your own unless you genuinely want a closer boundary (a nested shell like `ProjectShell` is a legitimate one — the helper keeps any `errorElement` a route already declares); **(b)** any recovery affordance that reloads or hard-navigates reads `getPendingWriteCount()` at click time and interrupts with a focus-trapped `role="alertdialog"` naming the count, because the guard it would otherwise rely on may already have been unmounted by the same crash. Read the count imperatively, not with a hook — the boundary can render *outside* the `QueryClientProvider`, which `AppShell` owns. The enumeration test in `src/router.test.tsx` is the regression guard: it fails if any shell child lacks a boundary, which is the only thing that stops this from recurring. Reference: `router.tsx` (`shellRoutes`), `components/RouteErrorBoundary.tsx` (`DiscardPendingWritesDialog`), `hooks/useSyncStatus.ts` (`getPendingWriteCount`), `src/router.test.tsx`.

337. **Every rung of one ordered notice ladder shares one live-region contract — decide it at the ladder, from the most announcement-worthy branch, never per rung.** When a component returns one of N notices from a single ordered `if` chain and the rungs look the same to a sighted user, they must all be live regions or none of them may be. A rung that quietly drops `role="status"`/`aria-live` hands the AT user a different product depending on which branch the server happened to hit, and nothing surfaces it: the markup is valid, `role="note"` is a real role, and an axe scan sees a well-formed note. The same reasoning covers the *action*: if one rung names a remedy, every rung must either offer that remedy or name a different one honestly — a notice that says "reconnect to replace it" on a card whose only controls are Sync now and Disconnect is worse than a notice that says nothing, because the user goes looking for a button that is not there. A notice that is genuinely a different *kind* of thing belongs outside the ladder, not inside it as an odd rung: `ConnectedAccountsPage`'s truncation note is neutral-toned and non-live because a truncated pull **succeeded**, so it renders as its own sibling rather than as a fourth branch of the health ladder. Reference: `features/me/ConnectedAccountsPage.tsx` (`ConnectionHealthNotice` — three rungs, all `ReconnectBanner`, `actionLabel={null}` on the rung whose remedy is not the wizard; `TruncationNotice` deliberately outside it), `features/integrations/syncOutcome.ts` (`syncFailureNeedsReconnect`) — #2925.

338. **Demoting a creation surface means deleting its FORM, not its affordance — and an affordance that carries context a route cannot express must keep its own control.** Case 18's disposition table said to demote the board's lane `+` into the Designer via `?author=`, and following that literally would have dropped three facts silently: the synthetic phase-less lane commits `BACKLOG` while a real phase commits `NOT_STARTED` (#387's VoC outcome, decided on purpose), and since #2967 a cell also carries a named lane. `?author=` has no representation for any of them, and widening it would turn a **hand-editable URL into a board write path** — `parseAuthorIntent` is strict precisely because the consumer's job is to create a row. So the lane keeps its control and loses its `TaskFormModal`, which is what the table was actually objecting to; the empty board, which has no lane and therefore no status, container or lane to preserve, is the one case the table is right about unamended. Four obligations. **(a) Ask what the affordance CARRIES before demoting it, not what it looks like.** Two buttons that both "create a task" are different surfaces if one of them knows where the row goes. The test is whether the destination route can express every fact the position implied; if it cannot, demoting is a silent data change wearing a refactor's clothes. **(b) The replacement shares the ORIGINAL's behavior through a hook, not through a copy.** `useRapidCompose` owns the optimistic clear, the error restore that never clobbers a half-typed replacement, the container-bound Escape (an input-bound one stops honoring the `aria-keyshortcuts` it advertises the moment focus tabs to Add), and `readOnly`-never-`disabled` (a disabled input is blurred by the browser, closing the soft keyboard, and nothing re-focuses). Two capture surfaces that drift are worse than one modal. **(c) Carry the old surface's DEFAULTS across, and assert the write rather than the widget.** `duration: 1` is what the modal created here — the backlog rail's `0` is the milestone definition in the locked vocabulary, so reusing it would have minted a zero-duration row for every task added to a phase. Once the status is no longer a select the user can see, the only honest assertion is what the POST body carries. **(d) A field on the payload TYPE is not a field on the wire.** `board_lane` was declared on `CreateTaskPayload` and type-checked green while `useCreateTask`'s `mutationFn` — which builds its body key by key — dropped it before the request; the spread that passed it in defeated excess-property checking too, so nothing anywhere complained. Grep the mutation body, not the interface, and pin both arms: forwarded when set, **absent** when not, because an unconditional spread puts `undefined` on every create the app makes. Corollary — when the demotion strands tests, check whether the assertion was ever a journey: three of this change's e2e casualties were duplicating `TaskFormModal.test.tsx` through a browser, one would have passed vacuously against a dialog that no longer renders, and only the genuinely-different ones were re-homed. Reference: `features/board/useRapidCompose.ts`, `features/board/LaneComposeField.tsx`, `features/board/BoardView.tsx` (`handleAddTask`, `handleComposeCommit`), `hooks/useTaskMutations.ts` — #2952.

339. **A control that performs two acts must SAY which one the next press does — and the label and the accessible name must be one derived string, spelled for the platform reading it.** `⌘⌥P` / `+ Phase` gained a subject in #2951: with a leaf row focused it adopts **that** row as the container; with nothing focused it still mints a fresh phase at the insertion point. The control's tooltip said "Add new phase, with its first task" for both, which is a claim about a write the user is about to make **to a row it never mentions** — rule 326's failure with a subject rather than a keystroke. Four obligations. **(a) Derive the sentence once and use it for both surfaces.** The `title` and the `aria-label` were separate literals here, and they had already drifted: the tooltip said "with its first task" and the accessible name did not, so a screen-reader user was told strictly less about what the press would do than a sighted one — rule 328's "a fact with three phrasings has no owner", reached by two. **(b) Never hardcode a chord in an accessible name.** The same `aria-label` spelled `Option+Cmd+P` as a literal while the tooltip beside it resolved `formatChord('mod+alt+p')`, so every Windows and Linux user was told the Mac chord by the one surface they could not visually correct against — and three e2e specs asserted the wrong string, passing only because the literal matched itself. Derive it, and derive it in the **test** too: a spec that restates the chord rots exactly as the label did and will pass on whichever OS CI happens to run (#3028, rule 326(d)). **(c) The stated act is the observable proof the mode is armed.** A gesture whose arming lives only in a component's state cannot be asserted except through the write it eventually makes; a control that names its subject gives the test something to gate on *before* the click, which is what separates "the gesture is armed" from "the mutation happened to fire". **(d) Prefer a second act on an EXISTING control over overloading a directional key.** The design wrote this gesture as `⇥`, and the tree binds indent to `⌥→` — but indent means "move this row under the row above", which makes the row ABOVE the container, not the row you just named. They are different acts, and giving one key both, distinguished only by which row is focused, is rule 329's trap (a key that is both text and a command needs a state that says which). Hanging the second act on the control that already produces the outcome costs one label and no ambiguity. Reference: `features/schedule/ScheduleAddPhaseButton.tsx` (`action`, `adoptsRowName`), `features/schedule/ScheduleView.tsx` (`phaseAdoptionTarget`, `handleAddPhase`), `e2e/schedule-add-phase.spec.ts` — #2951.

340. **A word the product must not say is not enforced by asking people not to say it — put the word in ONE module, brand its type, and let `tsc` refuse the literal.** A row in the outline may be a task, a phase, a milestone or a subtask, and `structure_role` is *declared*, never assumed (ADR-0843) — so on the surfaces that exist **before** the type does (column headers, create affordances, placeholders, and the name a create path mints) the noun must be **item**, because any other noun is a claim about a row nobody has made yet. That rule was swept by hand in #2952 and again in #3027, and rule 300 says a rule needing a second sweep has no mechanism. Four obligations. **(a) The enforcement is the TYPE SYSTEM, not a scan.** Governed copy is a branded `VocabularyToken` whose minter is not exported, so `<Footer label="Add a task at the end" />` is a compile error at the call site, there is no roster to maintain, and nothing can go vacuous — `tsc` cannot match nothing. A scan of the same shape would have to ask "is this word correct here?", which is unanswerable mechanically: **`task` is the right word wherever the type IS known, which is most of the product**, so a "no `task` in user-facing strings" gate would fire almost entirely on correct copy and demand wrong fixes. Make the governed prop **required**, never a defaulted `string`, for rule 325's reason — an optional "and also use the right noun" parameter is exactly what the next surface omits. **(b) A row's own NAME is a stronger type claim than any label, and it is where the sweeps kept failing.** #3027 found `+ Item` creating a row literally named `New task`: the user is asked to fill a Name cell that already asserts the type, and pressing Escape commits it into the plan, the WBS and the Σ rollup. Two shapes reach that slot and both need catching — `name: 'New task'` **and** the blank-name fallback `row.name || 'Untitled task'`, which is not an assignment and which a `name:`-only pattern misses (two were live). **(c) Sweep the ACCESSIBLE tree, not the painted one.** The name column headed `Item` had a resize handle announcing "Resize **task** column", because the handle built its label from the internal `colKey`; #3027 saw it, recorded it in a spec comment, and deferred it. Any control describing a column by a different noun than its heading is the same defect arriving where no visual review goes. **(d) State what the mechanism CANNOT see, in the mechanism.** Types cover governed props; the scan covers copies within the outline's tree; the DOM guard covers what the outline renders. A brand-new component with brand-new wrong wording is caught by none of them, and every layer here asserts its own non-vacuity (a token floor, a per-surface "found ≥1 string" check, a self-test that plants each violation) because a guard that reports green after its query stops matching is how the sub-12px lint gate survived six sweeps. A stale allowance is the same hazard in miniature: assert each exception still names the thing it excuses — one of this change's four did not, and the check deleted it. Reference: `features/schedule/rowVocabulary.ts` + `.test.ts`, `features/schedule/rowVocabularyLock.test.tsx`, `scripts/check-row-vocabulary.sh` (CI `web:row-vocabulary`, `make pre-push`) — #3031, after #2952 and #3027.

352. **An entry point whose precondition is "a row is selected" is DEAD on a surface where selecting a row opens a covering drawer — put it on the row.** The classification popover reached the product backlog in #3035, and ADR-0800 §6 had left its placeholder in the page *toolbar*. 353. **A surface fronting two independent server permissions has a PARTIAL-rights band, and one "View only" badge is wrong for it in both directions — re-derive the standing badge from the union, and sweep every piece of standing copy that names the withheld affordance.** Rule 302 splits presence (`hasEditRights`) from behavior (`readOnly`) on the assumption that a reader either has the apparatus or does not. The Schedule fronts two rules that do not nest — `IsProjectPlanAuthor` for task content (`role >= MEMBER` **minus** the 200–299 band) and `IsProjectScheduler` for dependency edges (`role >= SCHEDULER`) — so each admits exactly one band the other refuses, and a Resource Manager fails the first while passing the second. One boolean across both is wrong for one band whichever way it resolves, and #3034 resolved it as task content: a Scheduler lost canvas drag-to-link the server answers 200, and a Member was offered it while the server 403s. Four obligations, and the last two are the ones a split reliably forgets. **(a) Split the flag per permission and mirror the server rule, not a nearby one.** Deriving the second gate from `can_author` — the first gate's server field — reintroduces the same collapse under a new name; the edge rule is a threshold on the role ordinal and has to be written as one (`canAuthorDependencies`). **(b) Withhold the gesture, do not swallow it.** A canvas affordance refused only at the commit handler still paints its grab point and still offers its cursor, so the user aims at a mark and nothing happens — worse than absence, because their next guess is that the surface failed to render. Tell the engine (`setLinkAuthoring`), and do **not** let the refused hit fall through to a neighbouring gesture: the link zone abuts the bar's right edge, so a fall-through turns a refused link into a silent reschedule. **(c) The standing badge must gain a third state.** `ScheduleViewOnlyBadge` says "change anything here", which is placed by the task-content gate and is therefore false for the one reader who holds the other permission; rule 302's silence clause ("nothing is on offer, so there is no gesture to explain") stops holding the moment something *is* on offer. Reference: `features/schedule/ScheduleView.tsx` (`readOnly` vs `dependenciesReadOnly`), `lib/roles.ts` (`canAuthorDependencies` beside `canAuthorPlan`), `features/schedule/ScheduleViewOnlyBadge.tsx`, `features/schedule/ScheduleLegend.tsx`, `features/schedule/engine/GanttEngineImpl.ts` (`setLinkAuthoring`) — #3053, extending #2949 and #3034.

354. **A DOCKED region that can grow needs a height cap and its own scroller — and the ancestor that would otherwise clip it cannot scroll, which is why nobody notices.** Rule 351 covers the *floating* panel; this is its sibling for the in-flow one, and it is the more dangerous half. A popover that overruns the viewport at least spills where the page's own scrollbar might reach it. A strip, bar, or dialog body that overruns an `overflow: hidden` ancestor is **painted nowhere**: no scrollbar appears, the wheel does nothing, `scrollIntoView` is a no-op, and a keyboard user Tabs to a control that exists in the accessibility tree and at no visible coordinate. The class has now shipped four times — #539 (settings at 375px), #2665 (`NewProjectModal`, the Create button clipped off the bottom), #2674 (`ImportModal`, which #2665 *identified* and left live), #3166 (`ScheduleForecastBar`) — each found by a person looking at a screen, each fixed only at the site that was reported. Five obligations. **(a) The shape is fixed, and `min-h-0` is the half that gets dropped.** `max-h-[Nvh] overflow-hidden flex flex-col` on the shell, `shrink-0` on the pinned header and footer, `flex-1 min-h-0 overflow-y-auto` on the body. A flex item defaults to `min-height: auto` and so refuses to shrink below its content — without `min-h-0` the scroller never engages and the overflow is simply handed back to the clipping ancestor, so the cap alone just moves *where* the content is lost. `SettingsShell.tsx` carries this comment on both of its scrollers because it is where the rule was learned. **(b) Cap in `vh`, not `%`.** A percentage max-height resolves against the containing block only while every link in the height chain stays definite; the moment one stops being so it computes to `none` and fails back to exactly this bug with no signal anywhere. **(c) Scope the cap to what the surface is FOR.** `ScheduleForecastBar` caps at `40vh` rather than half its column because the Gantt is the product and the forecast is a strip about it — a fix that leaves a secondary surface larger than the primary one has traded a broken screen for a wrong one. Note the collateral damage runs the other way too: a `flex-shrink-0` region with no cap starves its siblings, and #3166 drove `ScheduleMainArea` to a **zero-pixel canvas**. **(d) The breakpoint-scoped fix is the recurring near-miss.** `ImportModal` had the entire correct shape behind `max-md:`, so the phone sheet scrolled and the ordinary desktop dialog had neither a cap nor a scroller. If the mobile sheet needs to scroll, so does the desktop card; only the *chrome* (edge-to-edge, rounding, safe-area padding) is breakpoint-scoped. **(e) A vitest assertion pins the mechanism and a browser pins the value.** jsdom computes no layout at all — `scrollHeight` is 0 everywhere — so a unit test can assert the classes and nothing else, and reading it as coverage of the behavior is rule 300(a)'s failure. The measurement is `e2e/clipped-content.spec.ts`, which sweeps the primary surfaces at **1280×720 and 375×667** (every instance of this class is invisible at 1080p, which is exactly why they reach users and not reviewers) and asserts the invariant directly: *no clipping container may hold content taller than itself*. Its one escape hatch is a `data-clip-ok="<reason>"` attribute on the element — on the element rather than in a list inside the fixture, for rule 351's reason, so the marker moves with the code it excuses and cannot be edited without landing in the same diff hunk; the reason may not be empty. Do **not** add an "unless some descendant scrolls" exemption to the detector: a correctly-built inner scroller already makes its parent measure clean, and the first draft's version of that let the Schedule's unrelated task-list scroller cancel the #3166 finding, reporting green against the unfixed tree. Reference: `features/schedule/ScheduleForecastBar.tsx`, `features/schedule/reconcile/ScheduleReconcileStrip.tsx`, `components/import/ImportModal.tsx`, `features/settings/SettingsShell.tsx`, `e2e/fixtures/clipped-content.ts` — #3166, closing #2674.

355. **A responsive surface that renders ONE state through TWO breakpoint-selected components must give that state ONE live-region contract — decide it at the state, not once per rendition.** Rule 337 settles this for an ordered `if` ladder inside a single component; a `useBreakpoint()` switch is the same hazard with a predicate no ladder-shaped check reaches, because the two rungs are two *files* and neither can see whether the other announced. The Calendar's "this window holds no tasks" state is rendered by `CalendarMobileList`'s `role="status"` block below `md` and by `CalendarGrid`'s centered week hint above it — same sentence, same condition, and only the mobile one was announced. A desktop screen-reader user stepping into an empty week heard the window change and then had to explore seven empty cells to learn what the sighted user read in one glance. Nothing surfaces this: each component is internally correct, both vitest suites pass, and an axe scan sees two well-formed subtrees. Three obligations. **(a) Locate the contract at the condition, not at the renderer** — if the state is "empty window", every rendition of "empty window" is live or none is; enumerate the renditions before writing either one. **(b) Prefer folding it into an already-mounted announcer over adding a second live region** (rule 335): a `role="status"` node that mounts together with its own text is announced inconsistently across AT, so the surface's permanent announcer is the right home for a "…, no tasks" suffix, and a fresh `role="status"` on the hint is the fallback, not the fix. **(c) An absolutely-positioned `pointer-events-none` hint is decoration to every non-visual consumer** — no role, no name, no meaningful place in the reading order — so it must never be the only carrier of a fact. Note the mechanism honestly (rule 300): "are these two components two renditions of one state?" is decidable by neither grep nor AST, so a zero-tolerance gate would misfire and get disabled. The proportionate mechanism is a paired vitest assertion in the same MR — the desktop empty-state spec asserts the announcement alongside the mobile `role="status"` spec — not a new script. Reference: `features/calendar/CalendarView.tsx` (the permanent announcer, which now carries the emptiness), `features/calendar/CalendarGrid.tsx`, `features/calendar/CalendarMobileList.tsx` — #3167.

358. **A modal's PINNED chrome is a budget charged against its scroller, and a scripted mount-focus SCROLLS that scroller — so autofocusing a control below the fold silently pushes the surface's lead content off the top, at every viewport height the reviewer did not open.** `element.focus()` defaults to `preventScroll: false`, so a `ref.current?.focus()` in a mount effect scrolls every scrollable ancestor until the target is visible. That is invisible on a tall display and total on a short one. #3130 reordered `NewProjectModal` so the way-in cards lead the sheet, then moved the working calendar into the pinned footer — taking fixed chrome from ~136px to ~309px — while still autofocusing the Name input, now ~300px into the scroller. On a 1366x768 CSS viewport under `max-h-[90vh]` the cards the reorder exists to promote are scrolled entirely out of view **at rest**, before the user has touched anything. Three obligations. **(a) Budget the chrome.** Header + pinned footer must leave the scroller a usable height at the surface's *minimum* supported viewport — 640px tall for a `max-h-[Nvh]` desktop dialog, and the device height for any full-screen compact branch, which has no `vh` cushion and is therefore the TIGHTER constraint, not the looser one. Growing a pinned footer is not free; it is subtracted from the body at every height, and multi-line helper text under a pinned control is the usual culprit. **(b) Autofocus the top, or do not scroll.** Seat mount focus on the first tab stop, or pass `{ preventScroll: true }` when a lower control is genuinely the better target (it is, when that control is the only empty required field). Never let the resting scroll position be decided by a focus call. **(c) Verify at the short viewport and in the compact branch, not at your own display.** A screenshot at 1080p passes on both failure modes; the check is opening the surface at the shortest viewport it claims to support and confirming its first meaningful content is on screen before any input. This is the height-axis twin of rule 316(c) ("never made conditional on the viewport") — same class, measured down instead of across. Reference: `features/shell/NewProjectModal.tsx`, `features/shell/useStartSheetCompact.ts`.
359. **A control gated on "there is something to do" must be gated on a fact the server owns or the client can always re-derive — never on a counter that only counts this session's own mutations.** A `useState(0)` version bumped from one mutation path is a truth about *this component instance's lifetime*, not about the data: it misses every sibling write path, every collaborator's change over the WebSocket, and it resets to zero on reload and on route re-entry. That is tolerable while the control is merely a *notice* — the user still has the action. It becomes a defect the moment the counter decides whether the **action exists**, because the state the user most needs the button in is precisely the state that reads as "nothing to do". **Falsification, and the one-line review test: open the surface in the state that should show the control, then reload — if the control disappears, the predicate is a session artifact and the gate is wrong.** Prefer a server-declared discriminant; where none exists, keep the action permanently available and let the *notice* carry the session signal. Two riders once you have the server fact. **(a) Default an absent discriminant toward offering the action, never toward hiding it** — a client that cannot tell must not assert the surface is fine, and the mapping default is where that is decided (`useMonteCarloResult`'s `mapStaleness` returns `unknown`, not `current`). **(b) Split the *action* from the *claim*.** A server value that is a sound trigger is often an unsound assertion: `forecast_staleness: project_changed` comes from a counter that any write in the project advances, so the bar offers Rerun but says only "Edited since this run" — never "your plan changed". Reference: `features/schedule/ScheduleForecastBar.tsx` (`useForecastStaleness`), `hooks/useMonteCarloResult.ts`, `apps/scheduling/forecast_staleness.py` — ADR-0954, #3140, sibling of #3132.

*Motion is never content.*

70. **`prefers-reduced-motion` is evaluated at engine init and on media query change.**
    When true: disable the today-line pulse, CP-flip animation, preview-bar fade,
    scroll-to-date smooth behavior. Functionality is never disabled — only motion.

181. **All transform/overlay motion uses the shared `ease-brand` + a named `duration-*` token, and the four entrance keyframes live in `globals.css` and are applied under `motion-safe:` — never hand-rolled per call site, never ungated.** The v2 motion layer is centralized so it stays consistent and honors the motion contract (rule 70: motion only, never content).

Do not add the dead `tailwindcss-animate` utilities (`animate-in`/`fade-in`); they emit no CSS.
    - **Micro-interactions:** the shared `<Button>` presses via `motion-safe:active:translate-y-px`; interactive cards (`ProgramCard`, `BoardCard`) lift via `motion-safe:hover:-translate-y-px`. **No shadow on the lift** (rule 1) — the card's own border (or a `hover:border-*` emphasis on a single-state border) supplies the depth cue the prototype's hover shadow would have; on a card whose border is state-driven (e.g. `BoardCard`'s critical/dashed border) use translate-only so the lift never overrides the state border. `shadow-pop` remains allowed only on true pop surfaces (toast/popover/drawer/modal/command palette — rule 1's standing exception).
    - **Coexisting transitions:** when a transform animation must share an element with an existing color/opacity transition, use ONE multi-property declaration (`transition`, or `transition-[opacity,transform]`) — never stack `transition-transform` on top of `transition-colors`/`transition-opacity`, which collide on `transition-property` (the later one in the cascade silently wins and drops the other).

## Controls and composition

*Reach for the shared primitive before writing a new one.*

179. **A segmented control (`role="radiogroup"` of `role="radio"` buttons) must fill the active segment with a token that contrasts against its container surface — never the same surface token the control sits on — and selection is conveyed by fill, not text color alone.** Active = `bg-brand-primary text-neutral-text-inverse`; inactive = `bg-neutral-surface text-neutral-text-secondary hover:bg-neutral-surface-raised` (visually distinct from the active fill). The failure this prevents: a toolbar segmented control filling the active segment with `bg-neutral-surface-raised` while sitting *on* a `surface-raised` toolbar renders zero fill contrast, leaving text shade as the only selection signal (WCAG 1.4.1). Roving tabindex (`tabIndex={selected ? 0 : -1}`), Arrow (wrapping) + Home/End key handling **bound to the focusable radios** (not the non-focusable group, per `jsx-a11y/interactive-supports-focus`), and the rule-4 focus ring (no dark-mode override — `brand-primary` is mode-aware sage, rules 4/137; the old `dark:focus-visible:ring-semantic-on-track` override is **retired**, do not reintroduce it) are mandatory; the selection commits immediately on move. Reference implementations: `features/schedule/ScheduleToolbarToggle.tsx` (single pressed/unpressed) and `features/schedule/ScheduleViewModeToggle.tsx` (multi-option Grid↔Timeline). Pattern also in use: `RetentionPurgePage`, `CalmToolbar`.

183. **App-wide confirmations use the global `toast()` API + the single `ToastHost`; board-local transient notices stay in `BoardDropNotice` (rule 170).** The toast system (`components/Toast/`) is a Zustand store (`toastStore`, pure — auto-dismiss timing lives in the host) + an imperative `toast.success/info/error/warm(message, durationMs?)` API callable from anywhere (mutation `onSuccess`, event handlers, plain modules — it reads the store via `getState()`, no hook) + ONE `ToastHost` mounted once in `AppShell`. The host is a bottom-center pair of **two fixed slots** (rule 356 — not a queue) rendered as inverse **ink pills** (`bg-neutral-text-primary text-neutral-text-inverse`, always high-contrast against the canvas in both themes), each rising in via `motion-safe:animate-toast-rise` (rule 181) with a decorative sage `✓` on success/info (`aria-hidden` — the message text carries the announcement), auto-dismissing after `durationMs` (default ~2.6s; ~8s for an actionable one). The wrap is `role="status" aria-live="polite" aria-atomic="false" pointer-events-none` so toasts are announced without stealing focus and never block the UI beneath; individual pills re-enable pointer events. `shadow-pop` is allowed (a toast is a pop surface — rule 1's standing exception). **Fire it only for genuinely app-wide events** (task created/completed/saved, pin/unpin, theme); do NOT route board-local pending-state notices here — rule 170 keeps `BoardDropNotice` board-scoped, neutral-toned, and off the global toast library.

356. **A capped set of transient surfaces must NOT evict by age when dwell is set by importance — give each class its own slot instead.** Age is a proxy for disposability, and the moment dwell length encodes importance the proxy inverts: the item that deserves to live longest becomes the oldest soonest, so drop-oldest kills exactly what the long dwell was bought for. The global toast host had an unbounded stack (three at once covered a third of the plan) and the obvious fix — cap at two, evict oldest — would have been worse than the bug it replaced: with a 2.6s passive dwell and an 8s actionable one, two routine confirmations evicted a "Deleted — Undo" before the user's hand arrived, and the failure is invisible in review because each toast is individually correct and the collision needs three (#3149). Five obligations. **(a) Slot by role, not by arrival — and the role axis is *every* field that already encodes importance, not the first one that suggests itself.** `toastStore` holds `{ transient, action }`, each a single item — a passive replaces the passive, an actionable replaces the actionable, and neither can touch the other. The cap is then *structural*: there is nowhere for a third to go, so no `while`, no `slice`, and no test that can pass while the bound leaks. But actionability is not the only importance signal in the tree: `variant` is one too, and a split that reads only `action ? … : …` drops a failure notice and a routine confirmation into the same slot, where the confirmation wins purely by being newer — which is drop-oldest walking back in through a second door. Before shipping a slot split, enumerate every dimension the surface already varies by importance (dwell, variant, severity, whether the user asked for it) and either read all of them or say why one is excluded. Concretely here: a passive `error` holds its slot against a `success`/`info` until its own dwell is up, and only another `error` replaces it early. **(b) The cap lives in the store, not the renderer.** A host that renders `items.slice(0, 2)` still holds the other items, still runs their timers, and still announces them — the bound has to be enforced where the state is or it is cosmetic. **(c) Order the slots by reachability, not recency.** The slot that can hold a control renders lowest (nearest the thumb); "newest on top" is a queue's habit and a queue is what was removed. **(d) An element with focus inside it is never auto-removed and never displaced** — the only way a keyboard user loses a control is by leaving it. An incoming item waits at **depth one** (newest wins, the loser is not silently dropped); an unbounded wait-queue is the same unbounded stack, only invisible. **(e) Eviction may cost convenience, never capability — so gate the eviction on the durable home, do not merely assert one exists.** Anything evicted must leave its action reachable somewhere durable *before* the eviction path ships, and *no copy explains the demotion in the moment*, because a notice about where the previous notice went is a notice about notices. The trap is that "it demotes to the session trail" is easy to write in a design and easy to implement as a field nothing reads: a store slot that collects evicted items is not a durable home, it is a leak with a name. Make the durability a **property of the item** (`ToastItem.trailBacked`) that the eviction branch actually reads, defaulting to *not* durable, so a surface with no trail queues at depth one instead of evicting. Then the invariant is true by construction on every surface rather than true on the one surface the designer had in mind — and the asymmetry is a contract a reader can see, not an inconsistency. Expect the honest answer to be that **no** caller qualifies yet: at 0.4 every global action toast is un-backed, because the one surface with a session trail (the Schedule) renders its own toast and does not use the global host. An eviction branch that is unreachable in production and correct is better than one that is reachable and destroys undos. Live-region corollary: the region **contains** the rendered items and nothing is written to it out of band, which makes "announced but never shown" impossible by construction rather than by discipline; it needs an explicit **`aria-atomic="false"`** or a re-render of one slot re-reads the other. Note the mechanism honestly (rule 300): jsdom has no layout and no `:focus-visible`, so slot *order* and real focus retention are `e2e/toast-host.spec.ts`, and the slot algebra — every eviction-table row, the coalescing window, the depth-one queue — is `toastStore.test.ts`. Generalizes past toasts to any bounded transient stack: snackbars, inline banners, presence chips, undo receipts. Reference: `components/Toast/toastStore.ts`, `components/Toast/ToastHost.tsx` — #3149.

250. **Menu/panel group headers (eyebrows) use one canonical recipe: `text-xs font-semibold uppercase tracking-[.06em] text-neutral-text-secondary`; inside a `role="menu"` or dialog, wrap the grouped rows in a `role="group"` labeled "like the header" (`aria-label` or `aria-labelledby`), with the visible header div `aria-hidden`.** The tree had grown ≥4 competing eyebrow treatments (`text-[11px] tracking-[.08em]`, `text-[11px] tracking-wide`, `tracking-widest`, …); `text-xs` is the rule-50 floor, so it is the canonical size — do not mint new size/tracking combos. `role="group"` is a permitted owned element of `role="menu"` and is transparent to `useFocusTrap` (descendant selector) and to Escape/outside-click handling. Reference: `features/shell/UserMenu.tsx` ("Personal" group).

253. **A neutral read-state chip may become a tap-to-explain disclosure, but the disclosure must stay neutral, grant no capability, and portal out of any clipping scroll container.** `PendingAcceptanceChip` (`features/board/PendingAcceptanceChip.tsx`) is the reference: pass an optional `explainer` string and the chip renders a real `<button aria-expanded aria-controls>` toggling a `role="note"` popover with one plain-language sentence + a **neutral** "Got it" close button; omit `explainer` and it stays the passive read-state `<span>` (rule 149) with no disclosure state mounted (a hook-free early return, so read-only surfaces keep the passivity contract — no `button` in the tree). Five invariants: (a) **tone** — trigger, popover, and close button use neutral tokens only (`bg-neutral-surface-sunken`/`surface-raised`, `text-neutral-*`, `border-neutral-border`, `shadow-pop`); do **not** reach for the shared `Button` `ghost` variant, which is sage-brand-toned (`text-brand-primary`) and violates rule 149 — hand-roll a neutral ghost. (b) **No capability** — the popover explains only; it never gains accept/reject/any-mutation control (the decision stays team-owned on role-gated planning surfaces, rule 144), and the close button uses dismissal copy ("Got it"), never an action verb; the acknowledge is ephemeral (close-only, no persistence, no API) because the read-state is server-owned and clears on accept/reject (ADR-0102). (c) **Disclosure a11y** — Escape and "Got it" both close **and** return focus to the trigger; click-outside closes without stealing focus (check the trigger **and** the portaled popover, which is no longer a DOM descendant of the wrapper); `stopPropagation` on pointerdown+click so opening never drags/selects/opens the host card; `before:inset-[-12px]` for a ≥44px hit target; rule-4 `focus-visible` ring. (d) **Escape the clip** — the chip lives in a board column whose card stack is `overflow-y-auto` and can be as narrow as 208px (narrower than the popover); an in-flow `absolute` popover would be clipped and `z-index` does **not** defeat an overflow-clipping ancestor, so **portal the popover to `document.body`** with `position: fixed`, position it from the trigger's `getBoundingClientRect()` (flip above when there's no room below, clamp horizontally to the viewport), and **close on scroll/resize** since a fixed popover can't track its anchor (pattern: `features/schedule/UnscheduledTaskRow.tsx`). Portaling also sidesteps the `<p>` phrasing constraint on My Work — the wrapper/trigger stay `<span>`/`<button>` (phrasing content) inside the paragraph while the popover renders out in the body. (e) **Copy** — built by `pendingAcceptanceExplainer(iterationLabelLower?)`: role-neutral ("someone on the team accepts it", never "your Scrum Master" — acceptance authority is any Admin/SM/PO holder), outcome-only (no state-machine jargon like "scope injection"), iteration-label-aware on the board (`itl.lower`) and generic on cross-project My Work. Reference: `features/board/PendingAcceptanceChip.tsx`, `features/board/BoardCard.tsx`, `features/me/MyWorkTaskRow.tsx`.

260. **A floating popover / menu / listbox that must escape a clipping ancestor (an `overflow-hidden` card, an `overflow-y-auto` scroll panel) or stay on a narrow viewport uses the shared `useAnchoredPopover` hook (`hooks/useAnchoredPopover.ts`) as its positioning + dismissal engine — do not hand-roll the `getBoundingClientRect` → `position:fixed` → flip-above → clamp → scroll(capture)/resize → outside-`pointerdown` math inline.** This names the *implementation* of web-rule 253, which remains the *specification* of those mechanics; the two are complementary (a new site could "follow 253" and still re-introduce a clip/flip bug by hand-rolling the math). The hook owns exactly four concerns: portal-`fixed` positioning, flip-above, horizontal/width clamp (to the viewport, replacing any `max-w-[calc(100vw-…)]`), and outside-`pointerdown` dismiss spanning the trigger + the portaled panel (once portaled they are no longer DOM-nested, so a single `containerRef.contains` check treats panel clicks as "outside"). The **call site keeps** its own contents, keyboard model (`aria-activedescendant` roving, two-stage Escape), open-state ownership, and focus-return — the hook deliberately does NOT handle Escape (a duplicate document listener double-fires — the rule-204 lesson). Usage: pass `open`, `width` (`number` | `'trigger'` to match the anchor), `estimatedHeight` (flip heuristic only), and optional `align` / `gap` / `margin` / `onDismiss` (omit `onDismiss` to keep a site's own `onBlur` dismissal); attach `triggerRef` to the anchor and `popoverRef` to the panel; render `open && popoverStyle && createPortal(<panel ref={popoverRef} style={popoverStyle} className="z-50 …" />, document.body)`. The hook returns a non-null off-screen `popoverStyle` immediately when `open` (real coords are measured in `useLayoutEffect` before paint), so the portal mounts in the **same** commit — required for a panel that focuses its own input on open (comboboxes). **A `role="menu"` with focusable items MUST move focus into the menu on open** (`popoverRef.current?.querySelector('[role="menuitem"]')?.focus()` in a `[open]` effect) and rove with Arrow/Home/End + close on Tab/Escape returning focus to the trigger — portaling removes the items from natural tab order, so without this a keyboard user cannot reach them. The two original inline implementations — `features/board/PendingAcceptanceChip.tsx` and `features/schedule/UnscheduledTaskRow.tsx` — are **grandfathered reference specs** (do not rewrite them onto the hook); every new call site uses the hook. Reference: `hooks/useAnchoredPopover.ts`, `components/EntitySelectCombobox.tsx`, `features/settings/SettingsContextSwitcher.tsx`, `features/settings/members/InviteForm.tsx`, `features/settings/program/ProgramCadencePage.tsx`.

351. **A floating `role="menu"` / `role="listbox"` panel must carry BOTH a height guard and `overflow-y-auto` — a panel that can grow taller than the viewport and has neither spills off the bottom of the screen with nothing to bring the rest into view.** The Schedule "Display" dropdown (`ScheduleDisplayMenu.tsx`) was a plain `absolute` `<div>` with no `max-height` and no `overflow-y-auto`; with its Outline + View filters + Render filters + optional Columns + optional Chart sections, content routinely reached 600–700px, taller than a laptop viewport at 100% zoom — and the audit that followed found the identical gap in roughly a dozen more panels, because no shared primitive owned vertical viewport-collision handling: `useAnchoredPopover` (rule 260) computed horizontal clamp and flip-above but never exposed a height (#3109). Two obligations, matched to how the panel is built: **(a) hook consumers** (rule 260) get it for free — `useAnchoredPopover` now derives `maxHeight` into `popoverStyle` (the real gap to whichever viewport edge the panel opened toward, not a guessed pixel value), so the call site only has to add its own `overflow-y-auto` on the actual scrolling element (which may be a descendant of the element carrying `style={popoverStyle}`, not that element itself — a search box or a keyboard handler routinely sits between them). **(b) bespoke panels** (a hand-rolled `absolute`/`position:fixed` implementation, not yet on the hook) add an explicit viewport-relative guard directly — `max-h-[min(70vh,<cap>)] overflow-y-auto` is the tree's standard spelling (`ScheduleDisplayMenu.tsx`, `ToolbarOverflowMenu.tsx`, `BoardViewDropdown.tsx`, `UserMenu.tsx`, `CardOverflowMenu.tsx`); `components/FieldHelp.tsx`'s `max-h-[min(60vh,320px)]` is the original reference for the pattern. **Never `overflow-hidden`** on a panel with unbounded content — it clips silently instead of scrolling, which is worse than doing nothing (`LoadSampleButton.tsx` was fixed for exactly this). A panel is exempt only when it is provably safe by construction — content is small and fixed (2–3 static items), hard-capped (`slice(0, MAX)`), or in-flow inside an ancestor that already scrolls (rule 260's clipping-ancestor case run in reverse, e.g. `ViewsMenu.tsx` inside the nav rail) — and that judgement is not mechanizable, so it is recorded as a reviewed, commented exclusion, never inferred per-component at review time. **That exclusion is a comment on the offending line itself** — `role="menu" // dropdown-scroll-ok: <reason>`, or `/* dropdown-scroll-ok: <reason> */` inline; both forms are legal in JSX attribute position, and the reason may not be empty. It has to be same-line, and that is the entire mechanism: the exemptions used to be `path:LINE` pairs inside the gate script, which any insert above the line invalidated — so the gate reddened against code the author had not touched, named a line they had not written, and prescribed a fix that would have been wrong to apply. It fired three times in nine days on `ScheduleView.tsx` alone, twice also producing a merge conflict where *neither* branch's renumbered value was correct on the merged tree (#3114, #3113, #3117). A same-line marker moves with the line, and — the property a coordinate could never have — the line cannot be edited without the reason landing in the same diff hunk as the edit. **A content hash was rejected on the tree's own data**: 15 of the 21 reviewed sites are the byte-identical text `role="menu"` or `role="listbox"` and two files hold identical pairs, so one hash entry would have covered both members of a pair and silently covered a third, unreviewed panel added later. A marker whose line no longer declares a role is itself an error — the panel was refactored away and the exemption outlived it. Enforced by `scripts/check-dropdown-scroll.sh` (`make dropdown-scroll-check`, CI `lint:dropdown-scroll`): every `role="menu"`/`role="listbox"` in `packages/web/src` must show both markers within a window of its declaration, OR (for a hook consumer) `overflow-y-auto` locally plus `useAnchoredPopover` + `style={popoverStyle}` anywhere in the file, OR carry a same-line `dropdown-scroll-ok:` marker — a ratchet, not zero-tolerance, per rule 300(c): the exception list is separated from the violation mechanically so it cannot become the hole. A `[role="menu"]` written as a CSS attribute selector inside a `document.querySelector` string is skipped structurally — it is not a rendered panel and there is nothing there to scroll. Reference: `hooks/useAnchoredPopover.ts`, `hooks/useAnchoredPopover.test.tsx` (`maxHeight` cases), `e2e/schedule-display-menu.spec.ts` ("short viewport scroll").

287. **Any abbreviation, code, percentile, or icon-only control ships with a plain-English explanation reachable by hover AND keyboard focus AND touch — via the shared `Tooltip` (`components/Tooltip.tsx`), never a bare `title` and never a `group-hover` class (#2389).** The bug class this closes is an *inversion*, not an omission: the codebase repeatedly added an `aria-label` to satisfy WCAG 1.4.1 and stopped, so a screen-reader user heard "Waterfall workspace" and a sighted mouse user got two undecodable letters (`MethodologyIndicator`'s `WF` chip was the trigger case; `SyncStatusBadge`, the `CP` float suffix, and the Monte Carlo row were the same shape). (d) **never the sole carrier of meaning** — it supplements the accessible name, it does not replace it. (e) **positioning is delegated to `useAnchoredPopover`** (rule 260) and the panel is portaled (rule 253) — no hand-rolled flip/clamp math. (f) **Escape peels one layer** — capture-phase `document` listener + `stopPropagation()`, so a tooltip open inside a modal dismisses without closing the modal (the rule-263f pattern). (g) **keyboard-vs-pointer focus is decided by pointer recency, NOT `:focus-visible`** — jsdom answers `false` to `element.matches(':focus-visible')` under every condition, so a `:focus-visible` guard silently kills the keyboard path while the unit suite stays green; `Tooltip` records the last `pointerdown` and treats a focus within 300ms of one as pointer-driven. Do not "simplify" it back to the pseudo-class. Shared strings live in `lib/abbreviations.ts` and `lib/percentileExplanation.ts` so the same token never acquires two different definitions on two surfaces. Exemption worth knowing: a decorative `aria-hidden` header row (`OutlineMode`'s column strip) must NOT get a tooltip — the trigger is a tab stop, and a tab stop inside an `aria-hidden` subtree is its own violation. Reference: `components/Tooltip.tsx`, `features/shell/MethodologyIndicator.tsx`, `features/schedule/MonteCarloTimeline.tsx`.
    - **(d, sharpened) A `Tooltip` child that is not natively focusable must carry its OWN `aria-label` — an `sr-only` sibling is not an accessible name.** `Tooltip` gives any non-native child a tab stop (`needsTabStop`), and a bare `<span tabIndex={0}>` computes to role `generic`, which **does not support name-from-content**. So descendant text — including a visually-hidden line that reads perfectly in browse mode — leaves that tab stop announcing as **blank** when a screen-reader user Tabs onto it. The fix is `role="img"` + `aria-label` on the trigger (which also makes the glyph presentational, so drop the `sr-only` node rather than keeping both and double-reading it per rule 171). The house pattern was already right everywhere else — `MethodologyIndicator.tsx:68`, `CardHealthPeek.tsx:100,121`, `ScheduleSummaryChip.tsx:129` all name the span explicitly; #3148's lane-header em-dash was the one that did not. **Do not read a green `a11y.spec.ts` as coverage here:** the only axe rule that fires on an unnamed focusable is `focus-order-semantics`, which is tagged `best-practice`, and `e2e/fixtures/a11y.ts` runs `wcag2a/2aa/21a/21aa` only — so the gate is *structurally* incapable of reporting this, in any file, in any tree (rule 300(a)). **No mechanism exists yet.** The proportionate one is an AST selector over every `JSXElement[name='Tooltip']` whose single child is outside `NATIVELY_FOCUSABLE` and declares neither `aria-label` nor `aria-labelledby`; it is *not* built, and until it is this clause is a convention, not a gate — tracked as follow-up, and per rule 300(a) whoever builds it must run it against `origin/main` and watch it report before trusting a zero. Reference: `features/board/LaneMeta.tsx` (the uncommitted progress slot) — #3148.

273. **`AppShell` renders the single `<main id="main-content">` landmark — a feature page, panel, or state-branch (loading/error/empty) rendered inside the shell must NOT emit its own `<main>`; use a labeled `<section aria-label>` (or a `<div>` when it already owns a `role`).** The skip-link (`#main-content`) and "jump to main content" both target AppShell's one main; a second `<main>` nested inside it is invalid HTML and makes the SR "jump to main" ambiguous. 304. **A form that edits a *set* the server owns must round-trip every member — including ones this build has no widget for. Never narrow a fetched collection to the client's own catalog and then write the narrowed value back.** The pattern that produces silent data loss is small and looks defensive: hydrate state as `new Set(remote.items.filter((i) => LOCAL_CATALOG.includes(i)))`, then `PATCH` the whole list on save. Every member the client did not recognize is deleted, with a success toast and no diff — and the client is not the authority on what is valid, so "unrecognized" reliably means "added by a newer server, or written through the API", not "invalid". This is what the webhook event picker did for two releases: it shipped 11 of the backend's 19 events, so an admin opening an API-created webhook to fix a URL typo destroyed eight real subscriptions (#2883). Three requirements: **(a) hydrate unfiltered** — the fetched collection is the source of truth for what is currently set; **(b) partition, don't filter** — split into "has a widget" and "does not", render the first normally and the second as its own read-and-clear section ("Other subscriptions", explaining they were registered elsewhere and stay unless cleared) so removal is always a deliberate act; **(c) the invariant must hold without a catalog update** — a member added to the server tomorrow, with no frontend change at all, must still survive a save today. A gate that keeps the two catalogs in step is complementary and **not** a substitute: it degrades a future gap from "silently deleted" to "not selectable here", which is the whole point. Note this is the inverse of the usual defensive-filtering instinct — carrying an inert value the server ignores costs nothing; deleting a live one is unrecoverable. Applies to any multi-select bound to a server-owned vocabulary (event subscriptions, labels, scopes, notification channels, feature toggles). Reference: `features/settings/components/integrations/WebhookEditorModal.tsx` + `events.ts`, gated by `test_web_event_catalog_covers_every_backend_event` in `packages/api/tests/apps/webhooks/test_webhook_format.py`.

314. **A settings section is five coupled edits across four files and two packages — and four of them fail somewhere other than the file you are writing.** Adding a row to a settings rail feels like one change (`buildProjectSettingsNav` gets an entry, the page gets a `<SettingsSection>`), and the other three only announce themselves as red in test files you had no reason to open. The full set: **(a)** the nav entry, whose icon must be unique *within its group* — a repeat fails `settingsNavIcons.test.tsx`, not the page's own spec, because a column where most glyphs are identical trains the eye to skip it; **(b)** the `<SettingsSection id="…">` mount in `ProjectSettingsPage.tsx` / `ProgramSettingsPage.tsx` / `workspaceNav.ts`, keyed to the same id the rail scroll-spies on — the shell is ONE scrolling page (ADR-0146), so the address is `/projects/:id/settings#<id>` and there is no route to add; **(c)** an entry in `SETTINGS_DOCS` (`settingsDocs.ts`), enforced by a coverage suite that fails on *any* nav id with no help mapping — the regression #2487 was filed for was 38 of 44 sections having none; **(d)** the hard-coded section total in `settingsDocs.test.ts` (`covers all N sections`), which is a bare number and gives no hint what it counts when it fails; **(e)** a real `##`/`###` heading in the mapped page under `packages/website/src/content/docs/`, because the resolution suite reads the docs tree **off disk** and slugifies headings the way github-slugger does (lowercase, drop everything outside `[a-z0-9 -]`, spaces to hyphens, runs of hyphens **not** collapsed — so an em-dash in a heading yields a double hyphen in the anchor). That last coupling is the one that surprises: a frontend-only branch cannot ship a settings section without touching `packages/website`, and that is deliberate — it is the mechanism that keeps in-product help links from rotting into 404s. Point at the parent page with no fragment rather than inventing an anchor if the section has no docs of its own yet. Reference: `features/settings/ProjectSettingsPage.tsx`, `features/settings/settingsDocs.ts`, `features/settings/settingsDocs.test.ts`, `features/settings/settingsNavIcons.test.tsx` — #2971.

317. **Merging settings sections is rule 314's five edits run backwards — plus the addresses the merged sections used to answer on, which fail SILENTLY and are not one mechanism but three.** All five of rule 314's couplings fire in reverse when rows collapse (the nav entry goes, the `<SettingsSection>` mount goes, the `SETTINGS_DOCS` keys become **orphans** the coverage suite fails on, the hard-coded section total moves, and the docs page needs a heading that slugifies to the new id). None of that is the hard part. The hard part is that a settings URL is a **public address** — ADR-0146 made every section an anchor, so every deep link the product has minted since, every runbook line and every mailed link, is `/…/settings#<id>` — and a retired anchor produces no error, no scroll, and a page top that reads like a slow load. Six obligations, in the order they bite.
     **(a) Redirect BOTH forms, because they are two layers that cannot see each other.** `SectionRedirect` in `router.tsx` covers `/…/settings/<slug>`; a hash is not part of the path a route matches, so the `#<slug>` form can only be resolved where the mounted sections are known — an `anchorAliases` map on `SettingsShell`, applied when the hash misses `inlineIds`. Fixing one and calling it done is the default outcome, because the route half is the one that visibly 404s. Alias only what you retired: a map that swallows every unknown hash makes a typo look like a working deep link. Pin all four states (retired → rewritten, live → untouched, unknown → untouched, **alias target not mounted in *this* rail → untouched**; that last one is the reduced member rail, where every alias points at a section it does not render).
     **(b) Landing on the section is not landing on the destination — declare sub-anchors.** `#guardrails` used to open the guardrail matrix; after a merge it opens a section three blocks tall with the matrix off-screen, which is "not a 404" and still a lost link. Wrap each absorbed block in a `SettingsBlock anchor="<retired id>"` and have the shell refine the scroll onto `[data-settings-anchor]` after scrolling the section. **Assert focus, not visibility** — every section is mounted at once, so `toBeVisible()` on the destination heading is true whether or not the scroll ever fired, and a spec built on it cannot see the difference.
     **(c) The rewrite must fire once per HASH, not once per render — and the deferred scroll must not be cancelled on cleanup.** `inlineIds` is a bare `flatMap` (new array each render) → `useScrollSpy`'s `recompute` → `scrollTo` all churn identity every render, so any effect depending on `scrollTo` re-runs on **every** render. An unguarded `navigate(…, {replace:true})` there fires once per render, each replace aborting the last, and under load the rewrite is dropped entirely and never retried because the hash it keys on never changed — green on an idle machine, silently dead on a busy one (reproduce with `--repeat-each=6 --workers≈cores`). Symmetrically, `return () => cancelAnimationFrame(raf)` plus an early-return guard means a re-render in the same tick **cancels the scroll and never reschedules it**; drop the cleanup and let the callees no-op on a gone container. Do the history write **synchronously** and the scroll in the frame — never the reverse, and never make the scroll conditional on the write landing.
     **(d) Only one title strip per section may own the heading id — and the blocks' INNER headings have to move too.** `settingsHeadingId()` is minted from the *section* id, so mounting N former section components under one `<SettingsSection>` stamps the same DOM id N times and `aria-labelledby` resolves to whichever the parser met first; same for `data-settings-section-heading`, the scroll-spy focus target. An `embedded` title strip drops to `<h3>` and claims neither (it claims `data-settings-block-heading` instead). **That is only half the fix**: each absorbed page's own sub-headings are still `<h2>`, so "Statuses" and "Board cadence" now announce as *siblings of the section containing them* — a WCAG 1.3.1 failure **axe cannot see**, because `heading-order` only flags skips *upward* and h3→h2 is a decrease. Route them through a level-aware `SettingsSubHeading` (h2 standalone, h4 in a block) driven by a `SettingsHeadingLevelContext`, so a page body never has to know where it was mounted.
     **(e) A merged section merges its blast radius and its save-store key unless you stop it.** `useDirtyForm` registers under the section id from context and `register` is a keyed map, so the *second* block to adopt a dirty form silently overwrites the first one's save handler — and "only one block registers today" is precisely the shape in which that arrives later as a mystery. One `SettingsSectionErrorBoundary` likewise now wraps all three, so a throw in the last block takes the other two down. `SettingsBlock` fixes both: a composite `${sectionId}::${anchor}` context value (the key is opaque to the store and matched against nothing) and its own boundary.
     **(f) Carry the retired rows' vocabulary and pay back the navigability.** The rail filter (#2320) matches label + keywords; a user who types "guardrails" into a rail that no longer has that word gets an empty result and no explanation — and carry **both** iteration nouns unconditionally (`sprint iteration`), not just the configured one, or a project that relabelled its container stops answering to the other. The rail's scroll-spy also now pins one row across the page's tallest stretch, and on mobile that rail is a `<select>` whose single option covers many screens; an in-section jump strip is what pays that back, and it is the only in-page route to a block for someone who did not arrive by a retired deep link. Make its controls scroll and nothing else — a merged configuration section must not grow a control that gates.
     One last trap, in prose rather than markup: **a merge invites a reassuring summary sentence, and the wide version of it is usually false on the same page.** "Every surface the preset switches off can be turned back on under Surfaces" named a screen that toggles a *different* four surfaces; "nothing on this page stops anyone" sat two screens above a guardrail matrix whose own help text reads "Block stops the action outright with no override." Both were pinned by a passing test. State the narrow claim, name the exception, and pin *that*. Reference: `features/settings/project/ProjectTeamWorkflowPage.tsx`, `features/settings/ProjectSettingsPage.tsx` (`PROJECT_SETTINGS_ANCHOR_ALIASES`), `features/settings/SettingsShell.tsx` (`anchorAliases`, `SettingsBlock`, `SettingsSubHeading`, `scrollToSettingsSubAnchor`), `features/settings/projectSettingsAnchors.test.ts`, `e2e/settings-anchor-redirects.spec.ts` — #2969.

## Dialogs, focus and keyboard

*Where focus goes, and what commits.*

303. **Never bind a manual refresh/retry control's `disabled` (or spinner) state to a query's raw `isFetching` when that query also polls (`refetchInterval` set) — track a local "this fetch was user-initiated" flag instead.** TanStack Query's `isFetching` is true for *every* in-flight fetch, a background poll tick as much as the user's own click. Wire it to a native `disabled` and the control disables itself on every interval — and because browsers blur an element the instant it becomes disabled, a keyboard user resting on that button is silently ejected to an arbitrary point in the document, on a timer, for as long as the page stays open. Nothing catches this: the types are fine, a unit test that clicks once and asserts the handler fired passes, and a sighted mouse user never notices because the flicker coincides with data they were not watching. `refetchIntervalInBackground: false` does not help — it means the poll runs *only* while the tab is foregrounded, i.e. exactly while someone is interacting. So: set a local flag before calling `refetch()`, clear it when the returned promise settles, and gate `disabled` + the spin animation on that flag; or drop `disabled` entirely and let the icon-spin alone carry busy state, since a duplicate click during an in-flight fetch is deduped anyway. The same reasoning applies to any ambient hook state that is true for reasons other than the user's action. Reference: `features/settings/workspace/systemHealth/TelemetryCard.tsx`'s `LiveRefreshButton` (the corrected form — local `pending`, and a `role="status"` announcement fired only for a user-initiated refresh, because putting `aria-live` on the polled region itself would re-announce every tick). Known remaining offender: `SystemHealthOverviewPage.tsx`'s "Force refresh" button, which disables off the same polled query's `isFetching` (#2880 ux-review).

217. **Every dialog/drawer/modal/panel that edits existing information or collects new information presents an explicit, consistent commit/discard affordance — Save (primary) + Cancel (secondary), Save disabled until dirty, a Cancel that reverts to the original values, and an unsaved-changes guard on any dirty dismiss — composed from the shared `@/components/dialog` primitives, never re-decided per surface.** The contract (issue #1361, generalizing web-rule 164 from the backlog drawers to all editable surfaces):
    - **Save is disabled until the form is dirty** (a field actually changed vs. the last-saved snapshot) and re-disabled after a successful save. Dirty is a structural `JSON.stringify(draft) !== JSON.stringify(baseline)` compare of flat scalars.
    - **Cancel discards pending edits and restores the baseline** — it never mutates.
    - **Dismissing while dirty** (Esc, scrim/backdrop click, close ✕) opens the **unsaved-changes guard** (`role="alertdialog"`, focus-trapped, default focus on the safe "Keep editing") instead of silently committing OR silently discarding. A clean dismiss closes immediately with no prompt.
    - Compose these, do not hand-roll them: **`useDirtyDraft<T>(initial)`** owns draft/baseline/dirty + `reset()` (Cancel) + `commit()` (post-save re-snapshot); **`useUnsavedChangesGuard({ dirty, onClose })`** owns the close-vs-guard decision, the guard's open state, and the document Escape listener; **`DialogFooter`** renders the Save/Cancel bar (shared `Button` primitive, ghost Cancel + primary Save, the muted "Unsaved changes" status, an inline `role="alert"` for validation/save errors); **`UnsavedChangesDialog`** is the discard prompt. Two valid compositions: a **deferred drawer** mounts `{dirty && <DialogFooter/>}` so the bar appears only while dirty (backlog drawers, rule 164); an **always-on modal** renders the footer for its whole lifetime and passes `dirty` so Save stays inert until a change. 206. **A dialog that declares `role="dialog"`/`role="alertdialog"` + `aria-modal="true"` MUST trap focus itself (`useFocusTrap`) — you cannot clone a confirm dialog that relied on a parent modal for focus containment into a standalone/bare mount and keep `aria-modal` honest.** The board's `DeleteConfirmDialog` has no internal trap because it is always nested inside `TaskFormModal`, which contains focus. `EpicDeleteConfirmDialog` (#1339) was cloned from it but is mounted **bare** on the Product Backlog page (rendered by `EpicHeader`, no outer modal), so without a trap Tab/Shift-Tab walks straight out behind the scrim — violating the `aria-modal` contract (WCAG 2.4.3 / 2.1.2). Pair this with **focus restoration**: the surface that opened the dialog (e.g. the epic kebab) must return focus to its trigger on close — for a trigger that unmounts while the action is open (the kebab is hidden during rename), restore via an effect keyed on the open/close state, not a direct `.focus()` in the close handler. 245. **A dialog that stays open while its content swaps state passes that state as `useFocusTrap`'s `focusKey`; a confirm dialog nested inside a modal whose parent trap yields must run its own `useFocusTrap` — never ship a modal surface where Tab can reach the background page (WCAG 2.4.3 / 2.1.2).** Two failure shapes, one hook. 335. **A phase swap that replaces a surface with its OUTCOME must announce the outcome, not just seat focus on a button beside it — a live region inserted together with its own content is not a reliable announcement, and moving focus states the control's name and nothing else.** Rule 245 says re-seat focus when a dialog swaps phase; rule 288 says prefer the phase's primary action over a `tabIndex={-1}` status node. 360. **A scroll container with no focusable descendant needs `tabIndex={0}` and a `focus:` ring — otherwise it is unreachable by keyboard, and the two attributes you added for accessibility are what hide the fact.** An `overflow-y-auto` region scrolls from the keyboard only when focus is inside it or on it. A *form* panel gets that for free — its inputs are the seats — which is why the pattern looks safe everywhere it is used. An **outcome** panel does not: it is pure prose, and rule 335 deliberately puts its actions (Retry / Done / Close) in a **sibling footer**, so nothing inside the scroll box can take focus and the arrow keys scroll nothing. 361. **A control that is inert *by design for a named release* is not rule 122's incidental placeholder — it takes an at-rest sentence, a version badge, `aria-disabled`, and an explicit `aria-label`; never a `title`, and never `disabled`.** Rule 122's `title` clause assumes a control whose unavailability is incidental. When the control is present specifically so the surface's geometry does not move when the capability ships, `title` is the wrong carrier: it is hover-only, so it is unreachable by keyboard and by touch — the same objection rule 121 raises against tooltip-borne upgrade links. 362. **A focus trap assumes its focusable set and its restore target are both stable — a one-way action invalidates both, and neither rule 206 nor rule 245 catches it as written.** Two failures on one confirm sheet (#3129), each a shape an existing rule describes with the wrong trigger, and both invisible to the unit tests that shipped with them. **(a) `disabled` empties a trap without unmounting anything.** Rule 245(a)'s `focusKey` requirement is written around *phase* dialogs where the focused control unmounts, so a sheet that merely disables its own buttons for the duration of a write does not read as covered — but `FOCUSABLE_SELECTOR` is `button:not([disabled])`, so the set goes **empty**, the browser drops focus to `<body>`, and nothing re-seats it. On any error path that leaves the sheet **open**, `document.activeElement` is then neither the first nor the last focusable, the Tab handler stops intercepting, and Tab walks into the page behind the scrim — an `aria-modal="true"` surface the keyboard can leave (WCAG 2.4.3 / 2.1.2). **Any dialog that disables its own controls while a request is in flight passes that pending flag as `focusKey`**, and gives the container `tabIndex={-1}` so the empty phase has a seat. **(b) A one-way action's trigger is gone before focus comes back, and open/close is the wrong key.** Rule 206 prescribes restoring an unmounting trigger "via an effect keyed on the open/close state" — insufficient here, because the trigger is still mounted when the sheet closes and disappears one refetch later when the lifecycle flips. Corollary for the guard, and the reason this class keeps shipping: **jsdom does not blur a focused element when it is disabled**, so a vitest assertion that focus stayed inside the trap passes with the fix reverted. It is vacuous by construction and must not be written; this class can only be pinned in a real browser. 315. **A layout constant that varies at runtime needs ONE owner and a read path that does not require React — a second declaration is not a duplicate, it is a silent mis-hit.** Schedule rows are 28px on a mouse and 44px on a coarse pointer (web rule 5, WCAG 2.5.5), and `ROW_HEIGHT` was read by five subsystems, three of which are not React and cannot take a hook: the canvas renderer, the pointer hit index, and the engine's virtualization. Before #2997 the same `= 28` was declared **three** times (`scheduleConstants.ts`, `engine/GanttHitIndex.ts`, `engine/GanttRenderer.ts`) and nothing noticed, because while the value is a literal the copies agree by luck. The moment it varies they can disagree, and **the disagreement has no visible symptom**: the hit index lays out rows at one pitch, the canvas paints them at another, taps open the task above or below the one under the finger, and every screenshot looks correct. That is why this is a rule about *ownership* rather than about touch targets. Four obligations. **(a) One module owns it; everyone else re-exports.** `export let X` plus a setter in the owning module is an ES **live binding** — importers read through to the variable, so ~70 existing `rowIndex * ROW_HEIGHT` call sites keep working unchanged and no signature grows a parameter. `export { X }` after `import { X }` preserves liveness, so a module that used to declare its own can re-export instead and its importers never notice. **(b) Never capture a live binding at module scope** (`const TWO_ROWS = ROW_HEIGHT * 2` at the top of a file freezes the first value forever) — read it inside the function, and hoist into a local only *within* a hot loop, where it is also the right thing for the 60fps paint path. **(c) A React consumer must SUBSCRIBE, not merely read.** Reading the binding during render yields the right number and will not re-render when the pointer class flips (a tablet gaining a keyboard, a hybrid laptop folding shut); the hook that subscribes must also be the thing that *writes* the binding and must return what it wrote (`useRowHeight`/`useRowMetrics` → `syncRowMetrics(coarse)`), so a hook computing `coarse ? 44 : 28` itself is exactly the second definition the rule forbids. Caching consumers need an explicit invalidation: TanStack Virtual keeps its measured sizes, so changing `estimateSize` alone leaves rows at the old pitch inside taller boxes — `virtualizer.measure()` on the height is what actually moves them. **(d) Gate the population, not the instance** (rule 300): a source scan asserting the declaration appears exactly once is the only thing that can see somebody *adding* a fourth copy, since no behavioral test on the existing consumers can. Reference: `features/schedule/scheduleConstants.ts` (the owner), `hooks/useRowHeight.ts`, `features/schedule/engine/{GanttHitIndex,GanttRenderer}.ts` (the re-exports), `features/schedule/scheduleConstants.test.ts` (the population gate), `e2e/schedule-coarse-row-height.spec.ts` — #2997, from `TruePPM - Designer Prototype.html` "Coarse pointers". **A second instance, and the sharper one: #3012 split `HEADER_HEIGHT`.** The same literal `28` meant *two different things* at 19+ sites — "the date ruler band" and "the y where row 0 starts" — and nothing could tell them apart because they were the same number. Corollary for the trigger: a single button that says `aria-haspopup="dialog"` while announcing itself as "Actions for X" is already lying about being a menu — the moment a second action exists, make it a real `role="menu"` with roving focus and Escape-to-trigger rather than stacking a second corner button. Reference: `features/board/BacklogBand.tsx` (`BacklogCardMenu`, `FileUnderTarget`), `features/board/BoardView.tsx` (`handleFileUnder`, next to `dropOnCell`), `e2e/board-backlog-band.spec.ts` — #2952, design `v6-cases.js` case 18.

321. **Two "views" of one collection are two SURFACES over one row model, and a surface may choose columns — never rows.** The Schedule shipped Grid and Timeline as a segmented toggle, and Timeline did not render the outline at all: it hid `TaskListPanel` and let the canvas paint task names itself, into a frozen 176px column it drew with its own truncation, its own row loop and its own idea of what a summary row looks like (#1221, #2096). A planner who switched layout to see the bars better lost the ability to see what contained what, and there was no moment at which anybody decided that. Four obligations. **(a) One call site, one derivation, fed one array.** The fix is structural, not disciplinary: render the *same component* on both surfaces from the same rows and the same fold state, so a surface **cannot** re-derive row identity, order, containment or expansion because it is never asked to. "Keep them in sync" is not an obligation you can discharge — a second `flattenVisible` will drift, and the drift's symptom is a missing affordance rather than an error. **(b) What a surface chooses is presentation, and the choice is a pure function of the surface.** `surfaceColumnVisibility(surface, visible)` narrows the user's persisted column set; it **narrows and never widens**, so a column hidden on one surface cannot reappear on the other, and there is nowhere for a surface-specific row filter to hide. Anything derived from that choice — the panel's width, the Display menu's Columns section, the overlay offsets — resolves through the same predicate, so the menu that offers a column and the panel that draws it cannot disagree (rule 316 applied to a layout). **(c) When the second surface arrives, DELETE what compensated for its absence, in the same MR.** The canvas name gutter existed only because "the task table is hidden (Timeline view)" — its own docstring said so. Leaving it once the outline renders on both gives you two frozen name columns side by side and, worse, a Display option that changes nothing; a retired option must come out of the menu, out of the persisted allow-list, and out of the renderer, with the stored preference falling back to the *closest surviving behavior* rather than to the list's first entry. **(d) Pin the invariant with a test that renders both surfaces and compares.** Assert the row ids, `aria-level` and `aria-expanded` are identical while the `columnheader` count differs — that is the one assertion a future Timeline-specific row list fails, and no test of either surface alone can make it. Corollary: geometry that was slack on the wide surface becomes load-bearing on the narrow one, so re-check the bounds you never needed — an unclamped splitter drag merely looked untidy beside five data columns and pushes the entire bar track off screen when the outline is the only thing to its left. Reference: `features/schedule/scheduleSurface.ts`, `features/schedule/ScheduleView.tsx` (`ScheduleMainArea`, `PanelSplitter`), `features/schedule/scheduleSurface.test.tsx`, `e2e/schedule-view-mode.spec.ts` — #2960, from `TruePPM - Designer Prototype.html` "The timeline is the grid".

322. **When two controls write ONE persisted layout value, they share one clamp and one announced range — and a bound must never reach backwards past the value the user already holds.** The Schedule stores `widths.task` once and offers it two `role="separator"` handles: `TaskListHeader`'s per-column `ResizeHandle` and `ScheduleView`'s `PanelSplitter`. #2960 gave the splitter a container-aware clamp so a drag could not push the bar track off the viewport — and left the header handle's pointer path **entirely unbounded** and its keyboard path on a local `MAX_COL_WIDTH` of its own. So the invariant the change existed to establish was defeated by the *other* control on the same value, and on the Timeline (where Task is the last column) the two hit zones ended up adjacent with the unclamped one three times wider: aim at the divider in the header row and you get the unbounded control, aim one row lower and you get the clamped one. Three obligations. **(a) One clamp function, taking the measurement, called by every writer.** A second writer is not a duplicate — it is the escape hatch, and it is invisible to any test that drives only the control the change touched, so the first thing to grep when adding a bound is who *else* writes the value. **(b) `aria-valuemin ≤ aria-valuenow ≤ aria-valuemax` is an invariant, not a rendering detail, and two separators over one quantity must announce the same range.** A range computed from available room goes inverted the moment the sibling columns eat the room — a 600px outline in a ~780px pane yields a max of 120 against a current of 220 — and an inverted range is a WCAG 4.1.2 failure that no visual check sees; assert `valuenow` inside `[valuemin, valuemax]` in the spec that adds the bound. **(c) An upper bound is permission to grow, never an instruction to shrink.** Clamp to `Math.max(bound, current)`: a user who has held 220px for a year did not ask for 120px by pressing ArrowLeft once, and a clamp that snaps on first contact reads as the control being broken rather than as a limit being enforced. Corollary, and it costs a debugging round: **a bound resolved from a DOM measurement must not be read during render or inside a pointer handler.** During render a null ref on first paint silently yields the fallback constant, which is then announced to assistive tech as fact; inside `onPointerMove` it is a write-then-read cycle at pointer rate, flushing layout for the whole pane 60–120 times a second on the one gesture whose job is to feel direct. Measure into state with a `ResizeObserver` (`useObservedWidth`) so the announcement and the enforcement come from the same number at the same time. Reference: `features/schedule/ScheduleView.tsx` (`PanelSplitter`, `clampTaskWidth`, `maxTaskWidthFor`, `useObservedWidth`), `features/schedule/TaskListHeader.tsx` (`ResizeHandle`), `hooks/useBoardResize.ts` (the same class, 2026-06) — #2960.

324. **A gesture that acts on a SELECTION cannot be reached if a child of the row swallows the click — and the swallow is invisible to every test that drives the keyboard.** The Schedule outline had `⇧↑`/`⇧↓` and `⌘A` multi-select since #2727 and no pointer way to build a range, because `TaskListRow`'s `onClick` took no event at all (`onClick={() => handleRowClick(surface)}`); giving it one was not enough. 326. **A persisted preference and a taught keystroke are both CLAIMS — each must resolve against the thing that implements it, and the gate that proves it must DERIVE the resolution rather than restate it.** Two controls on one Schedule surface shipped claiming something nothing implemented, and neither was catchable by any test of the control itself. `Comfortable rows` toggled, persisted to `localStorage`, echoed back into the menu's `checked` — and was read by nobody, because row height came from the pointer class alone (#3019). Cover the entry point *and* assert a downstream effect; the first without the second is what lets a control be renamed or unwired in silence. **(b) A preference that modifies a runtime-resolved value is a second INPUT to that value's single owner (rule 315), never a second resolution.** Latch it in the owner beside the existing input and recompute from all of them — do **not** widen the existing setter to take both, because the writers know different halves: eight components call `syncRowMetrics(coarse)` on every render and none of them knows the preference, so a combined setter clobbers it back to `false` on the next paint. And distinguish a keystroke claim from a glyph that names a **button** — a `<kbd>` chip is a claim, prose is one only when it carries a modifier glyph. That line is load-bearing rather than tidy: the coach bar's third line reads `+ ⇤ ⇥ ◆`, which is the row's own button glyphs and is correct where it stands, so a guard matching glyphs anywhere would demand a wrong "fix" to a right string. Corollary — **fix the claim wherever it is made**: the same dead `Tab` was being taught by `features/summary-tasks.md` and `features/subtasks.md` while `features/schedule-build-mode.md` three pages away documented `Alt + →` correctly, so grep the docs tree for a keystroke you are correcting in the UI. 331. **A server-computed rollup is not maintained by any optimistic update, so it must be invalidated on the ORIGINATING client too — and it must be added to an EXISTING `useProjectWebSocket` handler, never a new `on()` registration.** Two independent traps meet on the same line. **(a) Self-echo suppression is about the optimistic cache, not about freshness.** ADR-0152 skips the `tasks` refetch when `actor_id === currentUserId` because that client already applied its own edit locally — correct for rows the client wrote, and exactly wrong for `/overview/`, `/attention/`, `/my-tasks/` or a critical-path query, because nobody optimistically recomputes a server-side aggregate. Suppressing those leaves the *editor's own* health chip and critical path stale, so the defect survives the fix and moves one user over. Decide the self-echo branch per key: skip it for what the client wrote, never for what the server computed. **(b) `on()` is last-write-wins** (`eventHandlers[t] = handler`) — a second registration for an event type silently REPLACES the first, and the symptom is the *old* invalidation disappearing, not the new one failing. Extend the existing handler; `scheduleInvalidate` does accumulate, so several calls in one handler are fine and are also what keeps a paste-many or CPM cascade to one refetch per key instead of one per event. **(c) The hook is where this is testable.** Spy on `invalidateQueries`, dispatch the event, advance past the ~300ms debounce; a spec that only checks a collaborator event passes while the self-echo branch is wrong, so assert both. **(d) Do not invalidate a key no event reports — but ask what the RESPONSE is a function of, not what the endpoint is named.** *Superseded in part by #3140 (2026-08-30).* This clause originally cited `monte-carlo-latest` as the worked example: it serves the cached result of the last simulation, no broadcast announces a simulation, so wiring it to task events re-fetched an identical row. **That stopped being true when the payload gained a per-response staleness discriminant** derived from the project's live sync version and last recalc — every task event moves that input, so the row genuinely differs, and the forecast bar gates its Rerun *action* on it. The key is in `OVERVIEW_KEYS` now and the pin test asserts the inverse. The general rule survives and is sharper for it: a key is "reported" by any event that moves an input of its response, which includes inputs the server derives at read time and the endpoint's name never mentions. What has NOT changed is the other half of the original note — propagating a *collaborator's completed simulation* still needs a server-side event that does not exist; #3140 refreshed the verdict, not the forecast. This page's five rollups were invalidated by zero events and sat stale behind a 60s `staleTime` with `refetchOnWindowFocus: false` until the route remounted, which is indistinguishable from being current. Reference: `hooks/useProjectWebSocket.ts` (`OVERVIEW_KEYS`), `features/project/ProjectOverviewPage.tsx`, `lib/queryClient.ts` — #2912, sibling of #1867.

327. **A row's own state must render AT REST, and the cell that states it is where the cell edits it — adding that control changes what a geometric row click hits.** The Schedule row carried `←2` / `→1` dependency chips that appeared **only while the row was selected in focus mode**, so learning whether a row had links required selecting it, which is the opposite of scanning a plan; and the only way to change a link was a right-click menu, so the row could show what it was linked to or offer to change it, never both in one place (#3023, `design_handoff_trueppm_v4/`). Four obligations, and the fourth is the one that bites. **(a) A fact about the row renders unconditionally.** Selection, hover and focus mode are *emphasis*, never the precondition for a fact existing — a signal you have to go looking for answers a question you no longer have. **(b) State the SHAPE, not the tally — and state it in WORDS where a tint is doing the work.** `←2` cannot separate two finish-to-start links from an FS and an SS, and that is the difference between a chain and an overlap — the question the glance was actually asking. Name the types (`FS×2` / `FS·SS`), pick one honest reading for the case the design left open (here: three or more distinct types collapse to `Mixed×N`, counting links so the count means one thing in every arm; a type the client does not recognize echoes its own code rather than falsely reading `Mixed×1`), and put the full breakdown in the tooltip and the cell's `aria-label` rather than widening the token — capped, because a hub row otherwise produces a multi-kilobyte label nobody can read. Criticality belongs in that sentence too: red-on-chip was survivable while the chips appeared only on a selected row, but a column at rest makes hue the sole carrier of the one fact that changes what the reader does next, which is a WCAG 1.4.1 failure. **(c) The control is a control only for someone who may author** — a viewer gets the identical statement as text, absent rather than disabled (rule 302). Gate on the authoring API, not on the mode flag, which is also non-null for a reader because it carries navigation. **Two facts side by side are two targets**: a cell drawing `←FS×2` and `→FS` and routing both to the predecessor picker sends half the clicks to the wrong direction, so give each its own control; and let the control **fill the cell** rather than float in it, or the row's 44px coarse-pointer height wraps an 18px target. **(d) A cell that is also a control makes the row's CENTER a live target, and every pointer action aims at the center.** Seven E2E specs across two files were selecting or renaming a row by aiming at whichever column happened to sit at the midpoint — Duration at seven columns, the new Links control at eight — and the control `stopPropagation()`s, so each failed two lines later on an `aria-selected` assertion or a missing rename `input`, with nothing pointing at the column that had been added. The blast radius is **every row, not only linked ones**: the empty-state affordance means an unlinked row's cell is a control too. The fix is not an offset: **locate the cell by name** (`getByRole('gridcell', { name: /^(Duration|Estimate):/ })`), which survives the next column too, and remember one column can carry two labels across row kinds. Before adding any column, sweep `e2e/` for a pointer action on an **un-narrowed row locator** — and sweep it structurally, because the obvious grep does not find this: the two worst instances were a `dblclick()` (not `click`) on a `page.locator('[data-row-id="…"]')` (not `getByRole('row')`) **held in a variable** (not an inline chain). Cover `click` / `dblclick` / `tap`, both locator forms, and variable-held locators; a chain that narrows to a `gridcell` / `button` / testid first is safe, and `hover()` is safe because it bubbles. Nothing mechanizes this yet — a `scripts/` check that flags a pointer action on an un-narrowed row locator is what would catch the eighth instance. 310. **Two URL-param writes in the SAME commit lose the first — `setSearchParam`'s functional updater does not save you, and the failure is silent.** `setSearchParams` resolves each updater's `prev` from the **live location** at call time, and react-router does not apply an earlier write before a later one reads. So functional updaters compose only **across** commits. Within one commit — two `setSearchParam(…)` calls for two keys, or one racing a sibling effect that also writes on the mount pass — the later write's snapshot is the pre-write URL and it restores everything the earlier one deleted. Nothing throws, no test fails, and the param simply stays in the URL, which is why this reads as "my effect never ran" and sends you debugging the wrong function. `useUrlSelectedId`'s docstring used to claim same-flush composition; it is corrected, and #2031's fix was always about the *cross-commit* case. Two obligations: **(a)** one pass that must change several keys writes them in **one** `setSearchParams` updater, never N helper calls; **(b)** a write that must survive a sibling mount-pass write (in `ScheduleView` that is the focus/cp/crit/ms display-filter mirror, which fires on every mount) is deferred to a **later commit** — latch a state flag in the consuming effect and do the write in a second effect keyed on it. 309. **The Schedule row's far-left edge is spoken for twice — a third row-level meaning goes at the indent origin, not there.** `border-l-2 border-brand-primary` on the row already encodes **selection**, and `ModeGutter`'s absolutely-positioned 3px stripe at `left-0` already encodes **delivery mode** — the two were deliberately stacked (one is the padding edge, one is just inside it) and there is no room for a third without making all three ambiguous. 279. **An effect that needs a DOM node takes the node from `useElementRef` and lists it as a dependency — never `someRef.current` read inside an effect that cannot re-run when the node mounts (#2365).** A `RefObject`'s identity never changes and mutating `.current` does not re-render, so the ubiquitous shape `useEffect(() => { const el = ref.current; if (!el) return; el.addEventListener(…) }, [])` is **silently dead** whenever the node mounts after the first commit — which is the normal case on any surface that returns a loading skeleton or an error state before its real container (rules 246/248): the first commit renders the skeleton, the effect runs against `null`, bails, and never runs again. Use `const { el, setEl } = useElementRef<HTMLDivElement>()` (`hooks/useElementRef.ts`), attach `ref={setEl}`, and key the effect on `[el]`; a hook that owns such an effect exposes a **callback ref** (`setScrollEl`) plus the node (`scrollEl`) in its public API rather than a `RefObject`, so a consumer cannot reintroduce the bug, and any sibling hook that measures the same container takes `HTMLElement | null` rather than a ref. Three consequences: (a) `setEl` sets state, so it must only be called the way React calls a callback ref — after commit, never during render; (b) the effect's cleanup now genuinely runs when the node is swapped, so listeners/observers rebind correctly instead of leaking onto a detached node; (c) **a unit test must mount the container after the first commit** — the pre-#2365 tests passed a hand-built `{ current: el }` or assigned `ref.current` in the render body, which pre-seeds the very state the bug depends on and is why three broken hooks tested green. This bug class presents as e2e flake (it races query-cache warmth), so a spec covering such a surface should force the cold path with the `delayRoute` fixture (`e2e/fixtures/cold-load.ts`) rather than leave the ordering to chance. Reference: `hooks/{useElementRef.ts,useSpaceDragPan.ts,useHasScrollBelow.ts,useHasScrollRight.ts}`, `e2e/fixtures/cold-load.ts`, `e2e/board-space-pan.spec.ts`.

235. **On the interactive canvas Gantt, the task bar FILL carries task STATE and the critical path is a red BORDER frame — never colour the fill by criticality.** Same principle as the PDF export (rule 234 / ADR-0277), applied to `GanttRenderer.ts`. `barFillColor()` resolves fill by state only (external → `textSecondary`, summary → `barSummary`, complete → `barComplete` sage-600 green, else → `barNormal` blue-500); it must **not** return `barCritical`. `drawTaskBar()` draws a **2px red critical frame** (`barCritical` = #B91C1C light / #F87171 dark) as an inset border for non-external, non-summary critical tasks. The reason: `barFillColor` checks `isComplete` *before* `isCritical`, so a red critical fill lost to a completion-wins-precedence race — a done critical bar rendered solid green and the critical path vanished on a mostly-complete schedule. A completed critical task must read as a **green bar in a red frame**; the critical signal can never be masked by state. Constraints:
     - **Draw order:** the 30% progress overlay paints BEFORE the borders so they stay crisp rather than dimmed by the tint; the selection ring paints next; the **critical frame paints LAST**.
     - **Selection nests inside the critical frame; risk outranks selection.** The navy `selectionRing` (#1B2A4A) is a 2px inset ring; when a critical frame is present and `barWidth >= MIN_NEST_WIDTH` (12px) it nests one step further in (inset 3px, 1.5px wide) so a selected critical bar reads red-frame-outside / navy-ring-inside. Below 12px the two concentric rings collide, so the ring uses the standard inset and — because the frame is drawn last — the red frame paints over it: a narrow selected critical bar keeps its criticality rather than losing it under the navy ring (the dropped-signal bug the #1699 UX review caught). **Gantt bar visual channels are orthogonal — fill = state, border = risk, ring = selection, line = time (ADR-0103/0277/0280); never encode two on the same channel** (the pre-#1699 bug was critical stealing the fill channel from complete). When channels stack on one bar, each must stay independently perceivable: draw inner channels at a smaller inset than outer ones, and below a minimum width abandon nesting in favor of a treatment that preserves the higher-priority signal (**risk > selection**). A channel another can fully occlude is a dropped signal.
     - **The `%` chip uses the surface treatment only** (`chipPillOnSurface` dark pill + `chipTextOnSurface` white). The old white-on-red chip existed for the red critical fill; with no bar red-filled, every chip pairs with the blue/green state fill via the surface treatment. Do not reintroduce a criticality branch in `drawTaskBarChip`.
     - **Border clears WCAG 1.4.11** (≥3:1 non-text) in both modes as a 2px frame (#B91C1C ≈ 7:1 on white, #F87171 ≈ 4.87:1 on navy); criticality is additionally backed non-color by the task-list red dot + the critical-path-only filter (1.4.1) — do not remove them.
     - **`ScheduleLegend.tsx::CriticalSwatch`** must mirror the canvas: a red-framed neutral bar, not a solid red fill.
     - **`barCritical` still legitimately strokes late actuals** in `drawActualDateBar` (#80) — that path is unrelated and must stay.
     - **Scope:** the canvas `Task` exposes only `isCritical` (binary), so this is a critical-only red frame; graded at-risk/on-track amber bands (present on the PDF) wait until the risk-band data is plumbed to canvas tasks. Reference: `GanttRenderer.ts::{barFillColor,drawTaskBar,drawTaskBarChip}`, `ScheduleLegend.tsx::CriticalSwatch`.

244. **A `<canvas>` is not touched by the forced-colors (Windows High Contrast) user-agent transform, so canvas-drawn UI must detect `(forced-colors: active)` and repaint with CSS *system-color* keywords — otherwise it renders its fixed colors into a high-contrast theme and becomes invisible/unreadable.** DOM chrome gets forced-colors for free (the UA remaps `color`/`background`/`border` to the theme); pixels a component draws into a canvas do not. The Gantt engine (`GanttEngineImpl`) subscribes to `window.matchMedia('(forced-colors: active)')` (mirroring the `prefers-reduced-motion` pattern — detect at init, re-detect on `change`, full-repaint on flip, unsubscribe in `destroy`) and passes the flag to `setRendererColorMode(dark, forced)`, which selects a third palette `COLOR_FORCED` built entirely from system-color keywords the 2D context resolves against the active theme: `Canvas`/`CanvasText` (surface/ink), `GrayText` (de-emphasis), `Highlight` (accent + selection), `LinkText` (links). Because the system palette is intentionally flat, **bar *kinds* must not depend on hue** in this mode — lean on shape (milestone diamond, summary endcaps) and the `Highlight` accent for critical/selection (color is never the sole differentiator, rule 6). Semi-transparent tints (row banding, weekend shading, ghost fills) collapse to the solid surface/ink so nothing relies on alpha the theme may not honor. Keep the palette-selection function (`pickPalette(dark, forced)`) pure and exported so it is unit-testable without a canvas, and assert that a draw pass in forced mode emits system-color `fillStyle`s (not brand hex). Forced-colors wins over dark/light — it is a hard accessibility preference, not a cosmetic mode. Reference: `COLOR_FORCED` / `pickPalette` / `setRendererColorMode` in `engine/GanttRenderer.ts`, the `_forcedColors` wiring in `engine/GanttEngineImpl.ts`.

295. **A forced-colors palette entry that collapses an alpha tint to a solid system colour (`Canvas`/`CanvasText`) is only safe if that fill paints BEFORE everything it would occlude — check the draw ORDER, not just the palette.** Rule 244 requires semi-transparent tints to collapse to the solid surface/ink under `(forced-colors: active)`, because the theme may not honour alpha. That collapse is a *no-op* for a fill painted first (row banding, weekend shading — both drawn before `drawGridLines`) and **destructive** for a fill painted later: at 5% alpha the grid, separators and neighbouring marks read straight through; at 100% opacity they are erased. The failure is invisible in light and dark, invisible in any unit test that asserts only "forced mode emits system-colour `fillStyle`s", and appears only to a Windows High Contrast user — who loses the row separators they need most. So for a **region** fill (as opposed to a bar or a line) the forced-colors treatment is to **skip the fill entirely** and let the mark survive as its edges, hatch and label; branch on an explicit module-level `_forcedColors` flag set alongside the palette, never on the palette value alone. Two corollaries. (a) **Shape, not just hue, must separate a new full-height rule from the today line** — under the flat system palette `Highlight` is shared, so a solid 2px band edge is pixel-identical to ADR-0103's load-bearing "now" mark; dash it (`ctx.setLineDash`), which also keeps the mark non-colour-carried at zoom levels too narrow for its text label (WCAG 1.4.1). (b) **Anything drawn on the bars layer after `drawTaskBar` must clear the bar box** (`BAR_TOP_OFFSET`…`BAR_TOP_OFFSET + BAR_HEIGHT`, i.e. y 5–23 of a 28px row) — rule 235's critical frame is the first and last 2px of that box, and a label straddling a row boundary paints over the row above *and* the row below. The free strip is the 10px inter-bar gutter (`rowTop − 5 … rowTop + 5`); a mark that will not fit there paints *before* the bars so the bar wins the collision and the risk signal survives. Reference: `COLOR_FORCED.sprintBandFill`, `drawSprintBands` / `drawSprintBandLabels` in `engine/GanttRenderer.ts`, and their call sites in `engine/GanttEngineImpl.ts` (#2738, ADR-0803 — surfaced by `ux-review`).

## Iconography

*A glyph carries information or it does not exist.*

242. **A glyph that stands in for a *UI icon* — a status/affordance mark like a warning, lock, target, chart, pin, or disabled sign — must be a house SVG from `components/Icons.tsx`, never a Unicode emoji.** Emoji render inconsistently across platforms/fonts (flat vs. glossy, differing metrics, some monochrome some multicolor), do not inherit `currentColor`, and never match the design-system stroke weight — so a functional emoji reads as a foreign, off-brand mark and can't be tinted to the surrounding text/semantic color. #1739 converted the affordance families to house icons: `⚠`→`WarningIcon`, `🔒`→`LockIcon`, `🎯`→`TargetIcon`, `📊`→`BarChartIcon`, `📌`→`PinIcon`, `🚫`→`BanIcon`, and the file-type mime map (AttachmentSection, `previewType`) to the `FileIcon`/`FileTextIcon`/`FileSpreadsheetIcon`/`FileImageIcon`/`FilePdfIcon`/`FolderIcon`/`PaperclipIcon` set. The recipe for an inline `<span aria-hidden="true">GLYPH</span>`: replace with `<Icon className="inline-block h-3 w-3 align-[-0.125em]" aria-hidden="true" />` (the `inline-block h-3 w-3 align-[-0.125em]` baseline-aligns the SVG like the emoji it replaces; a trailing space inside the old span becomes `mr-1`; preserve any existing span classes by merging them before the standard ones). Keep the glyph `aria-hidden` — the adjacent text or an `aria-label` on the wrapper carries the accessible name (rule 6). **Three carve-outs stay as emoji** (they are *content*, not icons): user-chosen **reactions** (`CommentSection` 👍), an **emoji-scale input** (`TeamHealthPulse` mood 😞😐🙂😀🤩), and third-party **brand logos** (GitHub/GitLab/Figma/Notion/Slack host marks — a separate brand-asset/licensing decision, tracked in #1748). The remaining long tail of functional glyphs is a phased follow-up (#1749) — convert **one glyph family at a time**, updating its e2e/vitest assertions in the same commit. **The sweep is complete (#1749, #2480).** Every functional-glyph family and every string-stored `icon:`/`glyph:`/`emoji:` field now holds a house SVG, including the mixed maps that stalled the earlier slices (`OBJECT_TYPE_META`, `EVENT_META`, the Gantt and Queue row menus, `CalmToolbar`/`BoardLensBanners`, `notificationFilters`). **The unblocking move on a mixed map is to type it by *meaning*, not by shape** — `OBJECT_TYPE_META`'s `□ ◇ △ ⇢ ◈ ↻` had only two same-shape house icons between them, and inventing six abstract geometric marks would have produced a column that says nothing; reusing the icon each object type already carries elsewhere (`RiskIcon`, `SprintIcon`, `RepeatIcon`, …) made it readable instead. **Convert a map whole or not at all** — a half-converted map puts an SVG next to an emoji inside one control, which is worse than either alone. Four things stay glyphs on purpose, and are *not* regressions: `forecastDelta`'s `▲ ▼ ◆` direction triple (a redundant-encoding channel, not an icon family), **keycap legends** (`⇥ ⌘D ⌫ ⇧+Tab` — those are keys), the decorative `◆` on `OSSChip`/`BuildModeEmptyState`, and `$` on the cost toggle (a currency denomination — baking USD into an SVG path is worse for i18n). Two lessons from the `✓` pass: (a) **take the inventory in a script, not `grep -P` with a multi-codepoint bracket class** — that undercounted by an order of magnitude here (it reported one glyph where 27 were live), so a phase can silently believe a family is finished; count per-codepoint and exclude comment lines. (b) **A glyph span is not always a plain wrapper** — when the span carries sizing/background/border classes (`w-4 h-4 rounded-full bg-…`, a checkbox box, a 44px badge) it is a *container*: keep it and nest the icon inside at an explicit size, rather than merging its classes onto the SVG (which yields conflicting `h-4`+`h-3` and `inline-flex`+`inline-block`). Where the "off" state hid the glyph with `text-transparent`, omit the icon instead — the box already holds the layout. When a family's mark distinguishes *kinds* of selection, give each kind its own shape (`RadioDotIcon` for a `menuitemradio` row vs `CheckIcon` for `menuitemcheckbox`; `HalfCircleIcon` for a partially-met three-state outcome) so shape carries the state, not tint alone (rule 6). When a test asserts on the old glyph text (`getByText('⚠')`), re-anchor it to the rendered SVG (`getByLabelText(/…/).querySelector('svg')` or `.closest('.inline-flex')?.querySelector('svg')`) or a `data-testid` on the container. Reference: `components/Icons.tsx`, `previewType.ts`, `features/schedule/sections/AttachmentSection.tsx`.

283. **An icon column carries information or it does not exist: no glyph repeats inside a single settings nav group, `ExternalLinkIcon` means "this leaves the app", and `WarningIcon` means "exception" (#2425).** The defect this replaced: 6 of the 9 project `Configuration` rows rendered the same glyph (`SettingsIcon` ×5, `ExternalLinkIcon` ×2), with two more collisions in Setup and Danger — a column where most entries are identical is **negative information**, because it trains the eye to stop scanning the column and that costs the rows whose icon actually distinguishes them. Four invariants: (a) **uniqueness is per nav *group*, not per rail** — the same concept deliberately keeps the same glyph across the project / program / workspace rails (General = gear, Team/Members = resources, Access/Roles = lock, Working calendar = calendar, Integrations = plug), so a cross-group repeat is intended and a within-group repeat is the bug; (b) `ExternalLinkIcon` is reserved for navigation that genuinely departs the app and therefore appears in **no** settings nav row — an arrow leaving a box is a promise about where the click goes, and Attachments/Sharing stay inside TruePPM (Sharing gets the share-*network* glyph, because it grants access *inside* the product); (c) `WarningIcon` is reserved for the **Danger** group — spending a warning triangle on routine configuration (sprint guardrails, notifications) is exactly how it stopped reading as an exception; (d) new glyphs are hand-authored into `components/Icons.tsx` on the **16-box** house grid at `strokeWidth="1.5"` (rule 242 — no emoji, no icon library). A 24-box glyph dropped in unscaled renders at ~1.0px effective stroke beside the house set's 1.5px and reads visibly thinner, so convert the geometry rather than the `viewBox`. Each rail exposes its nav as a pure builder (`buildProjectSettingsNav`, `buildProgramSettingsNav`, `buildWorkspaceNavGroups`) so the invariant is asserted on the data, not on a rendered page — `src/features/settings/settingsNavIcons.test.tsx` fails on a reintroduced duplicate. Reference: `components/Icons.tsx`, `features/settings/{ProjectSettingsPage,ProgramSettingsPage}.tsx`, `features/settings/workspace/workspaceNav.tsx`.

292. **A 2px brand-primary left rule (`border-l-2 border-brand-primary`) is this app's SELECTION/ACTIVE idiom — a static informational block uses `border-l-4`.** The 2px form means "the thing you selected / the page you are on" everywhere it appears: `Sidebar.tsx` (active nav), `SettingsShell.tsx` (the active scroll-spy rail item), `TaskListRow`, `BoardView`, `BoardColumn`, `RosterList`, `TaskRow`, `columnHeaderParts`. Reusing it for a non-interactive note inside `features/settings/` is the worst case, because the shell's active rail item renders the identical treatment **in the same viewport** — two identical marks, same screen, different meanings, and a user who has learned the idiom gets a false positive on a static paragraph. The informational form is `border-l-4 border-brand-primary pl-3` (reference: `WebhookEditorModal.tsx`, `StakeholderReachSummary.tsx`), which also happens to align the block's text edge with a sibling `px-4` table header. If the block is not brand-relevant at all, use a neutral or semantic border instead. Surfaced by the #2529 ux-review.

293. **A `text-[12px]` paragraph of running prose in `features/settings/` carries a measure cap of `max-w-[440px]`–`max-w-[480px]`.** The settings shell's content column is `max-w-[920px]`, so an uncapped 12px paragraph sets ~145 characters per line at desktop width — roughly double the 45–75 character comfortable range, at the page's *smallest* type, on the surface where an admin actually reads prose. Desktop is the primary device for these pages (rule 118's own rationale), so this is the viewport that matters. Already the de-facto convention: `WorkspaceMethodologyPage.tsx` (`max-w-[480px]`), `ProjectMethodologyPage.tsx` (`max-w-[440px]`), `ProgramCadencePage.tsx` (`max-w-[460px]`), `StakeholderReachSummary.tsx` (`max-w-[480px]`). This is about *prose* — a 12px label, chip, or table cell needs no cap. Surfaced by the #2529 ux-review.

## Placeholders and operator surfaces

*What an unavailable control is allowed to look like.*

122. **Disabled placeholder/stub controls in `features/settings/` use the `.settings-stub` recipe — never `disabled:opacity-50`.** Half-opacity body text fails WCAG 1.4.3 and diverges from the established stub treatment. Two equivalent paths: wrap a whole section in `StubFieldset` (preferred — the `.settings-stub :disabled` rule in `globals.css` recolors every descendant in one place, used by `WorkspaceDangerPage`), or for an individual button apply the recipe as `disabled:` utilities at opacity 1 — `disabled:bg-neutral-surface-sunken disabled:text-neutral-text-secondary disabled:border-neutral-border/55 disabled:cursor-not-allowed` (drop the bg/border pair for borderless text-link buttons; recolor + `disabled:cursor-not-allowed` is enough). Always keep the full rule-4 `focus-visible` ring **including `ring-offset-1`**, and add a `title` explaining why the control is unavailable: `#NNN` for an OSS gap, "Available in TruePPM Enterprise" paired with `EnterpriseBadge` (rule 121) for an Enterprise-reserved action. Dead-but-clickable buttons are worse than disabled ones (#669) — disable the placeholder, link the tracking issue, ship. The **individual-button** form of this recipe (opacity-1 `disabled:` recolor + `disabled:cursor-not-allowed` + kept focus ring + explanatory `title`) is the app-wide convention for any inert placeholder, not only `features/settings/` — e.g. the schedule-export dialog's disabled "Layout B — Report" radio (until #1439) and its Export-when-empty button (#1438) both use it. Only the whole-section `StubFieldset`/`.settings-stub` path is settings-scoped.

274. **A read-only surface for an operator / deploy-time (env or Helm) value presents an honest *status* — a state chip, the controlling env-var name, and an explicit "configured in the server environment, not editable here" — never a disabled in-app toggle or a "fix it here" link.** Such values are set outside the app (env / Helm `values.yaml`) and no authenticated user may change them through the UI — that boundary is deliberate (e.g. a platform DoS protection must not be app-toggleable). Show the live state read-only and name the lever the operator actually uses; a dead toggle, or a link that goes nowhere, is worse than plain text. This is the operator-status corollary of the rule-8 live-wiring discipline ("hide a not-yet-wired control; never present a dead control as if it works"). Reference: `RateLimitDisabledBanner.tsx` + the `RateLimitCard` in `features/settings/workspace/SystemSummaryCards.tsx` (the `TRUEPPM_RATE_LIMIT_ENABLED` kill-switch status, #2316 / ADR-0604), mirroring the read-only OTel telemetry posture card.

306. **A security-relevant escaper (CSV cell, HTML, filename, shell) has exactly ONE implementation in this tree, and the thing that keeps it that way is a source-scanning test — not a code review.** CSV/formula injection was fixed in `utils/exportCsv.ts` and `features/risk/riskExport.ts` by #2762, and then found again at `WorkspaceMembersPage` and `WorkspaceRolesPage` (#2892), because each surface that needed a CSV cell had written its own `csvCell` doing RFC 4180 quoting only — no formula-prefix neutralization and no `\r` in the quoting regex, so a member display name beginning `=`/`+`/`-`/`@` executed on open in Excel and an interior lone CR could split the record and smuggle a live formula past the guard. Every one of those copies passed its own unit tests; what a per-file test structurally cannot see is that a *sibling* file has a weaker guard, which is why two rounds of site-by-site fixes did not end the class. Three obligations: **(a)** a new CSV surface imports `escapeField` and `downloadCsv` from `@/utils/exportCsv` and adds nothing of its own — widen the shared helper for a new cell type (`riskExport`'s one-line `String(value ?? '')` wrapper is the allowed shape) rather than reimplementing quoting beside it; **(b)** the guard and the quoting must **compose in that order** — prefixing never removes the need to quote, and quoting alone does not stop evaluation; **(c)** the invariant under test is *"there is only one"*, not *"this one is correct"* — `src/utils/exportCsv.conformance.test.ts` source-scans the tree for a second `FORMULA_PREFIX_CHARS`, a hand-rolled `replaceAll('"', '""')`, or a `new Blob` carrying `text/csv`, and asserts its own scan is non-vacuous so a broken glob cannot pass by finding nothing. Do not replace it with a hand-maintained list of sites to check: that enumeration is precisely what let the class survive #2762. This is rule 300 applied to an injection class — a rule that needed a second manual sweep did not have a working mechanism.

336. **A tinted control inside an already-tinted container composites TWICE — an AA-safe token pair is not AA-safe at nesting depth 2, and the DS-v2 gate's own prescribed fix does not rescue it.** Every `semantic-*` and `brand-primary` contrast figure in this file and in `globals.css` is measured against an **opaque** surface. Put a `bg-{token}/N` or `bg-{token}-bg` control *inside* a banner or card whose own background is a tint of the same hue and the two alphas stack: the foreground barely moves while the background travels toward it, and the pair drops below 4.5:1. Measured on `SprintCloseFailedBanner` over `bg-app-canvas` (**not** white — that is the surface anything under `SprintsView` actually composites onto): `text-semantic-critical` on `bg-semantic-critical/10` inside `bg-semantic-critical-bg` is **4.21:1 light / 3.58:1 on hover**, and swapping to `bg-semantic-critical-bg` — the substitution rule 8b prescribes — is only **4.34:1 light / 4.21:1 dark, still failing**. So: **an action button inside a tinted banner takes either no fill at all (border + text, hover wash on an opaque token) or an opaque `bg-neutral-surface` base** — 4.91:1/5.33:1 and 6.47:1/5.73:1 respectively. Two things this rule exists to say that no gate can. **(a) A green DS-v2 run is not evidence about nesting.** `sem_tint_offenders()` in `scripts/check-design-system-v2.sh` matches the `semantic-*` families only, so the identical `brand-primary` failure in the sibling `RetroHandoffBanner` (`text-brand-primary` on `bg-brand-primary/10` inside `bg-brand-primary/5`, **4.23:1 light**) is invisible to it — the gate caught this file and cannot catch that one. **(b) Compute contrast against the surface the element actually composites onto**, walking up to the nearest **opaque** ancestor, not against white and not against the immediate tinted parent alone. This is rule 300 applied to contrast: the reason the class recurs is that the arithmetic everyone does is one layer shallower than the DOM. Reference: `features/sprints/SprintCloseFailedBanner.tsx`, `features/sprints/RetroHandoffBanner.tsx` — #2992.

## Product boundary

*What OSS shows, and where Enterprise may be surfaced.*

231. **The OSS UI shows what one team can do; an Enterprise affordance appears ONLY at a surface where the user reaches for something inherently cross-program or org-governing — never as an ambient padlock, disabled control, or upsell teaser in the OSS daily path.** TruePPM is adoption-first (the GitLab model): the free tier must be *completely sufficient for one PM/team/program*, and the Enterprise need is discovered **structurally** — when a second program, a portfolio roll-up, org-wide SSO enforcement, or a directory sync becomes the actual task — not through locked doors sprinkled across the shell. Three constraints for any **new** shell/navigation or extension-point-slot surface:
     - **(a) No render absent the edition.** Enterprise features register into stable OSS extension points (slot registration ADR-0029; edition-based routing ADR-0030). When the enterprise package is not installed, `registry.get(<slot>)` returns `[]` and the OSS UI renders **nothing** in that slot — no grayed-out or padlocked placeholder. A disabled control the OSS user can never enable is a wall, and walls in the daily path are the "you must upgrade to work" signal adoption-first exists to avoid.
     - **(b) Discovery at the seam, not on the surface.** The upgrade signal is allowed only where the *shape of the work* crosses the boundary — the moment a user tries to compare two programs, open a portfolio roll-up, enforce org-wide SSO, or sync a directory. That is contextual and honest (it coincides with a need the user just expressed) and is the ONLY sanctioned place a "this is an Enterprise capability" affordance may appear. It is never ambient chrome.
     - **(c) An Enterprise affordance is a distinct opt-in surface, not a disabled OSS control.** Where an enterprise slot *is* registered, present it as its own surface with its own label — never as `disabled aria-disabled="true"` OSS UI. (Contrast rule 42's WBS/Table `disabled` state, which gates an *OSS* feature coming to *this* edition — a legitimate "not built yet" disable; an Enterprise capability is "not in this edition," a different meaning that must not read as "temporarily off.")

     Load-bearing at the shell seams: the 3-tier rail (You / This project / **Jump**, #1642) and the location switcher (#1643) are exactly where cross-program/portfolio scope becomes visible. In OSS, `Program` is a first-class entity, so *within-program* navigation is fully OSS; only **cross-program** and **portfolio** destinations are the Enterprise seam. The classification test is the CLAUDE.md two-repo test verbatim: "Would a PM/program manager need this to run their program?" → OSS, render it; "Is this cross-program coordination, org policy, or compliance evidence?" → Enterprise, surface it only at the seam per (b). Basic OIDC/OAuth login is OSS (auth carve-out) — never gate it. If a practitioner hits a locked door doing single-program work, the boundary is drawn wrong and no visual treatment can rescue it — fix the boundary, not the padlock.

     **Surface classifier — daily path vs seam.** Rules 231 and 121 are the *same* principle applied to two surface types, not competing rules. **Daily-path surfaces** (the shell, rail, nav, project workspace, My Work) get 231: empty slots, zero ambient upsell. **Seam surfaces** — where a user's own action crosses into governance (Settings → Roles & permissions, org-identity/governance settings, the `/programs`→portfolio boundary) — may carry a single contextual affordance, because that *is* discovery at the seam (constraint (b) above), not ambient chrome. This maps onto the project's own adoption-vs-governance boundary: the daily path is where a team gets work done, the governance/settings seam is the natural home for an upgrade signal. Consequences:
     - **Rule 121's `EnterpriseBadge` on the Settings→Roles capability matrix stays** — the matrix's job is to show the *full* capability space, so hiding Enterprise rows would misrepresent it. The badge is constrained to **seam surfaces only**, never the daily-path shell/nav.
     - **Rule 178 was corrected by this rule and the correction has SHIPPED (#1677, closed):** the disabled "Portfolio rollup" row in the rail was a slot on the *daily path* wearing a padlock. `Sidebar.tsx` now renders the empty `nav.portfolio_section` slot instead, with discovery moved to the `/programs` seam. **Do not re-add a padlocked or disabled Portfolio row.** This bullet previously ended "until it lands, leave the shipped `Sidebar.tsx` row in place" — a now-inverted instruction sitting inside the load-bearing anti-upsell rule for the whole shell (#2859).

121. **Enterprise-only capability rows carry an inline `EE` badge that is itself the link.** On any OSS surface that advertises capabilities reserved for TruePPM Enterprise (Settings → Roles & permissions matrix today; the future `/programs` and `/portfolio` gateways), mark each Enterprise row data-driven (`ee: true` on the capability/row object — never a hardcoded list in the render, so it stays in sync as the Enterprise repo adds capabilities) and render the `EnterpriseBadge`: a focusable `<a>` to the Enterprise page (`https://trueppm.com/enterprise`), `target="_blank" rel="noopener noreferrer"`, with `title` **and** `aria-label` "Available in TruePPM Enterprise". **The badge IS the link** — a hover-tooltip that contains a link is unreachable (it dismisses as the pointer travels to the link and is invisible to keyboard users), so never wrap the link in a tooltip. Gate rendering on `useEdition() === 'community'`: under the Enterprise edition the capability is available, so the badge is suppressed (it would be noise). Badge style (settings density, rule 118): `bg-brand-primary/10 text-brand-primary text-[10px] font-semibold uppercase tracking-wide` + the standard rule-4 `focus-visible` ring. This is the concrete implementation of the ux-review §6.2 boundary-affordance requirement — it turns "dead" Enterprise cells (a check in a column that does nothing in OSS) into a purchase-decision path and stops missing Enterprise features from reading as broken OSS. The badge is the shared `features/settings/components/EnterpriseBadge.tsx` (#791) — it **self-gates** on `useEdition()` (returns null unless community), so callers render `<EnterpriseBadge />` without an edition check of their own. It applies to whole action buttons too, not just matrix cells: an Enterprise-reserved action (e.g. "Sync from directory" = LDAP, "View change history" = audit trail) renders as a disabled button with the badge alongside it as the reachable upsell link.

## The other 228 rules

Every rule this file used to carry still exists. The ones bound to a single
surface and a single issue now live as individually-linkable **decision
records** under [`docs/design/decisions/`](../../docs/design/decisions/) —
see [the index](../../docs/design/decisions/README.md).

They are still binding for the surfaces they govern. What changed is that they
are no longer mandatory reading: this file is the set you are expected to hold,
and a decision record is what you reach for when you touch the surface it
covers. Rule numbers are unchanged, so an existing `rule 176` reference in code,
an ADR, or an MR description still resolves.

**Where does a new rule go?** Ask whether it would be correct for a surface that
does not exist yet. If yes it is an invariant and belongs here. If it only makes
sense for the surface that produced it, write a decision record. See ADR-0653.
