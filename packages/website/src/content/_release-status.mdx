{/*
  Release-status single source of truth (#807).

  Every release-status banner derives its version claims from these constants
  instead of hard-coding "0.2 shipped" in prose. When the next release tags,
  ONE file changes here and every banner that imports it flips simultaneously —
  the drift that produced the 2026-05-28 "0.2 shipped" regression cannot recur.

  The authoritative classification (Shipped / Underway / Planned) lives in
  overview/roadmap.md; these constants must stay in lockstep with its
  "## Shipped" section. The `docs:version-accuracy` CI job (scripts/check-version-status.sh)
  enforces that no doc references an unshipped version in past/present tense.

  This file lives at src/content/_release-status.mdx (outside src/content/docs/),
  so Starlight's docs loader does NOT render it as a page. Import it from .mdx
  banners:

      import { SHIPPED, IN_ALPHA, FIRST_BETA } from "../_release-status.mdx";

  Note: plain .md banners cannot import MDX exports. Convert a banner to .mdx
  before wiring it to these constants, or keep its prose aligned with the values
  below by hand (the CI gate still guards the tense).
*/}

{/* The next artifact to tag. `v0.4.0-beta.1` shipped 2026-09-15 (now SHIPPED_TAG
    above) and 0.4 hardens under further beta.N tags before an eventual 0.4.0
    stable — moving off beta is a quality judgment, not a date, so it is not
    yet known whether the next tag cut is another `v0.4.0-beta.N` or the first
    tag on the 0.5 line. Currently unused by any page (index.mdx dropped the
    import when 0.4 shipped); re-derive this constant, rather than trusting
    the value below, before wiring it to a new banner.

        v0.4.0-beta.1  … beta.N    the first beta (the 0.4 milestone)  <- shipped, hardening
        v0.4.0-rc.N                optional, if a candidate is cut
        v0.4.0

    Do not reach for a "candidate for the beta" spelling on the way to rc:
    `0.4.0-beta-rc.1` is INVALID under PEP 440 (`packaging` raises
    InvalidVersion), so it would break the trueppm-scheduler publish outright —
    and under SemVer 2.0.0 it sorts AFTER `0.4.0-beta.1`, inverting the
    meaning, because the `rc` rung of the alpha -> beta -> rc ladder sits after
    beta by construction. Go `beta.N` -> `rc.N`.

    Keep the `v` prefix: the registry cleanup policy retains `^v.*$|^latest$`,
    so a bare `0.4.0` tag is reaped by the daily sweep (#2803, #2811). */}
export const UNDERWAY_PRERELEASE_TAG = "0.4.0-beta.1";
