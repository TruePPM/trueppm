:::note[Ships in 0.5]
The corpus release artifact and the project-document JSON Schema ship with the first
`trueppm-scheduler` release cut after 0.4. Until then both exist only in the
repository: clone it and use `packages/wasm-scheduler/fixtures/` and
`packages/scheduler/src/trueppm_scheduler/project.schema.json`.
:::

The conformance corpus is a language-neutral set of (input, expected output) pairs
for critical-path scheduling. It is what keeps the Python engine
(`trueppm-scheduler`) and the Rust/WASM engine in step with each other, and you can
point a third implementation at it.

:::caution[Agreement, not correctness]
Passing this corpus shows that your implementation **agrees with the TruePPM
reference engine** on these inputs. It does not show that your implementation is
correct, and it is not a certification of any kind. The expected outputs bind the
two TruePPM engines to each other: a scheduling rule that is wrong, but ported
faithfully into both, still passes, and so would yours. The independent check on the
reference is the oracle described in
[Scheduler conformance and verification](/architecture/scheduler-conformance/); read
that page for what is and is not covered there.
:::

## Get the corpus

Each `scheduler-v*` release attaches two files to its GitLab Release page:

- `trueppm-scheduler-conformance-corpus-<version>.tar.gz`
- `trueppm-scheduler-conformance-corpus-<version>.tar.gz.sha256`

Verify the download before using it:

```bash
sha256sum -c trueppm-scheduler-conformance-corpus-<version>.tar.gz.sha256
tar xzf trueppm-scheduler-conformance-corpus-<version>.tar.gz
```

The archive is reproducible: the same tree yields the same checksum. The version in
the file name is the `trueppm-scheduler` version whose engine produced the expected
outputs.

## Layout

```text
trueppm-scheduler-conformance-corpus-<version>/
  README.txt
  fixtures/
    <name>.json              valid project documents (the inputs)
    expected/<name>.json     the reference engine's result for <name>.json
    invalid/<name>.json      documents a conforming engine must refuse
    parse_rejects/<name>.json  documents that must be refused while parsing
    cycle_errors/<name>.json   cyclic documents, with the expected error in expected/
    oracle/corpus.json       cases generated by an independent reference CPM
    PROVENANCE.json          how each fixture and snapshot came to be
```

Every top-level `fixtures/<name>.json` has exactly one matching
`fixtures/expected/<name>.json`.

## Input documents

Inputs are project documents. Their shape is published as a JSON Schema (draft
2020-12) at `trueppm_scheduler/project.schema.json` inside the wheel, and as
`packages/scheduler/src/trueppm_scheduler/project.schema.json` in the repository.
Validate a document before submitting it:

```python
import json
from importlib.resources import files

import jsonschema

schema = json.loads((files("trueppm_scheduler") / "project.schema.json").read_text())
jsonschema.validate(json.loads(open("fixtures/basic_fs_chain.json").read()), schema)
```

The schema checks **shape only**: property names, JSON types, enum values, required
keys and numeric ranges. It cannot express dependency cycles, duplicate task ids,
edges that name an unknown task, calendar consistency, or the span and duration
caps. A document that validates can still be refused by the engine, so a pass is not
a promise that the engine will accept it. Every valid fixture in the corpus validates
against the schema, and CI checks that.

Conventions you need to match:

- Durations, float and lag are numbers of **seconds**.
- Dates are strict ISO-8601 `YYYY-MM-DD` strings. Compact, unpadded, ordinal, week
  and signed forms are refused.
- Lag is counted in calendar days, then snapped forward to the next working day on
  the successor's calendar. `working_days` is a 7-bit mask, bit 0 Monday.

See [Scheduler conventions](/features/scheduler-conventions/) for the full rules.

## How to run it

For each `fixtures/<name>.json`:

1. Parse the document and schedule it with your implementation.
2. Compare your result to `fixtures/expected/<name>.json`.

For each file in `invalid/` and `parse_rejects/`, your implementation must refuse the
document, either while parsing or while scheduling; the corpus does not prescribe the
error type, only that the input is rejected. For `cycle_errors/`, refuse the document
and report the cycle described in `cycle_errors/expected/<name>.json`.

## What the expected-output fields mean

Compare dates as ISO strings and float as seconds, exactly.

| Field | Meaning |
|---|---|
| `project_id`, `project_start`, `project_finish` | Echo of the project id and start, and the latest early finish. |
| `tasks[].early_start`, `early_finish` | Forward-pass dates. For an in-progress task these are the **remaining-work** window, not the whole span. |
| `tasks[].late_start`, `late_finish` | Backward-pass dates. |
| `tasks[].total_float`, `free_float` | Seconds of slack against the project finish and against the earliest successor. |
| `tasks[].is_critical` | True when total float is zero. |
| `tasks[].scheduled_start` | The task's whole span start, which differs from `early_start` for a task with recorded progress. |
| `tasks[].milestone_at_day_end` | Present only when true: a zero-duration milestone sits at the end of its shown day rather than the start. |
| `critical_path` | Task ids on the critical path. |
| `driving_edges` | The links that place their successor, sorted. Absent means none. |

`PROVENANCE.json` records, for each fixture and snapshot, whether its expected output
was hand-verified against a documented convention, regenerated by running an engine
(which re-blesses whatever that engine emits), or of unknown origin. Read it before
treating any single expected output as ground truth.

## What a passing run shows

- Your implementation reproduces the reference engine's dates, float, criticality and
  driving edges on the corpus inputs, and refuses the corpus's refusal inputs.
- It does not show that those dates are the right answer for any real project, that
  inputs outside the corpus behave the same, or that Monte Carlo results agree: the
  corpus covers the deterministic critical-path pass.

If you find a case where the reference engine is wrong, that is a defect in the
reference. Report it on the project's issue tracker; do not match it.
