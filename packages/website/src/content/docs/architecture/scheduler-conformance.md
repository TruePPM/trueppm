`trueppm-scheduler` is a standalone library, and its correctness does not rest on
the TruePPM application. This page states, from the test suites, what is
checked against what — including the shapes that are **not** checked, so a reader
can see the edge of the claim instead of inferring it.

Everything between the markers below is generated by
`scripts/gen-scheduler-conformance-report.py`. The refusal list, budgets, corpora
and mutation scope are read from the tree; the coverage matrix cells are declared
by hand in the generator and reviewed against the oracle's strategies, and the build
checks only that each property they cite still exists. CI fails when the block no
longer matches the generator.

### Oracle coverage matrix

| Link | live / project calendar | live / per-task calendars | complete, no actuals / project calendar | complete, no actuals / per-task calendars | complete, with actuals / project calendar | complete, with actuals / per-task calendars |
|---|---|---|---|---|---|---|
| FS | reference-checked | reference-checked | reference-checked | reference-checked | reference-checked‡ | reference-checked‡ |
| SS | reference-checked | reference-checked | reference-checked | reference-checked | reference-checked‡ | reference-checked‡ |
| SF | reference-checked | reference-checked† | reference-checked | reference-checked† | reference-checked‡ | reference-checked†‡ |
| FF | reference-checked | reference-checked† | reference-checked | reference-checked† | reference-checked‡ | reference-checked†‡ |

*reference-checked*: the Python engine is compared date-for-date with an independent reference implementation (`tests/oracle/reference_cpm.py`). *parity-only*: no reference comparison, but a property over the engine's own output (the slip oracle) or a Python/Rust comparison covers it. *not generated*: no generator draws that shape. Cell values are declared by hand in the generator and reviewed against the oracle's strategies; the build checks only that each cited property still exists: `test_python_engine_matches_reference_on_networks_of_work`, `test_python_engine_matches_reference_with_progress`.

† On per-task calendars an FF/SF link is drawn only between two tasks on the same calendar (or two with none). An FF/SF link across two different calendars is refused by the reference (#4639), so it is rewritten to FS/SS and not generated.

‡ A completed milestone with recorded actuals is refused by the reference; the generator drops its actuals, so that shape is not generated.

**What the reference refuses, verbatim from the oracle's own documentation:**

> Generated for the reference comparison: every link shape with leads and lags, any working-day calendar, milestones, and — in the `*_with_progress` properties (#4633) — percent complete, actual starts and finishes (on non-working days and before the project start), a data date, SNETs, and four-, five- and seven-day per-task calendars with exceptions. Not generated there: `live_day_end_on` (#4684); and, because the reference refuses them, an FF/SF link across two calendars (`_on_one_calendar` makes it FS/SS; the rule is undecided, #4639) and a completed milestone with recorded actuals (its actuals are dropped; it keeps the day edge it had live, which is `live_day_end_on` history, #4684). A link out of a non-working actual is read in working time by all three (#4631, #4702) and compared like any other input. The last planning-network shapes the engines disagreed with the reference on — a lagged FF/SF link into a milestone (#4272) and an FF link out of one (#4273) — were fixed in the engines, not excluded here.
>
> Summary tasks (#4684): a summary tree over a planning network, with links at a summary end of every type, is expanded by `expand_summary_dependencies` and scheduled, against :func:`tests.oracle.reference_cpm.expand_summaries` — the same refusals, the same leaf links, the same schedule. Python only; the Rust engine does not expand summaries.

## What a release report adds

A release's report repeats the sections above and adds the numbers that exist only
after a run: the engine version, git sha and date; the mutation score over the
modules listed above; the `pytest-benchmark` timings for CPM and Monte Carlo; and
the result of the Python/Rust parity run. The generator refuses to write a report
when any of those inputs is missing rather than publishing a partial page.

## What this page does not claim

- It is not a proof of correctness. The reference implementation is independent of
  the engine, but it is still code, written by the same project.
- A cell marked *reference-checked* means the generator draws that shape, not that
  every value in it is drawn. Hypothesis samples; the budgets above say how much.
- Mutation scoring covers the modules listed, not the CPM core in `engine.py`.
